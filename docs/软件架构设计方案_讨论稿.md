## 1. 设计依据与目标

### 需求输入

需求输入为[需求规格说明书](需求规格说明书.md)、[需求基线](requirements/08-需求基线.md)及其详细材料；两份需求阶段报告提供既有确认与验证依据。当前需求提交为 `ff491a6`，分类统一表述为一级分类，商品可关联多个分类。功能覆盖 FR-01—FR-14，质量目标按第6、7章执行。

### 交付形态与技术方向

统一仓库组织用户端、管理端、后端及设计材料。用户端采用小屏优先的响应式网页与 PWA，管理端采用 PC 网页；两个前端应用独立构建和发布。

后端通过HTTP适配、契约校验、事务与持久化、迁移和类型化配置能力实现；Python／Java及框架按[技术栈独立的应用架构](#architecture-07)完成选型。前端采用 Vue、TypeScript 与 Vite，接口类型由 OpenAPI 契约生成。具体依赖版本在实现输入基线中登记。

### 设计目标

业务按主体及其强关联数据组织，统一数据库保障权威业务状态。支持单机多服务实例，通过共享机制协调会话、事务、IM 与任务；当前部署验收采用单机多实例，性能结果作为部署变化依据。

必需业务能力完整实现，启动时校验必要配置。代码明确权限、状态、事务及失败语义，白盒审查核对业务逻辑；运行时测试覆盖静态检查之外的并发、复杂关联、网络和跨实例行为。

### 确认与追踪

重要取舍见[确认与决策索引](design/decisions/01-确认与决策索引.md)。本轮文档按会话中的人工确认整理，交叉复核人与技术验证结果分别登记。架构基线版保持占位，阶段准入按接口、问题关闭及预期核验状态确定。

## 2. 总体架构与模块职责

### 总体结构

采用模块化单体，后端代码和版本统一维护；API、IM、worker、scheduler 按运行需要部署多个服务实例。业务模块提供统一用例与内部能力，实例通过同一逻辑 PostgreSQL 和 Redis 协作。

“模块”表达主体数据与动作的维护边界，“服务实例”表达运行单元。数据维护责任通过模块接口落实，跨模块用例共享数据库事务。

### 主体模块

| 模块 | 主体及维护数据 | 动作 |
|---|---|---|
| 账户 | 账户、邮箱验证、凭据版本、管理资格、账户限制；Redis Session | 注册登录、退出、资料和邮箱管理、凭据失效、封禁与解除 |
| 商品 | 商品、图片引用、编辑历史、审核、评论与回复、收藏、分类关联和申请、禁发范围 | 发布编辑、审核、上下架、查询、评论收藏、取得与释放占用 |
| 分类 | 一级分类、主名称、别名、启停状态 | 创建、更名、别名维护、停用、逻辑删除及名称解析 |
| 交易 | 请求／交易、成交快照、约定版本、确认、转换历史、冻结与计时、评价 | 请求处理、约定、完成、终止、争议、异常、恢复与评价 |
| 会话 | 普通私聊、交易分支、事项会话、消息、参与关系、已读 | 建立会话、发送读取、归档及资格校验 |
| 处置事项 | 举报、事项、认领、核查、证据关联、决定及执行关联 | 举报补充、认领处理、问询申辩业务、作出决定及协调执行 |
| 通知 | 通知、接收关系、已读 | 创建、查询、未读统计及已读 |

会话模块分别维护 ChatConversation、TradeConversation、CaseConversation 及各自消息和阅读进度，不设共同父会话或 Branch 实体。普通私聊与逐笔交易的双人入口由查询聚合。事项沟通消息独立于 C-08，由 C-13 关联；处置事项提供固定认领及相关用户的访问依据。商品评论与商品共同维护。分类模块管理公共分类，商品模块管理商品归属及随商品提出的申请。

### 数据归属与聚合

主体模块执行其数据变化；处置事项保存决定依据，账户维护账户限制，交易维护冻结及计时，商品维护展示限制。关联标识连接决定和执行结果。

本人业务、待办和统计由查询聚合能力读取各主体数据，写操作调用对应业务用例。文件、邮件、实时传输、日志审计和配置提供公共支撑。

### 账户资格

管理员保留校园用户基础功能并叠加管理能力；同一账户可使用用户端及管理端。权限按参与关系、对象归属、管理资格、认领及当前状态校验。

### 设计分工

四位成员均形成任务：TASK-001 承担账户、通知、聚合、公共技术设计及部署；其余三位承担商品与分类、交易、会话与处置事项。具体设计包见[任务索引](design/tasks/索引.md)。

### 任务交界归属

[并行对接安排](design/detailed-design/04-并行对接与交界归属.md)为商品占用、交易分支触发、会话模型和处置执行指定唯一设计任务。任务可以跨模块设计完整关联，主体模块依其职责执行状态维护。各 PR 指定实际交叉审查姓名。

### Maven 模块与服务边界

袁尚峰于 2026-11-18 确认采用 Maven 多模块，并将可复用能力抽象为服务。下表登记第 10 批建议的子模块划分。根 POM 聚合子模块并统一管理构建与依赖；应用装配模块产出可执行 JAR，按既有发布清单选择 API、实时入口、worker 或 scheduler 角色，角色可分别启动。全部业务模块使用同一个逻辑 PostgreSQL，跨模块业务用例共用一次事务。

| Maven 子模块 | 职责与对外能力 |
|---|---|
| `backend-app` | Spring Boot 启动与配置组装，持有 HTTP／WebSocket 等入口及跨主体业务用例；按角色启用入口、worker 与调度器。 |
| `backend-core` | 请求／操作上下文、业务错误、事务与幂等接口、审计与事件提交接口，集中提供日志、脱敏及追踪适配。 |
| `account`、`product`、`category`、`trade`、`conversation`、`case-management`、`notification` | 分别承接 ADR-002 的七个主体。模块持有自身模型、JPA 映射、Repository 及实现；公开具名服务接口、输入、结果和错误。例如账户资格、商品占用、会话追加消息以及通知登记。 |
| `file-storage` | 提供上传授权、核验、业务引用、签名读取及回收。商品图片与事项证据共用文件能力，调用用例提供各自的归属和资格。 |
| `messaging` | 运行 Redis Streams 事件派发、工作队列与认领调度。任务消息传类型及记录 ID；邮件等任务处理器由对应模块提供并由应用登记，SMTP 发送通过账户验证流程的邮件发送接口接入。 |

模块间通过公开的命令服务、查询服务和能力接口调用。应用用例收集账户资格及锁集合，依公共顺序调用主体服务。本人聚合、待办和管理查询由应用组合各模块的查询契约。跨模块调用传 ID、上下文和具名 DTO，JPA 实体及 Repository 留在所属模块。共享只读查询由维护该事实的模块提供，管理看板不直接改写主体数据。

编译依赖由应用指向主体及公共能力，由主体和基础设施适配器指向公共契约，保持无环。需要多个主体协作时，由应用组合服务，主体实现无需相互引用。公开接口和实现可先在各 Maven 子模块内按包组织，按实际复用需要再决定是否拆独立 API 制品。S1 优先落地账户、商品、分类、审核认领、通知、文件和其所需的消息任务能力；后续阶段接入交易、会话及处置的具体链路。

参见[技术映射](#architecture-07)、[公共事务](design/detailed-design/key-designs/公共事务与权限.md)、[日志与审计](design/decisions/adr/ADR-009-统一上下文与AOP日志审计.md#spring-入口及-aop-映射)。

## 3. 模块协作与关键业务流程

### 调用与事务

接口层解析请求并取得身份，应用层用例组织业务资格、加锁、跨模块调用与提交。内部能力共用本次事务上下文；并发请求和任务分别持有数据库会话。

### 接受请求并锁单

交易用例协调：锁定商品，再锁定并重读目标交易；校验卖方、双方资格、目标请求状态及商品占用；调用商品能力取得占用；接受目标请求、关闭其他待接受请求；维护受影响会话分支，生成通知、必要审计和待投递事件；统一提交。

锁顺序为商品→目标交易→其他受影响交易（稳定顺序）→关联记录。相关下架、结束和管理操作遵守同一商品占用协调协议。账户限制与多商品操作的完整锁序由 TASK-001进一步细化。

有效购买请求创建时建立交易分支，接受操作复用已有分支。请求或交易结束按规则归档。

### 其他跨模块协作

| 用例 | 协调模块 | 关联能力 |
|---|---|---|
| 发布审核并批准分类申请 | 商品 | 分类名称解析／创建、商品归属、审核历史及通知同事务保存 |
| 完成或终止交易 | 交易 | 确认与状态、占用释放和商品状态、分支归档、通知与审计 |
| 商品下架或撤销公开 | 商品／处置用例 | 商品资格、适用请求关闭、分支归档和通知 |
| 冻结、恢复及状态调整 | 处置事项 | 保存依据，调用交易及商品能力执行，按当前资格控制会话 |
| 封禁及解除 | 处置事项 | 账户限制、适用请求及交易处理、相关通知 |

### 幂等与实时副作用

关键写操作按操作者、操作类型、幂等键及输入摘要识别；同次结果与业务事务一起保存。网络重试返回同次结果，同键不同输入返回明确冲突。已提交事件异步投递，客户端按标识去重和恢复。

### 邮件验证

账户用例在同一张email_verification表保存验证请求及投递进度，code短期明文保存，任务队列仅携带记录ID，接口返回已受理后进入验证码输入交互。后台任务执行器异步 SMTP 投递，同轮重试沿用凭据及创建时期限；明确重发生成新轮并替代旧轮；过期或被替代任务结束。

同轮格式合法而不匹配的验证码提交原子累计失败次数；同次幂等重试计数一致；达到配置上限使本轮失效。成功验证原子消费凭据并衔接账户操作。消费或失效时清空原码，投递成功后保留至校验结束；协议见[邮箱验证与投递](design/detailed-design/key-designs/邮箱验证与投递.md)，采用Q-003实际决定。

## 4. 数据架构

### 权威数据与存储

PostgreSQL 统一保存业务数据、账户凭据版本、逐会话签发与撤销依据、历史、幂等、通知及待投递事件。Redis 保存有效 Session、共享控制状态及消息传递状态。OSS 保存文件内容，数据库保存文件状态和业务引用。邮箱验证及其投递进度由PostgreSQL的email_verification单表保存；code短期明文，仅在消费或失效前保留，任务队列只传记录ID。每类数据有明确权威位置。

数据库内部复制或分布式一致性由数据库架构承担；应用明确所需事务、读写语义和业务不变量。

### 公共表示

主体业务记录使用数据库生成的整数 ID，对外用字符串；请求、操作、任务、事件标识使用 UUID。金额采用整数分。时间使用带时区类型、按 UTC 处理，接口输出带时区 ISO 8601。

生命周期、确认进度、冻结和展示资格分别表达。主体数据按需求逻辑删除，编辑、审核、约定、确认及处置保存各自历史及操作者、时间和依据。

### 约束与规则版本

唯一性、外键和结构不变量由数据库及代码共同保障。可调整长度、大小、次数和期限读取后端配置，存储容量按可支持范围设计。

新操作采用当前配置；已签发验证码、上传授权和交易计时保存当次期限、必要参数或规则版本。历史读取保留原内容，后续修改按当前规则校验。影响既有业务的调整登记变更、处理方式和验证依据，审计关联适用版本。

### 文件生命周期

申请授权→浏览器直传 OSS→后端核验对象→登记可引用→业务事务建立引用。对象采用私有访问，读取时校验业务资格并签发短期地址；过期无引用暂存对象按授权及引用状态回收。对象存储与数据库通过可重试状态流程衔接。

### 详细设计输入

各模块细化属性、关联、唯一约束、索引、版本字段及历史结构。统一锁序、账户凭据版本校验和文件引用协议由 TASK-001 统筹。

### 字段与统一规则检查

按[设计约束与检查规则](design/设计约束与检查规则.md)的 DATA-01—04、RULE-01—04 及 DOC-01 检查字段来源、主体类接口、锁后判定、查询等价性和同源传播。实体与共享视图保留事实及必要关联，展示、搜索及动作资格通过所属类接口统一计算。

### 公共数据结构入口

[公共数据模型](design/detailed-design/key-designs/公共数据模型.md)定义账户及封禁、通知、幂等和审计，汇总Session、邮箱验证、文件、持久事件和任务的唯一专题输入、关系、约束及清理依据。角色／限制／未读／待办和统计通过所属方法及等义查询计算；临时许可／幂等／传输事件清理不级联删除业务历史。设计及专题评审版本随TASK-001第7批登记。

## 5. 部署与运行架构

### 运行单元

API、IM、worker、scheduler 共用后端版本及配置模型，支持单机多实例。各实例独立建立连接池；实例内维护连接和执行中临时数据，共享持久状态与协调通过 PostgreSQL／Redis 完成。

### 入口与生命周期

采用原生进程、systemd 与 Nginx，当前验收部署为单机多实例。API 和 IM 分别配置上游列表，支持应用内部进程分发及外部负载均衡。健康检查区分存活和就绪；优雅退出排空请求、衔接 IM 重连、停止领取新任务并按确认及租约机制接管。

多机变化基于性能结果评审，实例地址、依赖连接和上游关系由配置表达。

### 配置作用域

后端以指定的一份 .env 为运行配置事实来源，通过所选技术栈的配置加载适配器形成只读类型化配置；必要功能配置完整且类型、范围、关联关系校验通过后启动。具体策略数值来自配置，默认值集中登记依据。

用户端与管理端分别维护 dev server、代理、API／WS 公开地址、基础路径和构建选项，构建输入独立。前端通过接口取得业务能力限制；Nginx 和启动参数按部署输入派生。

后端 .env.example 及两端配置示例在对应实现任务中建立，并与配置模型同步。

### CI/CD 与发布

GitHub Actions 执行静态、文档契约、适用测试和构建验证；Jenkins 构建发布产物、检查环境、执行迁移、滚动更新实例、使入口配置生效并验证。发布关联明确提交、产物及配置版本。

迁移是独立发布步骤。滚动期间检查数据库、接口、事件和任务兼容性。保留可用版本及配置，按迁移兼容范围回退。部署工作归 TASK-001。

### 环境与资源

开发、测试、正式环境的数据库、Redis 命名空间、文件和邮件资源分别登记。全部署核算数据库／Redis 连接、内存及队列预算；参数值和默认值待清单评审。

### 2026-11-14 与legacy共存的部署输入

袁尚峰（iy88）明确：v2与legacy同机并存、独立目录，沿用类似legacy的部署方式。PostgreSQL共用实例，v2使用独立数据库名和数据库用户；Redis共用实例，本轮采用独立键前缀，逻辑DB可在部署配置时另选。域名和OSS资源由袁尚峰分别提供独立配置。该前缀同时覆盖Session、Stream、任务队列、锁、配额及调度键。

当前先完成接口与技术设计；实际目录、端口、连接预算、域名及OSS配置在部署阶段按上述边界落实。Redis逻辑DB及键前缀用于命名空间隔离，清理与恢复按v2范围执行。

## 6. 质量要求实现策略

### 性能目标

按[质量要求](requirements/06-质量要求.md)及[验收依据](requirements/07-验收与验证.md)执行：100 名同时活跃用户、10,000 条商品的代表性条件下，常用交互95%在3秒内、正常网络双方在线时文本消息95%在2秒内可见。记录读写及聊天配比、实际速率和网络。文件上传单独记录大小及网络条件。

通过单机多实例、连接池预算、稳定分页、必要索引和异步投递承载负载，结果以测量登记。

### 一致性与恢复

业务、历史、必要审计、幂等和待投递事件同事务提交。IM 独立游标读取共享 Stream，向本机目标连接分发；后台任务同组分担。数据库待投递事件支持多实例认领和有限租约；消费、客户端及业务用例按稳定标识去重。

客户端可重连任意实例，从持久记录补取，在线连接周期核对缺口。任务执行前重查当前业务状态。调度通过数据库触发标识和执行权协调。

### 身份、权限与隐私

持久 HttpOnly Cookie 携带随机凭据，Redis Session 使用绝对及空闲期限，按有效活动节流续期。退出持久撤销当前 Session，再异步清理 Redis 及连接；改密／重置及换绑邮箱更新账户凭据版本。鉴权同时核对 Redis 运行时状态、PostgreSQL SessionGuard签发／撤销事实、当前凭据版本及有效资格，在本次上下文复用。管理员保留普通用户功能并按事项和对象资格执行管理操作。

API、IM 及任务复用资格和业务规则。输入及网络／异步／I/O 边界明确处理，内部约束通过类型和代码结构落实。

### 日志审计

HTTP 请求中间件、任务中间件和类型化用例包装建立统一上下文，业务显式提供审计事实。必要成功审计提交前入同一事务。运行日志记录执行结果、耗时、实例和关联标识。字段按敏感性脱敏，业务历史与审计关联。

### 验证原则

全部业务逻辑白盒审查权限、状态、不变量、事务、锁序与错误分支；所选后端技术栈的静态检查及前端严格类型检查提供静态证据。运行时案例说明其运行时性质或复杂跨模块关联，聚焦真实数据库多连接、IM 跨实例、租约接管、重复处理、I/O 故障及恢复。技术验证与人工审查状态分别记录。

## 技术栈独立的应用架构

依据：袁尚峰于2026-11-17要求采用技术栈独立的应用架构描述，并将技术栈解耦纳入design；各公共能力的扩展细化随对应PR交付。

### 稳定契约与技术映射

模块化单体、主体事实归属、统一业务事务、资格与业务锁序、幂等、审计及事件同事务、任务租约与接管属于稳定架构契约。HTTP／WebSocket、OpenAPI、UTC时间、对外字符串ID及既有错误语义保持一致。PostgreSQL、Redis、OSS、SMTP与现有部署隔离决定继续作为基础设施输入；应用语言独立与基础设施无关分别描述。

后端选型及兼容性证据采用[ADR-010](design/decisions/adr/ADR-010-RESTful契约与技术栈.md#spring-data-jpa-与-postgresql)。主 ORM 采用 Spring Data JPA 与 Hibernate；数据库特定的锁和写入路径按公共契约使用显式 SQL，Flyway 维护数据库结构。HTTP适配、契约校验、事务管理、持久化、迁移、任务执行与静态检查能力按所选技术栈映射到具体工具。文档生成脚本的语言不限定后端语言。

接口采用语言无关的操作名、具名输入／结果及错误表。EntityId、ResourceRef、ExecutionContext、Transaction、LockPlan及Allowed为概念类型；list、可空值和具名结构表达集合与数据契约。方法签名不要求Python类、Java继承体系、装饰器或特定依赖注入容器。实体与外部响应模型分别承担持久事实和传输职责。

### 选型及验证

技术选型记录实际语言、框架与版本，以及每项稳定契约的实现位置。迁移、类型与质量检查采用所选技术栈对应工具；数据库并发、多实例身份、事件恢复、任务接管和外部I/O故障验证采用相同业务输入及可观察预期。编码准入检查技术映射完整性，运行证据登记实际技术栈。
