# C-15 站内通知

状态：候选类分析初稿（支撑性对象），负责人张新悦；是否进入 CL-01 主图待 P-20 决定，未开展人工模型评审。

## 职责与边界

记录业务事件对特定接收人的站内提醒与待办：事件类型、接收人、关联业务对象、未读／已读及产生时间。通知只负责提醒与已读，不复制审核结论、处置结论或交易结果；结论仍由 C-04、C-13、C-09 承载。

边界：与 C-13 的处置通知与沟通单分开——后者是受限期用户与认领管理员之间的受控沟通，含说明、反驳／申诉与回复；站内通知只是提醒与入口，不承载沟通内容，也不恢复买卖双方 IM。通知不作为业务对象状态的替代，不因已读改变商品、交易或举报的处理结果。

## 主要业务属性

事件类型、接收人、关联业务对象（弱关联）、未读／已读、产生时间。不写字段类型与索引；渠道（站内、邮件、短信）、分组展示与文案留待设计与 P-20。

## 关联与数量约束

| 关联 | 重数（候选） | 说明 |
|---|---|---|
| 站内通知—接收人（C-01） | 0..* : 1 | 一条通知对应一名接收人；已读按接收人区分 |
| 站内通知—来源业务对象 | 0..* : 0..1（弱关联） | 可指向审核记录、交易记录、处置记录等，仅作定位 |

## 关联规则、场景与用例

- 站内通知与待办提供审核结果、交易请求接受／拒绝／关闭、单方确认与超时、处置告知、评价与举报结果等业务事件的提醒，并区分未读与已读：FR-11。
- 具体触发范围、是否扩展邮件／短信及已读规则待 P-20，本类不预设渠道与触发清单。
- 通知不改变业务规则：已读不等于处理完成，未读不阻塞业务操作。
- 场景：SC-01—SC-08 的提醒环节（候选映射，未逐一展开）；用例：UC-C11。

## 状态归属

状态：未读、已读（候选）。不参与业务对象状态机；是否设“已失效”待 P-20，本节不预设。通知不因业务对象进入终止或完成而自动删除。

## 待决与边界

- P-20：通知触发范围；是否含邮件／短信；未读与已读规则。
- 与 FR-12“我的”聚合入口的关系：通知作为入口数据被聚合，不因此另建第二套记录。
- 待办与知会是否需区分类型：候选为以事件类型区分，不另立第二个类。
