# 文本长度与 Unicode 计数

用户输入的人类文本按 Unicode 17.0.0 的扩展字素簇计数。前端移动端和管理端固定使用 `unicode-segmenter@0.17.3`；后端固定使用 `regex==2026.4.4` 的 `\X`，不自行实现分段算法。密码、验证码、邮箱、URL、对象键、协议 ID 和状态枚举保持各自规则，不套用人类文本正规化或字素簇上限。

| 内容 | 最大字符数 |
|---|---:|
| 显示名、分类名称、分类别名、禁发类别 | 64 |
| 商品标题 | 120 |
| 商品描述 | 5000 |
| 商品评论、卖方回复、普通私聊、交易分支消息 | 2000／条 |
| 事项说明、申辩、管理员问询及回复 | 2000／条 |
| 举报详细说明、补充文字 | 2000／次 |
| 评价、争议描述 | 1000 |
| 举报原因、购买留言、完成确认备注、审核及处置理由与依据、禁发内容 | 500 |
| 交易取消及拒绝原因、交付时间／地点／方式、支付时机、处置摘要 | 200 |
| 支付方式 | 100 |

普通汉字、扩展汉字、单个 emoji、家庭或肤色组合 emoji、带组合重音的字符均依照字素簇分段规则计数。字素簇数不等于 UTF-16 代码单元数、Unicode 码点数或 UTF-8 字节数。API schema 使用 `x-max-graphemes`、`x-max-utf8-bytes` 描述约束，不以普通 `maxLength` 冒充字素簇上限。

前后端均把 CRLF／CR 换行转换为 LF，再删除约定集合中的首尾空白后计数。保留正文内部空白、组合符号和字形，不做 NFKC 等兼容性变换。空白必填内容被拒绝；可选内容允许空串。每字段另设 UTF-8 技术容量上限 `min(字符上限 × 32, 65536)` 字节，防止单个字素簇携带大量组合符号；孤立代理项不是合法输入。

移动端 `TextField` 和管理端 `TextInput` 共用计数策略，持续显示当前数量与上限；恰好达到上限仍可提交。超限粘贴保留完整草稿，显示超出量，由表单或请求前校验阻止提交。输入法组合期间不截断内容、不改写模型；聊天的 Enter 发送忽略 `isComposing`。失败不清空草稿。旧数据仍可读取，不执行清理或裁剪，新建及修改请求使用现行限制。

后端公共入口为 `app/core/text.py`，前端公共策略为 `frontend/shared/text.mjs`，两个应用分别注入相同版本库提供的计数函数。请求前校验覆盖业务文本，包括嵌套标签决定；服务端校验为最终依据。新增字段须同时接入请求 schema、相应输入组件及前端请求规则，并验证协议字段未被误正规化。

字素簇上限可能允许多于原 `VARCHAR(n)` 码点数的合法文本，因此迁移 `d1e2f3a4b5c6` 将对应人类文本字段扩为 `TEXT`，保留原值和索引。PostgreSQL 部署前执行现有显式迁移流程；SQLite 原 VARCHAR 不限制字符数，迁移不重建表。回退前检查旧字段容量，存在无法容纳的值时拒绝降级，不截断已有内容。

两端复用 Unicode 17 官方 `GraphemeBreakTest`，并共享组合表情、重音、换行与空白案例。测试集保留原始来源、版本和许可证头；依赖升级须继续通过同版本标准测试和 API 上限边界测试。
