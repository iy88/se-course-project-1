# 部署说明

## 生产拓扑

```text
浏览器 HTTPS
    |
边缘 HTTPS / DNS 与证书
    |
公网 Nginx
    |
内网隧道
    |
生产 Ubuntu VM / 源站 Nginx
    +-- 移动端静态资源 --> current/mobile
    +-- 管理端静态资源 --> current/admin
    +-- /api/ ----------> 127.0.0.1:8001 / API
    +-- /ws ------------> 127.0.0.1:8002 / WS
                              |
                      PostgreSQL / Redis
                              |
                    Taskiq worker / scheduler

API --> OSS 私有媒体桶、证据桶
API --> SMTP 验证码邮件服务
浏览器 --> 短期签名 PUT / GET --> OSS
```

公网和源站代理保持 Host 与 HTTPS 协议信息。源站按域名提供两套静态资源，前端使用同源 `/api/v1` 和 `/ws`。入口 HTML、Service Worker 及时更新，带摘要的静态资源采用长缓存，SPA 路由回退到 `index.html`。WebSocket 代理启用 Upgrade，访问日志采用隐藏 ticket 的策略。

## 资源与配置

生产需要 Linux、Python、uv、Node.js/npm、Nginx、systemd、PostgreSQL、Redis 8.2+、OSS 和 SMTP。应用使用专用 deploy 账号，数据库采用 owner、migrator 和 app 三角色，Redis 使用专用命名空间和连接预算。

| 配置组 | 生产设置 |
|---|---|
| 环境 | `ENVIRONMENT=prod`、`DATABASE_SCHEMA=app`、`DB_AUTO_CREATE=false` |
| 数据库 | 应用与迁移连接指向同一数据库，迁移角色可切换到 owner |
| Redis | 配置 `REDIS_URL`、非空 `REDIS_KEY_PREFIX`、认证与各角色池大小 |
| HTTP / WS | `API_HOST=127.0.0.1`、`API_PORT=8001`；`WS_HOST=127.0.0.1`、`WS_PORT=8002` |
| 浏览器来源 | `ALLOWED_ORIGINS` 列明两个前端实际 HTTPS Origin |
| 代理来源 | `AUDIT_TRUSTED_PROXIES` 按直连代理 IP/CIDR 配置 |
| OSS / SMTP | 私有双桶、区域、HTTPS endpoint、访问凭据，以及邮件连接和发件人 |
| 密钥 | 分别生成生产 `JWT_SECRET` 与 `FILE_URL_SECRET` |

持久配置源为 `/srv/se-course-project1/shared/.env.prod`，权限 `0600`。每次发布复制到 release；配置变更通过新发布生效。数据库结构由显式迁移维护。

## 服务器初始化

1. 创建 deploy 账号、应用根目录、releases 和 shared 目录，填写生产配置。
2. 准备 PostgreSQL 三角色、数据库及 app schema；初始化工具使用 `.env.prod` 完成创建和首次迁移。
3. 配置 Redis 监听、认证、内存预算、`noeviction` 与 AOF `everysec`，准备备份目录。
4. 管理员安装 API、WS、worker、scheduler 的 systemd unit，以及固定命令 sudoers、激活与备份工具。
5. 安装 Nginx upstream 和站点路由，将 `/api/`、`/ws` 转到对应端口，配置静态根、缓存和 SPA 回退。
6. 执行 `systemd-analyze verify`、`visudo -c`、`nginx -t`，再完成首次发布和公网访问检查。

HTTP 层模板 `scripts/deploy/nginx/se-course-project1-http.conf` 与站点路由模板 `se-course-project1-routes.conf` 分别安装到对应层级。系统 unit、sudoers、Nginx 和备份工具由管理员维护，发布包提供相应资产。

## 构建与发布

构建节点准备 Git、SSH 和 Node.js/npm，配置只读源码凭据、生产 SSH 凭据及 known_hosts。Jenkins 检出发布主线并依次完成下列阶段，双前端安装与构建并行执行，发布步骤按顺序执行，总超时 30 分钟。

| 阶段 | 处理 |
|---|---|
| 检出 | 检出主线，核对后端、前端和锁文件结构 |
| 前端构建 | 两端分别执行 `npm ci`，以 `PROJECT1_FRONTEND_CONFIG=public` 并行生成生产静态资源 |
| 打包 | 汇总 backend、mobile、admin、deploy，生成版本文件和 SHA256SUMS |
| 上传 | 严格 SSH 主机校验后上传版本目录并检查摘要 |
| 准备 | 复制私有生产配置，安装运行依赖，执行配置及连通性 preflight，写入 PREPARED |
| 备份 | 执行数据库与 Redis 备份，取得备份完成标记 |
| 迁移 | 执行 Alembic，核对 revision，写入关联备份路径的 MIGRATED |
| 激活 | 切换 current，启动四角色并检查进程目录、版本与 readiness，写入 ACTIVATED |

通知在构建失败及失败后恢复成功时发送，邮件通道由 Jenkins 管理。

## 版本目录

```text
/srv/se-course-project1/
  current -> releases/<commit-sha>-<build-number>
  releases/<release-id>/
    backend/           应用、迁移、.venv 和 .env.prod
    mobile/            移动端静态资源
    admin/             管理端静态资源
    deploy/            部署资产
    release.txt
    SHA256SUMS
    PREPARED
    MIGRATED
    ACTIVATED
  shared/
    .env.prod
    demo-manifest.json
  .activation.lock
```

每个 release 使用独立虚拟环境，通过 `uv sync --locked --no-dev` 安装。`PREPARED` 表示准备完成，`MIGRATED` 记录结构版本与备份关联，`ACTIVATED` 记录当前及上一版本信息。

## 服务与健康检查

| 角色 | systemd unit | 后端入口 |
|---|---|---|
| API | `se-course-project1-api.service` | `python -m app.manage serve-api` |
| WS | `se-course-project1-ws.service` | `python -m app.manage serve-ws` |
| worker | `se-course-project1-worker.service` | `python -m app.manage taskiq-worker` |
| scheduler | `se-course-project1-scheduler.service` | `python -m app.manage taskiq-scheduler` |

四角色共用 `current/backend` 和 `.env.prod`。激活器持有发布锁，停止上一版本服务，切换软链后按 scheduler → worker → WS → API 顺序启动；scheduler 保持单实例。

```bash
sudo systemctl status se-course-project1-api.service se-course-project1-ws.service se-course-project1-worker.service se-course-project1-scheduler.service --no-pager
curl -fsS http://127.0.0.1:8001/api/health
curl -fsS http://127.0.0.1:8002/health/ready
cd /srv/se-course-project1/current/backend
APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role worker
APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role scheduler
```

worker 检查任务心跳并投递探针，scheduler 检查调度心跳。发布后检查两个前端页面、API、双向消息及刷新重连；应用日志通过对应 unit 的 `journalctl` 查看。

## 回退、备份与保留

激活失败时恢复上一 `current` 和服务集合，并写入失败标记。数据库、Redis、OSS 与 Nginx 按各自备份及配置记录恢复。

发布前备份保存 PostgreSQL custom 归档、Redis RDB、元数据、摘要及完成标记，目录为 `/var/backups/se-course-project1/predeploy-*`。OSS 使用独立对象保护策略。

保留任务每日 04:30 附近执行，保留最近 5 个已激活 release 以及当前、上一版本；其余版本经过 7 天后进入清理范围。备份保留 30 天且至少 10 份，被保留版本引用的备份继续保存。激活、备份和清理通过文件锁互斥。

## 生产数据重新初始化

安排维护窗口，暂停发布并备份 PostgreSQL、Redis 和需要保留的对象，然后停止四角色。在当前 release 的 backend 目录预览：

```bash
.venv/bin/python -m app.devtools.reset --env-file .env.prod --allow-production
```

核对范围后添加 `--execute --confirm '<预览中的确认值>'`；专用整桶清理再添加 `--whole-buckets`。重置完成后重新初始化管理员，为 demo-seed 指定新的 manifest，再启动四角色并检查业务入口。
