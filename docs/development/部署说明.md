# 部署说明

本文描述生产部署的实际链路、发布流程与运维入口。私有部署的服务器地址、域名、端口映射、账号凭据、桶名及收件邮箱等可追踪信息不在仓库登记，由负责人在 Jenkins 凭据、生产配置文件与对应系统中管理。发布执行细节以仓库根目录的 `Jenkinsfile` 与 `scripts/deploy/` 为准，本文不重复其脚本内容。

## 总体链路

```text
浏览器 HTTPS
  → 边缘接入层（对外 HTTPS 终止，证书验证委托由 DNS 托管）
  → 公网接入层 Nginx（保留原始 Host，透传 WebSocket）
  → 内网隧道
  → 生产机 Nginx（按 Host 分流）
      ├─ 管理端静态文件：current/admin
      ├─ 移动端静态文件：current/mobile
      └─ /api/、/ws → 127.0.0.1:8001（combined）
```

split 目标拓扑（首次切换后）：

```text
生产机 Nginx
  ├─ /api/ → 127.0.0.1:8001  se-course-project1-api.service
  └─ /ws   → 127.0.0.1:8002  se-course-project1-ws.service

独立后台角色（无对外 HTTP）：
  se-course-project1-worker.service     Taskiq worker（outbox/超时/retention/幂等清理）
  se-course-project1-scheduler.service  单实例 Taskiq scheduler

过渡/回退（旧 3 角色 release）：
  127.0.0.1:8003  se-course-project1-jobs.service
```

后端由 systemd 服务以 `deploy` 用户运行；旧 combined 沿用 `se-course-project1-backend.service`，入口 `python -m app.manage serve`，保留为兼容回退。首次 split 需要维护窗口，不是零停机滚动发布；worker/scheduler 没有对外 HTTP，`jobs` 仅保留为旧 3 角色 release 的过渡/回退入口。生产机本机另运行 PostgreSQL 与 Redis。两个前端构建使用公开参数模式（`PROJECT1_FRONTEND_CONFIG=public`），API 基址默认同源 `/api/v1`，构建产物不含生产配置；正式接入由生产机 Nginx 提供同源反代与 SPA 路由回退（`/index.html`、`sw.js` 等入口文件不缓存，`/assets/` 长缓存）。

生产机 Nginx 的 split 模板是可并入现有 host 的 location/upstream fragment，不替换静态根、PWA 缓存或 TLS；`/ws` 保持源站 `X-Forwarded-Proto=https`（现有 HTTPS 边缘终止语义），并关闭该 location 的 access log，公网层也必须抑制 query 日志。

## 发布流水线

流水线由仓库 `Jenkinsfile` 定义，main 分支 push 经 Webhook 触发（分支过滤 `refs/heads/main`），禁止并发构建，总超时 30 分钟。阶段顺序：

| 阶段 | 内容 |
|---|---|
| 检出与结构校验 | 检出 main，校验仓库结构 |
| 后端依赖安装 | `uv sync --locked` 安装锁定依赖 |
| 实时集成门禁 | 真实 CI PostgreSQL+Redis runner（单一阶段），覆盖 API/WS/worker/scheduler 跨进程、杀 worker 接管、重试/终态、scheduler 重启与 Redis 重启/断连后 PG 补扫；缺 CI 凭据/前置条件失败，不静默跳过 |
| 部署脚本测试 | 用 fake systemctl/health 测 activation/preflight，不访问真实 systemd |
| 后端验收 | 生成临时 `.env.dev`（SQLite + 本地存储 + 测试邮件捕获，权限 0600，成功失败均删除），以独立端口运行统一业务验收 runner；不使用生产 PostgreSQL、OSS 或业务 SMTP 凭据 |
| 前端构建 | 双前端安装依赖并以公开参数模式生产构建 |
| 锁文件校验 | 构建过程不得修改 uv/npm 锁文件 |
| 打包 | `git archive` 打包 backend，CI 构建产物打包 mobile/admin，并把 `scripts/deploy/` 打包为 deploy 资产；生成 `release.txt` 与 `SHA256SUMS` |
| 上传 | 以 `deploy` 用户经 SSH（严格主机公钥校验）上传至生产机 releases 目录并校验和；`release_id` 为 `<完整提交SHA>-<构建号>` |
| 生产准备 | 远端校验 SHA256SUMS，拒绝覆盖已有内容；解包 backend/mobile/admin/deploy；从 `shared/.env.prod` 复制 0600 副本；`uv sync --locked --no-dev`；校验生产配置并执行 preflight（split 同时校验 combined 回退）；写 `PREPARED` |
| 生产备份 | sudo 执行备份脚本，输出 `predeploy-*` 目录；取得唯一 `BACKUP_COMPLETE` 标记，失败阻止发布 |
| 生产迁移 | `app.manage migrate` 后核验数据库 Alembic revision 与代码 head 一致（迁移角色 SET ROLE owner）；写 `MIGRATED`（含 release_id 与备份路径） |
| 生产激活 combined | `current` 原子切换、重启旧 combined、`/api/health` 与 MainPID cwd 校验；失败回退上一版本 |
| 生产激活 split | deploy 运行固定用途 `activate.py`：锁内识别 previous、按旧 ACTIVATED 服务集合成套停止旧 combined 或旧 3 角色、切换 current、启动 scheduler→worker→ws→api、逐角色 HTTP/受控 CLI readiness + MainPID cwd 校验（worker 执行真实 task probe）；失败恢复旧 current 与旧服务集合，写 `ACTIVATION_FAILED`/`ACTIVATED`（含 roles/services/protocol/previous_*） |

失败通知：构建失败及失败后恢复成功时发送邮件，连续成功不发送；通知模板与收件人在 Jenkins 全局配置维护，不写入项目代码。

## 服务器目录布局

```text
/srv/se-course-project1/
├── current -> releases/<release_id>
├── releases/<release_id>/
│   ├── backend/            应用、alembic、.venv、.env.prod
│   ├── mobile/             移动端静态产物
│   ├── admin/              管理端静态产物
│   ├── deploy/             systemd/Nginx/sudoers/preflight/activate 资产
│   ├── release.txt、SHA256SUMS
│   └── PREPARED、MIGRATED、ACTIVATED
├── shared/
│   ├── .env.prod           持久生产配置源（0600）
│   └── demo-manifest.json  演示账号清单
└── .activation.lock
```

- 配置生效规则：持久配置源是 `shared/.env.prod`，每次准备阶段复制进 release；只改 shared 不影响运行中版本，只重启也不会重新复制；需要立即生效时显式同步当前 release 副本再重启。
- 版本标记：`PREPARED` 表示解包、依赖安装与配置检查完成；`MIGRATED` 记录迁移完成及备份路径；`ACTIVATED` 记录激活完成、`previous_release`、模式与时间。当前版本以 `current` 软链为准。

## 运行环境

- 每个 release 自带 `backend/.venv`，由 `uv sync --locked --no-dev` 安装；系统 Python 不被替换。
- systemd 模板随 release 归档到 `deploy/systemd/`，需管理员一次性安装：combined（沿用 `se-course-project1-backend.service` 身份）、api、ws、worker、scheduler；旧 3 角色回退还需 jobs。运行用户 `deploy`，工作目录 `current/backend`，`APP_ENV_FILE=.env.prod`，各 unit 用 `APP_RUNTIME_ROLE=combined|api|ws|worker|scheduler|jobs` 选择角色；启用 UMask、NoNewPrivileges、ProtectSystem、RestrictAddressFamilies 等加固项。`ProtectHome=read-only` 允许读取 uv 管理的 Python，`ReadWritePaths` 仅放开 `current/backend`；上线前用 `systemd-analyze verify` 和实际解释器路径核对。
- 配置读取：业务配置仍只从 release 内 `.env.prod` 读取；`APP_RUNTIME_ROLE` 是运行角色选择器，不是业务配置。四个 split 角色共用一个 release 和一份 dotenv；`TASKIQ_WORKER_PROCESSES`、并发/prefetch、reclaim、retry、interval 与各 Redis 池全部从 dotenv 构建，systemd 不重复。
- 健康检查：API/combined `http://127.0.0.1:8001/api/health`；API/WS/combined/jobs 另有 `/health/live`、`/health/ready`。worker/scheduler 无 HTTP：`python -m app.manage health --role worker` 要求 SQL 心跳 + 最近成功执行并入队真实 probe；`--role scheduler` 只读 Redis 调度心跳。worker 缺席时 worker readiness 失败；scheduler 必须单实例，两个 scheduler 会重复派发。
- `deploy` 用户直接运行 `/usr/local/sbin/se-course-project1-activate`；脚本只对 sudoers 中逐条列出的固定 `systemctl start/stop <unit>` 调用 `sudo -n`，不获得任意 systemctl/shell、也不以 root 执行 release Python/health 钩子。模板见 `scripts/deploy/sudoers/`。

## 数据库、缓存与对象存储

- PostgreSQL：生产禁止自动 DDL，结构由迁移命令建立；应用、迁移登录、owner 三角色分离，迁移显式 SET ROLE 至 owner；迁移对审计等对象设置的细粒度权限不应在迁移后统一补授。建库与角色准备见[开发与人工测试指南](guidance.md)。API 写入口在新增事件前按 PostgreSQL pending 数量/年龄做软准入，超限返回 503/Retry-After；缓存窗口与在途事务意味着部署必须预留高于阈值的连接/磁盘余量，不能用删除未投递事件解决积压。
- Redis：控制/发布/reader 使用有界获取（获取等待、超时、耗尽指标），`REDIS_URL` 查询参数不得覆盖显式 max_connections/timeout/retry；生产机本机独立实例，键前缀区分项目；连接与认证配置以生产 dotenv 为准。实时分层要求共享 Redis：生产或 split 缺 `REDIS_URL/REDIS_KEY_PREFIX` 启动失败，不回退进程内 memory。管理员需核实监听/防火墙、独立 ACL 用户与最小命令权限、TLS 或受保护链路；实时/控制使用独立实例或专用 ACL/资源预算。stream 与 ticket/频控不应受普通缓存驱逐：设置预算明确的 `maxmemory`、`noeviction`，预留 fork/AOF 内存，启用 AOF `everysec` 并演练重启恢复。AOF 不能替代 PostgreSQL outbox；现有全实例备份可能含其他项目，不能自动整实例 restore。
- OSS：私有媒体／证据双桶，浏览器凭短期租约直传、读取走短期签名 URL；桶名、endpoint 与 AK 以生产 dotenv 为准。媒体桶 CORS 需允许两个前端实际 origin 的 PUT 及对应请求头（见[开发与人工测试指南](guidance.md)）。
- 业务 SMTP 与流水线通知邮件是两套独立配置；业务 SMTP 位于生产 dotenv，不能以构建通知发通认定业务验证码投递已验证。

## 实时分层发布与回退

仓库新增的部署资产随 release 打包到 `deploy/`，但系统 unit、Nginx 和 sudoers 必须由管理员安装，Git 发布不会自动更新它们。安装前备份并预览现有文件，使用 `systemd-analyze verify`、`nginx -t`、`visudo -cf` 校验。

| 资产 | 作用 |
|---|---|
| `deploy/preflight.py` | 按 `--mode combined|split` 只校验目标角色集合（split 另校验 combined 回退模式）的生产配置、连接预算、DB/Redis 连通性；缺项失败，不静默跳过 |
| `deploy/activate.py` | 以 deploy 运行；锁内识别 previous，**成套停止旧 combined 或旧 split 三服务**，校验 release/PREPARED/MIGRATED/backup，切换 `current`，启动新服务并逐角色做 HTTP/WS readiness + MainPID cwd 校验；失败恢复上一 release 与旧服务集合（旧基线用 `/api/health`），`ACTIVATED` 写 `previous_release=` |
| `deploy/systemd/` | combined/api/ws/worker/scheduler（及旧 jobs 回退）unit 模板 |
| `deploy/nginx/se-course-project1-http.conf` 与 `se-course-project1-routes.conf` | 前者只在 http 层安装，后者只 include 到既有 server 中；禁止混合层级直接复制进 conf.d；不丢静态/PWA 规则，`X-Forwarded-Proto https` |
| `deploy/sudoers/` | 仅允许固定 unit start/stop 与备份脚本 |

首次 combined→split 使用维护窗口：以 deploy 运行激活脚本（`--sudo --verify-process --mode split --backup-dir <predeploy-dir>`），脚本按旧 ACTIVATED 记录成套停止旧服务、切换 current、启动 scheduler→worker→ws→api、逐角色 readiness（worker 含真实 probe）通过后，管理员再把 Nginx `/ws` 切到 8002 并验证真实 ticket→WS→持久事件→ACK，最后开放流量。旧 scheduler 必须先停，不能新旧 scheduler 同时派发。任一步失败，脚本停止新角色、恢复旧 `current` 和旧服务集合；保留 `ACTIVATION_FAILED` 与现场日志。**脚本不会修改 root-owned Nginx 配置**：失败/回退时管理员必须人工恢复旧 `/ws` upstream/停用新路由，不能声称代理已自动回退。PG/Redis/outbox 也不自动回滚；重新升级时要求客户端 resync/版本水位。

Jenkins 新增单一真实 PostgreSQL+Redis 集成门禁（已含 Taskiq 队列覆盖），依赖 Jenkins 凭据 `realtime-ci-pg-admin-url`；当前 Jenkins 使用托管 Redis，不再要求 Redis URL 凭据；缺凭据或前置条件时该阶段失败。托管 Redis 重启门禁要求 CI agent 有 `redis-server`，测试先停 worker、在 Redis 停机期间提交事件并确认 WS 从 PG 补扫，再重启 Redis/worker；使用外部 Redis 时只按本轮 prefix 的 client_name 精确断开自己的 WS reader 并删除自己的 stream，绝不 `CLIENT KILL TYPE normal`，报告中明确这是连接/stream 丢失而非进程重启。`DEPLOY_MODE=split` 时调用固定用途激活脚本，`combined` 时保留旧单服务激活路径。

## 备份与保留

- 备份脚本由 root 维护并安装在系统路径；每份备份包含 PostgreSQL custom 格式归档、Redis 整实例 RDB、元数据、SHA256SUMS 与 `COMPLETE` 标记，输出至 `/var/backups/se-course-project1/predeploy-*`。两个系统分别在线快照，不保证跨系统同一瞬间一致。
- 备份不包含 OSS 对象；代码回退不会自动恢复数据库。
- 自动清理：`scripts/deploy/retention.py` 安装为 root 并由 systemd timer 每日 04:30 左右执行；保留最近 5 个已激活 release 及当前、上一版本，其余超 7 天删除；备份保留 30 天且至少 10 份，被 release 引用的备份继续受保护；清理与激活、备份通过文件锁互斥，无法确认当前版本时拒绝清理。直接运行脚本为预览，经 systemd service 启动才实际执行。

## 生产数据操作与邮件验证

- 生产 reset 与演示数据重建：见[开发与人工测试指南](guidance.md)生产节；reset 不自动备份、不停止服务，执行前须完成 PostgreSQL／Redis 备份。
- SMTP 通道验证：`scripts/deploy/mail-test.Jenkinsfile` 供独立临时流水线验证邮件通道，不执行生产部署；其结果不代表业务 SMTP 投递已验证。

```bash
readlink -f /srv/se-course-project1/current
sudo systemctl status se-course-project1-backend.service se-course-project1-scheduler.service se-course-project1-worker.service se-course-project1-api.service se-course-project1-ws.service --no-pager
sudo journalctl -u se-course-project1-backend.service -n 100 --no-pager
curl --noproxy '*' -fsS http://127.0.0.1:8001/api/health
curl --noproxy '*' -fsS http://127.0.0.1:8002/health/ready
curl --noproxy '*' -fsS http://127.0.0.1:8003/health/ready
cd /srv/se-course-project1/current/backend && APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role api
cd /srv/se-course-project1/current/backend && APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role ws
cd /srv/se-course-project1/current/backend && APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role jobs
sudo systemctl status se-course-project1-api.service se-course-project1-ws.service se-course-project1-worker.service se-course-project1-scheduler.service --no-pager
cd /srv/se-course-project1/current/backend && APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role worker
cd /srv/se-course-project1/current/backend && APP_ENV_FILE=.env.prod .venv/bin/python -m app.manage health --role scheduler
sudo systemctl status se-course-project1-retention.timer --no-pager
sudo du -sh /srv/se-course-project1/releases /var/backups/se-course-project1
```

本机健康正常而外部访问异常时，按"生产机 Nginx Host 分流 → 内网隧道 → 公网接入层 → 边缘接入层／证书"顺序排查；前端直传失败时检查 OSS 请求状态、签名有效期、桶 CORS 及允许的请求头。
