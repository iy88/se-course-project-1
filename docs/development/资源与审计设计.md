# 资源与审计设计

## 数据库

生产与集成测试各一个 PostgreSQL 数据库，分别 `campus_market_prod`、`campus_market_test`。可先共用本地 PostgreSQL 实例，但资源、备份和故障域仍共享，不等于生产基础设施已隔离。实例版本先由负责人执行版本查询确认，代码以实际版本测试；金额仍使用整数分，时间统一 UTC。

ORM模型与业务查询统一采用SQLModel的SQLModel/Field/Relationship及select/exec；SQLAlchemy仅作为其底层与异步连接、特殊列和迁移基础设施直接依赖。当前交易、约定版本、状态转移、确认、事项等关系表继续使用；不引入 MongoDB/Mongoose。必要快照在 PostgreSQL 使用 JSONB，在 SQLite 使用兼容 JSON。当前记录与历史记录分开，历史不靠修改当前内容重建。

每环境独立 owner、migrator、app 三个角色：owner 不登录，migrator 仅人工迁移时使用，app 只有业务 DML 和必要序列权限。生产 app 不建表、不执行迁移、不拥有表；迁移账号不放进服务进程环境。建库命令见[资源准备](PostgreSQL资源准备.md)。现有 SQLite 数据不自动迁移；要保留演示数据时另行制定导入、ID/序列校准和附件搬迁计划。

## Bucket：每环境两个，共四个

以下名字是全局唯一命名模板，创建前将 `YOUR-SUFFIX` 替换为实际可用的小写后缀，两环境选择相同地域。

| 用途 | test | production | 对象前缀 |
|---|---|---|---|
| 一般业务图片 | campus-market-test-media-YOUR-SUFFIX | campus-market-prod-media-YOUR-SUFFIX | product/、avatar/、chat/ |
| 举报证据 | campus-market-test-evidence-YOUR-SUFFIX | campus-market-prod-evidence-YOUR-SUFFIX | report/ |

全部为标准存储、私有 ACL、阻止公共访问，使用 HTTPS；开启服务端加密（先用 OSS 托管密钥，不引入额外 KMS 权限）。不按用户、商品或每个前缀再建 bucket。媒体与证据拆分是为了独立保留/生命周期策略，并不意味着媒体公开可读；聊天图片同样私有。暂不建审计 bucket：应用审计入数据库，OSS 访问日志将来启用时另建每环境日志 bucket，避免业务删除权限作用于日志。数据库备份不使用应用 AK 上传到业务 bucket。

不自动设置生产到期删除；举报证据、交易关联媒体的保留期限需负责人另定。版本控制可按预算开启，开启后逻辑删除不代表历史版本被物理清理；测试清理只删本次创建对象，版本历史由管理员制定生命周期回收，不向应用授予 DeleteObjectVersion。初期走后端上传和读取，不启用浏览器直传、不必开放 bucket CORS。

## 单 RAM 用户、单 AK

采用一个程序访问 专用 RAM 用户，一套 AK ID/Secret 同时访问四个 bucket，不按 bucket 创建 AK。由管理员创建 bucket、加密、生命周期及权限；应用用户不得管理 bucket/ACL/RAM。此模式下 test 与 prod 的凭据安全边界共享，泄漏任一配置都会影响四个 bucket，应用的环境 allowlist 只能防误操作，不能替代 RAM 权限隔离。轮换 AK 时两环境都要更新。

将四个实际名称逐一替换后，为该 RAM 用户绑定以下自定义策略。不要附加 AliyunOSSFullAccess。若 SDK 的 HEAD/exists 使用 HeadObject，其授权通常对应 GetObject，实施时按实际 SDK 操作核对，不为排错放宽为 oss:*。

```json
{
  "Version": "1",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["oss:GetObject", "oss:PutObject", "oss:DeleteObject"],
      "Resource": [
        "acs:oss:*:*:campus-market-test-media-YOUR-SUFFIX/*",
        "acs:oss:*:*:campus-market-test-evidence-YOUR-SUFFIX/*",
        "acs:oss:*:*:campus-market-prod-media-YOUR-SUFFIX/*",
        "acs:oss:*:*:campus-market-prod-evidence-YOUR-SUFFIX/*"
      ]
    }
  ]
}
```

不需要 ListBuckets/ListObjects：业务使用上传后返回的 key 定位；smoke 清理用本轮对象清单。验证探测通过指定随机测试 key 完成，不调用需要额外权限的 bucket 管理 API。管理员在控制台查看资源，不必授予应用控制台权限。生产对象的物理删除仍必须受应用资格、引用和保留策略控制；RAM DeleteObject 不是业务删除授权。

对象 key 继续使用 `namespace/YYYYMM/random.ext`，数据库保存逻辑 key，不保存带签名 URL 或 AK。命名空间到 bucket 的确定映射：report → evidence，其余允许前缀 → media；未知前缀拒绝。上传、读取、exists、删除使用同一映射。local 后端保留 HMAC 文件访问入口；OSS 桶保持私有，由后端签发短期签名 GET 直链，有效期与 `FILE_URL_EXPIRE_SECONDS` 一致，不开放公开读 ACL，同一进程内按对象复用未到期链接，避免元数据刷新触发图片重载；签名链接可由持有者直接读取，按敏感数据处理，不写日志或报告；使用OSS Python SDK V2，原oss2包已移除；同步 SDK 调用放入线程池，设置超时和有限重试。数据库事务与 OSS 无跨系统事务，采用上传登记/失败补偿及待回收对象清单，禁止在数据库回滚时误删已有共享对象。

### 对象登记与回收

上传租约签发时即登记 `stored_objects` 为 `staged`，以跟踪未完成或失败的上传。前端直接使用短期签名PUT上传，后端完成接口核对HEAD大小、MIME、SHA256元信息，再有界读取对象计算实际SHA256并用Pillow校验图片完整性，通过后租约为completed；未完成、失败、越权或命名空间不符不得业务引用。租约有效期间禁止staged回收，保持对象不可覆盖，避免旧签名链接重放。商品/举报业务事务提交时把对象改为 `committed` 并记录 `ref_type/ref_id`。表保存 key、namespace、bucket_role、owner、content_type、size、非敏感 metadata、state 及时间戳，不保存对象内容、签名 URL 或凭据。

回收只处理 `staged`，且每次都用 `product_images.file_key`、`reports.evidence_keys`、`report_supplements.evidence_keys` 实时确认无业务引用；`committed` 与仍被引用的对象不自动删除。举报证据没有默认 TTL，不引入定时清理；`python -m app.devtools.objects` 默认只列出，显式 `--delete` 才清理；执行前须通过 `APP_ENV_FILE` 选择并核实 test 配置。清理成功把登记改为 `deleted` 留痕。

清理与业务 `mark_committed` 对同一 `stored_objects` 登记行使用 PostgreSQL 行锁：实际删除路径先锁定未引用 staged 候选（已被业务锁定的行跳过），再查引用、删除对象并标记 `deleted`；业务在插入商品图片或举报证据的同一事务内锁定登记行并检测状态，发现已 `deleted` 即失败回滚，不能继续引用已物理删除的对象。只读列举与 dry-run 不加锁。证据对象默认禁止物理删除（即使 staged 且当前无引用），保留原因记为 `evidence_protected`，本轮不提供放宽入口。OSS 删除与数据库提交无跨系统事务：若对象已删除而提交失败，登记会回滚为 staged，下次清理以对象不存在补记 `deleted`，该窗口不能由数据库事务消除。

上述 `stored_objects` 运维回收与自动化验收的逐轮清理用途不同。自动化验收需按 run_id 隔离并清理本轮创建的所有数据库、存储和 Redis 资源；不得因此清理共享数据。此策略的实现及成功/失败路径复验单独记录于[整体验收](整体验收.md)，未完成复验前不视为通过。持久化管理员与必要参考数据由独立的 `app.manage seed` 保留，供人工浏览器流程使用。

## 登录与变更审计

独立审计表记录 event_id、UTC 时间、request_id、actor_id（匿名失败可空）、事件类型、目标类型/ID、结果、原因码和必要的脱敏前后值；IP/UA 受限长度，来源仅信任显式配置的代理。登录成功/失败、退出、改密/换邮箱、权限变更、商品编辑、约定提议/确认/拒绝、交易转换、确认/取消/争议、冻结/解冻与管理员处置纳入事件矩阵。

成功业务变更与审计同事务提交，审计写入失败应回滚本次变更。登录失败及拒绝操作独立短事务记录，不能随业务回滚丢失；禁止在持有业务锁时再开审计事务。后台扫描用 system actor。审计不复制密码、哈希、验证码、JWT、AK、完整数据库 URL、上传正文和整段聊天内容。失败登录标识最小化/脱敏，保留期限与清理审批另定。

迁移创建审计表后，对 app 撤销 UPDATE/DELETE/TRUNCATE，只授予 INSERT 和必要 SELECT；表由不登录 owner 所有。owner/数据库超级用户仍可修改，不能宣称数据库内审计防管理员篡改；若需要不可篡改归档，另行决定 WORM/外部审计系统。生产审计查询需要权限与分页，禁止面向普通用户暴露全量日志。回归覆盖密码等敏感字段不会进入审计。
