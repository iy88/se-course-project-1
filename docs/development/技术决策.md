# 开发技术决策

本文件登记 `dev` 分支的技术选型、资源与权限设计、需求到实现的关键口径及未处置事项。环境文件与运行命令见[开发与人工测试指南](guidance.md)；生产发布见[部署说明](部署说明.md)；当前统一验收状态见[整体验收](整体验收.md)。业务口径以 `docs/requirements/01—08` 为唯一依据；实现遇到规则未覆盖处按最接近的现行规则保守处理，并在本文件登记。

## 技术栈与三端结构

- 仓库布局：`backend/`（FastAPI）、`frontend/admin/`（桌面管理端）、`frontend/mobile/`（移动 PWA）；运行期数据全部位于被 Git 忽略的 `var/`。
- 后端：uv 管理依赖；FastAPI + SQLModel（ORM 模型与业务查询）+ SQLAlchemy 2.0 异步基础设施（引擎、关系加载、SQL 方言与迁移）+ Pydantic v2 + PyJWT + bcrypt。
- 数据库：集成与生产使用 PostgreSQL，SQLite 保留为离线测试与快速调试路径。结构变更一律通过 Alembic 迁移；生产禁止任何自动 DDL，非生产 SQLite 启动时仅按配置补建表和追加缺失列（D-51），不重建、不清空已有数据。现有 SQLite 数据不自动迁移，保留演示数据另行制定导入计划。
- KV：统一 `KeyValueStore` 抽象，配置 Redis 时使用 Redis，否则进程内 memory 兜底；验证码等短时状态经此访问。
- 认证：JWT Bearer（HS256，载荷 uid/role，默认 7 天），密码 bcrypt；首版不设刷新令牌与登录失败锁定（BR-21）。
- 实时消息：WebSocket `/ws`（token 鉴权）+ 进程内连接管理器；消息落库为准，WS 仅推送提醒；多实例跨进程广播未实现。
- 价格：库内以"分"（整数）存储，展示层转元，避免浮点误差；时间统一 UTC，必要快照 PostgreSQL 用 JSONB、SQLite 用兼容 JSON；当前记录与历史记录分开，历史不靠修改当前内容重建。

## 资源与权限设计

### 数据库角色

每环境独立 owner、migrator、app 三个角色：owner 不登录，migrator 仅迁移进程使用并显式 `SET ROLE owner`，app 只有业务 DML 和必要序列权限。生产 app 不建表、不执行迁移、不拥有表；迁移账号不放进服务进程环境。建库与角色命令见[开发与人工测试指南](guidance.md)。

### 对象存储

- 每环境媒体／证据两个私有桶，桶名由各环境 dotenv 配置（形如 `campus-market-<环境>-media`／`campus-market-<环境>-evidence`，以实际创建名为准）：一般业务图片（product/、avatar/、chat/ 前缀）入媒体桶，举报证据（report/ 前缀）入证据桶；全部标准存储、私有 ACL、HTTPS、服务端加密（OSS 托管密钥），不按用户或前缀再建桶。
- 命名空间到桶的固定映射：report → evidence，其余允许前缀 → media，未知前缀拒绝；上传、读取、exists、删除同一映射。数据库保存逻辑 key（`namespace/YYYYMM/random.ext`），不保存签名 URL 或凭据。
- 单 RAM 用户单 AK 访问全部桶：自定义策略按实际桶名编写 Resource，对象级（`<bucket>/*`）授予 GetObject／PutObject／DeleteObject，桶级授予 ListObjects，不附加 FullAccess，不授予 bucket／ACL／RAM 管理权限；test 与 prod 凭据边界共享，轮换 AK 两环境同换。
- 读取由后端签发短期签名 GET 直链，有效期与 `FILE_URL_EXPIRE_SECONDS` 一致，同进程复用未到期链接；不开放公开读 ACL，签名链接按敏感数据处理，不写日志或报告。
- 生产到期删除不自动设置，举报证据与交易关联媒体的保留期限由负责人另定；版本控制按预算开启，不向应用授予 DeleteObjectVersion。

### 对象登记与回收

上传租约签发时即登记 `stored_objects` 为 `staged`；前端用短期签名 PUT 直传（不携带应用 Bearer），完成接口核对 HEAD 大小、MIME、SHA256 元信息，再有界读取对象核对实际 SHA256 并用 Pillow 校验图片完整性，通过后租约 completed；未完成、失败、越权或命名空间不符不得业务引用，租约有效期内禁止回收、对象不可覆盖。业务事务提交时对象转 `committed` 并记录 `ref_type/ref_id`。

回收只处理无引用 `staged`，每次以 `product_images.file_key`、`reports.evidence_keys`、`report_supplements.evidence_keys` 实时确认；与业务 `mark_committed` 对同一登记行加 PostgreSQL 行锁，业务发现 `deleted` 即失败回滚。证据对象默认 `evidence_protected` 禁止物理删除；`app.devtools.objects` 默认只列出、显式 `--delete` 才清理。OSS 删除与数据库提交无跨系统事务，删除后提交失败由重跑以对象不存在补记。此回收与自动化验收的逐轮 run_id 隔离清理是两个用途，后者见[整体验收](整体验收.md)。

### 登录与变更审计

独立审计表记录事件类型、UTC 时间、request_id、actor（匿名失败可空）、目标、结果、原因码及必要的脱敏前后值；IP/UA 受限长度，来源仅信任显式配置的代理。登录成功/失败、退出、改密/换邮箱、权限变更、商品编辑、约定与交易转换、冻结/解冻及管理员处置纳入事件矩阵。成功业务变更与审计同事务提交，失败与拒绝走独立短事务，不在持有业务锁时再开审计事务；后台扫描用 system actor。审计不复制密码、哈希、验证码、JWT、AK、连接串、上传正文和整段聊天内容。迁移对 app 角色撤销 UPDATE/DELETE/TRUNCATE，仅授 SELECT/INSERT；owner 仍可修改，数据库内审计不防篡改，需要不可篡改归档时另定 WORM 方案。查询接口需管理员资格、分页与字段白名单。

## 需求到实现的关键口径

- 交易与请求同对象（`trades` 表），覆盖待接受、已拒绝、已撤回、已关闭、进行中、有争议、异常、已终止、已完成九个状态；进行中内部以当前有效约定区分"约定待确认"与"约定已确认待完成"；冻结为独立标记；单方确认进度用当前有效确认记录加 `confirm_wait_started_at` 计时（US-05、D-49、D-51）。
- 商品状态：待审核、审核未通过、公开可交易、交易中、已下架；违规撤销公开为独立展示限制字段，与生命周期分开（4.10）。
- IM：`conversations`（普通会话按双人复用唯一，交易分支按交易唯一）加 `messages`；未读按会话级 `last_read_message_id` 计算，仅打开会话时推进（BR-18）；交易结束自动归档分支；冻结按"用户对"判断，存在任一有效冻结即双人两类 IM 禁发（BR-33）。
- 通知（4.17 全事件清单）：`notifications` 表，打开才已读；WS 同步未读数。
- 超时识别：后台扫描任务按配置间隔运行，单方确认超时转异常并冻结，进入共享池待办（TR-14）；冻结期间暂停累计，解冻续算剩余时间。
- 管理事项：`disposal_cases` 统一承载商品审核、举报、争议、异常、封禁事项的认领、问询、说明、申辩、结论与沟通单消息；唯一认领人以数据库条件更新判定，同一事项同时仅一名管理员成功（BR-34）。认领举报事项时在同一事务把举报状态同步为 `processing`（结论仍为 `handled`／`unfounded`）；管理端"我的审核"页与待处理池同分区，经 `mine=true` 仅列出本人认领事项。
- 评论不设应用层长度上限，使用数据库 TEXT 字段承载；发表频率限制沿用现有配置。
