# 环境配置与测试隔离

## 文件与选择约定

负责人在后端工作目录将 `.env.dev.example`、`.env.prod.example` 分别复制为 `.env.dev`、`.env.prod`，自行填值；不要覆盖已有配置。两份实际配置均不提交。模板只使用 `REPLACE_*` 占位符，不写真实库名、角色名、bucket 或凭据。默认读取 `backend/.env.dev`，`APP_ENV_FILE` 显式选择文件。运行设置只从所选文件读取，系统环境中的其他配置变量不覆盖文件值。

首次复制（从仓库根目录执行；仅在目标文件不存在时复制）：

```bash
cp -n backend/.env.dev.example backend/.env.dev
cp -n backend/.env.prod.example backend/.env.prod
chmod 600 backend/.env.dev backend/.env.prod
```

开发与生产模板分别维护；生产配置应使用独立库名、角色、bucket 和密钥。生成应用密钥可运行 `python3 -c "import secrets; print(secrets.token_urlsafe(32))"`，每项重新生成后仅填入本地配置。

HTTP验收客户端、WebSocket本机连接及OSS SDK不读取隐式环境代理，OSS SDK也不读取netrc认证覆盖，避免终端配置改变既定连接目标。

现行规则：环境变量 `APP_ENV_FILE` 是唯一文件选择器，默认指向后端目录的 `.env.dev`，不受启动 cwd 影响；除该选择器外，应用不读取继承的设置环境变量。文件缺失、必填项缺失或空白、字段格式错误均在启动时报告字段并终止，不回退读取其他文件。

`ENVIRONMENT` 区分 dev/prod；`DATABASE_URL` 为普通应用连接；`MIGRATION_DATABASE_URL` 与 `MIGRATION_OWNER_ROLE` 仅用于单独迁移进程，服务加载时不得将迁移凭据传入 SDK、日志或诊断接口。生产部署注入 app 配置，迁移任务另行注入凭据，不给常驻服务 owner 能力。

数据库、存储及 KV 后端在所选环境文件中明确配置；测试与 seed 命令保持一致，不使用 `--profile`。同一全量业务验收套件按实际配置运行。

### 日常启动、初始化与配置修改

从仓库根目录运行 `./scripts/dev.sh start` 后三个应用在后台启动，`./scripts/dev.sh status` 查看进程，`./scripts/dev.sh stop` 停止托管服务。默认读取已有 `backend/.env.dev`，也可用 `APP_ENV_FILE` 显式选择其他 dotenv 文件；不自动创建/复制环境文件，不启动本机 PostgreSQL 或 Redis，不自动执行数据库迁移、持久化初始化或自动化 seed。后端8000、管理端5174、移动端5173需空闲。首次及结构升级先执行迁移；人工浏览器需要的管理员用独立持久化 seed 准备，自动化 runner 内部调用临时 seed。

脚本每次 `uv sync --frozen`；仅当前端 Vite 不存在时 `npm ci`，前端锁文件有变化需先停服再手动在两端 `npm ci`。启动等待约5秒后可能仅提示 preparing，使用 status/日志观察，不重复 start。status 是进程检查，停止时返回1，不等于异常；运行后还应检查 `http://127.0.0.1:8000/api/health` 和实际页面。

日志 `var/log/dev-services.log`，状态 `var/run/dev-services.json`。统一入口不会管理单独启动的服务；不要与手动方案重叠。修改所选 dotenv 文件后 stop/start，修改前端代理或依赖后也需重启相关 Vite。只改配置文件不保证已有进程重载。

运行前确认选定配置与预期一致。PostgreSQL 需先迁移；报告记录实际运行目标。应用设置从所选 dotenv 文件读取，环境变量只允许通过 `APP_ENV_FILE` 选文件。

前端从同一所选 dotenv 文件仅读取 `VITE_API_BASE_URL`、`VITE_API_TIMEOUT_MS` 和 `API_PROXY_TARGET`；三项可省略，默认 API 基址 `/api/v1`、超时15000毫秒、代理目标 `http://127.0.0.1:8000`。前端构建同样通过后端虚拟环境的集中加载器校验所选dotenv，因此需先准备后端依赖；Vite自身的dotenv加载和VITE前缀自动暴露已禁用。其余后端配置不会注入前端构建产物。当前 Vite 6 的 preview 默认继承 server.proxy；预览构建可使用4173/4174，但需另行启动后端服务，预览不由 dev.sh 管理。正式静态部署仍需独立反向代理和SPA路由回退。移动PWA安装需HTTPS或localhost，Vite dev不等于安装/缓存验收。

### 当前能力与命令

从仓库根目录进入后端。数据库迁移、持久化部署初始化、服务与自动化验收是不同入口：

```bash
cd backend
uv sync --locked
uv run python -m app.manage migrate
# 持久化部署初始化：交互设置初始管理员密码
uv run python -m app.manage seed
# 日常服务（或从根目录用dev.sh后台启动，不要同时启动两套）
uv run python -m app.manage serve --host 127.0.0.1 --port 8000
# 另一终端：唯一全量测试，自动调用内部临时seed并清理本轮资源
RUN_REAL_ACCEPTANCE=1 .venv/bin/python -m pytest -q
# 对象运维是独立功能，不是第二套测试
uv run python -m app.devtools.objects
```

自动化 runner 内部按本轮标识创建临时身份，退出时清理其创建的数据库、存储和 Redis 资源；成功与失败路径均须清理，不能删除共享数据。自动化 runner 使用每轮随机 schema 和私有临时 dotenv 文件；全量及故障清理复验状态见[整体验收](整体验收.md)。持久化 `app.manage seed` 只创建部署所需初始管理员及可选必要参考数据，供人工浏览器登录；需要第二名管理员时显式提供管理员邮箱。普通测试角色由注册流程创建。两类 seed 彼此独立，也不是 HTTP API。

`stored_objects` 登记上传和业务引用。自动化清理按本轮命名空间操作，不执行共享资源清库或全桶删除；持久化业务数据按既有保留策略管理。审计成功与业务同事务，失败/拒绝独立短事务；app角色无审计UPDATE/DELETE/TRUNCATE权限。

### 图片直传配置

移动端先通过带登录态的 API 创建短期上传 lease，并提交文件名、MIME、字节数和浏览器计算的 SHA-256；浏览器随后使用 lease 中的 method、URL 和签名 headers 直接上传对象存储，不向对象存储发送应用 Bearer token。上传成功后，客户端再调用完成接口；后端先核对HEAD的大小、MIME及SHA-256元数据，再有界读取实际对象，核对真实字节数和SHA-256，并通过Pillow检查图片结构与解码，确认后才返回可用于商品引用的key。过期或失败的 lease 不复用，重试时重新申请。

对象存储 CORS 需为实际移动端开发/部署 origin 显式配置 `PUT`（OSS自动响应OPTIONS预检），允许签名请求实际使用的 `Content-Type`、`x-oss-meta-sha256`、`x-oss-forbid-overwrite` headers；不要启用任意 origin 或凭据共享。签名 URL 可能包含临时签名参数，应按敏感数据处理，不能写日志或验收报告。浏览器跨域直传及真实对象验证仍须按浏览器验收清单实测。

## 关键配置矩阵

| 配置 | `.env.dev` | `.env.prod` | 集成配置 |
|---|---|---|---|
| ENVIRONMENT | `dev` | `prod` | `test` |
| DATABASE_URL | 必填：SQLite 或 PostgreSQL URL | 必填：PostgreSQL URL | 必填：PostgreSQL URL |
| DATABASE_SCHEMA | `app` | `app` | `app`；自动化 runner 独立生成随机 schema |
| OSS_MEDIA_BUCKET | local 时不需要；OSS 时必填 | 必填 | 必填 |
| OSS_EVIDENCE_BUCKET | local 时不需要；OSS 时必填 | 必填 | 必填 |
| OSS_ENDPOINT / OSS_REGION | OSS 时必填 | 必填：对应地域 | OSS 时必填 |
| OSS_ACCESS_KEY_ID/SECRET | OSS 时必填，单 RAM 用户 AK | OSS 时必填 | OSS 时必填 |
| SMTP_HOST / SMTP_PORT | 主机必填，端口默认465可覆盖 | 主机必填，端口默认465可覆盖 | 不连接真实邮件服务 |
| SMTP_SECURITY | 必填：`ssl`（465）或 `starttls` | 必填：`ssl`（465）或 `starttls` | 不用于发信 |
| SMTP_USERNAME / SMTP_PASSWORD | 必填：服务商提供的 SMTP 账户与密码 | 必填：服务商提供的 SMTP 账户与密码 | 不用于发信 |
| SMTP_FROM_EMAIL / SMTP_FROM_NAME | 必填：已获准发信的寄件地址及显示名称 | 必填：已获准发信的寄件地址及显示名称 | 不用于发信 |
| SMTP_TIMEOUT_SECONDS | 可选，默认 10 秒 | 可选，默认 10 秒 | 不用于发信 |
| REDIS_URL | 使用Redis时必填 | 使用Redis时必填 | Redis 连接地址 |
| REDIS_KEY_PREFIX | `dev:` | `prod:` | Redis 模式必填，隔离普通开发与生产 key；自动化使用每轮随机前缀 |
| AUDIT_TRUSTED_PROXIES | 必填：`none` 或代理 IP/CIDR 列表 | 必填 | 必填 |
| DB_AUTO_CREATE | 必填 | 必填：false | 必填：false |

现有 `OSS_BUCKET` 单桶项由开发改为媒体/证据两项；配置选择 OSS 时失败不得静默退回 local。配置REDIS_URL时推断为Redis且必须配非空REDIS_KEY_PREFIX；两项均省略时使用内存KV，仅有前缀而无URL视为不完整配置。任一OSS资源字段存在时必须配齐OSS字段；全无OSS资源字段时必须配STORAGE_LOCAL_ROOT。DATABASE_URL协议决定数据库类型，不设置backend选择项。任何已写出的字段不允许为空，配置/连接失败都不会回退。`AUDIT_TRUSTED_PROXIES=none` 显式表示不信任反向代理；否则必须提供合法 IP/CIDR 列表。常规服务固定使用SMTP，不设置邮件后端选择项，SMTP主机、端口、安全模式（SSL或STARTTLS）、账户、密码和寄件人缺失或仍为占位值时拒绝启动；连接超时默认10秒。自动化 runner 使用私有 `capture` outbox 并拦截邮件发送，不连接真实 SMTP，也不把真实验证码放入HTTP响应。全量验收命令按实际配置执行，报告标明实际后端，不将一种目标的结果说成另一种后端已验证。邮件服务商账号配置和真实收件箱人工验收仍待完成。

历史 PostgreSQL 与对象存储 HTTP smoke 结果只代表当时记录的 test 目标和代码版本；当前验收需按选定配置重新核对目标，见[整体验收](整体验收.md)。

密码包含 @、:、/、#、% 等字符时，连接 URL 的用户名/密码部分必须进行 percent-encoding；不编码整个 URL，不在报告中打印 URL。JWT_SECRET 与 FILE_URL_SECRET 分别生成至少32字节随机值，两个环境独立；生产启动检查占位密钥、PostgreSQL/OSS选择、HTTPS、自动建表与验证码暴露开关，不按资源名称猜测环境归属。

## 唯一测试入口与目标隔离

两个 dotenv 示例均不设置SMOKE专属变量。数据库、存储和 Redis 目标由所选配置文件明确指定。自动化身份仅由验收 runner 的临时 seed 创建；持久化管理员由独立初始化命令建立，不从 `.env` 写入普通账号密码。

全量入口按选定文件中的配置连接 SQLite/local 或 PostgreSQL/OSS，并使用明确选择的 memory 或 Redis KV。使用共享资源前需核实实际连接目标属于 test 环境；报告标明实际后端，不能仅以配置名称或本地端口推断通过。

自动化 CLI 与 pytest 使用相同 runner/seed，浏览器人工流程使用部署初始化管理员与注册用户。生产配置不得意外用于开发验收；命令不会自动创建生产资源。

从后端执行 `.venv/bin/python -m tests.acceptance_real.runner --port 8107` 或唯一 pytest 入口。runner 停止自己启动的服务，并清理本轮数据库、OSS/local、Redis 资源；其失败路径也必须执行清理。PG/OSS/Redis与SQLite/local的全量及失败路径清理已由主助手独立复验，证据及边界见[整体验收](整体验收.md)。共享数据和其他 run 的资源不得删除。账号密码、JWT、AK、连接串和签名链接不进入报告。来源覆盖、手工步骤与结果模板见[浏览器清单](浏览器交互验收清单.md)和[整体验收](整体验收.md)。

上传租约签发时即登记staged对象，完成前及失败后均禁止业务引用；预签名PUT绑定对象key、类型、SHA256元信息和禁止覆盖标记，浏览器不手动设置Content-Length，后端仍核验实际大小。租约有效期内不物理回收对象，以免有效PUT链接在删除后重建对象；过期后仍按staged无引用清理规则处理，证据保护策略保持。自动化测试独占前缀在服务停止后按日志清理，不删除共享业务对象。

ORM模型与业务查询使用SQLModel；SQLAlchemy仍提供异步引擎、关系加载策略、复杂列/索引和Alembic基础设施。已有业务表结构保持，新增upload_leases表需要运行迁移。新SDK为alibabacloud-oss-v2，原oss2及兼容时钟代码已移除。
