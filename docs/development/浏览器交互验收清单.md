# 浏览器交互验收清单与完整测试流程

## 使用方式与完成标准

本清单是唯一 UC/US/SC 全量测试的浏览器执行说明，业务范围、角色和预期与自动化一致，结果独立记录；初始状态为 **NOT-RUN**。两处界面入口的历史专项结果见[界面专项复验](管理界面专项复验.md)，不替代完整人工流程。自动化报告状态不能继承为本清单的 PASS。执行结论填写到[执行结果 CSV](浏览器验收结果模板.csv)；逐条需求复核见[浏览器需求覆盖矩阵](浏览器需求覆盖矩阵.md)，当前清单和验收状态见[整体验收](整体验收.md)。

完整测试由环境核验、自动化回归、浏览器多角色流程、异常/兼容测试、逐条需求复核及缺陷回归六部分组成。全部必测项完成、阻断缺陷关闭、AC/场景的每个子条件都有相符证据后，才可给出相应范围通过结论。缺界面入口记 BLOCKED-UI；缺账号/数据/设备记 BLOCKED 或 NOT-RUN；预期拒绝并证明未写入可以 PASS，不能把请求失败一律记 FAIL。N/A 必须写理由及负责人决定。未覆盖保留，不把模板勾选当验收事实。

**界面入口**：管理端侧栏“审计查询”可筛选和查看只读事件；消息举报、交易争议及异常交易事项的直接关联会话可在事项详情只读查看并分页。商品审核等不授予会话权限的事项不显示入口。两处已完成专项复验，完整跨浏览器及所有业务子条件仍按本清单执行。

## 1. 环境和会话准备

- 使用 `APP_ENV_FILE` 选定的开发配置，核实实际后端与 test 资源；PostgreSQL 需先确认迁移及资源可用。测试和 seed 不使用 `--profile`。
- 每轮登记 run_id（建议 `browser-YYYYMMDD-HHMMSS`）、分支/HEAD、是否有工作区差异、操作者、浏览器/OS/视口、API地址、开始时间及前后端源码快照。版本变化后注明受影响用例重跑范围。
- 至少准备 S/S2 卖方、B1/B2 买方、O 第三方、A1/A2 管理员；封禁/改密码/换邮箱使用额外可破坏身份，不破坏持久化初始化管理员。普通身份通过注册页创建；初始管理员由独立持久化初始化命令创建，第二名管理员由该命令显式指定邮箱，不靠 UI/SQL 越权提权。所有账号只用于 test。
- 使用 **独立浏览器配置文件或真正隔离的会话** 分别登录。不同标签页、同一隐私模式窗口通常共享 localStorage；移动端与管理端不同端口虽隔离，A1/A2 仍必须独立配置文件。同一配置文件多标签只用于验证旧页/并发场景。
- 自动化与人工共享同一清单、角色和预期，但不共用身份 seed：自动化 runner 内部创建临时角色，结束后清理；浏览器人工使用持久化管理员和注册用户。A1/A2对应admin/admin2，S/S2对应seller/seller2，B1/B2对应buyer/buyer2，O对应outsider；限频等可通过注册额外用户准备。

人工浏览器流程不运行自动化 seed，也不需要 `run_id` 凭据文件。用部署初始化管理员登录管理端，普通身份通过注册流程创建；需第二管理员时运行持久化 seed 并显式指定邮箱。密码通过终端交互输入，不写入命令行或本清单。

```bash
APP_ENV_FILE=.env.dev .venv/bin/python -m app.manage seed --admin-email admin2@example.test
```

该命令用于持久化初始化额外管理员；初始管理员运行 `python -m app.manage seed`，额外管理员可指定 `--admin-email`。密码通过 getpass 交互输入。必要参考分类可用可重复的 `--category NAME` 参数一并初始化，例如 `python -m app.manage seed --category 教材 --category 数码`。部署管理员及这些参考数据保留，不由自动化测试清理。普通测试角色由注册流程创建。自动化 seed 集成在 runner 中，不作为浏览器数据准备命令。来源与自动化 check_id 的关系见[共享覆盖矩阵](浏览器需求覆盖矩阵.md)。

## 2. 数据、浏览器与证据准备

所有对象标题/原因含本轮标识，记录实际商品/交易/事项 ID，不预设 ID。先由人工创建必要分类及别名，A1 在管理端审核本轮商品。用 UI 创造正常业务状态；时间和确定性竞态才由测试服务补充，不 SQL 改业务状态。数据组互相独立，防止完成/封禁后后续测试无前置条件。

| 数据组 | 初始状态与用途 |
|---|---|
| P01 | S 上架，B1/B2 各一待接受请求；排他接受与自动关闭 |
| P02 | 独立上架商品；拒绝、撤回各使用不同请求 |
| P03 | 进行中、有生效约定、B1 已确认且 S 未确认；约定变更未同意/同意分别复制 |
| P04 | 无约定进行中三份；买方直接取消、卖方申请未同意、同意分支 |
| P05 | 有效约定三份；协商取消、争议、双方完成互不复用 |
| P06 | 已完成与已终止各一份；评价、归档、统计 |
| P07 | 待审含两新标签、退回、已认领后改资料各一份 |
| P08 | 独立举报及冻结/封禁链；不得拿主线身份做封禁 |
| P09 | 受控时钟生成单方超时/暂停/恢复及另一笔冻结；记录 API 运行 ID 和参与方 |
| P10 | 九种管理目标各自独立样本；恢复冲突另设同商品历史与现有锁单 |

素材准备：合法 JPG/PNG/WebP/GIF，小图、多图、接近上限文件、超过上限文件、空文件、文本改图片扩展名；长中文/emoji/换行/HTML样本文本。具体长度和图片上限以当前前端校验与后端配置为准，同时验证恰好边界和超出边界，记录所用数值，不凭扩展名认定合法图片。

图片发布另核对直传 lease 全链路：上传前确认文件名、声明 MIME 与实际格式、精确字节数和 SHA-256；开发者工具确认创建 lease 与完成请求携带登录态，而对象存储 PUT 不含应用 `Authorization` 或 cookies，只带 lease 签名要求的 headers。验证 PUT 成功后完成接口确认对象大小及 `x-oss-meta-sha256`，只有完成响应返回的 key 被加入商品提交。覆盖无效类型、空文件、超过 10 MiB、上传中断、签名过期和完成校验拒绝；失败对象不得进入商品 `image_keys`，重试需取得新 lease。跨域失败时记录脱敏状态与响应，不保存完整签名 URL、请求头或 HAR。

为每项保存：前置角色/对象状态、步骤、预期、实际、结果、脱敏截图、时间、对象 ID 和缺陷号。至少保存动作前和刷新后的关键状态；双端流程保存两端结果。Network/WS 可作诊断证据，不能公开原始 HAR（可能含 Authorization、验证码、签名 URL、正文）。注册、找回密码和换邮箱须查收实际收件箱中的验证码邮件并记录到达结果；成功提示或HTTP响应本身不能替代邮件到达证据。页面文字正确还需刷新验证持久化；涉及私有图片要在授权用户和第三方分别验证。

## 3. 完整执行顺序和命令

从仓库根目录启动，脚本同步后端锁定依赖、前端缺Vite时安装依赖，并后台运行 API、管理端和移动端，默认读取已有 `.env.dev`，也可通过 `APP_ENV_FILE` 选择其他 dotenv 文件；不自动迁移、seed或启动PG/Redis。首次/升级先迁移并按前文准备身份；前端锁文件变化先停服手动npm ci：

```bash
./scripts/dev.sh start
./scripts/dev.sh status
```

手动模式：后端目录 `APP_ENV_FILE=.env.dev .venv/bin/python -m app.manage serve --host 127.0.0.1 --port 8000`；两前端分别 `npm run dev -- --strictPort`。不要同时启动两套服务争用端口。首次或结构升级先运行 `APP_ENV_FILE=.env.dev .venv/bin/python -m app.manage migrate`，不要自动演示 seed。移动端访问 `http://localhost:5173`，管理端 `http://localhost:5174`，后端健康页 `http://127.0.0.1:8000/api/health`。从手机访问需单独配置监听和代理，localhost 指手机自己；不把开发服务暴露公网。

1. 核对配置和选定环境，使用持久化管理员并注册本轮普通身份，登录隔离会话；确认 API 和实际业务操作可用，不能仅看首页加载。
2. 按同一全量清单分别执行自动化和浏览器通道；人工按共享check_id走账户、分类、发布、检索、交易、治理、消息通知与本人入口；冻结/封禁独立样本，最后做浏览器通道专项。
3. 对矩阵内每一 AC/SC 子条件逐条复核。只有浏览器结果、API补充和来源描述相符才能合并结论；界面缺口明确记录。
4. 缺陷修复后复测失败项、邻近成功/拒绝分支、跨端状态与相关自动化；后端业务源码有变化时重跑真实 runner 并绑定新摘要，前端变化则重做相应浏览器流程。
5. 收尾记录未覆盖设备、PWA、邮件、长时等待等边界。浏览器人工数据按持久化 test 数据保留；只停止自己启动的服务。手动服务分别停止，托管服务用 `./scripts/dev.sh stop`。

后端目录唯一自动化入口（数据库和存储目标取自配置；runner 自动 seed 并启动自己的专用服务）：

```bash
RUN_REAL_ACCEPTANCE=1 .venv/bin/python -m pytest -q
# 相同runner的CLI入口，支持专用端口和运行标识
.venv/bin/python -m tests.acceptance_real.runner --port 8107
```

没有第二套 smoke、旧 SQLite 生命周期或独立业务测试入口。数据库、存储与 KV 后端由所选 dotenv 文件明确指定；命令不使用 `--profile`。runner 为每轮生成随机 schema、私有临时 dotenv 文件、OSS prefix/local 临时目录及 Redis prefix，并在成功和失败时清理全部本轮资源，不清理共享数据。该清理行为完成实现及复验前仍属待验证。无需预先启动8000或手动创建自动化账号。

真实 runner 的七天场景使用测试进程受控时钟、保持七天业务阈值，不代表实际等候七天；普通8000服务不注入此时钟。需在普通浏览器上核验超时结果时，记录对应 runner 产生对象及身份，或单独受控测试服务接入前端；不能把普通实例的“仍未超时”误判。不要在共享 Redis 中执行 FLUSHALL/FLUSHDB，不停共享数据库/OSS来模拟网络故障；先只限制当前浏览器网络。

前端分别 `npm run build`；仓库根目录运行 `python3 scripts/cli.py check`。构建/lint/type属于工程检查，不是第二套业务测试。PWA 使用实际构建产物；当前锁定 Vite 6 的 preview 默认继承 server.proxy，所以两端 `npm run preview -- --port 4173 --strictPort`（移动）/ `4174`（管理）仍代理 `/api` 与 `/ws` 到本机8000。后端须另行启动，preview不由dev.sh管理；正式静态托管仍须配置反向代理及SPA路由回退。

## 4. 同一清单的浏览器执行

业务case_id、角色、前置、动作、预期统一见[全量测试共享清单](全量测试共享清单.md)；不要再维护独立76项人工业务清单。API自动化与人工按相同check_id记录结果，关联14主用例/66子用例/105AC/109场景分支。两种通道共享业务范围与逻辑角色；人工使用持久初始化管理员和注册用户，通过页面完成业务动作；自动化在本轮隔离环境使用一次性seed，通过真实HTTP完成，结束清理。

[执行结果CSV](浏览器验收结果模板.csv)同时包含共享业务项和浏览器通道专项，全部初始NOT-RUN。[需求复核CSV](浏览器需求复核结果模板.csv)记录每条来源及必需check_id。API报告PASS不更新人工结果。缺页面入口、测试设备或时钟条件时记录BLOCKED/NOT-RUN；不能为了与自动化数字一致填写PASS。

## 5. 缺陷分级、记录与结束条件

- P0：误用生产、越权读取/写入、秘密泄漏、数据不可恢复破坏；立即停止相关场景，保留脱敏证据。
- P1：主流程不可达、重复锁单/完成、重要状态错误、缺必要权限控制或必需入口；修复前不可宣告完整浏览器通过。
- P2：可恢复的局部功能/交互问题、明显状态提示错误；标明影响范围，完成相应回归。
- P3：不影响使用和规则判断的细节；仍需记录，不以视觉偏好篡改业务规则。

单条记录格式：`case_id / run_id / 浏览器版本与角色 / 对象ID / 初始状态 / 步骤 / 预期 / 实际 / 结果 / 缺陷级别及编号 / 截图路径 / 复测结果 / 复核人及时间`。CSV 的 actual、evidence、defect、reviewer 留给实际执行者填写。不要把账号密码写进 CSV 或截图。

建议分四个批次：账户及发布；检索/消息及完整交易；争议/治理/管理；异常网络/多浏览器/PWA与逐条需求复核。每批保存状态，不预先承诺固定时长；双管理员、多冻结、七天计时和真机测试所需准备较多。

最终报告分别列：自动化真实资源结果、浏览器通过/失败/阻塞/未执行数、294条来源条目及子条件的复核结果、修复与复测、未覆盖范围。两处已修复入口的专项结果不自动覆盖完整清单与跨浏览器结果；真实邮件、多实例广播、生产部署、备份恢复另立验收范围。本清单本身不宣告任何浏览器或人工确认完成。
