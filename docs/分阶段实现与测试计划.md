## 1. 阶段划分与依赖

### 设计准备 D0

四人任务并行开展需求核对、主体关系与 Q 整理；TASK-001 先形成公共契约和必要技术验证输入，模块成员依次细化当前阶段接口。四任务设计交付与交界复核完成后，将评审结果集成到design并形成已确认基线，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。

### 设计固化与编码边界

D0期间完成四任务的模型、接口契约、关键规则、验证预期及交界复核。四任务设计评审并集成到design、形成已确认基线后，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。各设计批次的并行安排用于设计交付。

依据：袁尚峰2026-11-15明确的推进顺序。设计固化采用四任务完整交付与实际审查结果，编码准备采用固化后的版本、经核验的预期及阶段运行条件。

### 候选实现阶段

| 阶段 | 可运行业务链 | 需求范围 | 前置Q/ADR | 接口 | 必测风险 | 退出条件 |
|---|---|---|---|---|
| S1 | 邮箱验证注册→登录→上传发布→分类申请／审核→检索详情→评论收藏及本人查询 | FR-01、02、03、04 商品部分、08 审核部分、09、13；FR-11／12 对应部分 | ADR-001—011 中适用于账户、通知、商品和部署的决定；Q-001—004 对应身份、文件、邮件及换绑 | 账户／邮箱验证、文件、商品审核／分类、检索评论收藏、本人查询及基本通知／待办；具体编号见动作映射 | 身份、配置、文件协议；审核与分类原子性，资格与上传引用 | 覆盖本阶段接口和预期，完成实现审查、人工联调及适用的开发测试 |
| S2 | 普通私聊→购买请求→交易分支→接受锁单／拒绝撤回→通知与本人交易 | FR-04 会话部分、FR-05 请求部分、09；FR-11／12 对应部分 | S1；ADR-003—005、010；C1—C4 与商品占用契约 | 会话、购买请求、接受拒绝撤回、通知；具体编号见动作映射 | S1 商品及账户能力；跨实例分发、竞争锁单、幂等 | S1 受影响回归及本阶段人工联调、适用开发测试 |
| S3 | 有效约定→变更→双方完成确认／协商终止→评价及历史 | FR-05 约定与结束部分、06、07 评价部分、09；FR-11／12 对应部分 | S2；ADR-002、003、006、010；确认及结束契约 | 约定、确认、终止、评价与历史；具体编号见动作映射 | S2 占用与会话；确认重置、关联结束、规则版本 | 前阶段受影响回归及本阶段规则、接口审查与人工联调 |
| S4 | 举报／争议／超时异常→认领沟通→处置冻结／恢复／封禁→管理统计与本人事项 | FR-07 举报、08 处置、10、14；FR-05 争议、FR-02 纠类部分、FR-09／11／12 完整覆盖 | S1—S3；ADR-002—005、009、010；事项及主体执行契约 | 举报、认领、事项沟通、申辩与结案、限制／调整、统计；具体编号见动作映射 | 各主体状态执行、事项会话、调度；限制叠加与恢复、匿名范围 | 全需求实现覆盖核对、前阶段受影响回归、人工联调及必要集成检查 |

阶段范围按 FR 拆分记录，已批准功能逐项映射至对应阶段。S1 即包含审核认领与基本通知、待办及本人入口；后续阶段随主体能力补齐聚合内容。S1 处理发布审核及分类目录维护，已发布商品的管理员纠类随 S4 事项处置上线。逐项阶段归属、接口及案例采用[需求与接口映射](design/detailed-design/01-需求与接口映射.md)。

- S1 的管理待办只启用商品审核；通知须能持久保存、查询及标读，并验证已启用的通知投递与恢复契约。普通私聊与购买请求属于 S2，举报和申辩属于 S4。
- S2 验证普通私聊及交易分支，并核对请求竞争、下架关闭与归档；约定、完成确认及普通终止由 S3 实现并验证适用契约。
- S3 的约定和取消用例直接核对正常进行中状态；S4 启用争议和异常后，补验争议期间约定暂停、争议中协商取消、超时冻结及恢复。适用阶段由动作及案例前置状态共同确定。

### S1 工作顺序

1. 袁尚峰先建立 Maven 多模块、双 Vue 应用、共享 API 类型生成和 CI 入口，发布模块依赖、服务接口及本地启动方式。
2. 金婉怡可先实现商品／分类独立规则，张新悦可先实现审核认领规则，孙含佳可使用 OpenAPI 与受控响应开发移动优先并适配桌面的用户界面。需联调的工作在相应服务、接口和迁移可用后接入。
3. 审核认领后处理采用同一事务，商品与分类由金婉怡提供服务，张新悦提供固定认领及管理端，袁尚峰装配用例、通知、待办和审计，孙含佳接通用户侧流程。各接口与验证归属见[编码任务索引](design/tasks/索引.md#s1-编码任务)。

### S2—S4 的确定时点与并行范围

阶段的业务边界、接口编号和用例预期已按[需求与接口映射](design/detailed-design/01-需求与接口映射.md)划定。交付批次、负责人、联调版本和准入证据随阶段任务卡确定。先在 S1 期间根据公共骨架整理 S2—S4 的候选任务和交界；当前一阶段提供相关服务签名、错误语义和测试数据时，复核下一阶段任务卡。涉及真实调用的能力按可用接口及阶段准入批准放行。

| 阶段 | 可独立准备或在获准后先行实现 | 真实联调所需输入 |
|---|---|---|
| S2 | 交易请求状态机与普通私聊可分开开发，前端按 OpenAPI 和受控响应并行 | S1 账户、商品和通知服务。交易分支创建／归档及竞争锁单需会话服务、商品占用端口和公共事务可运行 |
| S3 | 约定变更、确认重置、评价资格及历史投影可按既有契约开发和做单元测试 | S2 已接受交易、商品占用与交易会话。最后确认、终止和评价使用实际状态、事件和释放占用实现 |
| S4 | 事项认领、问询、申辩、申辩期及匿名投影可复用 S1 骨架开发。处置执行方先给具名命令与受控结果 | 争议和冻结／恢复、超时与封禁连动、管理统计依赖 S2／S3 活动交易的状态、计时与会话，并需账户、商品、交易和调度适配可运行 |

S1-001 完成首个共享交付后，S1-002／003／004 根据任务卡并行推进，公共模块的后续实现与各自主体规则可以交错进行。并行开发先交付模块公开接口、DTO、可生成的 OpenAPI 和代表性数据；用例由应用装配，迁移修改由数据归属模块维护。跨领域真实联调按 S1 → S2 → S3 → S4 的能力依赖推进。阶段重叠时，派发前核对同一成员承担的任务以及共享应用装配、迁移和接口的修改边界。

### 准入关联

各阶段在接口细化时登记具体 API、TC、前置 Q／ADR 和任务，按[准入模板](design/acceptance/阶段准入记录模板.md)批准。S1—S4 的开发完成条件采用静态检查、审查、人工前后端联合测试及适用的单元与集成证据。系统测试和人工验收在开发完成后开展，按[测试策略](#分阶段回归)执行。任务参见[四人索引](design/tasks/索引.md)。

## 2. 测试策略与依据

### 预期来源

需求正文、BR／TR／权限矩阵、详细 US／UC／SC 与人工确认构成预期依据。AI 辅助扩展案例，对应任务登记的审查姓名核验预期及适用范围。

### 静态与白盒验证

后端执行 Maven 编译与静态检查。前端使用 Oxlint、Oxfmt、`vue-tsc` 严格类型检查及 Rsbuild 构建检查。全部业务逻辑白盒核对输入、主体资格、状态、不变量、事务、锁序、失败分支与审计。审查记录对应版本和差异。

### 运行时验证选取

每个案例说明不可静态确认的性质，或所覆盖的复杂关联／跨模块黑盒行为。使用真实 PostgreSQL 多连接验证并发；使用多 API／IM／worker 实例验证共享机制。合成数据和环境版本随案例登记。

### 测试层级

| 层级 | 验证对象 | 本项目示例 |
|---|---|---|
| 单元测试 | 独立的领域方法或纯逻辑，使用显式输入和可控时钟 | 状态转换资格、配置校验、有效等待时间计算 |
| 集成测试 | 模块、接口或外部依赖之间的契约及协作 | 真实 PostgreSQL 多连接竞争锁单，PostgreSQL／Redis 会话撤销，OSS 与邮件投递 |
| 系统测试 | 已部署系统的完整业务链路与质量要求 | 跨实例发消息并在接收端显示，浏览器端到端交易链路，滚动更新与故障恢复 |
| 验收测试 | 以需求和阶段退出条件为依据，由实际验收人确认结果 | 阶段主流程与异常演示，最终部署的全链路、权限、性能与恢复验收 |

接口测试按被测范围归入相应层级。只验证 API 与数据库协作时属于集成测试，经已部署系统完成跨模块用户流程时属于系统测试。性能是测试目标，可在集成、系统或验收阶段测量。验收可引用已有运行证据，并按验收记录登记确认人和日期。单元案例在实现任务中按独立规则和回归风险登记，白盒审查及静态检查另记证据。

### 开发阶段用例选择

开发期自动化优先编写单元测试。业务逻辑验证以人工前后端联合测试为主，使用当前阶段可启动的前端、API 和明确的测试数据。按角色覆盖正常操作与关键异常，核对界面反馈、API 响应及相关状态。记录版本、环境、数据、操作步骤和实际结果。

- 单元测试优先覆盖有分支的资格、状态、时间边界和界面状态转换。每例登记输入、固定时间或模拟依赖及可观察预期。可直接审查的简单映射随静态和白盒检查验证。
- 按需补集成测试，覆盖需稳定复现的真实依赖或跨模块契约行为，例如数据库约束、事务回滚、并发竞争、会话失效、持久化事件恢复，以及生成 API 客户端与接口契约协作。并发用真实 PostgreSQL 的独立连接，Session 或队列行为用真实 Redis。可控替身用于触发 OSS 或 SMTP 的指定响应。登记所接入的依赖和所用替身。
- 测试预期沿用已有 TC 的业务规则，注明具体子场景及验证层级。前端对受控接口响应可验证页面状态及错误处理，真实浏览器跨模块端到端链路列入开发完成后的系统测试。

### 必要技术验证计划

| 专题 | 场景 | 预期及证据 |
|---|---|---|
| 事务及锁单 | 两实例竞争接受；提交失败；同次重试 | 唯一占用、整体回滚、稳定结果；数据库状态与命令 |
| IM | 用户连接分布两实例；重连；流裁剪或分发中断 | 目标覆盖、去重、补取与已读独立；系统测试以接收端真实显示记录验证正常网络双方在线的 2 秒可见目标，测量口径见[部署验收安排](#性能测量) |
| 任务调度 | worker 退出、租约接管、重复投递 | 幂等业务结果、可恢复执行权；领取与执行证据 |
| Session | 跨实例续期、退出、改密、换绑邮箱及 Redis 恢复 | Q-001／Q-004；逐会话撤销与凭据版本变更分别核验，客户端身份错误按共享接口约定 |
| 文件 | 上传中断、重复完成、核验后覆盖、回收竞争 | 文件内容稳定、引用与权限正确；Q-002 作为预期 |
| 邮件 | 异步重试、重发替代、并发错误提交 | 单表原码生命周期、幂等计数、worker恢复及脱敏；Q-003实际决定、TC-COM-018—021作为预期 |

测试代码、批准执行范围、环境与真实结果在各任务及证据记录中登记。

### 分阶段回归

S1—S4 开发期间，任务合入前执行静态检查、审查、适用的单元与集成回归。阶段退出核对当前范围、接口和人工联调等开发证据。

开发完成后，对部署版本执行系统测试，覆盖阶段业务主链、关键异常、跨实例行为、性能及恢复，再按需求与对应阶段退出预期开展人工验收。验收可引用系统测试与适用的开发验证证据。最终部署验证按[部署验收安排](#plan-04)执行。

## 3. 阶段准入与验收安排

### 准入

四任务设计评审集成并固化design后，准备拟进入阶段的编码任务卡及准入材料；通过阶段准入批准后开始业务编码。按阶段核对前置 Q 关闭、ADR 接受、接口双方及复核确认、状态／错误／事务／权限明确、人工前后端联合测试及适用的单元／集成预期已核验、环境与配置齐备、责任及完成条件。批准记录采用[准入模板](design/acceptance/阶段准入记录模板.md)。

### Issue 与任务分支

四位成员各自的任务 Issue 在派发时登记，输入包含 design 的具体提交、需求与 ADR／Q、文件范围及依赖。分支、Draft PR、单一职责的小步 commit 及批次集成按[任务索引](design/tasks/索引.md)组织。TASK-001 统筹正式决定、共享文档与生成物；成员维护自己的模块源文件并交叉审查。

### 审查与阶段验收

开发阶段按[审查模板](design/reviews/模板.md)记录版本、业务与约束检查、人工前后端联合测试、优先单元测试、按需集成测试及问题处理。开发完成后执行系统测试与人工验收，按[验收模板](design/acceptance/阶段验收单模板.md)记录完整业务链、关键异常、回归、残余风险与验收人。

### 变更

原因→影响需求／ADR／接口／数据／测试→人工决定→修改→回归。重大取舍新建替代 ADR，原版本通过 Git 及记录追踪。

## 4. 最终部署验收安排

部署归 TASK-001，各模块提交配置、迁移、依赖及兼容性信息。

### 执行依据

批准阶段及需求覆盖完成后，按运行说明从干净环境启动，登记提交、产物、配置、迁移及资源版本。检查单机多实例及 Nginx 分流、健康和优雅退出。

### 验收范围

全链路、权限与隐私、真实数据库及媒体访问、外部故障与备份恢复、滚动更新及回退兼容、获准负载。性能采用需求第6、7章条件，执行前核验参数、样本和口径。

### 性能测量

按[质量要求](requirements/06-质量要求.md)及[验收依据](requirements/07-验收与验证.md)执行。记录环境、发布版本、网络条件、活跃用户数、商品规模、操作配比、实际速率、有效样本和失败样本。

- 常用交互采用 100 名同时活跃用户及 10,000 条商品记录，从用户发起到可用结果计时，至少 95% 在 3 秒内返回。
- 文本消息在双方在线、网络正常时，从发送方发出到接收端实际显示计时，至少 95% 在 2 秒内显示。用本次发送结果的消息标识与接收端显示记录关联样本，纳入未显示或超时样本，并保存端点计时的时钟校验依据。覆盖双方连接分布在不同 IM 实例的情形。S2 开发期间可通过集成测试验证事件分发、顺序及恢复。接收端显示时延在开发完成后的系统测试测量，最终部署按实际环境复测。
