## 1. 阶段划分与依赖

### 设计固化与编码边界

D0 完成模型、契约、关键规则及验证预期，评审成果由 `design` 合入 `main`。S1 交付工程底座、通用基础设施、依赖验证、GitHub CI、分进程开发启动和维护工具，为 S2—S4 提供共同工程前置。阶段开发可以重叠，依赖前一阶段真实实现的功能使用[阶段开发基线](#阶段开发基线)推进。阶段批准版本、责任人和证据在[准入记录](design/acceptance/阶段准入记录模板.md)登记。

### 实现目标与用户故事

| 阶段 | 实现范围 | 可独立体验的主链 |
|---|---|---|
| S1 工程底座 | Java/Maven API、双前端、GitHub CI、分进程开发启动，PostgreSQL、Redis、OSS、SMTP、共享运行机制及维护工具 | 构建并分进程启动示例，验证文件、事务、投递、调度及维护工具的初始化、清理和重试 |
| S2 账户、商品与基础管理 | US-01 账户与头像；US-02／03／09／13 商品、目录、基础审核和展示；US-04 商品评论、回复和收藏。实现审核结果的站内持久化与查看 | 用户登录后上传图片、选择分类并发布商品；管理员维护分类、认领并审核；用户查看结果，审核通过的商品可浏览、筛选、互动及下架。各路径以账户、商品与审核数据运行 |
| S3 交易与沟通 | US-05／06 请求、占用、约定、确认及取消；US-07 交易评价；US-04 私聊与交易会话；US-11 实时通知；US-12 交易入口；US-14 超时与争议触发异常事项 | 买家从商品发起请求，卖家接受并锁单，双方从交易进入会话、约定并确认，完成后评价；核对通知、已读和断线恢复。超时或争议时验证异常事项真实创建并关联交易 |
| S4 治理与管理完善 | US-07 举报与匿名结果；US-08 事项问询、审核处置沟通与申辩；US-10 管理统计；US-12 本人事项；US-14 异常事项处置 | 用户提交举报与证据，管理员认领、问询、执行处置，用户查看结果并按规则申辩，管理员结案；核对主体状态、审计及统计 |

业务场景和规则见[用户故事及验收条件](appendices/user-stories/index.md)及[需求与接口映射](design/detailed-design/01-需求与接口映射.md)。

### S1 工作顺序

袁尚峰交付 Hello World 工程、双前端、API、通用基础设施、GitHub Actions、分进程开发启动和维护工具。Jenkins v2 部署由袁尚峰提前推进，用当前 `main` 验证构建与部署，支持后续小步交付。详见 [S1 任务卡](design/tasks/S1-工程骨架与基础设施.md)和[部署验收安排](#plan-04)。

### 工作量安排

每阶段四人各维护一个工作包和一条工作分支。一个工作包可以保留多个可独立审查的 PR，其阶段工作分支纳入本包全部联调输入。各阶段的责任人和完成条件见 [S2](design/tasks/S2-商品与交易.md)、[S3](design/tasks/S3-账户与沟通.md)和 [S4](design/tasks/S4-治理与管理.md)任务卡。四人可以按契约和可用工时交错推进。

### 并行开发约定

- 账户、商品、交易、会话、通知和事项各由所属模块写入本域事实。跨主体操作沿用具名命令、只读投影及公共事务、锁序和幂等约定。
- 开工时核对签名、权限、错误、事务及代表性测试数据。受控替身复用同一套预期，正式联调接入真实模块。测试专用装配和数据留在测试范围内。
- 共享 OpenAPI 入口、装配和迁移按阶段合成版本核对。涉及 Flyway 时检查版本冲突，并验证干净数据库及上一阶段数据库升级。

### 跨目标契约与验证数据

| 契约 | 提供方与接入阶段 | 重点验证 |
|---|---|---|
| 账户和文件 | S2 账户及资格、S1 文件服务供各阶段复用 | 真实 Session、管理员权限、头像与商品图片核验及引用；S4 验证账户限制和事项证据 |
| 商品审核及交易占用 | S2 接入审核认领、分类及通知；S3 接入商品占用和释放 | 审核结论、认可分类及商品展示同事务；并发接受时商品占用唯一 |
| 会话及通知 | S2 提供基础审核通知；S3 接入私聊、交易会话和实时投递；S4 接入事项会话 | 当前读权限、业务写入与会话和通知的一致性，真实投递、已读及补取 |
| 异常事项与处置 | S3 提交超时或争议触发的异常事项；S4 接入认领、处置和恢复 | 对应交易与异常事项可追溯；处置结果、证据、审计及主体状态一致 |

## 2. 测试策略与依据

### 预期来源

需求正文、BR／TR／权限矩阵、详细 US／UC／SC 与人工确认构成预期依据。AI 辅助扩展案例，对应任务登记的审查姓名核验预期及适用范围。

### 静态与白盒验证

后端执行 Maven 编译与静态检查。前端使用 Oxlint、Oxfmt、`vue-tsc` 严格类型检查及 Rsbuild 构建检查。全部业务逻辑白盒核对输入、主体资格、状态、不变量、事务、锁序、失败分支与审计。审查记录对应版本和差异。

### 运行时验证选取

人工前端交互是主要业务验证方式。按[用户故事执行测试项](design/test-cases/执行测试项.md)的 72 项流程从注册、数据准备到页面结果连续执行，一条流程可以覆盖多个 TC。使用真实 PostgreSQL 多连接验证并发；使用多 API／IM／worker 实例验证共享机制。合成数据和环境版本随案例登记。

### 测试层级

| 层级 | 验证对象 | 本项目示例 |
|---|---|---|
| 单元测试 | 独立的领域方法或纯逻辑，使用显式输入和可控时钟 | 状态转换资格、配置校验、有效等待时间计算 |
| 集成测试 | 模块、接口或外部依赖之间的契约及协作 | 真实 PostgreSQL 多连接竞争锁单，PostgreSQL／Redis 会话撤销，OSS 与邮件投递 |
| 系统测试 | 已部署系统的完整业务链路与质量要求 | 跨实例发消息并在接收端显示，浏览器端到端交易链路，滚动更新与故障恢复 |
| 验收测试 | 以需求和阶段退出条件为依据，由实际验收人确认结果 | 阶段主流程与异常演示，最终部署的全链路、权限、性能与恢复验收 |

接口测试按被测范围归入相应层级。只验证 API 与数据库协作时属于集成测试，经已部署系统完成跨模块用户流程时属于系统测试。性能是测试目标，可在集成、系统或验收阶段测量。验收可引用已有运行证据，并按验收记录登记确认人和日期。单元案例在实现任务中按独立规则和回归风险登记，白盒审查及静态检查另记证据。

### 开发阶段验证方式

业务逻辑验证以人工前后端联合测试为主，使用当前阶段可启动的前端、API 和明确的测试数据。按角色覆盖正常操作与关键异常，核对界面反馈、API 响应及相关状态。记录版本、环境、数据、操作步骤和实际结果。

- 单元测试作为补充，覆盖有分支的资格、状态、时间边界和界面状态转换；可以使用 Mock 隔离无关依赖。每例登记输入、固定时间或模拟依赖及可观察预期。
- 按需补集成测试，覆盖需稳定复现的真实依赖或跨模块契约行为，例如数据库约束、事务回滚、并发竞争、会话失效、持久化事件恢复，以及生成 API 客户端与接口契约协作。并发用真实 PostgreSQL 的独立连接，Session 或队列行为用真实 Redis。可控替身用于触发 OSS 或 SMTP 的指定响应。登记所接入的依赖和所用替身。
- 测试预期沿用已有 TC 的业务规则，注明具体子场景及验证层级。前端对受控接口响应可验证页面状态及错误处理，真实浏览器跨模块端到端链路列入各阶段的主链验证及最终系统回归。

人工主验证必须使用真实 PostgreSQL、Redis、OSS 和 SMTP。自动单测中的 Mock 结果不得替代人工页面结果；跨模块事务、数据库约束、并发和真实依赖行为仍须有集成测试作为补充证据。

### 必要技术验证计划

| 专题 | 场景 | 预期及证据 |
|---|---|---|
| 事务及锁单 | 两实例竞争接受；提交失败；同次重试 | 唯一占用、整体回滚、稳定结果；数据库状态与命令 |
| IM | 用户连接分布两实例；重连；流裁剪或分发中断 | 目标覆盖、去重、补取与已读独立；系统测试以接收端真实显示记录验证正常网络双方在线的 2 秒可见目标，测量口径见[部署验收安排](#性能测量) |
| 任务调度 | worker 退出、租约接管、重复投递 | 幂等业务结果、可恢复执行权；领取与执行证据 |
| Session | 跨实例续期、退出、改密、换绑邮箱及 Redis 恢复 | Q-001／Q-004；逐会话撤销与凭据版本变更分别核验，客户端身份错误按共享接口约定 |
| 文件 | 上传中断、重复完成、核验后覆盖、回收竞争 | 文件内容稳定、引用与权限正确；Q-002 作为预期 |
| 邮件 | 异步重试、重发替代、并发错误提交 | 单表原码生命周期、幂等计数、worker恢复及脱敏；Q-003实际决定、TC-COM-018—021作为预期 |

测试代码、批准执行范围、环境与真实结果在各任务及证据记录中登记。

### 分阶段回归

S1 验证工具链、基础设施和维护操作，并提供隔离资源与装配入口。各工作包同步编写业务测试，先在受控环境验证，再在阶段合成版本中接入真实依赖。每次增量合入前，在本地用对应提交启动服务，冒烟验证受影响的关键路径并记录结果。Jenkins 负责 `main` 合入后的构建和部署。

每个阶段以[主链](#实现目标与用户故事)为范围，开展真实前后端联合验证，覆盖正常流程、关键异常及上一阶段回归。阶段验收复用适用的开发验证证据。最终系统测试与部署验收继续覆盖全链路、跨实例行为、性能及恢复，见[部署验收安排](#plan-04)。

## 3. 阶段准入与验收安排

### 准入

阶段任务以 `main` 中的设计基线准备编码任务卡及准入材料；通过阶段准入批准后开始业务编码。按阶段核对前置 Q 关闭、ADR 接受、接口双方及复核确认、状态／错误／事务／权限明确、人工前后端联合测试及适用的单元／集成预期已核验、环境与配置齐备、责任及完成条件。批准记录采用[准入模板](design/acceptance/阶段准入记录模板.md)。

### Issue 与任务分支

派发 Issue 记录阶段、责任、文件边界、依赖及验收条件，引用最新 main 的需求与 ADR／Q。实际采用的代码基线提交在 PR 和准入记录登记。TASK-001 统筹正式决定、共享文档与生成物，各成员维护本模块源文件并交叉审查。每个工作包维护一条阶段工作分支，按[任务索引](design/tasks/索引.md#提交与集成)组织小步提交及 Draft PR。独立可交付增量从最新 `main` 开发并提交到 `main`，有依赖的改动先在明确的联调基线上评审和验证。

### 阶段开发基线

1. 当前一阶段正式基线尚未形成，阶段集成人从其共同基线合入四条工作分支的明确提交，建立临时开发基线，并登记各分支 SHA、合成 SHA 和组合检查结果。下一阶段可据此开工。S2 先供给 S3，S3 的合成结果可继续供给 S4。
2. 任一输入分支更新时，提供方登记新提交和受影响的契约。阶段集成人刷新临时基线，验证组合构建及受影响检查。下游负责人逐次同步合成版本，修正本工作包内的适配、迁移、生成物及测试，并记录已同步 SHA。有多级依赖时按 S2 → S3 → S4 传递。
3. 上一阶段完成主链验收和修正并正式合入 `main` 后，登记包含该阶段完整交付的 `main` SHA。下游把自身改动迁移到包含该 SHA 的最新 `main`，核对差异、数据库升级、构建及跨阶段主链，再更新下游联调基线和 PR 目标。

### 审查与阶段验收

开发阶段按[审查模板](design/reviews/模板.md)记录版本、业务与约束检查、单元和适用集成测试，以及本地冒烟结果。通过当前范围检查、具备所需真实依赖且可运行的增量可合入 `main`，由 Jenkins 构建与部署。同一阶段可多次合并与部署。

阶段验收使用真实用户端、管理端及后端依赖，验证本阶段主链、关键异常和上一阶段回归。按[验收模板](design/acceptance/阶段验收单模板.md)记录结果、证据及验收人。最终部署完成全量需求覆盖、质量要求及恢复验收。

### 变更

原因→影响需求／ADR／接口／数据／测试→人工决定→修改→回归。重大取舍新建替代 ADR，原版本通过 Git 及记录追踪。

## 4. 最终部署验收安排

部署归 TASK-001，各模块提交配置、迁移、依赖及兼容性信息。

### 增量构建与部署

开发者在本地执行构建、冒烟与受影响的回归验证，结果随 PR 登记。最终课程验收使用执行时最新 [`main`](https://github.com/iy88/se-course-project-1/tree/main) 的本地隔离环境。生产验收登记实际责任人和日期。

### 执行依据

批准阶段及需求覆盖完成后，按运行说明从干净环境启动，登记来源分支、产物、环境配置、迁移及资源版本。依据实际拓扑核对分流、健康与退出。

### 验收范围

全链路、权限与隐私、真实数据库及媒体访问、外部故障与备份恢复、发布切换及回退兼容、获准负载。当前发布脚本按整组切换验证，滚动流程按对应演练登记。性能采用需求第6、7章条件，执行前核验参数、样本和口径。

### 性能测量

按[质量要求](requirements/06-质量要求.md)及[验收依据](requirements/07-验收与验证.md)执行。记录环境、发布版本、网络条件、活跃用户数、商品规模、操作配比、实际速率、有效样本和失败样本。

2026-11-27 的本机代表性执行、默认 capacity、性能上限和 legacy 对照见 [TC-PERF-001 性能与容量测试报告](design/test-cases/reports/performance-capacity/测试报告.md)。该证据适用于所列 Mac loopback 环境，不代替目标部署的 WAN 复测。

- 常用交互采用 100 名同时活跃用户及 10,000 条商品记录，从用户发起到可用结果计时，至少 95% 在 3 秒内返回。
- 文本消息在双方在线、网络正常时，从发送方发出到接收端实际显示计时，至少 95% 在 2 秒内显示。用本次发送结果的消息标识与接收端显示记录关联样本，纳入未显示或超时样本，并保存端点计时的时钟校验依据。覆盖双方连接分布在不同 IM 实例的情形。S3 开发期间可通过集成测试验证事件分发、顺序及恢复。接收端显示时延在开发完成后的系统测试测量，最终部署按实际环境复测。
