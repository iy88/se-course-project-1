## 1. 阶段划分与依赖

### 设计准备 D0

四人任务并行开展需求核对、主体关系与 Q 整理；TASK-001 先形成公共契约和必要技术验证输入，模块成员依次细化当前阶段接口。四任务设计交付与交界复核完成后，将评审结果集成到design并形成已确认基线，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。

### 设计固化与编码边界

D0期间完成四任务的模型、接口契约、关键规则、验证预期及交界复核。四任务设计评审并集成到design、形成已确认基线后，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。各设计批次的并行安排用于设计交付。

依据：袁尚峰2026-11-15明确的推进顺序。设计固化采用四任务完整交付与实际审查结果，编码准备采用固化后的版本、经核验的预期及阶段运行条件。

### 候选实现阶段

| 阶段 | 可运行业务链 | 需求范围 | 前置Q/ADR | 接口 | 必测风险 | 退出条件 |
|---|---|---|---|---|
| S1 | 邮箱验证注册→登录→上传发布→分类申请／审核→检索详情→评论收藏及本人查询 | FR-01、02、03、04 商品部分、08 审核部分、09、13；FR-11／12 对应部分 | ADR-001—011 中适用于账户、通知、商品和部署的决定；Q-001—004 对应身份、文件、邮件及换绑 | 账户／邮箱验证、文件、商品审核／分类、检索评论收藏、本人查询及基本通知／待办；具体编号见动作映射 | 身份、配置、文件协议；审核与分类原子性，资格与上传引用 | 链路及异常演示、适用测试、人工审查；接口与预期确认 |
| S2 | 普通私聊→购买请求→交易分支→接受锁单／拒绝撤回→通知与本人交易 | FR-04 会话部分、FR-05 请求部分、09；FR-11／12 对应部分 | S1；ADR-003—005、010；C1—C4 与商品占用契约 | 会话、购买请求、接受拒绝撤回、通知；具体编号见动作映射 | S1 商品及账户能力；跨实例分发、收件端可见时延、竞争锁单、幂等 | S1 回归及本阶段主流程、异常、并发证据 |
| S3 | 有效约定→变更→双方完成确认／协商终止→评价及历史 | FR-05 约定与结束部分、06、07 评价部分、09；FR-11／12 对应部分 | S2；ADR-002、003、006、010；确认及结束契约 | 约定、确认、终止、评价与历史；具体编号见动作映射 | S2 占用与会话；确认重置、关联结束、规则版本 | 前阶段回归与本阶段确认／终止／评价链路审查 |
| S4 | 举报／争议／超时异常→认领沟通→处置冻结／恢复／封禁→管理统计与本人事项 | FR-07 举报、08 处置、10、14；FR-05 争议、FR-09、11、12 完整覆盖 | S1—S3；ADR-002—005、009、010；事项及主体执行契约 | 举报、认领、事项沟通、申辩与结案、限制／调整、统计；具体编号见动作映射 | 各主体状态执行、事项会话、调度；限制叠加与恢复、匿名范围 | 全需求覆盖核对、前阶段回归、关键异常与恢复证据 |

阶段范围按 FR 拆分记录，已批准功能逐项映射至对应阶段。S1 即包含审核认领与基本通知、待办及本人入口；后续阶段随主体能力补齐聚合内容。逐项阶段归属、接口及案例采用[需求与接口映射](design/detailed-design/01-需求与接口映射.md)。

- S1 的管理待办只启用商品审核；通知须能持久保存、查询及标读，并验证已启用的通知投递与恢复契约。普通私聊与购买请求属于 S2，举报和申辩属于 S4。
- S2 验证普通私聊及交易分支，并核对请求竞争、下架关闭与归档；约定、完成确认及普通终止在 S3 验收。
- S3 的约定和取消用例直接核对正常进行中状态；S4 启用争议和异常后，补验争议期间约定暂停、争议中协商取消、超时冻结及恢复。适用阶段由动作及案例前置状态共同确定。

### 准入关联

各阶段在接口细化时登记具体 API、TC、前置 Q／ADR 和任务，按[准入模板](design/acceptance/阶段准入记录模板.md)批准。最终部署验收在各阶段完成后开展。任务参见[四人索引](design/tasks/索引.md)。

## 2. 测试策略与依据

### 预期来源

需求正文、BR／TR／权限矩阵、详细 US／UC／SC 与人工确认构成预期依据。AI 辅助扩展案例，对应任务登记的审查姓名核验预期及适用范围。

### 静态与白盒验证

后端按所选技术栈执行严格类型与静态检查（Python候选为Pyright strict、Ruff），前端使用 TypeScript 严格类型检查及构建检查。全部业务逻辑白盒核对输入、主体资格、状态、不变量、事务、锁序、失败分支与审计。审查记录对应版本和差异。

### 运行时验证选取

每个案例说明不可静态确认的性质，或所覆盖的复杂关联／跨模块黑盒行为。使用真实 PostgreSQL 多连接验证并发；使用多 API／IM／worker 实例验证共享机制。合成数据和环境版本随案例登记。

### 测试层级

| 层级 | 验证对象 | 本项目示例 |
|---|---|---|
| 单元测试 | 独立的领域方法或纯逻辑，使用显式输入和可控时钟 | 状态转换资格、配置校验、有效等待时间计算 |
| 集成测试 | 模块、接口或外部依赖之间的契约及协作 | 真实 PostgreSQL 多连接竞争锁单，PostgreSQL／Redis 会话撤销，OSS 与邮件投递 |
| 系统测试 | 已部署系统的完整业务链路与质量要求 | 跨实例发消息并在接收端显示，浏览器端到端交易链路，滚动更新与故障恢复 |
| 验收测试 | 以需求和阶段退出条件为依据，由实际验收人确认结果 | 阶段主流程与异常演示，最终部署的全链路、权限、性能与恢复验收 |

接口测试按被测范围归入相应层级。只验证 API 与数据库协作时属于集成测试，经已部署系统完成跨模块用户流程时属于系统测试。性能是测试目标，可在集成、系统或验收阶段测量。验收可引用已有运行证据，并按验收记录登记确认人和日期。单元案例在实现任务中按独立规则和回归风险登记，白盒审查及静态检查另记证据。

### 必要技术验证计划

| 专题 | 场景 | 预期及证据 |
|---|---|---|
| 事务及锁单 | 两实例竞争接受；提交失败；同次重试 | 唯一占用、整体回滚、稳定结果；数据库状态与命令 |
| IM | 用户连接分布两实例；重连；流裁剪或分发中断 | 目标覆盖、去重、补取与已读独立；以接收端真实显示记录验证正常网络双方在线的 2 秒可见目标，测量口径见[部署验收安排](#性能测量) |
| 任务调度 | worker 退出、租约接管、重复投递 | 幂等业务结果、可恢复执行权；领取与执行证据 |
| Session | 跨实例续期、退出、改密、换绑邮箱及 Redis 恢复 | Q-001／Q-004；逐会话撤销与凭据版本变更分别核验，客户端身份错误按共享接口约定 |
| 文件 | 上传中断、重复完成、核验后覆盖、回收竞争 | 文件内容稳定、引用与权限正确；Q-002 作为预期 |
| 邮件 | 异步重试、重发替代、并发错误提交 | 单表原码生命周期、幂等计数、worker恢复及脱敏；Q-003实际决定、TC-COM-018—021作为预期 |

测试代码、批准执行范围、环境与真实结果在各任务及证据记录中登记。

### 分阶段回归

任务合入前运行适用检查与受影响回归；阶段验收核对主流程、关键异常和前阶段回归；最终按需求负载、权限和恢复要求验证。

## 3. 阶段准入与验收安排

### 准入

四任务设计评审集成并固化design后，准备拟进入阶段的编码任务卡及准入材料；通过阶段准入批准后开始业务编码。按阶段核对前置 Q 关闭、ADR 接受、接口双方及复核确认、状态／错误／事务／权限明确、测试预期人工核验、环境与配置齐备、责任及完成条件。批准记录采用[准入模板](design/acceptance/阶段准入记录模板.md)。

### Issue 与任务分支

四位成员各自的任务 Issue 在派发时登记，输入包含 design 的具体提交、需求与 ADR／Q、文件范围及依赖。分支、Draft PR、单一职责的小步 commit 及批次集成按[任务索引](design/tasks/索引.md)组织。TASK-001 统筹正式决定、共享文档与生成物；成员维护自己的模块源文件并交叉审查。

### 审查与阶段验收

按[审查模板](design/reviews/模板.md)记录版本、业务与约束检查、真实命令及问题处理；按[验收模板](design/acceptance/阶段验收单模板.md)记录完整业务链、关键异常、回归、残余风险与验收人。人工确认和运行证据分别标记。

### 变更

原因→影响需求／ADR／接口／数据／测试→人工决定→修改→回归。重大取舍新建替代 ADR，原版本通过 Git 及记录追踪。

## 4. 最终部署验收安排

部署归 TASK-001，各模块提交配置、迁移、依赖及兼容性信息。

### 执行依据

批准阶段及需求覆盖完成后，按运行说明从干净环境启动，登记提交、产物、配置、迁移及资源版本。检查单机多实例及 Nginx 分流、健康和优雅退出。

### 验收范围

全链路、权限与隐私、真实数据库及媒体访问、外部故障与备份恢复、滚动更新及回退兼容、获准负载。性能采用需求第6、7章条件，执行前核验参数、样本和口径。

### 性能测量

按[质量要求](requirements/06-质量要求.md)及[验收依据](requirements/07-验收与验证.md)执行。记录环境、发布版本、网络条件、活跃用户数、商品规模、操作配比、实际速率、有效样本和失败样本。

- 常用交互采用 100 名同时活跃用户及 10,000 条商品记录，从用户发起到可用结果计时，至少 95% 在 3 秒内返回。
- 文本消息在双方在线、网络正常时，从发送方发出到接收端实际显示计时，至少 95% 在 2 秒内显示。用本次发送结果的消息标识与接收端显示记录关联样本，纳入未显示或超时样本，并保存端点计时的时钟校验依据。覆盖双方连接分布在不同 IM 实例的情形。S2 沿用同一计时口径验证可见时延，最终部署按实际部署环境复测。
