## 1. 阶段划分与依赖

### 设计固化与编码边界

D0 完成四任务的模型、契约、关键规则、验证预期和交界复核。D0 评审成果由 `design` 合入 `main`，后续任务以最新 `main` 为输入。S1 的工程底座、通用基础设施、依赖验证、GitHub CI、分进程开发启动和维护工具全部交付后，S2、S3、S4 下的 12 个子任务同时具备开工资格。每个子任务独立开发和验证，以自身的交付条件完成评审；提供方的业务实现和 PR 合并属于统一联调输入。实际批准版本、责任人和证据在[准入记录](design/acceptance/阶段准入记录模板.md)登记。

### 实现目标与用户故事

| 目标 | 主链及用户故事 | 独立开发输入 | 完成条件 |
|---|---|---|---|
| S1 工程底座 | Java/Maven API → 用户端和管理端 → GitHub Actions → 分进程开发启动。交付 PostgreSQL、Redis、OSS、SMTP 基础设施、共享运行机制及维护工具 | ADR-001、004、007、008、010、011 与隔离的开发测试资源 | 可构建并分进程启动示例；核验通用文件、事务、事件投递和调度，维护工具验证初始化、清理与重试 |
| S2 商品与交易 | US-02／03／09／13 商品与分类，US-04 评论收藏，US-05／06 请求、约定与确认，US-07 评价，US-14 交易计时和状态执行 | S1 实际通用文件、事务和调度服务；账户、会话、通知和事项认领契约 | 完整交易生命周期同属本目标；商品和交易场景能用受控依赖独立验证 |
| S3 账户与沟通 | US-01 账户，US-04 三类会话的通用交互，US-11 通知与实时投递，US-12 本人业务的入口与通用聚合 | S1 实际传输、调度和邮件服务；交易、事项和商品只读契约 | 使用代表性交易和事项数据验证三类会话、Session、通知与恢复，验收场景可从受控输入启动 |
| S4 治理与管理 | US-07 举报及匿名结果，US-08 审核与处置沟通，US-10 管理统计，US-12 本人事项、US-14 异常事项与管理处置，US-13 管理端分类维护 | S1 及账户、商品、交易、会话的命令和查询契约 | 用受控主体数据验证管理员与用户路径、固定认领、申辩期、依据及审计；使用 S1 文件能力验证事项证据用途及引用 |

[用户故事及验收条件](appendices/user-stories/index.md)定义完整场景。[需求与接口映射](design/detailed-design/01-需求与接口映射.md)定位接口和案例。跨业务故事按动作归属，例如 US-14 的计时和交易状态变化由 S2 实现，管理员认领和处置决定由 S4 实现，会话投递由 S3 实现。

### S1 工作顺序

袁尚峰交付 Hello World 工程、双前端、API、全部通用基础设施、GitHub Actions、分进程开发启动和维护工具。Jenkins 发布和生产环境验证由后续部署工作完成。通用文件、事务、事件、调度、邮件和认证校验入口使用示例领域输入验证。S2—S4 分别提供账户、商品、交易、会话、通知及事项业务的规则、处理器和数据。详见[S1](design/tasks/S1-工程骨架与基础设施.md)。

### 并行开发约定

1. **单一写入归属。** 同一业务对象的主状态、迁移和规则由一个目标维护。S2 持有商品及交易状态，S3 持有账户、会话及通知事实，S4 持有事项决定；S1 管理通用文件元数据及引用机制，各业务维护本域用途和资格。目标间调用服务命令和只读投影。跨主体用例的编排仍在同一业务数据库事务内。
2. **以契约和数据解除开工依赖。** 在 S1 交付前一起核对既有接口文档，确定跨目标签名、错误、权限、锁顺序及代表性数据。S1 提供可运行设施、构建入口、隔离资源和依赖装配方式。各子任务随开发编写本域测试、样例数据和其他业务的替身，采用同一份已确认的服务签名及 HTTP 契约。阶段专属业务模块的编译、单元测试和局部联调均以 S1 与公共契约为输入。
3. **用共同的预期替换测试替身。** 服务的正常返回、具名错误和幂等结果由同一组契约预期核对。联合环境接入真实提供方，再验证商品占用、交易与会话原子提交、事项执行及恢复。目标内独立验证先完成，统一联调验证跨目标不变量，开发完成后进行系统测试和验收。
4. **管理共享文件。** 需求和接口文档按业务源维护，OpenAPI 聚合入口与应用装配由公共负责人集成。目标内按子模块、路由或数据迁移拆分 PR，迁移登记的版本在集成前检查冲突并在空库复现。四名成员各在 S2—S4 有一个子任务，以各自工时安排交错推进。

### 跨目标契约与验证数据

| 契约 | 提供方 → 调用方 | 开工时约定的数据和结果 | 统一联调 |
|---|---|---|---|
| 账户资格和限制 | S3-02 → S2、S3-04、S4 | 普通账户、封禁账户、卖方和认领管理员；当前资格、版本失效及限制结果 | 真实 Session、锁后资格与账户限制来源 |
| 商品占用及审核 | S2-02 ↔ S2-01；S4-02／04 调用 | 可售、待审、已占用商品；接受、释放、审核决定和资格冲突 | 占用唯一，认可分类、商品状态及记录一起提交 |
| 交易命令和资格投影 | S2-01 → S3-04、S4-01／04 | 待接受、带有效约定、争议中及终态交易；参与者、状态、限制来源及具名失败 | 冻结、恢复、终止及交易超时，核对锁序、归档和通知 |
| 会话和通知副作用 | S3-04／03 → S2、S4；S1 投递机制、S3-01 业务分发 | 三类会话和获准参与者；幂等创建、追加系统消息、归档、通知去重、折叠为游标推进的不可见事件 | 业务、会话、通知与待投递事件在同一事务中落库，真实投递及补取 |
| 事项认领与治理结果 | S4-04／01 → S2-02、S3-04 | 两名管理员、唯一认领、已决定／申辩中事项，校验对方角色和依据 | 验证真实管理员权限、事项参与和各目标状态及历史 |
| 文件 | S1 → S2-02／03、S4-03／04 | 使用真实 OSS 文件服务与受控资格，复核上传、核验、读取、引用和回收。各目标提供用途与绑定规则 | 校验商品图片与事项证据的真实访问权限及事务一致性 |
| 事务与调度 | S1 → S2—S4 | 使用实际通用事务、幂等和调度机制，装配受控业务命令与时钟，验证回滚、锁、重放及接管 | 在真实业务事务和处理器上复核锁序、提交与异步恢复 |

每个子任务都能从 S1 的干净检出和自己的分支构建、启动及执行检查。后端以公共服务签名编译，在测试配置装配依赖替身；涉及外键时加载测试专用的引用数据与最小测试表。前端按同一份 OpenAPI 使用受控响应及事件流，共享页面组件按约定提供独立预览或占位替身。各子任务在 PR 中登记独立检查命令和结果。统一联调切换到真实服务与完整 Flyway 迁移，验证跨域事务、权限及端到端链路。完成统一联调与验收的功能随应用版本一并发布。

### 工作量安排

按 [US 的可验收动作](appendices/user-stories/index.md)、状态机、事务和权限风险估工作量。US-05 和 US-14 包含多条共享交易状态及计时规则，S2-01 集中交给袁尚峰。S3-01 业务实时同步和 S4-01 处置执行编排同样由袁尚峰负责，二者复用其 S1 基础设施。商品检索与分类、交易及账户页面、会话规则、事项生命周期分别由对应负责人交付。管理统计由 S4-02 组合读取，减少业务主体重复实现。每人各在三个目标承担一项，派发时按审查发现的高风险子项和实际产能安排个人顺序。

### 准入关联

[S1 准入材料](design/acceptance/S1-阶段准入.md)核对工程基础与隔离资源。[任务索引](design/tasks/索引.md)列出三组业务任务。S2—S4 在同一工程交付点核对准入，12 个子任务先各自完成功能开发、单元测试和适用的局部验证。开发优先单元测试，按需采用集成测试，业务逻辑以人工前后端联合测试为主。执行记录按[测试策略](#分阶段回归)登记。

## 2. 测试策略与依据

### 预期来源

需求正文、BR／TR／权限矩阵、详细 US／UC／SC 与人工确认构成预期依据。AI 辅助扩展案例，对应任务登记的审查姓名核验预期及适用范围。

### 静态与白盒验证

后端执行 Maven 编译与静态检查。前端使用 Oxlint、Oxfmt、`vue-tsc` 严格类型检查及 Rsbuild 构建检查。全部业务逻辑白盒核对输入、主体资格、状态、不变量、事务、锁序、失败分支与审计。审查记录对应版本和差异。

### 运行时验证选取

每个案例说明不可静态确认的性质，或所覆盖的复杂关联／跨模块黑盒行为。使用真实 PostgreSQL 多连接验证并发；使用多 API／IM／worker 实例验证共享机制。合成数据和环境版本随案例登记。

### 测试层级

| 层级 | 验证对象 | 本项目示例 |
|---|---|---|
| 单元测试 | 独立的领域方法或纯逻辑，使用显式输入和可控时钟 | 状态转换资格、配置校验、有效等待时间计算 |
| 集成测试 | 模块、接口或外部依赖之间的契约及协作 | 真实 PostgreSQL 多连接竞争锁单，PostgreSQL／Redis 会话撤销，OSS 与邮件投递 |
| 系统测试 | 已部署系统的完整业务链路与质量要求 | 跨实例发消息并在接收端显示，浏览器端到端交易链路，滚动更新与故障恢复 |
| 验收测试 | 以需求和阶段退出条件为依据，由实际验收人确认结果 | 阶段主流程与异常演示，最终部署的全链路、权限、性能与恢复验收 |

接口测试按被测范围归入相应层级。只验证 API 与数据库协作时属于集成测试，经已部署系统完成跨模块用户流程时属于系统测试。性能是测试目标，可在集成、系统或验收阶段测量。验收可引用已有运行证据，并按验收记录登记确认人和日期。单元案例在实现任务中按独立规则和回归风险登记，白盒审查及静态检查另记证据。

### 开发阶段用例选择

开发期自动化优先编写单元测试。业务逻辑验证以人工前后端联合测试为主，使用当前阶段可启动的前端、API 和明确的测试数据。按角色覆盖正常操作与关键异常，核对界面反馈、API 响应及相关状态。记录版本、环境、数据、操作步骤和实际结果。

- 单元测试优先覆盖有分支的资格、状态、时间边界和界面状态转换。每例登记输入、固定时间或模拟依赖及可观察预期。可直接审查的简单映射随静态和白盒检查验证。
- 按需补集成测试，覆盖需稳定复现的真实依赖或跨模块契约行为，例如数据库约束、事务回滚、并发竞争、会话失效、持久化事件恢复，以及生成 API 客户端与接口契约协作。并发用真实 PostgreSQL 的独立连接，Session 或队列行为用真实 Redis。可控替身用于触发 OSS 或 SMTP 的指定响应。登记所接入的依赖和所用替身。
- 测试预期沿用已有 TC 的业务规则，注明具体子场景及验证层级。前端对受控接口响应可验证页面状态及错误处理，真实浏览器跨模块端到端链路列入开发完成后的系统测试。

### 必要技术验证计划

| 专题 | 场景 | 预期及证据 |
|---|---|---|
| 事务及锁单 | 两实例竞争接受；提交失败；同次重试 | 唯一占用、整体回滚、稳定结果；数据库状态与命令 |
| IM | 用户连接分布两实例；重连；流裁剪或分发中断 | 目标覆盖、去重、补取与已读独立；系统测试以接收端真实显示记录验证正常网络双方在线的 2 秒可见目标，测量口径见[部署验收安排](#性能测量) |
| 任务调度 | worker 退出、租约接管、重复投递 | 幂等业务结果、可恢复执行权；领取与执行证据 |
| Session | 跨实例续期、退出、改密、换绑邮箱及 Redis 恢复 | Q-001／Q-004；逐会话撤销与凭据版本变更分别核验，客户端身份错误按共享接口约定 |
| 文件 | 上传中断、重复完成、核验后覆盖、回收竞争 | 文件内容稳定、引用与权限正确；Q-002 作为预期 |
| 邮件 | 异步重试、重发替代、并发错误提交 | 单表原码生命周期、幂等计数、worker恢复及脱敏；Q-003实际决定、TC-COM-018—021作为预期 |

测试代码、批准执行范围、环境与真实结果在各任务及证据记录中登记。

### 分阶段回归

S1 验证自身交付的工具链、基础设施、发布和维护操作，并提供隔离资源与装配入口。各业务子任务同步开发及编写业务测试。S2—S4 各自使用受控依赖完成静态检查、审查及必要单元／集成测试，先做各自前后端联合测试，再把真实模块放在同一环境联调。各目标记录独立证据和统一联调复核结果。

开发完成后，对部署版本执行系统测试，覆盖阶段业务主链、关键异常、跨实例行为、性能及恢复，再按需求与对应阶段退出预期开展人工验收。验收可引用系统测试与适用的开发验证证据。最终部署验证按[部署验收安排](#plan-04)执行。

## 3. 阶段准入与验收安排

### 准入

阶段任务以 `main` 中的设计基线准备编码任务卡及准入材料；通过阶段准入批准后开始业务编码。按阶段核对前置 Q 关闭、ADR 接受、接口双方及复核确认、状态／错误／事务／权限明确、人工前后端联合测试及适用的单元／集成预期已核验、环境与配置齐备、责任及完成条件。批准记录采用[准入模板](design/acceptance/阶段准入记录模板.md)。

### Issue 与任务分支

派发 Issue 引用最新 `main` 的需求与 ADR／Q、文件范围及依赖。独立批次从 `main` 建立分支并向 `main` 提交 PR。关联批次可按[联调基线约定](design/tasks/索引.md#提交与集成)合并相关 PR，在基线上开发和验证。实际采用提交在 PR 和准入记录登记。分支、Draft PR、单一职责的小步 commit 及批次集成按[任务索引](design/tasks/索引.md)组织。TASK-001 统筹正式决定、共享文档与生成物；成员维护自己的模块源文件并交叉审查。

### 审查与阶段验收

开发阶段按[审查模板](design/reviews/模板.md)记录版本、业务与约束检查、人工前后端联合测试、优先单元测试、按需集成测试及问题处理。开发完成后执行系统测试与人工验收，按[验收模板](design/acceptance/阶段验收单模板.md)记录完整业务链、关键异常、回归、残余风险与验收人。

### 变更

原因→影响需求／ADR／接口／数据／测试→人工决定→修改→回归。重大取舍新建替代 ADR，原版本通过 Git 及记录追踪。

## 4. 最终部署验收安排

部署归 TASK-001，各模块提交配置、迁移、依赖及兼容性信息。

### 执行依据

批准阶段及需求覆盖完成后，按运行说明从干净环境启动，登记提交、产物、配置、迁移及资源版本。检查单机多实例及 Nginx 分流、健康和优雅退出。

### 验收范围

全链路、权限与隐私、真实数据库及媒体访问、外部故障与备份恢复、滚动更新及回退兼容、获准负载。性能采用需求第6、7章条件，执行前核验参数、样本和口径。

### 性能测量

按[质量要求](requirements/06-质量要求.md)及[验收依据](requirements/07-验收与验证.md)执行。记录环境、发布版本、网络条件、活跃用户数、商品规模、操作配比、实际速率、有效样本和失败样本。

- 常用交互采用 100 名同时活跃用户及 10,000 条商品记录，从用户发起到可用结果计时，至少 95% 在 3 秒内返回。
- 文本消息在双方在线、网络正常时，从发送方发出到接收端实际显示计时，至少 95% 在 2 秒内显示。用本次发送结果的消息标识与接收端显示记录关联样本，纳入未显示或超时样本，并保存端点计时的时钟校验依据。覆盖双方连接分布在不同 IM 实例的情形。S3 开发期间可通过集成测试验证事件分发、顺序及恢复。接收端显示时延在开发完成后的系统测试测量，最终部署按实际环境复测。
