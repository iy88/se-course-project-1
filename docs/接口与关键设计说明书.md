| DATA-03 | 当前业务状态与历史事实分开 | 当前规则由当前事实计算，快照和审计保留当时发生的内容 | 以当前商品内容重建成交时商品内容，或删除历史快照后从当前数据推导 | 核对历史记录在后续编辑后的预期，检查明确的历史字段及引用 |

| RULE-01 | 统一规则由所属类提供接口 | 每项规则有具名方法、输入、返回／错误及适用动作；调用方调用该方法 | 控制器、服务和页面各自复制一套商品编辑资格条件 | 建立“规则→类方法→调用入口→案例”映射，定位所有实现和调用 |
| RULE-02 | 跨主体资格由用例收集事实，主体方法统一判断 | 用例提供当前身份、账户限制、参与和事项上下文；方法读取显式输入，返回 Allowed 或具名业务错误 | 将商品侧 can_edit 当作完整授权，遗漏账户封禁或事项资格 | 核对方法签名、输入来源、各限制组合和错误分支 |
| RULE-03 | 写操作以锁后事实执行规则 | 按 C1 规划锁、重读后调用主体方法，成功后维护主体及历史 | 信任页面上次取得的 can_relist，跳过写入时复核 | 按事务顺序审查；用并发状态变化案例检查结果 |

## 2. 共享接口约定

### HTTP 与模型

采用 RESTful，以复数名词组织资源，GET 查询、POST 创建或提交业务动作、PATCH 部分更新、DELETE 删除或解除关系。归属用子资源表达，关键状态转换明确业务契约。版本前缀采用统一约定，前端独立配置公开入口。

JSON 使用 snake_case。对象 ID 对外字符串，金额整数分并体现单位，时间 UTC ISO 8601。状态采用具名字符串枚举。省略、null 及更新清空语义逐字段注明。

成功响应按资源组织，列表包含 items 和分页信息；错误包含稳定业务错误码、展示说明、必要字段错误及 request_id，HTTP 状态表达协议结果。错误码清单待接口评审。

### 身份与权限

随机 Session 凭据通过持久 Secure／HttpOnly Cookie 传递，状态变更请求采用 CSRF 校验，具体同源部署及 Cookie 属性在配置清单中确定。Redis 保存有效 Session，PostgreSQL 保存账户、凭据版本及逐会话 SessionGuard，每次鉴权同时核对签发／撤销事实并复用请求上下文。

绝对期限与空闲期限取较早者，用户有效活动按配置间隔续期，心跳与自动轮询单独处理。账户多 Session、Session 多连接。退出撤销当前 Session；改密／重置使已有版本失效；封禁保留需求规定的读取及事项沟通。

Session 不存在或到期返回重新登录语义；Redis 查询未完成返回暂时服务错误，客户端保留凭据。Q-001采用B，退出先持久撤销，再清理Redis及连接；Redis恢复旧值后已撤销Session仍拒绝。细节见[会话与身份](#interfaces-07)。

### 分页与并发

普通列表页码分页，明确过滤、主次稳定排序及总数口径；聊天历史和事件恢复采用游标。默认页大小和上限由后端配置。

关键写接口按主体、操作、幂等键及输入摘要返回同次结果；同键不同输入返回冲突。旧页面敏感操作携带版本依据，过期提交按契约返回冲突。事务由用例统一提交，内部能力复用同一上下文。

### 配置与能力接口

后端配置按应用入口、实例、数据库、Redis、身份、IM、任务、业务策略、文件邮件及日志分组，登记类型、单位、依据、默认值、范围、关联关系、公开范围与生效方式。前端配置在各应用中维护，构建独立；输入限制和上传能力从接口取得。配置模型及 .env.example 在实现阶段同步建立。

新操作用当前配置，既有期限及授权保存当次参数／版本；受影响的既有业务通过明确变更处理。

### 日志审计与类型

统一 request_id、operation_id、event_id、task_id、correlation_id、causation_id、instance_id 和 connection_id 的含义。自动记录公共上下文，业务用例提供审计事实并在提交前持久化。

接口类型由 OpenAPI 契约生成；所选后端技术栈和 TypeScript 严格类型检查配合白盒审查，运行时案例针对运行时性质或复杂关联。

### 协作接口

模块提供方、调用方和复核人按模板登记。共享契约由 TASK-001 维护；各任务提出所需变更，由指定审查人核对交界后汇入。

### 字段与统一规则检查

按[设计约束与检查规则](#interfaces-02)的 DATA-01—04、RULE-01—04 及 DOC-01 检查字段来源、主体类接口、锁后判定、查询等价性和同源传播。实体与共享视图保留事实及必要关联，展示、搜索及动作资格通过所属类接口统一计算。

## 公共事务与权限交接契约

设计归属：TASK-001；编写账号：iy88。输入：design 提交 `6250473`。

### 关联需求、决策与接口

依据 FR-01—FR-14 的主体资格、BR／TR／权限矩阵、第6章一致性与隐私要求，关联 ADR-002、003、005、009、010。调用方为 TASK-002／003／004 的业务用例，本契约定义公共输入、事务、资格、幂等及错误。数据模型和业务状态仍由各主体专题定义。

### 公共数据类型

| 类型 | 字段与约定 |
|---|---|
| EntityId | 正整数 ID 对外使用十进制字符串；数据库为整数；接口模型校验其范围 |
| ResourceRef | `resource_type`：具名主体类型；`resource_id`：EntityId |
| ExecutionContext | `request_id`：本次执行 UUID；`operation_id`：逻辑操作 UUID；`actor_kind`：account／entry／system；`actor_id`：账户ID、受服务端保护的entry摘要或已登记系统任务名；`session_id`：账户操作的内部 Session 标识；`origin_connection_id`：经服务端核对属于当前Session的来源连接UUID或null，用于本人其他连接的已读同步；`credential_version`：鉴权读取的账户版本；`config_version`：本次配置版本 |
| LockPlan | `shared_account_ids`、`exclusive_account_ids`：资格判定所需账户集合；`resource_candidates`：按锁域登记的候选对象标识；`planning_basis`：来源对象及读取依据。账户集合合并后采用所需最强模式；resource_candidates包含从服务端context及内部用例确定的session_id及所需模式，system无用户Session；候选对象按公共锁序排列 |
| AccountQualifications | 按账户 ID 索引的当前身份、凭据版本、限制及对应判定字段；由资格锁取得后的读取构建 |
| EventIntentBatch | items为按账户ID排序的recipient_account_id及稳定event_id；单个接收人也返回同一具名结构，详见[C2](#interfaces-09) |
| Allowed | 本次动作的具名允许结果，关联动作及对象；由主体在当前资格和已锁定状态下检查取得 |
| TransactionContext | 同一用例持有的 SQLAlchemy AsyncSession、ExecutionContext 及本次审计／事件意图集合 |
| BusinessError | `code`：稳定错误码；`message`：可展示说明；`details`：按接口定义的公开字段；`resource`：允许公开时的 ResourceRef |
| OperationResult | `operation_id`、HTTP 状态、已确认响应数据及结果资源引用；用于成功操作的同次重试 |

账户上下文由身份依赖构建；system 上下文由登记的任务入口构建，附触发事件／任务标识。entry上下文只用于已登记的公开账户入口，签名Cookie及CSRF由[邮箱验证协议](#interfaces-08)核对，不用于访问业务内容。外部输入通过 Pydantic 转成用例参数，执行上下文由服务端补齐。当前请求中的关联查询复用已核验身份，用例写入时按下述协议重查资格。

### 用例和模块调用签名

以下为设计签名，T 为模块具名结果类型。

```text
run_write(context, operation_name, idempotency_key, request, prepare, use_case) -> OperationResult[T]
prepare(read_session, context, request) -> LockPlan
use_case(tx, context, request, qualifications, lock_plan) -> T
lock_account_qualifications(tx, shared_account_ids, exclusive_account_ids) -> AccountQualifications
require_action(qualifications, action, resource_state, participation) -> Allowed
record_audit(tx, action, target, before_after, basis_ref) -> audit_id
add_event_intent(tx, recipient_ids, event_type, source, intent_key, payload_ref) -> EventIntentBatch
```

request 为经过 schema 校验的具名业务参数；公共入口从同一 request 生成规范化输入摘要，并将该参数交给准备函数及业务用例。prepare 和 use_case 由该业务动作一起提供。

内部能力成功时返回具名结果，业务失败统一抛出具名 BusinessError。require_action 成功返回 Allowed，失败抛出 BusinessError；公共包装捕获该异常，先回滚整个事务再映射 HTTP 错误。用例协调跨模块动作，公共包装完成最终提交及错误映射。内部能力的必要 flush 保持在调用方事务内。每个并发请求／后台任务持有自己的 AsyncSession。建议采用 PostgreSQL READ COMMITTED 隔离级别；等待锁后显式刷新或重新查询资格及业务状态，使后续语句读取最新已提交事实。

### 写操作执行顺序

run_write 组织如下阶段；prepare 只做候选对象及账户标识的只读查询，权威资格和状态检查在写事务中完成。

1. **准备锁集合**：在独立只读会话中调用 prepare，收集动作涉及的账户资格集合及候选业务对象。查询使用完成后结束该会话；此阶段输出 LockPlan。
2. **取得资格锁**：开启写事务，由公共入口合并 LockPlan 的账户集合，按 ID 升序、首次即采用所需最强模式取得资格锁，再按 session_id 升序锁定当前操作所需 SessionGuard（普通写入FOR SHARE，退出FOR UPDATE），读取 AccountQualifications 并重查持久会话有效性、当前身份及凭据版本。system上下文按登记任务身份核对；公开entry按其专用账户用例准备已有目标账户锁，按会话专题核对入口，不要求用户Session。邮箱相关用例在该资格锁域末尾按稳定散列锁键升序取得所需邮箱advisory锁，再进入幂等占位。
3. **登记幂等占位**：在资格锁之后查找或创建本操作的幂等占位。已有成功结果时，按当前结果读取资格重放；首次操作继续调用 use_case。当前动作的写入资格在业务用例中检查，结果重放采用读取资格。
4. **执行业务**：use_case 接收同一 tx、request、qualifications 和 LockPlan；按第3级及之后的锁域取得业务对象锁，重读状态并调用 require_action，再完成主体、历史、审计、文件及通知意图的变化。
5. **统一提交**：公共入口在业务锁操作完成后，统一取得接收账户的事件序号锁、保存事件及成功响应，提交事务后返回 OperationResult。

prepare 的候选是规划依据。写事务重查时，如发现新的资格账户、所需更强模式，或需要取得已经越过的锁域／更小对象键，业务用例抛出内部 LockPlanChanged，附补充集合。公共入口回滚本次全部变化，使用新只读会话重新准备并合并补充集合，再从资格锁阶段开始整次重试。次数及退避采用配置；业务事件与成功结果在最终成功事务中提交。

封禁等资格变化动作可在取得目标资格锁后发现关联集合；新增集合依同一重规划流程处理。最终业务资格与锁集合由写事务重查确定，候选读取和锁后的实际对象共同参与一致性核对。

### 状态转换与数据约束

| 对象 | 规则 |
|---|---|
| 资格 | 账户当前身份、凭据版本和限制来自 PostgreSQL；主体进一步核对归属、参与、状态及认领 |
| 成功写入 | 主体变化、历史、必要审计、幂等结果、通知及待投递事件统一提交 |
| 业务校验结果 | 整体回滚，本次业务状态及成功审计保持原状，接口按错误码表达 |
| 唯一约束竞争 | 只将已登记的约束映射为对应业务冲突，其他异常记录关联标识后返回内部错误 |
| 查询 | 按当前读取资格构造响应字段；记录读取本身与需要审计的业务动作分别定义 |

时间判断使用同一逻辑数据库的当前时钟；等待行锁后重新读取状态，并以实际判定时刻检查期限。修改期限的规则按既有规则版本语义执行。

### 账户资格与并发写入

本交接稿建议采用 PostgreSQL 事务级共享／排他 advisory 资格锁，在统一登记的资格锁命名空间内以账户整数 ID 作为键。该机制的取舍依据及评审意见记录于关联 PR。

- 普通写操作取得操作者和直接业务参与账户的共享资格锁，例如购买请求与交易取得买卖双方的锁，消息发送取得相关参与账户的锁。
- 封禁、解除、改密／重置及管理资格变更，对变化账户取得排他资格锁；管理操作者按需要取得共享锁。
- 用例在开始时合并账户集合，按账户 ID 升序取得所需最强模式，再重读账户资格和凭据版本。资格锁由事务结束释放。
- 资格变化事务通过账户模块保存当前状态，并协调适用的业务变化。封禁目标的锁取得后，读取其当前请求／交易集合，其他涉及该账户的新写入在取得资格锁后检查最新状态。
- 资格 advisory 锁与实际账户行的更新锁分别表达职责；账户模块在资格锁内执行普通字段更新。通知接收人存在性查询及外键关联沿数据库结构规则执行。

两种时序都有确定结果：业务事务先取得共享资格锁时，该业务先完成，后续限制按已提交状态处理；资格变化先取得排他锁时，后续业务读取新资格并返回对应结果。读接口依据当前账户和对象范围判定，Q-001采用持久逐会话撤销，资格锁域内按[会话专题](#interfaces-07)重查当前Session。

### 锁顺序与事务边界

| 顺序 | 锁域及动作 |
|---|---|
| 1 | 本用例资格锁域：先账户ID升序取得全部账户资格锁，再按session_id升序取得SessionGuard行锁；模式首次确定，身份专题规定共享／排他模式；邮箱用例在其后按实际锁键升序取得邮箱资格锁 |
| 2 | 幂等键的事务内唯一占位：操作者＋操作类型＋请求键 |
| 2a | 账户资料及邮箱验证行：先账户ID升序锁资料行，再验证ID升序锁全部验证行；随后进入主体业务锁域 |
| 3 | 商品行：商品 ID 升序；锁后重读占用及状态 |
| 4 | 交易行：已知受影响集合按 ID 升序；单商品场景在商品锁内确定集合 |
| 5 | 处置事项行：事项 ID 升序，重查认领与当前状态 |
| 6 | 固定子序：ChatConversation → TradeConversation → CaseConversation → 各类消息 → 各类阅读进度 → 文件登记 → 文件引用 → 通知 → 任务执行记录；每个子域内部按稳定对象键升序 |
| 7 | 用户事件序号行：收集全部接收账户后按账户 ID 升序锁定、分配序号并保存事件 |

第6级按业务对象语义划分子域；具体表结构由主体模型定义，同一物理行首次取得锁后按该次锁覆盖处理。整数 ID 使用数值顺序，复合键采用主体契约声明的字段顺序逐项比较。文件引用以 reference_id 排序。新增行由当前事务创建，涉及已存在对象的锁及唯一关系竞争仍按公共顺序组织。

每个用例按涉及的锁域推进，并在具体专题登记其集合和顺序。需要补充更早锁域的对象时，回滚并重新规划整次用例；此分支计入统一的有限事务重试。事项认领可作为独立短事务；处置执行重新按全局顺序取得相关锁和资格。

接受请求的具体交易转换和商品占用由 TASK-003 定义；事项执行请求由 TASK-004 定义。调用方使用本表组织公共顺序，模块维护自身数据。

### 幂等作用域与结果

客户端关键写操作提交 `Idempotency-Key`。账户或公开entry已按对应身份入口核验，服务端校验键的格式和配置长度。作用域为 `(actor_kind, actor_id, operation_name, idempotency_key)`，数据库唯一约束保障跨实例同次识别。

输入摘要采用具名用例参数的规范 JSON：包含路径对象和有效业务字段，排序键并固定编码；各字段按 schema 处理省略、null、时间、金额及文本。摘要使用 SHA-256；凭据与敏感载荷通过其专用验证接口处理。规范化方案版本随记录保存。

| 情况 | 结果 |
|---|---|
| 已有成功记录、摘要相同 | 按当前身份及结果读取资格返回已保存业务结果，沿用 operation_id |
| 已有记录、摘要不同 | `IDEMPOTENCY_PAYLOAD_CONFLICT` |
| 首次请求 | prepare 收集候选，公共入口先取得账户资格锁，再创建事务内占位；调用用例取得业务锁并完成动作，保存响应状态、数据和资源引用，统一提交 |
| 同次请求并发 | 使用 INSERT ... ON CONFLICT DO NOTHING 协调唯一占位等待，再以新语句读取；先到事务提交后，后到者读取成功记录；先到者回滚后可接续执行 |
| 校验结束且事务回滚 | 本次占位随事务回滚，重试依据当前业务状态重新判断 |
| 响应丢失 | 使用同键重试，取得已提交结果 |

成功结果的重放复用原业务数据和状态码，当前执行产生新的 request_id。验证码格式合法但不匹配时，专用验证用例原子保存失败次数及该次失败幂等结果并提交，随后返回具名422结果，公共包装不再次回滚已提交计数；格式错误在事务前拒绝。涉及验证码及密码的输入摘要采用邮箱专题的专用HMAC协议，敏感原文不进入普通幂等表。其余校验失败按普通回滚处理。保留期限内重复请求按本表执行；到达保留期限后的客户端重试策略在配置／接口中明确。

### 错误映射与输出

| 错误码 | HTTP 状态 | 语义 |
|---|---|---|
| SESSION_REQUIRED／SESSION_EXPIRED | 401 | 进入登录流程 |
| ACTION_NOT_ALLOWED／ACCOUNT_WRITE_RESTRICTED | 403 | 当前资格与动作不匹配 |
| RESOURCE_NOT_VISIBLE | 404 | 当前访问范围内没有对应资源 |
| STATE_CONFLICT／VERSION_CONFLICT | 409 | 状态或提交版本已变化 |
| IDEMPOTENCY_PAYLOAD_CONFLICT | 409 | 同键对应其他输入 |
| INPUT_INVALID | 422 | 输入格式、字段范围或组合校验结果 |
| RATE_LIMITED | 429 | 返回可用重试时间 |
| DEPENDENCY_UNAVAILABLE／TRANSACTION_RETRY_EXHAUSTED | 503 | 返回服务暂不可用及适用重试提示 |
| INTERNAL_ERROR | 500 | 返回请求标识，内部日志关联具体原因 |

错误 JSON 结构：`error: {code, message, details}`、`request_id`，以及已建立逻辑操作时的 `operation_id`。details 按接口声明字段输出，资源可见性由主体确认。模块通过稳定前缀补充具名业务错误并登记 HTTP 映射。

### 超时、重试与异常恢复

数据库锁等待、事务时间、重试次数及退避来自后端配置。只有已登记的死锁／序列化或锁集合重规划等整事务可重试条件进入有限重试；每次从新事务重读。外部网络、OSS、SMTP 和 Redis 投递通过提交后的状态流程处理。

数据库事务完成后返回成功；实时投递从持久事件推进。运行日志在公共包装输出 request_id、operation_id、实例及实际结果，审计记录业务主体和依据。原始密码、验证码、Cookie 及签名 URL 采用各自保护与脱敏约定。

### 规则版本

ExecutionContext 固定本次 config_version，幂等记录保存摘要规范版本及结果。存储结构承载不变量；阈值、超时及长度由配置校验。已有期限和授权保留创建时参数及版本。

## 会话与身份：持久撤销与故障恢复

设计归属：TASK-001 第3批，输入 design `2a7cb17`。依据 FR-01、BR-20—22、ADR-005 和 [Q-001](design/decisions/questions/Q-001-Session撤销与Redis故障恢复.md)。袁尚峰（iy88）于2026-11-14选择 B，PostgreSQL 保存逐会话撤销依据。账户及邮件HTTP契约见[账户与通知](#interfaces-13)，单表短期明文方案见Q-003及邮箱专题，换绑后的全部旧Session失效采用Q-004实际决定。

### 权威数据及字段来源

| 存储／对象 | 字段、类型及用途 | 约束、索引和维护方 |
|---|---|---|
| PostgreSQL SessionGuard | session_id：数据库整数主键，对外字符串；token_digest：32字节 SHA-256 摘要；account_id：账户外键；credential_version：签发时账户版本快照；issued_at、absolute_expires_at：UTC时间；idle_timeout_seconds、renew_interval_seconds：签发规则快照；csrf_digest：32字节随机 CSRF 凭据摘要；revoked_at：UTC时间或null | 账户模块唯一维护；token_digest 唯一索引；account_id＋absolute_expires_at 及过期扫描索引；期限晚于签发时间，空闲期限为正，0＜续期间隔＜空闲期限；不存原始 Session／CSRF 凭据 |
| Redis Session | 键采用命名空间＋token_digest；值含 session_id、last_activity_at，键到期时间取 min(absolute_expires_at, last_activity_at＋idle_timeout) | 账户模块维护；会话归属、凭据版本、绝对期限和规则均读取 SessionGuard；Redis 仅保留运行时活动事实及定位关联，原始凭据不入键或日志 |
| PostgreSQL 撤销清理意图 | session_id（唯一关联）、created_at、next_attempt_at、attempts、completed_at 或null | 与 revoked_at、必要审计同事务；worker清理 Redis 并向IM发布撤销提示；认领及接管采用公共任务协议，重试保留稳定 session_id |
| Account | 当前 credential_version、账户角色及限制事实 | 沿用账户主体事实；SessionGuard 的版本为历史签发依据，鉴权比较当前值 |

SessionGuard 表示曾签发的许可及撤销事实；当前有效性由方法计算。Redis 命中且持久依据存在、未撤销、绝对及空闲期限有效、凭据版本一致时才授权。账户封禁不等于登录失效，后续动作仍按 BR-32／33 核对；不存 active／is_valid 等重复资格字段。

### 统一身份方法

| 方法 | 输入／返回与失败 | 调用处 |
|---|---|---|
| SessionGuard.require_valid(account, runtime_session, now) | 显式输入账户当前事实、Redis运行时值及当前时间；核对定位一致、revoked_at、期限及版本，成功返回当前身份依据，失败 AUTHENTICATION_REQUIRED（401） | HTTP鉴权、业务写入资格锁后、IM建立及每次收发／投递 |
| SessionGuard.require_logout(token_digest, csrf_digest) | 以当前Cookie摘要定位登记；核对本Session的CSRF；成功返回撤销目标，已撤销沿用原事实；CSRF不符抛 CSRF_INVALID（403） | 当前Session退出；可在Redis不可用时由持久依据完成 |
| SessionGuard.revoke(now) | 在行锁内首次设置 revoked_at，重复调用沿用原时间；原子创建唯一清理意图 | 当前退出；签发失败清理 |
| Account.require_credential_version(version) | 当前版本等于请求签发版本才成功；不符401 | 与会话方法及C1当前身份检查复用 |

查询范围和清理候选使用这些事实的等义条件；所有路径共用一套有效性方法，身份上下文由服务端建立。系统任务采用 C1 的 system 身份，不伪造用户Session；向用户连接投递仍核对该连接的Session。

### 签发、鉴权及续期

1. 登录用例核对邮箱密码，按账户资格锁读取当前凭据版本；签发至少256位随机 Session 凭据和独立随机 CSRF 凭据，将摘要、原期限及规则保存在 SessionGuard 后提交。
2. 在事务外创建 Redis Session，保存运行时活动时间并设置到期时间，成功后设置Cookie；失败返回503，执行持久撤销及清理，不下发新凭据。未知 Redis 写入结果同样进入清理；新登录可签发不同的Session，响应丢失的旧许可按期限清理。
3. HTTP请求由Cookie计算摘要，读取Redis值及 PostgreSQL 当前 SessionGuard／Account，调用 require_valid；身份结果在本次请求内复用。Redis缺失、持久依据缺失、已撤销、过期或版本不同为401；依赖查询超时或失败为503，保留客户端Cookie。
4. 有效用户活动达到节流间隔才续期；按签发的规则快照，Redis原子脚本仅更新已存在且尚未到期的键，活动时间取新旧较大值，到期时间受持久绝对期限约束。心跳、自动轮询、自动补拉及服务端投递不续期；用户主动阅读、发送及提交视为活动。
5. 续期在事务外执行，采用有限超时；失败不创建缺失键，不从 SessionGuard 自动恢复 Session。与退出交错时即使产生旧Redis残留，持久撤销仍使后续鉴权拒绝。Session绝对期限不随续期延长。

Cookie 由同源 HTTPS 入口维护：`__Host-se_session` 采用 Secure、HttpOnly、SameSite=Lax、Path=/、无Domain；`__Host-se_csrf` 采用相同作用域、Secure及Lax，允许前端读取以放入 `X-CSRF-Token`。Max-Age受保存的绝对期限约束。状态变更还检查已配置Origin及CSRF Cookie／请求头相等，摘要与本Session登记相符；CORS不作为授权依据。登录前账户入口的防跨站协议随C4接口组细化。

### 退出、改密及锁序

账户操作的资格锁域先按账户ID升序取得全部共享／排他锁，再按 session_id 升序取得涉及的 SessionGuard 行锁，随后进入幂等占位及原 C1 业务锁序。普通业务写入对当前Session采用 FOR SHARE，退出对当前Session采用 FOR UPDATE；首次即采用所需最强模式，锁后重查 require_valid。会话行锁持有到业务事务结束，不在后续锁域追加更早的Session；发现新集合时按 C1 回滚重规划。

- 写入先取得共享会话锁：写入按当时资格完成，退出等待后登记撤销。
- 退出先取得排他会话锁并提交：后来写入重查后401，主体、审计成功记录及事件均不提交。
- 普通只读在本次读取身份依据时判定；退出前已通过鉴权的读取可完成。退出成功后的新读取拒绝。
- 改密／重置及换绑邮箱按既有规则和Q-004在账户排他资格锁内更新凭据版本；业务和登录在账户锁后重查版本。旧Session均失效，Cookie清理及重新登录由对应C4接口表达。

退出事务保存 revoked_at、退出审计及清理意图，提交即为成功；Redis删除及IM撤销提示在提交后执行。删除／提示失败不改变成功事实，worker根据持久意图重试。重复退出不重复生成撤销和审计。清理意图只携带 session_id，清理方由登记取得摘要，Redis凭据不进入消息载荷。

### HTTP 与 IM 的失效及故障恢复

| 情况 | 对外结果及数据变化 |
|---|---|
| Redis恢复退出前的Session值 | SessionGuard.revoked_at已存在，401；异步删除残留键，原撤销事实保持 |
| Redis丢失有效Session | 401重新登录；持久签发登记不自动重建Redis键 |
| Redis／PostgreSQL暂时不可用 | 503，保留客户端Cookie；拒绝建立受保护连接或发送受保护数据；连接可按配置重试身份检查 |
| PostgreSQL登记不存在 | 401，即使Redis仍有记录；已过绝对期限后清理登记不会使旧Session恢复 |
| IM已经连接 | 建连、入站动作及每次受保护出站事件前重新检查相同Session与账户资格；入站写入另按C1锁后重查。跨实例撤销提示及周期检查用于及时断开，授权正确性来自持久依据 |
| PostgreSQL历史备份恢复 | 恢复期间阻断API／IM入口并停止签发与续期；撤销全部恢复出的 SessionGuard 并清空其Redis命名空间，断开既有连接后恢复入口，全部用户重新登录；保留恢复操作证据 |

IM发送中已经取得资格及会话锁的写操作与退出按共同锁序排列；出站数据以实际读取鉴权点为准，已经发出的网络帧按已发生事实保留。心跳与客户端持有旧连接不能替代新的身份核对。连接定时检查频率属于C2配置，身份过期及撤销采用本专题方法。

### 保留、配置及运行验证

SessionGuard 与撤销清理意图至少保留至绝对期限，未完成清理意图继续保留；到期且清理完成可按配置归档／删除。已删除登记按缺失拒绝，Session凭据及session_id均不复用。清理扫描在行锁内重查期限及意图；历史审计沿审计保留规则维护。Redis从旧备份恢复时，缺失或撤销登记均拒绝，完成过的旧清理意图无需重新生成才生效。

| 配置 | 类型／单位及输入依据 | 范围、公开性及生效 |
|---|---|---|
| SESSION_ABSOLUTE_SECONDS | 正整数秒，默认2592000（30天，持久登录的初始实现值） | 1—7776000；内部配置；新签发保存快照 |
| SESSION_IDLE_SECONDS | 正整数秒，默认604800（7天，限制长期无活动会话） | 不大于绝对期限；新签发保存快照 |
| SESSION_RENEW_INTERVAL_SECONDS | 正整数秒，默认60，减少高频续期写入 | 小于空闲期限；新签发保存快照 |
| SESSION_CLEANUP_SCAN_SECONDS | 正整数秒，默认300，周期重试及到期清理 | 1—3600；内部配置，调度采用实际发布值 |
| SESSION_DEPENDENCY_TIMEOUT_SECONDS | 正整数秒，默认3，限制依赖等待 | 1—30；内部配置，新请求采用配置快照 |

具体采用值随阶段准入登记；启动时核对关联范围，配置及 .env.example 随代码实现建立。Cookie秘密、CSRF凭据、密码和摘要不进日志；运行日志使用内部 session_id、request_id、operation_id及结果码。

技术依据：[PostgreSQL行锁](https://www.postgresql.org/docs/current/explicit-locking.html)、[Redis过期机制](https://redis.io/docs/latest/commands/expire/)。验证见 TC-COM-015—017，真实 PostgreSQL／Redis及多实例环境随编码任务执行。

## 邮箱验证与异步投递：单表协议

归属：TASK-001第3批，PR #47。输入design `2a7cb17`及本批会话契约 `4759b1d`。依据FR-01、BR-20—22、需求4.19、ADR-008、[Q-003](design/decisions/questions/Q-003-异步邮件敏感投递内容保护.md)。袁尚峰（iy88）2026-11-14通过标注决定：一张表承载邮箱验证及其投递进度，PostgreSQL短期明文保存验证码，不增加应用层加密。

### 单表字段、约束与用途

账户模块维护 `email_verification`。一条记录对应一封邮件及一轮验证码；一次换邮箱创建同组的旧邮箱／新邮箱两行。该表同时是持久待投递来源，Taskiq消息只携带记录ID；定时扫描可重新发现未完成任务。邮件不另设载荷表、校验摘要表或专属投递表。

| 字段 | 类型／空值及事实来源 |
|---|---|
| id | 数据库整数主键，对外字符串；本轮稳定标识 |
| purpose | registration、password_reset、email_change_old、email_change_new具名枚举 |
| email | 去首尾空白的实际投递地址；比较与唯一性使用Account.normalize_email；不设重复的normalized_email列 |
| account_id | 账户外键或null；注册为null，其他为对应账户；服务端由当前身份或邮箱查找确定 |
| entry_digest | 32字节公开账户入口上下文摘要，或null；注册／重置必填，登录后的换邮箱为null |
| group_id | UUID；换邮箱两行共用且purpose不同，其他每轮独立生成；用于两份验证不可混搭 |
| credential_version | 已有账户签发时的凭据版本快照，注册为null；版本变化使旧验证失效 |
| created_at／expires_at | UTC时间；保存本轮期限，重试不延长 |
| code | 按本轮配置长度生成的十进制字符串，保留前导0；短期明文，可为null；消费或失效后清空 |
| code_length／max_failed_attempts／rule_version | 本轮格式、错误次数上限及规则版本快照；校验与旧授权一致 |
| failed_attempts | 非负整数，初始0，按不同逻辑提交的错误校验次数原子递增 |
| consumed_at／invalidated_at | UTC时间或null；分别保存成功消费与重发替代／耗尽等失效事实，结束原因随审计记录 |
| delivery_rules | 本轮投递次数上限及重试间隔快照，供接管与重试沿用 |
| send_attempts／next_attempt_at | 实际发送尝试次数、下次可认领时间，未结束轮由任务规则维护 |
| lease_token／lease_until | 本次认领UUID及UTC租约截止时间，未认领为null；更新投递结果必须匹配token |
| sent_at | SMTP服务接受本轮邮件的首次已确认时间或null；不宣称收件人已收取 |
| last_delivery_error | 脱敏错误类别或null，保存网络／SMTP分类；不保存邮件正文、验证码或原始服务响应 |

主键、账户外键、(group_id,purpose)唯一；按purpose＋account_id＋邮箱规范化表达式、purpose＋entry_digest＋邮箱规范化表达式建立查询索引。scope是这些事实构成的查询条件，不新增scope_key列。约束：expires_at＞created_at、failed_attempts≥0、send_attempts≥0、有效code长度符合保存的code_length、已消费或已失效时code为null、租约token与截止时间成对存在。索引覆盖到期清理及 next_attempt_at／lease_until 的未发送任务扫描。当前有效状态、可认领状态及是否过期由方法计算；不存active、verified或delivery_status等派生列。

### 类方法与事务

| 方法 | 输入／结果及唯一规则 | 调用入口 |
|---|---|---|

Account.normalize_email对去首尾空白后的登录标识作大小写无关比较，账户唯一索引、邮箱锁及全部账户入口共用；实际投递仍使用保存的输入地址。规范化属于统一方法及索引表达式，不新增重复列；已有邮箱在迁移时核对重复归并风险。

锁域遵守C1：先所有账户资格锁，再SessionGuard行锁，再取得邮箱命名空间的事务级advisory锁（规范邮箱稳定散列为锁键，按实际锁键排序并去重），随后幂等占位；在业务锁之前按账户ID锁账户资料行、按id锁本用例全部邮箱验证行。匿名注册通过邮箱锁串行与邮箱占用变化协调；换邮箱先准备旧／新邮箱和两行记录。发现需要更早对象时整次回滚重规划。worker／到期清理只锁本表行，不在持有该锁时反向取得账户或Session锁。

### 申请、重发及公开账户入口

注册／忘记密码入口由服务端创建短期、签名保护的 `__Host-se_entry` HttpOnly／Secure／Lax Cookie，包含随机入口nonce、截止时间和CSRF凭据摘要；GET /account/entry-context提供对应CSRF值，状态变更校验Origin及请求头。与已有Session CSRF分开，访问账户入口不覆盖当前Session。入口nonce摘要绑定验证行和公开幂等作用域，不接受客户端自选entry_id；签名密钥通过后端配置提供。此签名用于入口完整性，与本轮验证码明文决定分别表达。

同次申请按入口或账户＋操作＋Idempotency-Key重放原请求ID及期限；敏感原码与SMTP内容不保存到幂等响应。不同键明确重发时，在同一scope的邮箱锁内使旧轮失效并清空code，再建立新轮。换邮箱重发作用域按account_id确定，与拟换入邮箱变化无关，成组重发旧／新两行并使该账户旧组失效，避免跨组拼接。注册创建账户前，账户与全部业务对象均不建立。

忘记密码申请对邮箱存在与否统一返回202及相同结构。邮箱不存在时返回无法命中真实行的请求标识及统一期限，不创建投递记录；后续提交统一验证失败。标识生成、响应结构及请求处理时间不暴露账户存在性，具体时延策略通过接口集成验证。注册使用已占用邮箱按BR-21返回明确EMAIL_IN_USE。

### 错误次数与同次重试

格式不合法在schema边界422，不累计；格式合法但不匹配时，专用验证用例在行锁内累计一次failed_attempts，并保存该逻辑提交的失败结果后提交；达到上限同事务失效并清空code。该分支返回422 VERIFICATION_CODE_INVALID，不能由普通BusinessError处理再次回滚计数。共用幂等结果存储按原键重放失败结果，同键重试不重复计数。

涉及密码及验证码的请求由专用输入摘要协议使用服务端密钥HMAC计算、保存算法及密钥版本；使用已有入口签名密钥派生独立用途子键，密钥可用期覆盖幂等保留期。日志、追踪、原始request dump及通用幂等表不保存密码／验证码原文。校验摘要仅用于区分同次请求负载，不作为验证码校验的第二份权威数据，也不引入验证码加密存储。

换邮箱先核对两行purpose、group、账户及当前旧邮箱；两个格式合法验证码在同一事务全部检查，对不匹配的行各累计一次，匹配行不提前消费。全部匹配时才原子消费两行、更新账户邮箱及必要审计；任何账户唯一性或后续写入失败均整体回滚。注册和重置遵循同一账户变更／消费提交边界。

成功消费后原码已清空，同次成功请求仍由幂等记录识别并按当前结果读取资格重放；旧入口提交不同键只能得到已使用／失效错误。重置成功后的同次请求可在原entry及请求键范围内取得原无敏感信息的成功确认，不以已变化的凭据版本重新执行重置。新密码与原码都不返回客户端。

### worker认领、发送与清理

1. 调度读取未投递且有效的行；短事务使用行锁及公共租约协议分配lease_token、lease_until，递增send_attempts；在事务内重查当前账户版本及is_sendable，随后提交。
2. 事务外发送SMTP。发送前重新读取行及当前版本并调用require_delivery_lease核对token、剩余期限、消费／失效事实；短时将收件地址与code加载到worker内存，SMTP网络超时及取消均显式处理。
3. 成功后短事务按lease_token条件记录sent_at并清理租约；失败记录脱敏类别、下次有限重试时点并释放租约；token已被接管时旧worker不覆盖新认领结果。进程在发送后、落库前退出时，后续认领可能重发同一个code，属于同轮重复邮件，不生成新轮或延长期限。
4. 重发、成功消费或到期可以与已开始的SMTP交错；本轮在数据库先失效后，外部已在途邮件可能到达，但其code不能再消费。若worker已读取原码，数据库清空不撤回其内存及在途邮件；worker在发送结束后释放内容引用，错误及日志采用字段白名单。
5. 发送成功只结束投递进度，code仍供用户校验。消费、替代、到期或失败次数耗尽时清空code；周期扫描兜底，业务校验始终先检查expires_at，清理滞后不会延长有效性。到达本轮投递尝试上限时停止自动发送并允许用户按新键重发；本轮已成功到达的code仍按原期限可用。

数据库备份可包含当时有效原码，随备份策略保留；历史恢复先隔离账户入口，批量失效恢复出的全部验证行、清空code及租约，再恢复worker和入口。应用数据库账户及worker只读取本流程所需字段，日志与审计不留code。记录归档时清除入口摘要、邮箱等非必要数据，保留期限采用阶段实际配置；交易、聊天与处置历史不使用本表清理规则。

## C2 实时事件、恢复与任务执行

### 业务事实、持久事件与Redis的分工

三类消息、通知、阅读进度、交易和事项分别由所属主体维护。C2只传递变更提示及稳定引用，读取正文、历史和动作仍调用主体接口及当前资格方法。传输ACK只推进本连接的投递游标，不修改聊天已读、通知已读、交易确认或待办。

| 数据／维护方 | 字段、约束及用途 |
|---|---|
| EventNamespace／公共事件能力 | 单例epoch UUID，标识本业务数据库当前事件世代；首次迁移建立，历史数据库恢复后轮换，各实例读取同一值 |
| AccountEventHead／公共事件能力 | account_id账户主外键、seq_head非负整数、replay_floor非负整数且≤seq_head；seq_head是账户事件事务序号基准，replay_floor是已删除连续前缀的边界 |
| UserEvent／公共事件能力 | event_id UUID主键；recipient_account_id外键；account_seq正整数；event_type具名类型；schema_version正整数；intent_key；source具名引用；origin_connection_id为已校验的来源连接UUID或null；occurred_at、created_at、expires_at UTC时间；同账户account_seq唯一，同账户intent_key唯一 |

UserEvent按(recipient_account_id,account_seq)及清理期限建立索引，派发按未发布及next_attempt_at／lease_until扫描。TaskSchedule按有效未完成的due_at、next_attempt_at及lease_until扫描；completed_at与cancelled_at至多一项非空，lease_token与lease_until成对存在，attempts非负。当前可派发／可认领由类方法计算，不额外持久化active、can_run等判断。具体公共数据汇总由C9采用本专题。

### 事件意图内部契约

```text
add_event_intent(tx, recipient_ids, event_type, source, intent_key, payload_ref) -> EventIntentBatch
persist_event_intents(tx, context, intents) -> list[PersistedEvent]
UserEvent.require_recipient(account) -> Allowed
UserEvent.project_for(context, source_qualifications) -> EventHint | CursorAdvance
```

add_event_intent将C1原占位返回类型细化为EventIntentBatch，固定返回items=[{recipient_account_id,event_id}]，按账户ID排序，单接收人也使用同一结构。每个接收账户生成稳定投递event_id；C3从对应item取得通知结果中的event_id。意图参数均由服务端用例构建，payload_ref为类型化主体引用及必要消息序号，不保存正文、验证码、Cookie、签名URL或举报身份。source／payload_ref是事件传输定位依据，不替代三类消息表各自明确外键；投影时解析引用并核对归属。

主体资格及触发成立后登记意图，与消息／通知／历史／审计共享同一事务。公共包装收集全部接收账户，按账户ID升序在C1最后锁域锁AccountEventHead，按用例的稳定因果次序分配account_seq并保存UserEvent；同一次事务中连续分配，回滚不推进seq_head。intent_key作用域固定到接收账户，冲突载荷拒绝并回滚，不按“已存在”忽略不一致意图。

business_event_id是系统消息与通知共用的业务来源，event_id标识每一份投递。不同接收人或不同子事件拥有不同event_id；重投沿用原event_id及account_seq。Redis的Stream ID仅是实例读取位置，不作为业务消息序号或客户端恢复游标。

### 事件提示schema及可见性

客户端事件外壳为 `{epoch,event_id,account_seq,event_type,schema_version,occurred_at,data}`；ID字符串、时间UTC ISO 8601、seq为0—9007199254740991范围内整数，数据库计数约束及接口schema一致。data按下表白名单构造，缺省字段省略，不用null伪造某种消息ID。

| event_type | data及来源约束 |
|---|---|
| message_created | conversation_kind=chat／trade／case、conversation_id、message_id、message_seq；系统消息可含business_event_id；不含正文，由对应类型消息查询接口获取 |
| message_read | conversation_kind、conversation_id、last_read_seq；仅本人其他连接同步，含发送成功推进；不发送给对端 |
| conversation_archived | conversation_kind、conversation_id；当前归档与原因由主体查询取得，不伪造message_id |
| notification_created／notification_read | notification_id；read事件可带首次read_at；前端依当前资格查询具体通知，不以事件代替标读 |
| source_changed | source类型及ID，按主体当前可见范围提示刷新；用于已登记且无会话／通知专用类型的变更 |

发送、补拉及正文读取均核对当前Session、账户及对应主体require_read／通知接收资格；事项还检查固定认领人及其当前管理资格。事件保存的接收人是创建时投递依据，不授予永久读取权。源对象不再可见时投影为CursorAdvance，帧只含epoch、from_seq、through_seq，不含原事件类型、对象或私有正文。扫描顺序覆盖连续账户序号，即使页面全部被抑制也可前进。

对发起已读／发送的当前连接，业务响应提供对应消息／权威阅读进度；C2对该连接的message_read投影为CursorAdvance，对本人其他连接保留提示。公共请求上下文以可选origin_connection_id关联该设备当前连接，服务端验证它属于当前Session；缺失时对本账户全部连接发送可去重提示。连接标识只是路由提示，不替代身份与主体授权。

### Redis发布、IM广播与缺口修复

公共派发器从数据库短事务认领UserEvent，提交后XADD到独立前缀下的实时Stream，条目仅含event_id、recipient_account_id和account_seq。XADD成功后按lease_token条件保存published_at。提交响应丢失或worker退出可以重复XADD，客户端及数据库均按稳定事件去重；不得以published_at推断每个客户端已收到。

每个IM实例以自己的XREAD游标读取同一实时Stream，针对本机当前连接分发；不把所有IM放入一个消费组分摊事件。实例启动先取得Redis当前读取位置，建立读取循环后再允许接入；已有连接的数据库补拉与定期seq_head核对覆盖读循环重启、Stream裁剪、Redis恢复或发布乱序。实例游标可保存在带实例启动标识的独立键；丢失时按当前尾部启动，并对本机连接执行数据库补拉。

每个连接只按account_seq连续交付；收到更大序号先从数据库补齐中间段，不跳过尚未扫描的序号。账户不同事务的Redis发布可能乱序，数据库序号决定展示提示次序；消息显示顺序采用所属会话message_seq。定期比较数据库head，发现Redis提示丢失也会主动补拉，修复不依赖下一条Redis事件到来。

派发失败采用有限快速重试；达到快速重试上限后保留持久记录及低频重试时间并告警，未过保留期的事件仍能从数据库补拉。数据库事件达到保留期限后清理不等于删除业务消息／通知历史。

| 成功响应 | hello_ok={connection_id,epoch,replay_floor,head_seq,heartbeat_seconds,max_frame_bytes}；连接持续推送event、cursor_advance及控制帧 |
| 失败响应 | 升级前401／403／429／503；升级后auth_required并关闭4401、权限失败4403、协议错误4400、配额4409、暂时故障4503；错误不含对象私有内容 |
| 前置与后置 | 身份与hello有效，原子取得账户／Session连接配额租约；注册本机连接，建立恢复游标；关闭或超时释放租约 |
| 并发与幂等 | 每次连接生成独立connection_id，重连可到任意IM；同账户多Session／连接分别维护游标；重复event沿用event_id |
| 事务 | 身份读取及配额操作采用有限超时，连接期间不持有数据库事务；入站控制和出站前重查身份，业务写入仍用C1 |
| 隐私 | 每次补拉按当前主体资格投影，正文经主体API读取；无权事件只推进序号；日志不保存Cookie、CSRF或消息正文 |
| 测试关联 | TC-COM-023—025、028 |
| 确认 | TASK-001编写；TASK-004提供R2a业务规则；公共契约交叉复核通过本批PR登记 |

控制帧：`resume={epoch,after_seq}`在快照加载后发起，服务端检查恢复范围后开始连续推送；`ack={epoch,through_seq}`、`ping={nonce}`、`pong={nonce}`。ACK必须是本连接已经连续发送／扫描的范围内单调值；超前值拒绝、重复或较小值保持当前进度。ACK只帮助背压及重连优化；不是聊天阅读，也不是Redis消费组XACK。客户端保存本账户当前epoch及连续处理游标；事件引用已入本地待刷新队列后才ACK，正文加载可独立重试。刷新提示去重不抹去持久业务记录。

首帧及最大帧长度、心跳超时、接收队列和未ACK窗口均有界；超过窗口暂停推送，持续超时关闭并要求按最后安全游标重连。控制帧不延长Session空闲期限。Session撤销／过期时停止受保护数据发送并断开；依赖暂时不可用时暂停投递并返回可重试控制错误，保留浏览器凭据。会话发送、业务确认及业务已读使用TASK-004／主体本域接口，本协议不另建第二套业务写规则。

### 初次加载、超期游标与事件保留

无cursor、epoch不符或游标越界时返回sync_reset及当前边界，并暂停本连接业务事件直至有效resume帧，客户端执行：先读取head得到H，再按主体API加载当前会话列表、通知、阅读进度及必要可见内容，随后从H恢复事件。H之后的并发变更可与快照重复，客户端按event_id、消息ID、会话seq及权威只增进度合并；资源变更提示触发重新查询当前事实，避免旧提示覆盖较新快照。加载期间连接可缓存有界提示，超界重新执行恢复，不静默跳过未扫描范围。

UserEvent采用有期限的传输保留，业务消息、通知及事项历史分别沿主体保留规则。清理只删除每账户已过期的连续序号前缀，锁AccountEventHead后更新replay_floor，同事务删除对应行；新配置不倒推已有expires_at。过期但被早序号保留阻挡的事件可留到下一轮，不造中间缺口。客户端ACK不触发其他设备事件的删除。历史数据库恢复轮换epoch，旧游标统一全量刷新，避免恢复前后序号重用造成跳过。

### 任务持久化、认领及执行结果

```text
schedule_task(tx, context, task_kind, source_ref, trigger_key, source_version, due_at, rule_version) -> TaskRef
ClaimableWork.try_claim(now, lease_token, lease_seconds) -> WorkLease | None
ClaimableWork.require_lease(token, now) -> Allowed
TaskSchedule.require_applicable(source, now) -> Allowed | Obsolete
complete_task(tx, lease, result_ref) -> TaskCompletion
```

trigger_key由来源事实及触发版本稳定构造，重复调度返回既有task_id；同键不同语义冲突。交易确认、冻结／恢复及超时的due_at与source_version由TASK-003保存的有效等待及规则事实提供，scheduler不重新定义业务期限。失效或被替代的触发由主体判定Obsolete，并在同次事务取消任务，不产生业务副作用。

任务执行适配器采用同组worker分担、消费者标识区分实例及启动周期。队列消息只传task_kind及持久记录ID；数据库是待执行的恢复依据。队列丢失、PEL被裁剪或调度进程退出时，数据库扫描重新投递有效到期记录。Redis组ACK用于确认队列条目处理，不替代数据库完成事实。

worker以短事务领取工作并提交lease_token及lease_until，外部执行在事务外；业务任务另开system用例，遵循C1账户资格、商品／交易／事项等锁序，最后在用户事件序号锁之前锁TaskSchedule并require_lease，调用主体require_applicable，原子保存业务、历史、审计、事件及completed_at。持有任务行锁到提交，接管方等待并重查；旧token拒绝提交。任意业务失败整体回滚，任务按当前状态有限重试并记录脱敏错误。任务执行不得在持有TaskSchedule行锁时反向取得更早业务锁。

队列条目在持久完成、持久取消、已保存下次重试时点或确认另有有效认领者后ACK；仅接收消息不ACK。达到自动重试上限后保留错误及可审查的持久记录、告警，按登记的原trigger及幂等依据人工重试。SMTP及Redis发布等外部副作用采用各来源状态协议允许同次重复，不能声称网络发送恰好一次。

邮箱投递直接由email_verification同表字段实现ClaimableWork，文件回收及事件派发也使用各自持久记录，不再为同一事实增加第二份TaskSchedule。TaskSchedule只承载需要独立时点／触发记录的通用业务任务。公共任务执行接口统一租约／token概念，避免把业务完成与broker投递结果混存。

### 连接配额、命名空间及参数输入

跨实例账户／Session连接额度通过Redis有期限的租约集合及原子脚本维护，租约集合使用Redis服务器时钟，数据库任务及事件使用数据库当前时钟；清理过期成员后同时检查两种额度，成功分配随机connection_id，续租及释放只作用本token。断连不及时释放由TTL收敛，Redis不可用时拒绝新连接并暂停受保护推送；实例回滚不复用启动标识。

### 主体端口、组装与执行层映射

采用[公共能力扩展边界](#interfaces-18)。C2声明EventSourceProjector.project(context, event, source_facts)，主体实现来源解析及当前资格投影，结果为EventHint或CursorAdvance。应用组装层按来源类型及schema版本绑定；C2负责序号、恢复、投递和背压，不导入主体实现。未知类型／版本不得跳过权限核对或静默丢弃，停止该段投递并报告依赖错误及告警；启动检查已启用来源完整性。

公共任务能力声明TaskHandler.prepare_dependencies(source_ref)、require_applicable(source_facts, now)和execute(transaction, context, source_facts)。主体实现锁依赖、触发适用性和业务变化，应用按task_kind绑定处理器。依赖先纳入C1 LockPlan；主体锁后重查适用性，随后按现有任务锁域验证token并同事务完成业务及任务事实。Obsolete同事务取消，旧token拒绝提交；处理器不得自行提前提交。外部副作用由相应来源协议在事务外执行。

Taskiq／RedisStreamBroker是Python候选执行适配器。稳定要求是独立IM读取、worker分担、持久待执行事实、租约接管、token约束提交及队列确认，不限定任务库API。Java映射使用同等队列／worker能力并验证命名空间、确认和恢复语义。新增处理器无需修改调度与租约核心流程；保留中的来源、任务及schema版本必须继续可解析。

### 规则与迁移检查清单

1. 字段来源逐项应用DATA-01—04：身份及归属只存必要事实，历史快照和版本有明确用途；本人概览、待办、管理统计、can_*及unread_count都通过查询／类方法取得，不新增持久镜像表。
2. 数据库唯一、外键、空值配对、期限与计数约束由迁移承载；用途大小、次数上限与期限参数由类型化配置及保存的快照校验。跨模块外键／引用采用主体实际模型后核对，不能以未交付字段假装已有迁移。
3. 按C1资格与业务锁序核对各关系创建、释放及清理；迁移测试验证失效与清理不会级联抹除历史、恢复不能重新授权，索引支持当前查询谓词。
4. PostgreSQL使用同一v2业务数据库，legacy与v2库名／用户独立；真实DDL、Alembic修订号及数据迁移命令随实现提供，当前交付为设计及检查输入。

实际验证采用TC-COM-033／034，并复用文件011—014、身份邮箱015—022、事件任务023—028及查询029—032的专题预期；对应运行环境与结果随编码任务登记。

### 扩展标识与技术栈映射

采用[公共能力扩展边界](#interfaces-18)。本模型的主外键、唯一性、保留及事务约束以PostgreSQL语义表达，持久化类、DDL迁移工具及框架由技术映射确定。FileRecord.purpose是服务端登记的稳定标识，首批公开product_image／case_evidence；其目标类型、策略和核验器由文件专题与应用组装定义。新增正式用途同步API schema与数据库适用约束，保持文件生命周期算法稳定。

### 内部能力签名

```text
attach_files(tx, context, target, purpose, file_ids, slot) -> list[FileReference]
retain_files(tx, context, source_target, target, file_ids, slot) -> list[FileReference]
release_references(tx, context, target, reference_ids, retention_basis) -> ReleasedReferences
prepare_file_read(context, target, file_id) -> AuthorizedFileRead
```

file_ids 为去重后的 EntityId 集合，数量由用途及主体规则检查；slot 为该资源具名图片／证据位置。target 由已授权主体用例提供，context 由服务端建立。

- attach_files 核对当前动作资格、文件为操作者所有、用途匹配、state=verified 及内容稳定；在同一事务建立引用，返回包含 reference_id 的完整 FileReference；相同有效关系重复建立时沿用已有 reference_id。
- retain_files 用于编辑历史等已有授权关联的保留，由主体证明 source_target 的读取与复制依据，核对原引用和用途，再建立新的历史引用。该入口以主体内部能力调用表达授权。
- release_references 按下述 RetentionBasis 核对主体保留规则，成功时在同一事务撤销整组指定关系并返回 ReleasedReferences；历史与证据继续由各自目标的有效引用保留。
- prepare_file_read 先由主体核对目标及引用的当前可见性，取得必要内容标识后在事务外签发短期只读 URL，返回 file_id、url、expires_at 及公开元数据。授权期限来自配置，URL 按持有者访问语义生效。

业务模块持久保存 file_id／引用，读取地址在获准查询时签发。文件使用关系及授权从主体读取，商品编辑历史和事项证据保留由各主体提出明确引用对象。

### 引用释放输入与结果

`reference_ids` 为去重后的 EntityId 集合，按数值升序处理；`target` 是本次获准维护的业务对象。空集合返回空的释放结果。RetentionBasis 由主体用例根据动作与规则构建，并由主体核对当前动作、对象状态和保留义务。

| RetentionBasis 字段 | 类型及含义 |
|---|---|
| action | 必填具名主体动作，如 product.image_replaced；值由该主体动作契约定义 |
| rule_refs | 必填且非空的规则引用集合，关联 BR／TR／UC 或人工决定记录 |
| basis_ref | ResourceRef 或 null；有处置决定等业务依据时指向对应对象，普通主体维护动作按其契约使用 null |
| preserved_targets | ResourceRef 集合；列出本次释放后仍承担历史或证据保留的目标，规则允许完全解除时采用空集合 |

主体用例核对 RetentionBasis 所引用的规则和依据；文件能力在文件锁内重查对应保留目标具有同一 file_id 的有效引用。该参数表达本次动作的保留依据，动作授权来自公共资格与主体规则。主体审计随本事务保存依据及关联对象。

| ReleasedReferences 字段 | 类型及含义 |
|---|---|
| target | 本次维护对象的 ResourceRef |
| released_reference_ids | EntityId 列表，按数值升序列出本次解除的全部引用 |
| affected_file_ids | EntityId 列表，去重并按数值升序列出涉及的文件；文件后续回收按到期及有效引用数判断 |

引用解除成功后，该 reference_id 结束其关系；同一文件随后在相同 target／slot 重新建立引用时分配新的 reference_id。当前引用关系与业务历史的引用分别维护。

| 调用情况 | 处理结果 |
|---|---|
| 全部引用属于获准 target，且保留规则满足 | 统一解除，返回完整 ReleasedReferences；主体变化、历史、审计及释放共用事务 |
| 部分 reference_id 不存在或位于其他目标的范围 | 统一抛出 RESOURCE_NOT_VISIBLE（404），本次整组变更回滚 |
| 规则要求的历史／证据引用尚未保留 | 抛出 FILE_RETENTION_REQUIRED（409），本次整组变更回滚 |
| 同一业务操作、同一幂等键重复提交 | 公共入口重放原业务响应并沿用 operation_id；后来建立的新引用保持原状 |
| 新操作再次提交已解除的 reference_id | 采用当前引用范围检查，返回 RESOURCE_NOT_VISIBLE（404） |

### 状态转换与数据约束

| 情况 | 结果 |
|---|---|
| 首次合法引用 | verified 文件保持内容标识，建立唯一引用关系 |
| 同一引用重复登记 | 返回已存在关系；同次业务结果按公共幂等契约重放 |
| 文件处于 uploading／cleaning／deleted | FILE_NOT_REFERENCEABLE（409） |
| 用途不匹配 | FILE_PURPOSE_MISMATCH（422） |
| 可见文件但归属或复制资格不符 | FILE_ACTION_NOT_ALLOWED（403） |
| 文件位于当前可见范围外 | RESOURCE_NOT_VISIBLE（404） |
| 内容核验尚待完成 | 按核验结果维持 uploading，业务引用返回状态冲突 |

删除商品展示或替换图片时，由主体规则确定当前引用与历史引用的保留。回收选取到期且所有有效引用均已解除的文件。

### 锁顺序与事务边界

主体用例通过 prepare 以授权 target 读取候选引用及 file_id，登记到 LockPlan；在写事务先取得资格及业务对象锁，再依第6级子序按 file_id 升序锁文件登记行、重读引用，并按 reference_id 升序锁既有引用行后校验和变更。attach／retain／release 与主体数据、历史、审计及事件共用事务；全部文件集合在进入文件锁域前确定；补充更早对象按公共重规划流程执行。

回收服务按 file_id 锁定登记行，在同一事务再次检查到期、状态和有效引用，认领 cleaning 后提交。此后执行 OSS 删除，成功后保存 deleted；删除失败保留 cleaning 进度重试。业务引用与回收通过同一登记行锁排序，回收认领后新的引用得到状态冲突。

### 超时、重试与异常恢复

OSS 核验、签名、删除在网络边界按配置处理超时及重试，上传完成核验接口以 file_id 对应登记的授权及内容核验事实推进。verified 的就绪条件是已核验且内容稳定；Q-002 选择独立对象键及签名禁止覆盖，具体上传及核验接口见[文件上传](#interfaces-12)。引用方以该就绪条件设计业务关联，文件上传实现按 Q-002 的评审结论准入。

### 规则版本

授权保存用途、有效期和当次大小／格式规则及版本；核验依照该授权。回收任务读取已保存期限，引用数量等业务规则按具体用例和当前配置校验。配置模型及 .env.example 随实现建立。

### 第2批：清理边界及迟到上传

回收候选包含到期 uploading、到期且无引用的 verified 及 cleaning 重试。文件行锁内统一检查所有有效引用和 cleanup_after，并要求当前时间晚于 upload_expires_at；引用与回收的竞争继续使用同一行锁。清理删除仅由回收角色执行；含有效引用的对象和历史引用对象保持。

OSS 删除发生在认领 cleaning 的事务提交之后，失败按配置重试，成功或对象不存在时登记 deleted。deleted 记录作为墓碑保留原对象键和授权截止时间；完成核验及任何引用均拒绝推进该记录。周期扫描 cleaning／deleted 的对象键，发现迟到对象再次删除，记录最近尝试时间和 OSS request_id。该扫描同时处理上传请求在授权到期前开始、在清理后才落地的情况；临时失败保留可重试记录，持续失败进入运维告警。

墓碑及对象键索引作为去重与迟到清理的必要技术数据保留；后续归档迁移保留这些事实。应用业务对象不重新使用任何已分配 key，运维清理和 OSS 生命周期规则以本协议为依据，避免直接删除仍有引用的对象。

### 文件端口与业务策略组装

采用[公共能力扩展边界](#interfaces-18)。C3声明FilePurposePolicy及ContentVerifier端口，商品／事项模块实现业务策略，内容解析适配器实现核验器，应用组装层绑定purpose、允许target类型、策略、核验器及规则schema。现有product_image与case_evidence为首批公开用途。新增用途更新实现、组装和正式API能力声明，上传、状态转换、引用及回收核心流程复用。

| 端口操作 | 输入、结果及调用阶段 |
|---|---|
| FilePurposePolicy.prepare_dependencies(action, context, target) | 返回所需主体引用及锁模式，纳入C1 LockPlan；null target必须定义创建前上下文及资格来源 |
| FilePurposePolicy.require_action(action, context, facts) | action为create／complete／attach／retain／read／release；显式锁后事实用于写动作，读取使用当前可见性事实；返回Allowed或既有具名业务错误 |
| ContentVerifier.verify(content_stream, saved_rules) | 事务外按保存的规则及资源预算处理实际字节，返回核验元数据或FILE_CONTENT_INVALID；不查询业务资格 |

FileUpload.require_create／require_complete作为公共编排入口委托对应策略；FileRecord负责归属、状态、用途一致、期限及内容稳定，C3负责引用与保留目标一致性。主体策略维护发布／编辑、参与、认领、受限沟通及历史保留的判断。retain与release继续采用主体提供的来源及RetentionBasis，并由C3核对引用事实。策略依赖在文件锁前确定，锁后重查；核验器完成不代替业务授权。

启动检查用途标识唯一、策略与核验器齐全、目标类型及规则schema匹配。未知用途采用422 INPUT_INVALID；错误目标采用既有用途／可见性错误。旧授权使用保存的规则版本，适用核验器需保留至存量授权处理完毕；停用用途时明确新授权与已有授权／引用的处理，不使历史引用失去解析能力。

#### OSS 表单与签名条件

后端使用官方 SDK 的 PostObject V4 签名，返回固定 Bucket HTTPS 入口及完整字段。policy 固定 expiration、Bucket、精确 key（不使用客户端前缀匹配）、x-oss-forbid-overwrite=true、x-oss-object-acl=private、声明 MIME 对应的 x-oss-content-type、success_action_status=204、V4 签名字段及适用的 STS token 条件；content-length-range 限制为本次 declared_size。用途格式由后端能力规则校验。对象键由后端随机生成，包含环境／用途隔离前缀；数据库唯一约束，永不复用，客户端无法自选或补签另一个键。

客户端向 OSS 提交同一表单及一个 file 字段。首次成功返回204；同键再次上传由 OSS 返回 FileAlreadyExists，客户端随后调用完成接口查询核验结果。网络中断时可在有效期内重用同一表单；若原对象已经存在，直接进入完成核验。修改 MIME、大小、key、ACL、禁止覆盖字段或签名策略均须被拒绝。声明 MIME 只提供预筛选，后端核验实际字节后才允许业务引用。

#### 实际内容核验

从登记中的 Bucket／key 获取对象，读取实际字节，核对长度与声明值及授权用途上限、检测实际类型并核对其与声明 MIME 一致；图片使用受限解码核对格式、尺寸及像素预算，证据按用途允许的格式作相应解析。后端流式计算 SHA-256，检查读完整性及读取前后的对象标识；PostObject ETag 仅作对象变化标识。内容不合法返回 FILE_CONTENT_INVALID 并保持 uploading，原对象保持禁止覆盖；重新选择文件需要新上传授权，原登记按期限清理。

核验所得 content_identity 为内部 {bucket, object_key, etag, sha256}；etag 用于变化检测，sha256 是后端对字节的摘要。读取失败或校验前后变化保持原状态并返回对应错误。上传阶段无删除权限，应用仅由回收能力删除无引用对象；对象维护工具遵循相同协议。非法对象留存受暂存清理和上传配额约束。

#### 正常、失败和重复调用

正常：创建授权 → OSS 首次上传 → 完成核验 → 主体写入时 attach_files → 主体查询时签发读取地址。完成响应丢失：原键重试返回同一文件核验事实；不同键也不创建第二份核验及引用。上传响应丢失且重复上传返回409：调用完成接口核对已有对象。OSS 暂时故障：返回503并保留 uploading；到期后重新创建授权。

上传授权 expires_at 是允许进入 verified 的完成期限。接近到期才完成传输的对象可能无法及时核验，客户端使用新授权重传；verified 文件之后按业务引用及保存的回收期限管理，上传授权到期不撤销已有有效引用。

### 系统消息、通知及 C2 的交界

依据 [R2a review 修订](https://github.com/iy88/se-course-project-1/pull/43)，交易系统消息与通知使用同一稳定 business_event_id 和原业务记录；各投递 event_id 分别稳定，不能将不同投递误作同一事件。消息按业务事件唯一，通知按 intent_key 及接收账户幂等，不凭消息接收双方扩大通知范围。业务、消息、通知、审计及持久事件同一事务，最后统一分配账户事件序号；提交后派发失败重试。具体业务记录类型由 TASK-003 主体模型绑定，不声明已完成绑定。

C2 采用 conversation_kind（chat／trade／case）与对应 conversation_id 路由传输，数据库消息仍使用各自明确外键。已读事件仅发本账户其他连接，包括发送成功触发的游标推进。本人发送成功推进至本消息序号并清除较早未读，系统消息不推进任一方已读；归档历史仍可推进已读。传输恢复以数据库序号补拉、投递去重及当前资格重查为依据，事项事件仅到相关用户及固定认领且当前有管理资格的管理员。完整 C2 协议随本任务第 4 批交付。

### 通知来源端口与技术映射

采用[公共能力扩展边界](#interfaces-18)。通知核心声明NotificationSourceView.project(context, notification, source_facts)，返回获准summary及可空source；主体模块实现来源解析与可见性规则，应用组装层绑定来源类型、业务事件、模板schema和版本。C2事件投影复用同一主体资格定义，通知的接收归属与已读仍由通知模块维护。来源不可见时按本接口保留获准事件提示并隐藏跳转；不得把通知历史误按C2游标抑制规则处理。缺失／重复绑定在能力启用前拒绝，运行时依赖不可用返回503。账户、邮件及Session操作以概念类型及事务语义定义，框架和任务库由技术映射选择。


### C9通知与传输数据交界

Notification保存业务event_type、模板、来源与首次已读事实；传输事件按C2投影为notification_created／notification_read并引用notification_id。创建结果的event_id由对应接收人的事件结果取得，不在Notification保存反向event_id或复制未读总数。business_event_id输入及公共数据关系见[公共数据模型](#interfaces-10)；C2评审输入为PR #48。

R1 涉及商品占用、请求关闭和交易会话三类联动；请求与交易在同一记录中表达。商品字段、会话字段、调用签名与锁集合由 R0／R2a 及第 4 批适配定义，本文件不重复。

#### 术语与边界

- **商品占用**：一笔已接受且未结束的交易对商品的排他锁单关系；同一商品同时至多一笔占用。占用由商品模块保存，交易模块保存持有占用的交易标识。
- **有效交易**：状态为进行中、有争议或异常交易的交易；只有有效交易持有商品占用。已完成／已终止／已拒绝／已撤回／已关闭不持有占用。
- **请求结束**：待接受请求因接受其他请求（转已关闭）、拒绝（转已拒绝）、撤回（转已撤回）、商品生命周期下架、撤销公开访问或相关账户封禁（转已关闭）而结束；按结果与原因记录。
- **交易会话**：每笔有效请求／交易唯一对应的会话；请求被判拒绝、撤回、关闭或交易结束时归档。
- 具体字段、调用签名、锁集合和会话消息结构在第 4 批细化；管理事项状态机由 TASK-004 定义；本文件只定义 R1 的业务事实、结果和通知范围。

#### 能力契约

R1 包含以下五项能力，触发、结果、事务位置和通知范围一并列明。

| 能力 | 触发事实 | 调用方 → 维护方 | 业务标识 | 前置与状态重读 | 成功结果 | 具名失败／冲突 | 事务与锁位置 | 通知与幂等 |
|---|---|---|---|---|---|---|---|---|
| 取得商品占用 | 卖方接受一条待接受请求 | 交易用例 → 商品模块（R0） | product_id、trade_id、actor_account_id | 商品公开可交易且无其他有效占用；请求为待接受；锁商品后重读状态与占用 | 商品交易中，占用持有者为 trade_id | OCCUPANCY_CONFLICT；PRODUCT_NOT_AVAILABLE；REQUEST_ALREADY_ENDED（请求已拒绝／撤回／关闭） | 同一事务；账户资格锁 → 幂等占位 → 商品行锁 → 重读 → 交易行锁；商品先锁、状态重读 | 通知请求买方接受结果；被关闭请求的买方关闭原因；以接受动作幂等键定位 |
| 释放商品占用 | 交易完成、有效取消／协商终止、管理调整结束 | 交易用例 → 商品模块（R0） | product_id、trade_id、结束依据 | 占用持有者必须等于 trade_id；锁商品后重读占用；商品按结束规则置默认下架；卖方是否继续上架另行处理 | 占用解除；商品按结束规则置默认下架；继续上架由卖方另行选择，不在本能力内 | OCCUPANCY_NOT_HELD；STATE_CONFLICT（版本变化） | 同一事务；账户资格锁 → 幂等占位 → 商品行锁 → 交易行锁；释放与交易终态同一提交 | 通知双方交易结束与商品默认下架的结果；在卖方的结束通知中附重新上架提示；完成时的评价入口由 T1 提供；以结束动作幂等键定位 |
| 关闭待接受请求（非拒绝／撤回） | 接受一条请求（关闭同商品其他待接受请求）；商品生命周期下架；撤销公开访问；相关账户封禁；管理处置撤销公开 | 交易用例 → 交易模块（本域） | product_id、trade_id（被关闭请求）、原因码、触发来源 | 请求必须为待接受；接受场景下同商品其他待接受请求一并关闭；原因与实际触发一致 | 请求转已关闭，原因记为其他用户锁单／商品已下架／公开访问已撤销／相关账户被封禁；不计失败交易 | REQUEST_ALREADY_ENDED；STATE_CONFLICT | 同一事务；随接受或关闭动作在同一交易锁集合内完成；逐请求按 ID 升序 | 通知每个被关闭请求的买方；封禁场景同时通知双方；由业务动作触发，不单独接受客户端幂等键 |
| 创建交易会话 | 有效购买请求创建成功（BR-01） | 交易用例 → 会话模块（R2a） | trade_id、product_id、buyer_id、seller_id、trade_conversation_id | 同一事务已写入待接受记录；同一 trade_id 无分支时创建，已有分支返回原分支并由入口打开，不重复创建；分支创建失败不得留下无分支请求 | 返回唯一 trade_conversation_id；已有分支返回原分支；分支与系统消息同事务写入；交易保存标识 | TRADE_CONVERSATION_CREATE_FAILED | 同一事务；交易记录写入后调用；分支创建在会话子域锁内；失败整体回滚 | 通知卖方新请求；系统消息定位请求与分支；按 trade_id 唯一，重试返回已有 trade_conversation_id |
| 归档交易会话 | 请求拒绝／撤回／关闭；交易完成／终止；管理调整结束 | 交易用例 → 会话模块（R2a） | trade_id、trade_conversation_id、结束原因 | 分支存在；归档幂等，重复调用返回既有结果；归档不删除消息、已读和历史 | 分支只读；历史保留；不自动重开；普通私聊不受影响；冻结不归档 | TRADE_CONVERSATION_NOT_FOUND | 同一事务；在请求或交易结束写入后调用；会话子域锁内；失败整体回滚 | 归档本身不通知；结束动作按通知表通知对方、受影响买方或双方；按 trade_conversation_id 唯一，重复归档返回既有结果 |

拒绝、撤回是独立请求动作，分别转已拒绝、已撤回，不经过“关闭待接受请求”能力；已拒绝、已撤回、已关闭均不计失败交易。

#### 动作触发矩阵

| 业务动作 | 商品占用 | 请求结果 | 交易会话 | 通知 |
|---|---|---|---|---|
| 提交购买请求 | 不变 | 不关闭 | 创建该笔分支 | 卖方：新请求；关联商品、请求、发起人及时间 |
| 接受请求 | 取得 | 同商品其他待接受请求全部关闭 | 保持 | 请求买方：已接受；被关闭请求的买方：关闭及原因 |
| 拒绝请求 | 不变 | 本请求结束（已拒绝） | 归档 | 请求买方：已拒绝及原因 |
| 买方撤回 | 不变 | 本请求结束（已撤回） | 归档 | 卖方：已撤回；买方获即时反馈 |
| 下架／撤销公开／账户封禁导致关闭 | 待接受请求不占用，不释放；已有有效交易占用保持，按冻结／处置处理 | 仅关闭相关待接受请求；进行中交易不转已关闭、不终止 | 仅归档被关闭请求的分支；有效交易会话不归档 | 下架／撤销公开：受影响买方；账户封禁：双方；注明实际原因 |
| 双方完成确认 | 释放 | 不变 | 归档 | 双方：完成、商品已下架、评价入口 |
| 首约前买方直接取消 | 释放 | 不变 | 归档 | 双方：已终止及原因 |
| 卖方申请取消／约定后协商取消 | 生效后释放 | 不变 | 生效后归档 | 待同意方：申请；生效后双方：已终止 |
| 取消申请拒绝／撤回 | 不变 | 不变 | 不归档 | 拒绝时通知提案方；撤回时通知对方；交易继续 |
| 发起争议 | 保持 | 不变 | 不归档 | 详情显示有争议；不新增用户通知；管理事项由 R2b 处理 |
| 争议解决恢复进行中 | 保持（继续锁单） | 不变 | 保持原状；不归档、不重开 | 自行解决：详情可见、不另发；管理解决按 4.17 管理调整通知双方 |
| 争议中双方同意终止 | 释放 | 不变 | 归档 | 双方：已终止及原因；争议记录保留 |
| 单方确认超时转异常 | 保持（不释放，异常仍锁单） | 不关闭 | 不归档（冻结不归档） | 双方：异常、冻结、暂停上架及交易操作、禁止双方 IM、管理沟通入口、剩余其他限制 |
| 处置／封禁冻结 | 保持 | 不关闭（待接受请求按封禁另关） | 不归档 | 双方：冻结原因、限制范围、沟通入口 |
| 解冻 | 保持 | 不变 | 不归档 | 双方：解除及剩余限制 |
| 管理调整结束 | 释放 | 不变 | 归档 | 双方：前后状态、原因、剩余限制 |
| 管理恢复进行中（异常／争议） | 保持（继续锁单） | 保持已接受（不回退待接受） | 不重开原分支 | 双方：恢复及依据 |

每笔已接受交易结束时，在卖方的现有结束通知中提示「商品已下架。如需继续出售，可前往商品详情重新上架。」提示面向卖方，随现有业务通知登记一次。卖方随后通过 API-PRD-008 提交独立上架操作，按请求时的审核、账户和展示限制校验。

未结束交易的管理恢复不启动等待计时；恢复后任一方重新提交完成确认，才重新开始完整等待。

#### 结果语义

| 结果 | 语义 | 使用场景 |
|---|---|---|
| OCCUPANCY_ACQUIRED | 占用取得成功 | 接受请求 |
| OCCUPANCY_RELEASED | 占用释放成功 | 完成、终止、管理调整结束 |
| OCCUPANCY_CONFLICT | 同商品已有其他有效占用；本次事务不写入占用、交易或分支（并发失败方的请求状态可能已由成功方接受动作关闭，不属于本次写入） | 并发接受 |
| PRODUCT_NOT_AVAILABLE | 商品生命周期或展示资格不允许首次接受取得占用 | 接受请求 |
| OCCUPANCY_NOT_HELD | 释放时占用持有者不是本交易 | 释放竞态 |
| REQUEST_CLOSED | 请求按实际原因关闭 | 接受关闭其他请求、下架／撤销公开／封禁关闭 |
| REQUEST_ALREADY_ENDED | 请求已结束（拒绝／撤回／关闭），当前动作不可执行；同键重试由 C1 幂等重放 | 对已结束请求再次操作 |
| TRADE_CONVERSATION_CREATED | 分支创建成功，返回唯一 trade_conversation_id | 请求创建 |
| TRADE_CONVERSATION_REUSED | 已有分支，返回原分支，不重复创建 | 分支已存在时的重复进入（同键重试由 C1 重放） |
| TRADE_CONVERSATION_ARCHIVED | 分支归档成功，返回归档结果 | 请求或交易结束 |
| TRADE_CONVERSATION_ALREADY_ARCHIVED | 已归档，返回既有结果 | 重复归档／补偿重放（同键重试由 C1 入口重放，不进入本结果） |
| TRADE_CONVERSATION_CREATE_FAILED | 会话侧创建失败，业务事务回滚 | 分支创建失败 |
| TRADE_CONVERSATION_NOT_FOUND | 分支不存在，无法归档 | 数据不一致或错误调用 |

接口层把具名结果映射为稳定错误码与 HTTP 状态；错误码在第 3 批接口文件中登记，不在此重复。

#### 不变量

1. 同一商品同时至多一笔有效交易；待接受请求不占用商品。
2. 占用的持有交易必须是该商品的有效交易；占用只由该交易结束（完成／终止）或认领管理员有依据调整而释放，商品模块不得自行释放。
3. 接受请求、关闭其他待接受请求、取得占用、保持请求创建时已建立的分支、登记通知意图在同一事务提交；占用、交易、其他请求关闭、分支或通知意图的持久化失败整体回滚。其他待接受请求已结束时按幂等跳过，不因并发关闭使本次接受失败；通知投递失败发生在提交后，不回滚业务。
4. 同一交易只有一条分支；分支不因冻结解除或交易恢复自动重开；归档保留消息、已读与历史。
5. 冻结不释放占用、不改变生命周期状态、不终止交易、不归档分支；暂停双方上架及交易操作、禁止双方两类 IM，只读与管理沟通保留；等待计时暂停／续算见 T1。
6. 交易结束（完成／终止）时释放本笔占用，并解除本笔交易名下的全部冻结记录；其他交易的有效冻结与账户封禁继续。商品默认已下架；卖方在无其他限制且符合资格时另行选择继续上架。
7. 商品及交易时内容在接受请求时形成不可变快照；提交请求时不建快照，后续商品编辑不改变历史内容。
8. 已完成／已终止保持终态；管理员也不能恢复或改写终态，返回 TRADE_TERMINAL。恢复仅适用于未结束交易，仍持原占用；有争议／异常恢复与解除冻结分别校验，恢复不启动计时。
9. 待接受请求无自动有效期；普通商品编辑（标题、描述、图片、价格、分类等）不关闭已有请求；商品下架、撤销公开访问、账户封禁仍按关闭规则处理。
10. 请求或交易结束时保留请求结果、确认、约定、争议及管理依据历史，不物理删除。
11. 同一交易至多一条生效约定、一条待决取消、一条未解决争议；每方至多一条当前完成确认，历史只增不减。
12. **完成与终止均保留双方当前确认**；变更生效、争议解决、管理恢复时清空当前标记并保留历史；终止后的“当前”仅表示最后一次有效声明，不表示待完成。
13. 等待计时每交易至多一条活动记录；冻结暂停、解冻续算，变更／争议／终止／超时结束。
14. 存在未结束有效交易时，卖方不得下架商品；R0 必须拒绝并保持占用。

| 归档交易会话 | R2a 会话模块 | `archive_trade_conversation(tx, context, trade_conversation_id, trade) -> TradeConversation` | 终态消息写入后；同一事务 |
| 冻结／解冻交易 | R2b 事项与交易模块 | 认领管理员持事项依据；交易侧写 `TradeFreeze`，不改变生命周期 | 交易锁、事项锁后；会话锁前 |
| 管理调整／未结束恢复 | R2b 事项与 TASK-003 交易 | 校验 case_id、认领人、依据；终态拒绝；恢复只回进行中 | 商品锁（结束时）→交易锁→事项锁→会话锁 |
| 通知接收范围 | C3 通知模块 | R1 表登记事件与接收方；C3 生成模板、intent_key、已读 | 同事务登记意图；提交后投递 |

R0 0.1.2 的释放占用以 R0-3 的能力为调用契约（product_id、trade_id、结束依据）；具名方法由 R0 实现，本文件不另造方法名。R2b 0.1.3 提供事项认领、事项依据与处置目标边界；冻结、解冻、状态调整、评价内容移除的具体 action 名待 TASK-004 0.3.0 按 CHG-001 更新并合并后绑定。当前 T4 按 R2b 通用请求（case_id、enforcement_id、action、target_ref、basis_ref）与事项边界对接。

#### 接受请求调用顺序

1. 账户资格锁后重读买方、卖方资格；校验商品未被删除。
2. 幂等占位后锁商品行，读取 `ProductStateView`；重读生命周期、`Product.has_valid_review(audits)`、展示限制与 `occupancy_trade_id`。
3. 调用 `Product.require_acquire_occupancy`；不通过返回 `PRODUCT_NOT_AVAILABLE`／`OCCUPANCY_CONFLICT`。
4. 锁本交易及同商品其他待接受请求；按 ID 升序收集、排序，避免逐请求跨域取锁。
5. R0 取得占用；交易转进行中；写快照。
6. 读取本交易既有 `TradeConversation`（trade_id 唯一）；接受不新建，缺失按数据不一致失败。
7. 关闭其他待接受请求，逐条写请求结果、系统消息与通知意图。
8. 为接受事件生成 `business_event_id`，`append_trade_system_event` 写 `request_accepted`；被关闭请求各写 `request_closed`。
9. 登记通知意图；提交事务；提交后投递。
10. 任一步持久化失败整体回滚；其他请求已结束按幂等跳过。

#### 结束调用顺序

1. 锁账户资格；锁商品行，重读占用；锁交易、会话；`Trade.require_transition` 终态校验通过后继续。
2. R0 释放占用（product_id、trade_id、结束依据）；商品默认下架。
3. 结束计时；保留双方当前确认；解除本笔交易全部冻结。
4. 生成终态 `business_event_id`；先写最后业务消息，再 `archive_trade_conversation`。
5. 写状态历史、通知意图；提交；提交后投递。
6. 终态后拒绝再次调整；`TRADE_TERMINAL` 不改变任何对象。

#### 恢复调用顺序

1. 仅未结束交易（有争议／异常）允许；终态拒绝。
2. 锁交易、事项、会话；校验认领人、依据；不重新取得占用、不重开会话、不解除冻结。
3. 清空当前确认、结束原计时、写历史与 `trade_restored` 系统消息；不启动计时。
4. 任一方重新提交完成确认后，才启动完整等待。

#### 失败与幂等

- R0：`PRODUCT_NOT_AVAILABLE`、`OCCUPANCY_CONFLICT`、`OCCUPANCY_NOT_HELD`、`STATE_CONFLICT`；映射为 R1 结果。
- R2a：`TRADE_CONVERSATION_CREATE_FAILED`、`TRADE_CONVERSATION_NOT_FOUND`；创建／归档失败整体回滚；重复调用返回既有会话／归档结果。
- R2b：事项未认领、无依据、终态目标返回业务错误；不改变交易。
- 系统消息按 `business_event_id` 唯一；通知按同一事件与接收账户去重；同键重试由 C1 重放。

### 通用请求与结果

| 项目 | 内容 |
|---|---|
| 请求方 | 事项用例；动作发起人必须是该事项当前认领管理人（`claimed_manager_id`），由事项在调用前校验 |
| 请求字段 | `case_id`、`enforcement_id`（本次执行标识）、`action`、`target_ref`（`resource_type` + `resource_id`）、`basis_ref`（决定与证据引用集合）、`requested_by`、`requested_at`、`expected_result` |
| 前置 | 事项处于 `claimed` 且已有决定；`basis_ref` 非空；目标对象存在且当前状态允许该动作 |
| 成功结果 | 具名结果：`action`、`target_ref`、`result_ref`（目标主体记录标识）、`previous_state`、`current_state`、`affected_scope`（实际受影响对象集合）、`occurred_at` |
| 失败结果 | 具名错误；目标主体不变，整次事务回滚 |
| 重复请求 | 同一 `enforcement_id` 重放返回原结果；同事项同动作同目标已生效时返回既有 `result_ref`，不重复记录限制或重复通知 |
| 事务 | 与事项决定同一用例事务；目标主体写入、事项执行关联、通知意图与审计同次提交；实时与外部副作用在提交后推进 |

`expected_result` 只表达业务预期，不作为目标主体可用性的判断依据：实际可执行性由目标主体在取得锁后按当前状态重新判定，不符即返回具名错误，事项改为记录未执行及原因。

### 账户限制

| 动作 | 目标 | 预期结果 | 具名错误 |
|---|---|---|---|
| `restrict_account` | 账户 ID | 账户模块按来源分别记录限制（类型、原因、依据、执行者、生效时间）；不同来源可同时生效，同一来源重试沿用原限制；用例协调该账户参与的待接受请求按 D-52 关闭并归档对应分支、未结束交易按冻结规则处理、双方通知；实际受影响范围写入 `affected_scope` | `BASIS_REQUIRED`、`OWNERSHIP_MISMATCH` |
| `lift_account_restriction` | 账户 ID、限制记录 ID | 记录解除时间、解除人与依据；按当前资格恢复权限及因该处置停止的展示；其他有效限制保留；不将原非在售商品变为在售 | `RESTRICTION_NOT_ACTIVE`、`BASIS_REQUIRED` |

### 商品与评论内容

| 动作 | 目标 | 预期结果 | 具名错误 |
|---|---|---|---|
| `withdraw_public_access` | 商品 ID | 商品停止公开展示但不改变生命周期；该商品待接受请求按 BR-02 关闭并记录原因；相关收藏按失效提示处理；通知卖方 | `TARGET_STATE_CONFLICT`（已撤销公开访问） |
| `remove_content` | 评论 ID 或评价 ID | 逻辑删除违规内容并保留原文、作者、时间与处理依据；不连带撤销无关商品公开访问；通知作者 | `TARGET_STATE_CONFLICT`（已移除）、`CONTENT_NOT_FOUND` |
| `restore_display` | 商品 ID | 仅恢复原展示资格，不重审、不将处置前非在售商品恢复为在售；与商品当前生命周期及交易占用分别判断 | `TARGET_STATE_CONFLICT`（无需恢复） |

### 交易与评价

| 动作 | 目标 | 预期结果 | 具名错误 |
|---|---|---|---|
| `freeze_trade` | 交易 ID | 交易模块记录进度暂停标记，暂停双方交易操作与计时、保留当前完成确认与已用等待时间；禁止该对用户之间普通私聊与全部交易分支发送（历史可读），不影响双方与第三方会话；通知双方原因、范围与处置沟通入口 | `TARGET_STATE_CONFLICT`（已结束或已冻结） |
| `lift_trade_freeze` | 交易 ID、冻结依据 | 解除指定冻结；仅当原确认仍有效时续算剩余等待时间；其他有效冻结或账户封禁继续生效 | `TRADE_FREEZE_NOT_ACTIVE` |
| `adjust_trade_status` | 交易 ID、目标状态 | 按 BR-08 有依据调整未结束交易的状态，记录前后状态、执行人、时间与原因；已完成、已终止交易保持终态，不接受恢复；不伪造用户确认；仅恢复未结束交易，保留原占用，解除冻结另行处理 | `TRADE_TERMINAL`（已完成或已终止）、`TRANSITION_NOT_ALLOWED`（未结束交易的转换条件不满足）、`BASIS_REQUIRED` |
| `remove_evaluation_content` | 评价 ID | 逻辑删除违规评价并保留依据；不改变交易结束状态与统计口径 | `TARGET_STATE_CONFLICT` |

冻结不等于交易结束，也不产生分支归档；交易进入已完成或已终止时自动解除本笔冻结并通知（4.15、BR-33）。解除非结束状态冻结须认领管理员有依据处理。

### 事项线程

事项线程的读取与发送由[会话与处置事项](design/detailed-design/key-designs/会话与处置事项.md)维护，本专题只确认执行结果对线程的影响：实际处置与冻结、状态调整须通知受影响者并给出处置沟通入口；线程不随交易结束归档，随事项结案归档。买卖双方 IM 的限制由 `freeze_trade` 与 `restrict_account` 的结果表达，不在线程侧另存状态。

### 事务与锁序

| 顺序 | 内容 |
|---|---|
| 1 | 账户资格锁：操作者、目标账户及受影响双方，按账户 ID 升序取所需最强模式 |
| 2 | 幂等占位：操作者＋操作类型＋请求键 |
| 3 | 商品行：目标商品及同商品其他受影响对象，按商品 ID 升序，锁后重读展示与占用 |
| 4 | 交易行：目标交易及同商品其他交易，按 ID 升序；单商品场景在商品锁内确定集合 |
| 5 | 处置事项行：按事项 ID 升序，重查认领与当前状态 |
| 6 | 会话子序：会话 → 分支 → 参与关系 → 消息 → 已读进度 |
| 7 | 用户事件序号：接收账户按 ID 升序分配并保存通知事件 |

执行目标在决定后才扩展时（例如封禁导致该账户其余待接受请求进入范围），按公共重新规划流程整事务重做，不在第 5 级锁内回取第 3、4 级（[公共事务与权限](#interfaces-06)）。每个动作列出自身涉及的锁域集合，调用方按本表组织，主体维护自身数据。

### 通知与审计

| 触发 | 接收与内容 |
|---|---|
| 冻结、解冻、状态调整 | 交易双方；原因、实际限制或恢复范围、剩余其他限制及处置沟通入口 |
| 封禁、解除 | 受限账户；原因、范围、恢复结果及沟通入口；D-52 关闭的请求另通知双方 |
| 内容移除、撤销公开访问 | 受影响作者或卖方；原因与可查看入口 |
| 举报处理确认 | 举报人；可公开结论与原因，不披露他人私人消息、申辩内容或管理员信息 |

审计记录动作、目标、前后状态、依据引用、执行者与时间，不记录消息正文与证据内容（ADR-009）。通知意图与业务同事务保存，投递在提交后推进；重复执行不重复发送同一意图（[账户与通知](#interfaces-13)）。

### 幂等与错误

- 幂等作用域为 `(actor_id, operation_name, idempotency_key)`；`enforcement_id` 与事项动作绑定，重试返回原结果（ADR-003）。
- 跨主体具名错误统一为 `TARGET_STATE_CONFLICT`、`TRADE_TERMINAL`、`TRANSITION_NOT_ALLOWED`、`LOCK_CONFLICT`、`RESTRICTION_NOT_ACTIVE`、`TRADE_FREEZE_NOT_ACTIVE`、`CONTENT_NOT_FOUND`、`BASIS_REQUIRED`、`OWNERSHIP_MISMATCH`；HTTP 映射按公共表，主体可补充前缀化业务错误。
- 部分成功不允许：一个决定涉及多个目标时，任一目标校验失败即整次回滚，事项记录未执行及原因，不留下半处置状态。

### 第4批：主体能力绑定

以下按 R0 商品能力、R1 交易触发、R2a 会话模型、C1 公共事务与 C3 文件／通知的评审版本，绑定执行入口、主体能力、锁集合与结果映射。事项用例持同一事务，主体能力只写自身数据、不提交事务（ADR-003）。

#### 执行入口

```text
execute_enforcement(context, operation_name, idempotency_key, request) -> OperationResult[EnforcementResult]
```

| 项目 | 内容 |
|---|---|
| request 字段 | `case_id`、`enforcement_id`、`action`、`target`（ResourceRef）、`basis_ref`、`reason_text`、`expected_result`、`occurred_at` |
| operation_name | `case.enforcement.<action>`，逐动作登记；与幂等作用域 `(actor_id, operation_name, idempotency_key)` 一致 |
| idempotency_key | 取 `enforcement_id`；同一事项内由其与 `case_id` 组成数据库唯一约束 |
| 入口组织 | C1 `run_write`；prepare 只读收集目标对象与账户标识，资格与状态在写事务取得锁后重查 |
| 成功结果 | `EnforcementResult`：`action`、`target`、`result_ref`、`previous_state`、`current_state`、`affected_scope`、`occurred_at` |
| 复用 | 同一 `enforcement_id` 重放 C1 已保存的 `OperationResult`；摘要不一致返回 `IDEMPOTENCY_PAYLOAD_CONFLICT` |

#### 动作与主体能力

| action | 目标读取 | 主体能力 | 成功与幂等结果 | 具名错误 |
|---|---|---|---|---|
| `restrict_account` | `AccountQualifications`（目标账户）；该卖方 `ProductStateView` 集合；该账户参与的未结束交易与待接受请求 | 账户侧按来源保存限制记录（账户契约 C4 登记）；不同来源可叠加；`Product` 对该卖方全部未删除商品应用展示限制（`source_type=账户封禁`、`source_ref=限制标识`）；R1 关闭待接受请求并按冻结规则处理未结束交易；R2a `archive_trade_conversation` 归档被关闭请求的分支 | 限制标识；`RESTRICTION_APPLIED`，同一执行重试重放原结果；同来源已生效时沿用原限制 | `BASIS_REQUIRED`、`OWNERSHIP_MISMATCH` |
| `lift_account_restriction` | 限制记录及其来源商品集合 | 账户侧记录解除；`Product` 按同一来源标识解除展示限制 | `RESTRICTION_RELEASED`，重复解除取 `RESTRICTION_NOT_ACTIVE` 的既有结果 | `RESTRICTION_NOT_ACTIVE`、`BASIS_REQUIRED` |
| `withdraw_public_access` | `ProductStateView` | `Product` 应用展示限制（`source_type=管理撤销公开`、`source_ref=决定引用`）；R1 关闭该商品待接受请求；C3 `create_notifications` | `RESTRICTION_APPLIED`；`affected_scope` 含受影响待接受请求 | `TARGET_STATE_CONFLICT`、`RESOURCE_NOT_VISIBLE` |
| `restore_display` | `ProductStateView.display_restrictions` | `Product` 解除管理撤销公开来源的展示限制，重新计算可见性 | `RESTRICTION_RELEASED` | `RESTRICTION_NOT_ACTIVE`、`RESOURCE_NOT_VISIBLE` |
| `remove_content` | 评论记录（商品）／评价记录（交易） | 商品侧按管理员移除写入 `removed_at`、`removed_by_admin_id`、`removed_reason`、`basis_ref`；评价由 TASK-003 评价能力逻辑删除 | 留存记录标识；原文、作者与时间保留 | `CONTENT_NOT_FOUND`、`TARGET_STATE_CONFLICT` |
| `freeze_trade` | 交易记录及 `trade_transition` 历史 | 交易侧写冻结事实；R2a `append_trade_system_event` 追加 `trade_frozen`；C3 `create_notifications` | `trade_transition` 标识；会话不归档 | `TARGET_STATE_CONFLICT`（已结束或已冻结） |
| `lift_trade_freeze` | 生效冻结记录 | 交易侧写解除事实；追加 `trade_unfrozen`；通知双方 | `trade_transition` 标识；其他有效冻结与账户封禁保留 | `TRADE_FREEZE_NOT_ACTIVE` |
| `adjust_trade_status` | 交易记录与 `Trade.require_transition(target, context)` | 交易侧按目标状态校验转换；调整为已完成或已终止时，按结束依据释放商品占用、默认下架、解除本笔冻结；写入终态并追加对应系统消息后，由 R2a 在同一事务归档会话。异常恢复为进行中时保留原占用、冻结及会话，追加 `trade_restored` | 前后状态与 `trade_transition` 标识；终态交易返回 `TRADE_TERMINAL` | `TRADE_TERMINAL`、`TRANSITION_NOT_ALLOWED`、`BASIS_REQUIRED` |
| `remove_evaluation_content` | 评价记录 | 交易侧评价逻辑删除并保留依据；不改写交易结束状态与统计口径 | 留存记录标识 | `TARGET_STATE_CONFLICT` |

各动作在取得锁后重读目标事实：商品按 `ProductStateView` 的 `lifecycle_state`、`occupancy_trade_id`、`display_restrictions`；交易按 R1 的当前状态、冻结记录与占用归属；账户按资格锁后读取的 `AccountQualifications`。`expected_result` 只登记业务预期，不作为跳过重读的依据。

#### 系统消息与分支归档

处置执行不建立新会话，也不写入消息正文；交易侧事实变化按 R2a 的事件类型追加系统消息。

| 执行动作 | 系统消息 `event_type` | `source_ref` | 归档 |
|---|---|---|---|
| `freeze_trade` | `trade_frozen` | `trade_transition` + 本次变更 ID | 不归档 |
| `lift_trade_freeze` | `trade_unfrozen` | `trade_transition` + 本次变更 ID | 不归档 |
| `adjust_trade_status`（完成） | `trade_completed` | `trade_transition` + 本次变更 ID | 写入终态及系统消息后同事务归档 |
| `adjust_trade_status`（异常恢复为进行中） | `trade_restored` | `trade_transition` + 本次变更 ID | 维持会话现状 |
| `adjust_trade_status`（终止） | `trade_terminated` | `trade_transition` + 本次变更 ID | 写入终态及系统消息后同事务归档 |
| 事项结案 | 不产生交易消息 | — | `archive_case_conversation` |

冻结、解冻与状态调整都不重开已归档会话、不迁移消息、不新建第二条交易会话。买卖双方的普通私聊与交易消息限制由 R2a 的 `require_send` 按双方账户资格与二人冻结计算，执行请求不另存会话状态。事实变化向事项相关方告知时调用 `append_case_message`（`message_kind=system_notice`），事件标识沿用事项事件。

#### 通知意图

通知按 C3 `create_notifications` 与业务同事务提交；`intent_key` 由动作、执行标识与通知种类构成，同次执行重试保持一致。

| 执行动作 | `event_type` | 接收账户 | `intent_key` 组成 |
|---|---|---|---|
| `restrict_account` | `case.account_restricted` | 目标账户 | `{enforcement_id}:restricted` |
| `lift_account_restriction` | `case.account_restriction_lifted` | 目标账户 | `{enforcement_id}:lifted` |
| `withdraw_public_access` | `case.display_withdrawn` | 卖方 | `{enforcement_id}:withdrawn` |
| `restore_display` | `case.display_restored` | 卖方 | `{enforcement_id}:restored` |
| `remove_content` | `case.content_removed` | 内容作者 | `{enforcement_id}:removed` |
| `remove_evaluation_content` | `case.evaluation_removed` | 评价作者 | `{enforcement_id}:evaluated` |
| `freeze_trade` | `case.trade_frozen` | 交易双方 | `{enforcement_id}:frozen` |
| `lift_trade_freeze` | `case.trade_unfrozen` | 交易双方 | `{enforcement_id}:unfrozen` |
| `adjust_trade_status` | `case.trade_adjusted` | 交易双方 | `{enforcement_id}:adjusted` |

模板标识与版本从 C3 事件登记表取得；`display_params` 只含原因、范围、恢复结果与处置沟通入口，不含消息正文与证据内容。被关闭待接受请求的买方通知由 R1 的关闭动作登记，本动作不重复提交同一 `intent_key`。

#### 锁集合与原子范围

| 动作 | 第1级 账户资格 | 第3级 商品 | 第4级 交易 | 第5级 事项 | 第6级 会话子序 | 第7级 事件序号 |
|---|---|---|---|---|---|---|
| `restrict_account` | 目标账户排他、操作者共享 | 该卖方全部未删除商品，按 `product_id` 升序 | 该账户参与的未结束交易，按 ID 升序 | 本事项 | 被关闭请求的交易会话（归档）、事项会话 | 接收账户按 ID 升序 |
| `lift_account_restriction` | 目标账户排他、操作者共享 | 限制来源涉及的商品 | 无 | 本事项 | 事项会话 | 同上 |
| `withdraw_public_access` | 操作者共享 | 目标商品及同商品展示限制行 | 同商品待接受请求涉及交易 | 本事项 | 被关闭请求的交易会话 | 同上 |
| `restore_display` | 操作者共享 | 目标商品及展示限制行 | 无 | 本事项 | 无 | 同上 |
| `remove_content` | 操作者共享 | 商品及评论记录行 | 评价所属交易行 | 本事项 | 无 | 同上 |
| `freeze_trade`／`lift_trade_freeze` | 操作者与交易双方共享 | 无 | 目标交易及同商品其他交易 | 本事项 | 本笔交易会话 | 同上 |
| `adjust_trade_status` | 操作者与交易双方共享 | 结束目标时的目标商品 | 目标交易及同商品其他交易 | 本事项 | 本笔交易会话（终止时归档） | 同上 |
| `remove_evaluation_content` | 操作者共享 | 无 | 评价所属交易行 | 本事项 | 无 | 同上 |

执行目标在决定后才确定时，例如封禁后新增的待关闭请求，按 C1 回滚本次事务并以补充集合整次重规划，不在第 5 级锁内回取第 3、4 级对象。同一决定涉及多个目标时按上表合并集合后一次排序，不逐目标依次跨域回取。

#### 证据与审计绑定

- 决定与执行依据取事项的证据引用记录；`basis_ref` 指向该组引用，非空是执行前置条件。
- 证据文件按 C3 `attach_files`（`purpose=case_evidence`、`target` 为事项）建立引用，写入与主体变化同事务，第 6 级文件子序按 `file_id` 升序。
- 审计按 C1 `record_audit` 记录动作、目标、前后状态、依据引用、执行者与时间；不记录消息正文与证据内容。

### 验证场景与测试关联

设计阶段按下列预期核对请求语义与事务边界，TC 编号与运行条件随第 5 批登记：

1. 同一决定含交易冻结与商品撤销公开访问：两项在同一事务生效；任一项校验失败时交易、商品、通知均回滚（BR-26、BR-33）。
2. 封禁执行时该账户存在待接受请求与未结束交易：请求按 D-52 关闭并归档分支，交易按冻结规则处理，双方均收到通知（BR-32、DT-03）。
3. 冻结期间双方尝试推进交易或互发消息被拒绝，历史只读，与第三方会话不受影响；解冻且原确认有效时续算剩余等待（BR-33、D-51）。
4. 管理员尝试恢复已完成或已终止的交易时返回 `TRADE_TERMINAL`；同商品存在另一笔锁单交易时，两笔交易、商品占用、会话及限制均保持原状（BR-08）。
5. 解除封禁后恢复原资格，其他有效限制保留，非在售商品不自动上架（BR-32、TR-10）。
6. 同一 `enforcement_id` 重复请求返回原结果，不重复记录限制、不重复通知（ADR-003）。

## C5 配置、审计与可观测性

### 配置加载与发布

后端从显式指定的单份.env加载运行参数，通过类型化Settings建立不可变配置快照；受控加载器仅组合该文件与代码声明默认值，不以业务代码读取os.environ、临时文件或另一配置源补缺。启动检查未知字段、类型、范围、关联、必需凭据引用与所需依赖；失败输出脱敏字段名和原因并停止启动。密码、DSN、密钥和签名内容不输出到配置报告。

每个入口取得同一配置版本及作用域，HTTP／IM／worker／scheduler共享业务规则，实例ID、监听地址等实例参数单独具名；新进程读取发布的快照，不热改已运行对象。配置版本由非秘密有效值及秘密来源版本引用确定，日志只输出版本标识；原始秘密不参与公开报告。滚动期间的新旧期限使用记录保存的快照，各入口在阶段测试检查兼容性。

两个前端分别维护开发服务器、代理、公开API／WS地址、基础路径及构建配置；仅构建公开值进入前端包。输入限制与能力由后端API取得，前端显示与校验不替代后端规则。部署目录／域名及数据库／Redis实际值按用户确定的同机隔离边界，在后续部署阶段配置。

### 审计与运行日志的字段及提交点

运行日志覆盖请求／任务开始、完成、拒绝及异常；业务审计保存已发生的主体变化和依据。统一上下文包括request_id、operation_id、correlation_id、causation_id、event_id、task_id、instance_id、connection_id，按实际入口填值或null，禁止把互不相同的标识混用。

业务审计字段：audit_id、occurred_at、actor_kind、actor_account_id或系统任务名、action、target具名引用、basis_ref或null、受限before_after、operation_id及必要配置／规则版本。公共包装生成技术上下文，主体用例提供业务事实；审计与业务／历史／幂等／事件同事务。回滚不保留成功审计，业务拒绝在事务外写脱敏运行日志，不伪造主体变化。

| 动作组 | 具名审计动作及最少事实 | 原码及私有内容处理 |
|---|---|---|
| 账户 | account.registered／password_changed／password_reset／email_changed／name_changed；稳定账户、变更字段名及必要前后值、实际操作者 | 不保存密码、散列、验证码、Cookie、CSRF、输入摘要或密钥；邮箱前后值仅限获准审计范围 |
| Session | session.issued／revoked；内部SessionID、签发／撤销时间及来源操作 | 不记录原始凭据或token_digest；失败鉴权只记类别和关联标识 |
| 邮件验证 | verification.requested／replaced／consumed／invalidated，记录验证ID、用途、结果类别及规则依据 | code只在单表专用字段，SMTP正文及原始服务响应不进入日志／审计 |
| 文件 | file.authorized／verified／references_changed／cleanup_claimed／deleted；file_id、用途、引用ID及保留依据 | 不记录签名表单／URL、存储凭据及用户原始文件名；必要元数据受限 |
| 主体业务 | 商品提交／编辑／审核、交易请求／约定／确认／终态、事项认领／处置／解除，动作名由主体唯一登记 | 保留前后业务事实及basis_ref，不把整段聊天／证据正文写入通用审计 |
| 事件及任务 | 派发／认领／重试／接管／完成及取消的运行记录，token对应内部任务与结果类别 | broker载荷只含稳定ID，日志不记消息正文、SMTP内容或完整私有事件 |

账户公开入口在验证前以entry标识运行上下文，成功建立／验证账户后审计实际账户主体及相应验证依据；不由客户端自报操作者。系统任务记录task_id与原业务basis，管理动作记录当前实际管理员及事项依据。

成功幂等重放沿用原operation_id及业务审计，本次request_id生成新运行记录，标明重放但不重复写业务审计。失败的验证码次数是专用已提交事实，按Q-003保存失败结果与计数，运行日志只记录失败类别；不将整个事务标成普通回滚后又重放计数。

### 白盒及动态验证输入

逐入口检查配置对象读取、类型范围、密钥引用版本、审计提交位置和脱敏白名单。日志字段序列化与错误响应采用显式schema，异常库原文仅在经过清洗的内部边界处理，不直接回显请求体。TC-COM-032覆盖配置缺失／非法关联、公开白名单、实例版本变化、回滚／重试审计及敏感字段扫描；真实运行结果随编码任务登记。

## 本人聚合、待办与管理查询

TASK-001第5批。输入design `2a7cb17`的R0／R1／R2a、需求FR-10／11／12、BR-16／24／27／31—34、需求4.17／4.18。账户与通知评审输入[PR #47提交2fc423b](https://github.com/iy88/se-course-project-1/tree/2fc423b)，事件及配置交界输入[PR #48提交46033be](https://github.com/iy88/se-course-project-1/tree/46033be)。主体任务提供各自字段及等义查询实现；本专题定义统一输出与查询规则，不给主体新增重复计数或待办实体。

所有路径相对于统一API前缀。ID字符串、时间UTC ISO 8601；计数为非负安全整数。分页page默认1，page_size默认20、最大100，均从后端配置取得；列表按明确次序分页，total使用相同过滤谓词。本组查询返回Cache-Control:no-store，在同一短只读数据库快照构造列表、总数及as_of（UTC查询时点）；多语句组合使用短只读REPEATABLE READ或等价单语句查询，不改变C1写事务隔离级别。

### 统一规则及适配接口

```text
AccountQueries.require_self(context) -> AccountScope
ManagementQueries.require_manager(context) -> ManagerScope
OwnerReadModel.list_owned(scope, filters, page) -> OwnedPage
OwnerReadModel.count_owned(scope, filters) -> int
OwnerReadModel.todo_candidates(scope, now) -> QueryPredicate
OwnerReadModel.require_todo_action(source, actor, qualifications, now) -> Allowed
ManagementQueries.statistics(scope, time_selection, as_of) -> ManagementStatistics
```

各主体由同一规则方法提供对象判定及等义SQL谓词。聚合层组织同一数据库快照、分页与输出白名单，不复制账户／商品／交易／事项资格条件。所有参与、归属、当前限制和事项认领在分页前处理，total、overview及待办counts复用同一谓词。

R0商品与收藏、R1交易与评价、R2a会话及后续事项模型的字段由对应任务绑定。TASK-002／003／004在本域接口批次交付OwnerReadModel实现及字段映射，当前源文件已有的归属与权限直接作为本批设计依据；源字段未交付项以具名适配要求登记，集成逐项核对，编码采用design实际集成版本。

| 隐私 | 只输出管理统计计数，不泄露个体用户、举报内容、真实支付金额或资金凭证 |
| 测试关联 | TC-COM-031 |
| 确认 | TASK-001提供，TASK-002／003／004核对来源口径，实际复核通过PR登记 |

| 指标 | 计算口径与来源 |
|---|---|
| accounts.total／banned | 账户总数包含被封禁账户；banned按当前有效封禁事实计算，多个封禁来源对同账户只计一次 |
| products_by_state | 按R0生命周期每件商品一次；展示限制不改生命周期，不把搜索可见数当各状态商品数 |
| pending.reviews／reports | 查询时点尚未处理结束的审核／举报事项，包含已认领未处理；一事项计一次；TASK-004唯一维护处理事实 |
| trades.completed／terminated／disputed | 当前分别已完成、已终止、有争议的交易；拒绝／撤回／请求关闭不计已终止；每笔记录一次 |
| completed_in_selection | 当前已完成交易的结果确认时间在[start_at,end_at)内，all取全部；结果确认时间取TASK-003不可变完成记录或其统一方法，不能用创建／更新时间或单方完成确认时间代替 |

range只影响completed_in_selection，其余当前计数始终采用as_of；前端界面据此明确显示当前统计与所选范围完成数。任务输入需要TASK-003提供结果确认时间及等义查询、TASK-004提供未处理事项口径，适配及索引在主体对应接口批次绑定。

### 查询适配的组合与能力检查

采用[公共能力扩展边界](#interfaces-18)。OwnerReadModel为聚合侧声明的端口，各主体提供实现，应用组装层按资源kind绑定。QueryScope显式携带当前身份、as_of及同一只读快照参与句柄；list_owned、count_owned及todo_candidates在该scope内执行，不开启独立快照。QueryPredicate表示查询语义及参数，可由持久化适配器实现，不能要求跨模块传递某一ORM的表达式或会话对象。

聚合层组合主体投影、稳定排序、计数与分页；主体维护当前资格及等义筛选条件。更新业务类型时同步公开schema及输出白名单，统一快照和分页算法复用。启动时检查ENABLED_CAPABILITIES所需适配完整且唯一，已启用能力缺失适配拒绝启动；运行时依赖故障沿既有503语义处理。文件用途的策略、内容核验器及规则schema也由配置完整性检查验证，配置值不承载业务实现。

## 公共能力扩展边界

依据：袁尚峰于2026-11-17要求通过接口职责、依赖方向及组装关系表达扩展；本批扩展细化随对应PR交付。应用语言及框架采用[技术栈独立的应用架构](design/architecture/07-技术栈独立的应用架构.md)。

### 依赖结构与应用组装

公共能力声明所需端口及输入／结果，主体模块实现业务资格、来源解析和投影，应用组装层显式连接实现。公共核心依赖端口，不导入商品、交易或事项实现；主体用例调用公共能力并提供所属事实。基础设施适配器实现存储、队列和网络端口。组装可采用静态映射或显式构造，类型及配置检查保证完整性。

扩展通过增加所属模块实现与组装项完成，公共生命周期算法保持稳定。API枚举、schema、输出白名单及应用组装随正式能力变化更新。当前业务用途的枚举是已开放能力集合，不表示公共核心必须按业务用途分支。扩展无需动态插件加载或数据库插件表。

端口契约必须定义调用阶段、显式事实、结果／错误、事务参与及锁需求。prepare阶段发现全部依赖并纳入C1 LockPlan；资格与业务锁后重读事实再判断。端口执行不得在较晚锁域追加较早的锁；依赖集合变化使用C1回滚重规划。外部I/O在事务外执行，提交前重查必要事实。

### 扩展验证

扩展检查使用测试夹具增加一种用途或来源实现，覆盖成功、策略拒绝、缺失／重复组装和锁后资格变化。模拟用途不增加正式业务需求；实际运行结果在对应编码任务登记。
