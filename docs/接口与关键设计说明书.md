## 设计约束与检查规则

本文件定义项目设计与协作表达的检查条件。依据为袁尚峰在 2026-11-14 的 review 及本轮要求。需求中的业务规则保持在对应需求源文件；本文件约束字段、规则归属和协作表达。AGENTS.md 引用本文件作为工作指引，接口、数据模型及 PR 按下表提供检查依据。

### 字段与规则实现

| 编号 | 规则及适用范围 | 通过条件 | 反例 | 检查方法与证据 |
|---|---|---|---|---|
| DATA-01 | 实体及共享状态视图保存事实与必要关联，移除可推导的重复字段 | 每个字段能说明独立业务事实、关联、历史依据或并发用途；可以从已有权威事实无损计算的当前判断通过方法取得 | 同时保存审核结论和 review_valid，或在状态视图输出 can_relist | 对字段表逐项登记来源，检查数据库列、DTO 与关联定义，列出推导输入及所属方法 |
| DATA-02 | 同一事实由一个主体维护 | 引用方保存必要外键，通过关联读取维护方事实 | TradeConversation 已有关联 trade_id 又复制 buyer_id／seller_id；商品审核重复事项认领人 | 逐外键追溯维护方，核对创建及修改路径，引用方通过关联读取 |
| DATA-03 | 当前业务状态与历史事实分开 | 当前规则由当前事实计算，快照和审计保留当时发生的内容 | 以当前商品内容重建成交时商品内容，或删除历史快照后从当前数据推导 | 核对历史记录在后续编辑后的预期，检查明确的历史字段及引用 |
| DATA-04 | 保留有实际用途的技术数据 | 版本用于并发控制，序号基准用于事务内分配，索引用于约束或查询；用途及维护方写明 | 为方便调用而增加多个需要同步刷新的资格布尔值 | 核对对应并发协议、唯一约束或查询依据；可计算的纯查询结果通过方法取得 |
| RULE-01 | 统一规则由所属类提供接口 | 每项规则有具名方法、输入、返回／错误及适用动作；调用方调用该方法 | 控制器、服务和页面各自复制一套商品编辑资格条件 | 建立“规则→类方法→调用入口→案例”映射，定位所有实现和调用 |
| RULE-02 | 跨主体资格由用例收集事实，主体方法统一判断 | 用例提供当前身份、账户限制、参与和事项上下文；方法读取显式输入，返回 Allowed 或具名业务错误 | 将商品侧 can_edit 当作完整授权，遗漏账户封禁或事项资格 | 核对方法签名、输入来源、各限制组合和错误分支 |
| RULE-03 | 写操作以锁后事实执行规则 | 按 C1 规划锁、重读后调用主体方法，成功后维护主体及历史 | 信任页面上次取得的 can_relist，跳过写入时复核 | 按事务顺序审查；用并发状态变化案例检查结果 |
| RULE-04 | 列表、详情、统计与写操作共享同一规则定义 | 类方法提供对象判定及等义查询条件；筛选在分页前执行，统计使用同一口径 | 页面过滤搜索结果，或者列表与详情对同一商品给出相反资格 | 逐规则列真值表，对对象方法、数据库筛选及统计结果作等价核对 |

接口返回的资源事实与页面所需内容按具体契约定义。派生判断通过所属类方法取得；历史快照、并发版本和事务序号分别依据 DATA-03／04 说明用途。业务生命周期、账户限制和授权事实按所属主体维护。

### 检查执行方式

1. 字段审查：对实体字段和共享 DTO 逐行应用 DATA-01—04，记录权威来源及保留用途。
2. 规则审查：对每项业务动作列所属类方法、输入、错误和调用点，按 RULE-01—04 核对。
3. 表达审查：按 TEXT-01—03 检查本轮评论、描述及记录，使用原生流程字段维护协作。
4. 同源检查：执行 `python3 scripts/cli.py report --documents all`、`python3 scripts/cli.py check --documents all` 及 `git diff --check`。

现有 check 命令检查生成一致性、图稿摘要、本地链接与锚点。字段是否可推导及规则是否只有一个实现来源，按字段来源表、类方法及实际调用关系核对；确定的旧字段和措辞可用精确搜索辅助定位。代码实现时，规则真值表用于检验对象方法与查询条件的等价性，并发案例用于检验锁后判定。

## 2. 共享接口约定

### HTTP 与模型

采用 RESTful，以复数名词组织资源，GET 查询、POST 创建或提交业务动作、PATCH 部分更新、DELETE 删除或解除关系。归属用子资源表达，关键状态转换明确业务契约。版本前缀采用统一约定，前端独立配置公开入口。

JSON 使用 snake_case。对象 ID 对外字符串，金额整数分并体现单位，时间 UTC ISO 8601。状态采用具名字符串枚举。省略、null 及更新清空语义逐字段注明。

成功响应按资源组织，列表包含 items 和分页信息；错误包含稳定业务错误码、展示说明、必要字段错误及 request_id，HTTP 状态表达协议结果。错误码清单待接口评审。

### 身份与权限

随机 Session 凭据通过持久 Secure／HttpOnly Cookie 传递，状态变更请求采用 CSRF 校验，具体同源部署及 Cookie 属性在配置清单中确定。Redis 保存有效 Session，PostgreSQL 保存账户及凭据版本，每次鉴权校验并复用请求上下文。

绝对期限与空闲期限取较早者，用户有效活动按配置间隔续期，心跳与自动轮询单独处理。账户多 Session、Session 多连接。退出撤销当前 Session；改密／重置使已有版本失效；封禁保留需求规定的读取及事项沟通。

Session 不存在或到期返回重新登录语义；Redis 查询未完成返回暂时服务错误，客户端保留凭据。恢复撤销语义见 Q-001。

### 分页与并发

普通列表页码分页，明确过滤、主次稳定排序及总数口径；聊天历史和事件恢复采用游标。默认页大小和上限由后端配置。

关键写接口按主体、操作、幂等键及输入摘要返回同次结果；同键不同输入返回冲突。旧页面敏感操作携带版本依据，过期提交按契约返回冲突。事务由用例统一提交，内部能力复用同一上下文。

### 配置与能力接口

后端配置按应用入口、实例、数据库、Redis、身份、IM、任务、业务策略、文件邮件及日志分组，登记类型、单位、依据、默认值、范围、关联关系、公开范围与生效方式。前端配置在各应用中维护，构建独立；输入限制和上传能力从接口取得。配置模型及 .env.example 在实现阶段同步建立。

新操作用当前配置，既有期限及授权保存当次参数／版本；受影响的既有业务通过明确变更处理。

### 日志审计与类型

统一 request_id、operation_id、event_id、task_id、correlation_id、causation_id、instance_id 和 connection_id 的含义。自动记录公共上下文，业务用例提供审计事实并在提交前持久化。

接口类型由 OpenAPI 契约生成；所选后端技术栈和 TypeScript 严格类型检查配合白盒审查，运行时案例针对运行时性质或复杂关联。

### 协作接口

模块提供方、调用方和复核人按模板登记。共享契约由 TASK-001 维护；各任务提出所需变更，由指定审查人核对交界后汇入。

### 字段与统一规则检查

按[设计约束与检查规则](#interfaces-02)的 DATA-01—04、RULE-01—04 及 DOC-01 检查字段来源、主体类接口、锁后判定、查询等价性和同源传播。实体与共享视图保留事实及必要关联，展示、搜索及动作资格通过所属类接口统一计算。

## 公共事务与权限交接契约

设计归属：TASK-001；编写账号：iy88。输入：design 提交 `6250473`。

### 关联需求、决策与接口

依据 FR-01—FR-14 的主体资格、BR／TR／权限矩阵、第6章一致性与隐私要求，关联 ADR-002、003、005、009、010。调用方为 TASK-002／003／004 的业务用例，本契约定义公共输入、事务、资格、幂等及错误。数据模型和业务状态仍由各主体专题定义。

### 公共数据类型

| 类型 | 字段与约定 |
|---|---|
| EntityId | 正整数 ID 对外使用十进制字符串；数据库为整数；接口模型校验其范围 |
| ResourceRef | `resource_type`：具名主体类型；`resource_id`：EntityId |
| ExecutionContext | `request_id`：本次执行 UUID；`operation_id`：逻辑操作 UUID；`actor_kind`：account／system；`actor_id`：账户 ID 或已登记系统任务名；`session_id`：账户操作的内部 Session 标识；`credential_version`：鉴权读取的账户版本；`config_version`：本次配置版本 |
| LockPlan | `shared_account_ids`、`exclusive_account_ids`：资格判定所需账户集合；`resource_candidates`：按锁域登记的候选对象标识；`planning_basis`：来源对象及读取依据。账户集合合并后采用所需最强模式，候选对象按公共锁序排列 |
| AccountQualifications | 按账户 ID 索引的当前身份、凭据版本、限制及对应判定字段；由资格锁取得后的读取构建 |
| Allowed | 本次动作的具名允许结果，关联动作及对象；由主体在当前资格和已锁定状态下检查取得 |
| TransactionContext | 同一用例持有的 SQLAlchemy AsyncSession、ExecutionContext 及本次审计／事件意图集合 |
| BusinessError | `code`：稳定错误码；`message`：可展示说明；`details`：按接口定义的公开字段；`resource`：允许公开时的 ResourceRef |
| OperationResult | `operation_id`、HTTP 状态、已确认响应数据及结果资源引用；用于成功操作的同次重试 |

账户上下文由身份依赖构建；system 上下文由登记的任务入口构建，附触发事件／任务标识。外部输入通过 Pydantic 转成用例参数，执行上下文由服务端补齐。当前请求中的关联查询复用已核验身份，用例写入时按下述协议重查资格。

### 用例和模块调用签名

以下为设计签名，T 为模块具名结果类型。

```text
run_write(context, operation_name, idempotency_key, request, prepare, use_case) -> OperationResult[T]
prepare(read_session, context, request) -> LockPlan
use_case(tx, context, request, qualifications, lock_plan) -> T
lock_account_qualifications(tx, shared_account_ids, exclusive_account_ids) -> AccountQualifications
require_action(qualifications, action, resource_state, participation) -> Allowed
record_audit(tx, action, target, before_after, basis_ref) -> audit_id
add_event_intent(tx, recipient_ids, event_type, source, intent_key, payload_ref) -> event_id
```

request 为经过 schema 校验的具名业务参数；公共入口从同一 request 生成规范化输入摘要，并将该参数交给准备函数及业务用例。prepare 和 use_case 由该业务动作一起提供。

内部能力成功时返回具名结果，业务失败统一抛出具名 BusinessError。require_action 成功返回 Allowed，失败抛出 BusinessError；公共包装捕获该异常，先回滚整个事务再映射 HTTP 错误。用例协调跨模块动作，公共包装完成最终提交及错误映射。内部能力的必要 flush 保持在调用方事务内。每个并发请求／后台任务持有自己的 AsyncSession。建议采用 PostgreSQL READ COMMITTED 隔离级别；等待锁后显式刷新或重新查询资格及业务状态，使后续语句读取最新已提交事实。

### 写操作执行顺序

run_write 组织如下阶段；prepare 只做候选对象及账户标识的只读查询，权威资格和状态检查在写事务中完成。

1. **准备锁集合**：在独立只读会话中调用 prepare，收集动作涉及的账户资格集合及候选业务对象。查询使用完成后结束该会话；此阶段输出 LockPlan。
2. **取得资格锁**：开启写事务，由公共入口合并 LockPlan 的账户集合，按 ID 升序、首次即采用所需最强模式取得资格锁，再读取 AccountQualifications 并核对当前身份与凭据版本。
3. **登记幂等占位**：在资格锁之后查找或创建本操作的幂等占位。已有成功结果时，按当前结果读取资格重放；首次操作继续调用 use_case。当前动作的写入资格在业务用例中检查，结果重放采用读取资格。
4. **执行业务**：use_case 接收同一 tx、request、qualifications 和 LockPlan；按第3级及之后的锁域取得业务对象锁，重读状态并调用 require_action，再完成主体、历史、审计、文件及通知意图的变化。
5. **统一提交**：公共入口在业务锁操作完成后，统一取得接收账户的事件序号锁、保存事件及成功响应，提交事务后返回 OperationResult。

prepare 的候选是规划依据。写事务重查时，如发现新的资格账户、所需更强模式，或需要取得已经越过的锁域／更小对象键，业务用例抛出内部 LockPlanChanged，附补充集合。公共入口回滚本次全部变化，使用新只读会话重新准备并合并补充集合，再从资格锁阶段开始整次重试。次数及退避采用配置；业务事件与成功结果在最终成功事务中提交。

封禁等资格变化动作可在取得目标资格锁后发现关联集合；新增集合依同一重规划流程处理。最终业务资格与锁集合由写事务重查确定，候选读取和锁后的实际对象共同参与一致性核对。

### 状态转换与数据约束

| 对象 | 规则 |
|---|---|
| 资格 | 账户当前身份、凭据版本和限制来自 PostgreSQL；主体进一步核对归属、参与、状态及认领 |
| 成功写入 | 主体变化、历史、必要审计、幂等结果、通知及待投递事件统一提交 |
| 业务校验结果 | 整体回滚，本次业务状态及成功审计保持原状，接口按错误码表达 |
| 唯一约束竞争 | 只将已登记的约束映射为对应业务冲突，其他异常记录关联标识后返回内部错误 |
| 查询 | 按当前读取资格构造响应字段；记录读取本身与需要审计的业务动作分别定义 |

时间判断使用同一逻辑数据库的当前时钟；等待行锁后重新读取状态，并以实际判定时刻检查期限。修改期限的规则按既有规则版本语义执行。

### 账户资格与并发写入

本交接稿建议采用 PostgreSQL 事务级共享／排他 advisory 资格锁，在统一登记的资格锁命名空间内以账户整数 ID 作为键。该机制的取舍依据及评审意见记录于关联 PR。

- 普通写操作取得操作者和直接业务参与账户的共享资格锁，例如购买请求与交易取得买卖双方的锁，消息发送取得相关参与账户的锁。
- 封禁、解除、改密／重置及管理资格变更，对变化账户取得排他资格锁；管理操作者按需要取得共享锁。
- 用例在开始时合并账户集合，按账户 ID 升序取得所需最强模式，再重读账户资格和凭据版本。资格锁由事务结束释放。
- 资格变化事务通过账户模块保存当前状态，并协调适用的业务变化。封禁目标的锁取得后，读取其当前请求／交易集合，其他涉及该账户的新写入在取得资格锁后检查最新状态。
- 资格 advisory 锁与实际账户行的更新锁分别表达职责；账户模块在资格锁内执行普通字段更新。通知接收人存在性查询及外键关联沿数据库结构规则执行。

两种时序都有确定结果：业务事务先取得共享资格锁时，该业务先完成，后续限制按已提交状态处理；资格变化先取得排他锁时，后续业务读取新资格并返回对应结果。读接口依据当前账户和对象范围判定，Session 撤销恢复语义继续由 Q-001 细化。

### 锁顺序与事务边界

| 顺序 | 锁域及动作 |
|---|---|
| 1 | 本用例账户资格锁：账户 ID 升序，模式在首次取得时确定 |
| 2 | 幂等键的事务内唯一占位：操作者＋操作类型＋请求键 |
| 3 | 商品行：商品 ID 升序；锁后重读占用及状态 |
| 4 | 交易行：已知受影响集合按 ID 升序；单商品场景在商品锁内确定集合 |
| 5 | 处置事项行：事项 ID 升序，重查认领与当前状态 |
| 6 | 固定子序：ChatConversation → TradeConversation → CaseConversation → 各类消息 → 各类阅读进度 → 文件登记 → 文件引用；每个子域内部按稳定对象键升序 |
| 7 | 用户事件序号行：收集全部接收账户后按账户 ID 升序锁定、分配序号并保存事件 |

第6级按业务对象语义划分子域；具体表结构由主体模型定义，同一物理行首次取得锁后按该次锁覆盖处理。整数 ID 使用数值顺序，复合键采用主体契约声明的字段顺序逐项比较。文件引用以 reference_id 排序。新增行由当前事务创建，涉及已存在对象的锁及唯一关系竞争仍按公共顺序组织。

每个用例按涉及的锁域推进，并在具体专题登记其集合和顺序。需要补充更早锁域的对象时，回滚并重新规划整次用例；此分支计入统一的有限事务重试。事项认领可作为独立短事务；处置执行重新按全局顺序取得相关锁和资格。

接受请求的具体交易转换和商品占用由 TASK-003 定义；事项执行请求由 TASK-004 定义。调用方使用本表组织公共顺序，模块维护自身数据。

### 幂等作用域与结果

客户端关键写操作提交 `Idempotency-Key`。账户已鉴权，服务端校验键的格式和配置长度。作用域为 `(actor_id, operation_name, idempotency_key)`，数据库唯一约束保障跨实例同次识别。

输入摘要采用具名用例参数的规范 JSON：包含路径对象和有效业务字段，排序键并固定编码；各字段按 schema 处理省略、null、时间、金额及文本。摘要使用 SHA-256；凭据与敏感载荷通过其专用验证接口处理。规范化方案版本随记录保存。

| 情况 | 结果 |
|---|---|
| 已有成功记录、摘要相同 | 按当前身份及结果读取资格返回已保存业务结果，沿用 operation_id |
| 已有记录、摘要不同 | `IDEMPOTENCY_PAYLOAD_CONFLICT` |
| 首次请求 | prepare 收集候选，公共入口先取得账户资格锁，再创建事务内占位；调用用例取得业务锁并完成动作，保存响应状态、数据和资源引用，统一提交 |
| 同次请求并发 | 使用 INSERT ... ON CONFLICT DO NOTHING 协调唯一占位等待，再以新语句读取；先到事务提交后，后到者读取成功记录；先到者回滚后可接续执行 |
| 校验结束且事务回滚 | 本次占位随事务回滚，重试依据当前业务状态重新判断 |
| 响应丢失 | 使用同键重试，取得已提交结果 |

成功结果的重放复用原业务数据和状态码，当前执行产生新的 request_id。校验失败且有明确业务副作用的专用流程（如验证码尝试计数）在其契约中定义结果保存语义。保留期限内重复请求按本表执行；到达保留期限后的客户端重试策略在配置／接口中明确。

| OperationResult／C1公共能力 | operation_id UUID PK；actor_kind、actor_ref（账户／entry／system服务端依据）、operation_name、idempotency_key；request_digest bytea、digest_version／key_version；HTTP状态、受限result_data JSON、result_refs、created_at／expires_at | UNIQUE(actor_kind,actor_ref,operation_name,idempotency_key)；expiry扫描索引；同键异输入409；成功结果与业务同事务，验证码错误结果按专用语义提交；到期后客户端先同步事实，不能假定键永久保留 |

### 账户事件与通用任务：采用C2唯一源

源定义：PR #48实时与任务0.1.0。下面汇总结构约束与保留，具体传输、权限投影、认领及ACK仍由C2维护。

| AccountEventHead | account_id PK／FK、seq_head／replay_floor bigint | 0≤floor≤head；事件最终锁域分配，回滚不推进；清理同事务推进连续前缀floor |

邮箱、文件及事件派发由自己的持久记录实现ClaimableWork，不把同一事实复制进TaskSchedule。Redis只保存运行时Session、流／队列、连接租约与协调状态；命名空间按v2前缀隔离，逻辑DB可在后续部署选择。客户端ACK、消息阅读与通知阅读分别维护。

### 规则与迁移检查清单

1. 字段来源逐项应用DATA-01—04：身份及归属只存必要事实，历史快照和版本有明确用途；本人概览、待办、管理统计、can_*及unread_count都通过查询／类方法取得，不新增持久镜像表。
2. 数据库唯一、外键、空值配对、期限与计数约束由迁移承载；用途大小、次数上限与期限参数由类型化配置及保存的快照校验。跨模块外键／引用采用主体实际模型后核对，不能以未交付字段假装已有迁移。
3. 按C1资格与业务锁序核对各关系创建、释放及清理；迁移测试验证失效与清理不会级联抹除历史、恢复不能重新授权，索引支持当前查询谓词。
4. PostgreSQL使用同一v2业务数据库，legacy与v2库名／用户独立；真实DDL、Alembic修订号及数据迁移命令随实现提供，当前交付为设计及检查输入。

实际验证采用TC-COM-033／034，并复用文件011—014、身份邮箱015—022、事件任务023—028及查询029—032的专题预期；对应运行环境与结果随编码任务登记。

### 扩展标识与技术栈映射

采用[公共能力扩展边界](#interfaces-12)。本模型的主外键、唯一性、保留及事务约束以PostgreSQL语义表达，持久化类、DDL迁移工具及框架由技术映射确定。FileRecord.purpose是服务端登记的稳定标识，首批公开product_image／case_evidence；其目标类型、策略和核验器由文件专题与应用组装定义。新增正式用途同步API schema与数据库适用约束，保持文件生命周期算法稳定。

历史授权保存的规则及版本继续可解析；用途停用不删除有效引用或改变已核验内容。Notification来源、UserEvent来源及TaskSchedule.task_kind通过对应主体端口解析，清理或部署升级前检查存量版本可处理。数据库保存事实与必要版本，策略实现和框架类名不进入业务表；无需新增插件表。文件专题、C2与查询端口为唯一行为来源，本汇总同步其实际集成版本。

## 文件引用与回收交接契约

设计归属：TASK-001；编写账号：iy88。输入：design `6250473`。本文件承载文件专题；邮件验证及敏感内容保护随 C4／Q-003 在后续批次补齐。

### 关联需求、决策与接口

依据 FR-02 商品图片、FR-07／08 事项证据及其读取权限、ADR-007、Q-002。TASK-002／004 使用 file_id 及下列内部能力；[公共事务](#interfaces-06)提供上下文、锁序与错误映射。用途、归属和资源访问范围遵循相应主体规则。

### 标识、字段与状态

| 字段 | 类型及含义 |
|---|---|
| file_id | EntityId，稳定文件登记标识 |
| owner_account_id | EntityId，上传授权归属账户 |
| purpose | 具名用途枚举：product_image、case_evidence；每种用途在配置中登记类型、大小及数量规则 |
| state | uploading、verified、cleaning、deleted |
| content_identity | 内部内容标识，由 Q-002 的对象稳定性方案提供；包含核验取得的对象定位及完整性依据 |
| verified_metadata | 实际大小、核验内容类型及适用完整性数据；上限和可用格式来自配置 |
| created_at／verified_at／cleanup_after | UTC 时间；回收时间保存当次配置依据 |
| FileReference | `reference_id`：EntityId，当前引用关系的稳定标识；`file_id`：EntityId；`target`：ResourceRef；`slot`：具名用途位置；`created_by`：建立引用的账户 ID 或系统任务名；`created_at`：UTC 时间。同一 file_id＋target＋slot 的有效引用唯一 |

uploading 表示直传授权已登记；核验完成并满足 Q-002 确认的内容稳定条件后成为 verified。回收事务在到期且引用数为零时改为 cleaning，OSS 删除成功后改为 deleted。引用作为独立关系保存，verified 文件既可暂存也可被多个获准资源引用。

### 内部能力签名

```text
attach_files(tx, context, target, purpose, file_ids, slot) -> list[FileReference]
retain_files(tx, context, source_target, target, file_ids, slot) -> list[FileReference]
release_references(tx, context, target, reference_ids, retention_basis) -> ReleasedReferences
prepare_file_read(context, target, file_id) -> AuthorizedFileRead
```

file_ids 为去重后的 EntityId 集合，数量由用途及主体规则检查；slot 为该资源具名图片／证据位置。target 由已授权主体用例提供，context 由服务端建立。

- attach_files 核对当前动作资格、文件为操作者所有、用途匹配、state=verified 及内容稳定；在同一事务建立引用，返回包含 reference_id 的完整 FileReference；相同有效关系重复建立时沿用已有 reference_id。
- retain_files 用于编辑历史等已有授权关联的保留，由主体证明 source_target 的读取与复制依据，核对原引用和用途，再建立新的历史引用。该入口以主体内部能力调用表达授权。
- release_references 按下述 RetentionBasis 核对主体保留规则，成功时在同一事务撤销整组指定关系并返回 ReleasedReferences；历史与证据继续由各自目标的有效引用保留。
- prepare_file_read 先由主体核对目标及引用的当前可见性，取得必要内容标识后在事务外签发短期只读 URL，返回 file_id、url、expires_at 及公开元数据。授权期限来自配置，URL 按持有者访问语义生效。

业务模块持久保存 file_id／引用，读取地址在获准查询时签发。文件使用关系及授权从主体读取，商品编辑历史和事项证据保留由各主体提出明确引用对象。

### 引用释放输入与结果

`reference_ids` 为去重后的 EntityId 集合，按数值升序处理；`target` 是本次获准维护的业务对象。空集合返回空的释放结果。RetentionBasis 由主体用例根据动作与规则构建，并由主体核对当前动作、对象状态和保留义务。

| RetentionBasis 字段 | 类型及含义 |
|---|---|
| action | 必填具名主体动作，如 product.image_replaced；值由该主体动作契约定义 |
| rule_refs | 必填且非空的规则引用集合，关联 BR／TR／UC 或人工决定记录 |
| basis_ref | ResourceRef 或 null；有处置决定等业务依据时指向对应对象，普通主体维护动作按其契约使用 null |
| preserved_targets | ResourceRef 集合；列出本次释放后仍承担历史或证据保留的目标，规则允许完全解除时采用空集合 |

主体用例核对 RetentionBasis 所引用的规则和依据；文件能力在文件锁内重查对应保留目标具有同一 file_id 的有效引用。该参数表达本次动作的保留依据，动作授权来自公共资格与主体规则。主体审计随本事务保存依据及关联对象。

| ReleasedReferences 字段 | 类型及含义 |
|---|---|
| target | 本次维护对象的 ResourceRef |
| released_reference_ids | EntityId 列表，按数值升序列出本次解除的全部引用 |
| affected_file_ids | EntityId 列表，去重并按数值升序列出涉及的文件；文件后续回收按到期及有效引用数判断 |

引用解除成功后，该 reference_id 结束其关系；同一文件随后在相同 target／slot 重新建立引用时分配新的 reference_id。当前引用关系与业务历史的引用分别维护。

| 调用情况 | 处理结果 |
|---|---|
| 全部引用属于获准 target，且保留规则满足 | 统一解除，返回完整 ReleasedReferences；主体变化、历史、审计及释放共用事务 |
| 部分 reference_id 不存在或位于其他目标的范围 | 统一抛出 RESOURCE_NOT_VISIBLE（404），本次整组变更回滚 |
| 规则要求的历史／证据引用尚未保留 | 抛出 FILE_RETENTION_REQUIRED（409），本次整组变更回滚 |
| 同一业务操作、同一幂等键重复提交 | 公共入口重放原业务响应并沿用 operation_id；后来建立的新引用保持原状 |
| 新操作再次提交已解除的 reference_id | 采用当前引用范围检查，返回 RESOURCE_NOT_VISIBLE（404） |

### 状态转换与数据约束

| 情况 | 结果 |
|---|---|
| 首次合法引用 | verified 文件保持内容标识，建立唯一引用关系 |
| 同一引用重复登记 | 返回已存在关系；同次业务结果按公共幂等契约重放 |
| 文件处于 uploading／cleaning／deleted | FILE_NOT_REFERENCEABLE（409） |
| 用途不匹配 | FILE_PURPOSE_MISMATCH（422） |
| 可见文件但归属或复制资格不符 | FILE_ACTION_NOT_ALLOWED（403） |
| 文件位于当前可见范围外 | RESOURCE_NOT_VISIBLE（404） |
| 内容核验尚待完成 | 按核验结果维持 uploading，业务引用返回状态冲突 |

删除商品展示或替换图片时，由主体规则确定当前引用与历史引用的保留。回收选取到期且所有有效引用均已解除的文件。

### 锁顺序与事务边界

主体用例通过 prepare 以授权 target 读取候选引用及 file_id，登记到 LockPlan；在写事务先取得资格及业务对象锁，再依第6级子序按 file_id 升序锁文件登记行、重读引用，并按 reference_id 升序锁既有引用行后校验和变更。attach／retain／release 与主体数据、历史、审计及事件共用事务；全部文件集合在进入文件锁域前确定；补充更早对象按公共重规划流程执行。

回收服务按 file_id 锁定登记行，在同一事务再次检查到期、状态和有效引用，认领 cleaning 后提交。此后执行 OSS 删除，成功后保存 deleted；删除失败保留 cleaning 进度重试。业务引用与回收通过同一登记行锁排序，回收认领后新的引用得到状态冲突。

### 超时、重试与异常恢复

OSS 核验、签名、删除在网络边界按配置处理超时及重试，上传完成回调以 file_id 对应登记的授权及内容核验事实推进。verified 的就绪条件是已核验且内容稳定；Q-002 将明确对象覆盖保护、具体内容标识和验证证据。引用方以该就绪条件设计业务关联，文件上传实现按 Q-002 的评审结论准入。

### 规则版本

授权保存用途、有效期和当次大小／格式规则及版本；核验依照该授权。回收任务读取已保存期限，引用数量等业务规则按具体用例和当前配置校验。配置模型及 .env.example 随实现建立。

### 验证场景与测试关联

[公共案例](design/test-cases/公共能力.md)：TC-COM-006 引用与回收竞争；TC-COM-007 资格、释放依据、重复释放及业务回滚；TC-COM-010 会话／事项与文件的共同锁序。Q-002 另外登记授权重复使用及内容稳定性验证。

#### NotificationIntent 输入

| 字段 | 类型／必填／范围与空值 |
|---|---|

| event_type | 已登记具名字符串，如 trade.request_accepted；具体触发、接收范围及模板由该动作唯一维护方定义 |

NotificationBatchResult 包含 items：每项为 recipient_account_id、notification_id、event_id、intent_key、created_at、read_at（新通知为 null）。event_id 在同一持久事件的重投中保持稳定；事件传输字段、游标及确认由 C2 细化。内部批量结果按接收账户 ID 排序。

#### 正常、业务失败与重复请求

正常：接受请求的用例先完成交易及商品转换，再提交接收人、来源交易和具名通知意图，通知与业务统一提交。失败：后续业务校验或写入失败时整体回滚。重复：同次幂等键重放原业务结果；内部同一 intent_key 返回既有通知／事件 ID。

#### 查询、已读与权限

通知已读和会话消息已读分别由各自能力维护；C4 定义通知列表、分页、已读接口。来源对象的当前可见范围决定可展示字段及跳转结果，接收通知本身保留按需求允许的事件提示。前端接收实时通知后按 event_id 去重，并按通知 ID 更新对应条目；投递恢复协议由 C2 完成。

#### 事件持久化及派发

create_notifications 登记事件意图并预分配稳定 event_id；公共事务包装在完成业务锁操作后，收集全部接收账户并按 ID 升序分配各自序号、保存事件，再提交。实时派发及后台投递从持久记录推进；通知创建结果表明数据库已持久化的业务结果，投递进度按 C2 的恢复流程追踪。

### 系统消息、通知及 C2 的交界

依据 [R2a review 修订](https://github.com/iy88/se-course-project-1/pull/43)，交易系统消息与通知使用同一稳定 business_event_id 和原业务记录；各投递 event_id 分别稳定，不能将不同投递误作同一事件。消息按业务事件唯一，通知按 intent_key 及接收账户幂等，不凭消息接收双方扩大通知范围。业务、消息、通知、审计及持久事件同一事务，最后统一分配账户事件序号；提交后派发失败重试。具体业务记录类型由 TASK-003 主体模型绑定，不声明已完成绑定。

C2 采用 conversation_kind（chat／trade／case）与对应 conversation_id 路由传输，数据库消息仍使用各自明确外键。已读事件仅发本账户其他连接，包括发送成功触发的游标推进。本人发送成功推进至本消息序号并清除较早未读，系统消息不推进任一方已读；归档历史仍可推进已读。传输恢复以数据库序号补拉、投递去重及当前资格重查为依据，事项事件仅到相关用户及固定认领且当前有管理资格的管理员。完整 C2 协议随本任务第 4 批交付。

### C9通知与传输数据交界

Notification保存业务event_type、模板、来源与首次已读事实；传输事件按C2投影为notification_created／notification_read并引用notification_id。创建结果的event_id由对应接收人的事件结果取得，不在Notification保存反向event_id或复制未读总数。business_event_id输入及公共数据关系见[公共数据模型](#interfaces-07)；C2评审输入为PR #48。

### R1 业务契约

R1 涉及商品占用、请求关闭和交易会话三类联动；请求与交易在同一记录中表达。商品字段、会话字段、调用签名与锁集合由 R0／R2a 及第 4 批适配定义，本文件不重复。

#### 术语与边界

- **商品占用**：一笔已接受且未结束的交易对商品的排他锁单关系；同一商品同时至多一笔占用。占用由商品模块保存，交易模块保存持有占用的交易标识。
- **有效交易**：状态为进行中、有争议或异常交易的交易；只有有效交易持有商品占用。已完成／已终止／已拒绝／已撤回／已关闭不持有占用。
- **请求结束**：待接受请求因接受其他请求（转已关闭）、拒绝（转已拒绝）、撤回（转已撤回）、商品生命周期下架、撤销公开访问或相关账户封禁（转已关闭）而结束；按结果与原因记录。
- **交易会话**：每笔有效请求／交易唯一对应的会话；请求被判拒绝、撤回、关闭或交易结束时归档。
- 具体字段、调用签名、锁集合和会话消息结构在第 4 批细化；管理事项状态机由 TASK-004 定义；本文件只定义 R1 的业务事实、结果和通知范围。

#### 能力契约

R1 包含以下五项能力，触发、结果、事务位置和通知范围一并列明。

| 能力 | 触发事实 | 调用方 → 维护方 | 业务标识 | 前置与状态重读 | 成功结果 | 具名失败／冲突 | 事务与锁位置 | 通知与幂等 |
|---|---|---|---|---|---|---|---|---|
| 取得商品占用 | 卖方接受一条待接受请求 | 交易用例 → 商品模块（R0） | product_id、trade_id、actor_account_id | 商品公开可交易且无其他有效占用；请求为待接受；锁商品后重读状态与占用 | 商品交易中，占用持有者为 trade_id | OCCUPANCY_CONFLICT；PRODUCT_NOT_AVAILABLE；REQUEST_ALREADY_ENDED（请求已拒绝／撤回／关闭） | 同一事务；账户资格锁 → 幂等占位 → 商品行锁 → 重读 → 交易行锁；商品先锁、状态重读 | 通知请求买方接受结果；被关闭请求的买方关闭原因；以接受动作幂等键定位 |
| 释放商品占用 | 交易完成、有效取消／协商终止、管理调整结束 | 交易用例 → 商品模块（R0） | product_id、trade_id、结束依据 | 占用持有者必须等于 trade_id；锁商品后重读占用；商品按结束规则置默认下架；卖方是否继续上架另行处理 | 占用解除；商品按结束规则置默认下架；继续上架由卖方另行选择，不在本能力内 | OCCUPANCY_NOT_HELD；STATE_CONFLICT（版本变化） | 同一事务；账户资格锁 → 幂等占位 → 商品行锁 → 交易行锁；释放与交易终态同一提交 | 通知双方结束结果与商品上架结果；完成时的评价入口由 T1 提供；以结束动作幂等键定位 |
| 关闭待接受请求（非拒绝／撤回） | 接受一条请求（关闭同商品其他待接受请求）；商品生命周期下架；撤销公开访问；相关账户封禁；管理处置撤销公开 | 交易用例 → 交易模块（本域） | product_id、trade_id（被关闭请求）、原因码、触发来源 | 请求必须为待接受；接受场景下同商品其他待接受请求一并关闭；原因与实际触发一致 | 请求转已关闭，原因记为其他用户锁单／商品已下架／公开访问已撤销／相关账户被封禁；不计失败交易 | REQUEST_ALREADY_ENDED；STATE_CONFLICT | 同一事务；随接受或关闭动作在同一交易锁集合内完成；逐请求按 ID 升序 | 通知每个被关闭请求的买方；封禁场景同时通知双方；由业务动作触发，不单独接受客户端幂等键 |
| 创建交易会话 | 有效购买请求创建成功（BR-01） | 交易用例 → 会话模块（R2a） | trade_id、product_id、buyer_id、seller_id、trade_conversation_id | 同一事务已写入待接受记录；同一 trade_id 无分支时创建，已有分支返回原分支并由入口打开，不重复创建；分支创建失败不得留下无分支请求 | 返回唯一 trade_conversation_id；已有分支返回原分支；分支与系统消息同事务写入；交易保存标识 | TRADE_CONVERSATION_CREATE_FAILED | 同一事务；交易记录写入后调用；分支创建在会话子域锁内；失败整体回滚 | 通知卖方新请求；系统消息定位请求与分支；按 trade_id 唯一，重试返回已有 trade_conversation_id |

拒绝、撤回是独立请求动作，分别转已拒绝、已撤回，不经过“关闭待接受请求”能力；已拒绝、已撤回、已关闭均不计失败交易。

#### 结果语义

| 结果 | 语义 | 使用场景 |
|---|---|---|
| OCCUPANCY_ACQUIRED | 占用取得成功 | 接受请求 |
| OCCUPANCY_RELEASED | 占用释放成功 | 完成、终止、管理调整结束 |
| OCCUPANCY_CONFLICT | 同商品已有其他有效占用；本次事务不写入占用、交易或分支（并发失败方的请求状态可能已由成功方接受动作关闭，不属于本次写入） | 并发接受 |
| PRODUCT_NOT_AVAILABLE | 商品生命周期或展示资格不允许首次接受取得占用 | 接受请求 |
| OCCUPANCY_NOT_HELD | 释放时占用持有者不是本交易 | 释放竞态 |
| REQUEST_CLOSED | 请求按实际原因关闭 | 接受关闭其他请求、下架／撤销公开／封禁关闭 |
| REQUEST_ALREADY_ENDED | 请求已结束（拒绝／撤回／关闭），当前动作不可执行；同键重试由 C1 幂等重放 | 对已结束请求再次操作 |
| TRADE_CONVERSATION_CREATED | 分支创建成功，返回唯一 trade_conversation_id | 请求创建 |
| TRADE_CONVERSATION_REUSED | 已有分支，返回原分支，不重复创建 | 分支已存在时的重复进入（同键重试由 C1 重放） |
| TRADE_CONVERSATION_ARCHIVED | 分支归档成功，返回归档结果 | 请求或交易结束 |
| TRADE_CONVERSATION_ALREADY_ARCHIVED | 已归档，返回既有结果 | 重复归档／补偿重放（同键重试由 C1 入口重放，不进入本结果） |
| TRADE_CONVERSATION_CREATE_FAILED | 会话侧创建失败，业务事务回滚 | 分支创建失败 |
| TRADE_CONVERSATION_NOT_FOUND | 分支不存在，无法归档 | 数据不一致或错误调用 |

接口层把具名结果映射为稳定错误码与 HTTP 状态；错误码在第 3 批接口文件中登记，不在此重复。

#### 不变量

1. 同一商品同时至多一笔有效交易；待接受请求不占用商品。
2. 占用的持有交易必须是该商品的有效交易；占用只由该交易结束（完成／终止）或认领管理员有依据调整而释放，商品模块不得自行释放。
3. 接受请求、关闭其他待接受请求、取得占用、保持请求创建时已建立的分支、登记通知意图在同一事务提交；占用、交易、其他请求关闭、分支或通知意图的持久化失败整体回滚。其他待接受请求已结束时按幂等跳过，不因并发关闭使本次接受失败；通知投递失败发生在提交后，不回滚业务。
4. 同一交易只有一条分支；分支不因冻结解除或交易恢复自动重开；归档保留消息、已读与历史。
5. 冻结不释放占用、不改变生命周期状态、不终止交易、不归档分支；暂停双方上架及交易操作、禁止双方两类 IM，只读与管理沟通保留；等待计时暂停／续算见 T1。
6. 交易结束（完成／终止）时释放本笔占用，并解除本笔交易名下的全部冻结记录；其他交易的有效冻结与账户封禁继续。商品默认已下架；卖方在无其他限制且符合资格时另行选择继续上架。
7. 商品及交易时内容在接受请求时形成不可变快照；提交请求时不建快照，后续商品编辑不改变历史内容。
8. 已完成／已终止保持终态；管理员也不能恢复或改写终态，返回 TRADE_TERMINAL。恢复仅适用于未结束交易，仍持原占用；有争议／异常恢复与解除冻结分别校验，恢复不启动计时。
9. 待接受请求无自动有效期；普通商品编辑（标题、描述、图片、价格、分类等）不关闭已有请求；商品下架、撤销公开访问、账户封禁仍按关闭规则处理。
10. 请求或交易结束时保留请求结果、确认、约定、争议及管理依据历史，不物理删除。
11. 同一交易至多一条生效约定、一条待决取消、一条未解决争议；每方至多一条当前完成确认，历史只增不减。
12. **完成与终止均保留双方当前确认**；变更生效、争议解决、管理恢复时清空当前标记并保留历史；终止后的“当前”仅表示最后一次有效声明，不表示待完成。
13. 等待计时每交易至多一条活动记录；冻结暂停、解冻续算，变更／争议／终止／超时结束。
14. 存在未结束有效交易时，卖方不得下架商品；R0 必须拒绝并保持占用。

## 公共能力扩展边界

依据：袁尚峰于2026-11-17要求通过接口职责、依赖方向及组装关系表达扩展；本批扩展细化随对应PR交付。应用语言及框架采用[技术栈独立的应用架构](design/architecture/07-技术栈独立的应用架构.md)。

### 依赖结构与应用组装

公共能力声明所需端口及输入／结果，主体模块实现业务资格、来源解析和投影，应用组装层显式连接实现。公共核心依赖端口，不导入商品、交易或事项实现；主体用例调用公共能力并提供所属事实。基础设施适配器实现存储、队列和网络端口。组装可采用静态映射或显式构造，类型及配置检查保证完整性。

扩展通过增加所属模块实现与组装项完成，公共生命周期算法保持稳定。API枚举、schema、输出白名单及应用组装随正式能力变化更新。当前业务用途的枚举是已开放能力集合，不表示公共核心必须按业务用途分支。扩展无需动态插件加载或数据库插件表。

端口契约必须定义调用阶段、显式事实、结果／错误、事务参与及锁需求。prepare阶段发现全部依赖并纳入C1 LockPlan；资格与业务锁后重读事实再判断。端口执行不得在较晚锁域追加较早的锁；依赖集合变化使用C1回滚重规划。外部I/O在事务外执行，提交前重查必要事实。

### 扩展验证

扩展检查使用测试夹具增加一种用途或来源实现，覆盖成功、策略拒绝、缺失／重复组装和锁后资格变化。模拟用途不增加正式业务需求；实际运行结果在对应编码任务登记。
