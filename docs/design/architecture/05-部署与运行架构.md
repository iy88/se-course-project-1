# 5. 部署与运行架构

## 运行单元

API、IM、worker、scheduler 共用后端版本及配置模型，支持单机多实例。各实例独立建立连接池；实例内维护连接和执行中临时数据，共享持久状态与协调通过 PostgreSQL／Redis 完成。

## 入口与生命周期

采用原生进程、systemd 与 Nginx，当前验收部署为单机多实例。API 和 IM 分别配置上游列表，支持应用内部进程分发及外部负载均衡。健康检查区分存活和就绪；优雅退出排空请求、衔接 IM 重连、停止领取新任务并按确认及租约机制接管。

多机变化基于性能结果评审，实例地址、依赖连接和上游关系由配置表达。

## 配置作用域

后端以指定的一份 .env 为运行配置事实来源，Pydantic Settings 定制配置源，形成只读类型化配置；必要功能配置完整且类型、范围、关联关系校验通过后启动。具体策略数值来自配置，默认值集中登记依据。

用户端与管理端分别维护 dev server、代理、API／WS 公开地址、基础路径和构建选项，构建输入独立。前端通过接口取得业务能力限制；Nginx 和启动参数按部署输入派生。

后端 .env.example 及两端配置示例在对应实现任务中建立，并与配置模型同步。

## CI/CD 与发布

GitHub Actions 执行静态、文档契约、适用测试和构建验证；Jenkins 构建发布产物、检查环境、执行迁移、滚动更新实例、使入口配置生效并验证。发布关联明确提交、产物及配置版本。

迁移是独立发布步骤。滚动期间检查数据库、接口、事件和任务兼容性。保留可用版本及配置，按迁移兼容范围回退。部署工作归 TASK-001。

## 环境与资源

开发、测试、正式环境的数据库、Redis 命名空间、文件和邮件资源分别登记。全部署核算数据库／Redis 连接、内存及队列预算；参数值和默认值待清单评审。
