# 5. 部署与运行架构

## 运行单元

API、IM、worker、scheduler 共用后端版本及配置模型，支持单机多实例。各实例独立建立连接池；实例内维护连接和执行中临时数据，共享持久状态与协调通过 PostgreSQL／Redis 完成。

## 入口与生命周期

采用原生进程、systemd 与 Nginx，当前验收部署为单机多实例。API 和 IM 分别配置上游列表，支持应用内部进程分发及外部负载均衡。健康检查区分存活和就绪；优雅退出排空请求、衔接 IM 重连、停止领取新任务并按确认及租约机制接管。

多机变化基于性能结果评审，实例地址、依赖连接和上游关系由配置表达。

## 配置作用域

后端以指定的一份 .env 为运行配置事实来源，通过所选技术栈的配置加载适配器形成只读类型化配置；必要功能配置完整且类型、范围、关联关系校验通过后启动。具体策略数值来自配置，默认值集中登记依据。

用户端与管理端各自维护 Rsbuild 开发服务器与构建配置。两端浏览器都通过当前页面同源的 `/api/v1` 访问 API。开发使用 Rsbuild 代理，生产由 Nginx 在各前端 HTTPS 入口路由静态文件和 API。代理保留浏览器提供的 `Origin` 并保留 API 路径前缀，后端 API 监听本机或私网，由代理访问。应用使用各环境配置的公开 Origin 校验写请求。开发联调会话与 CSRF 时使用 HTTPS，以验证与生产一致的 Secure Cookie。

WS 公开入口及上游按部署输入配置。前端通过接口取得业务能力限制。

后端 .env.example 及两端配置示例在对应实现任务中建立，并与配置模型同步。

## CI/CD 与发布

GitHub Actions 执行静态、文档契约、适用测试和构建验证。开发者在本地执行业务冒烟验证。Jenkins 为 main 提交构建发布产物，执行环境检查、迁移、滚动更新、入口配置生效与部署就绪检查。发布关联明确提交、产物及配置版本。

迁移是独立发布步骤。滚动期间检查数据库、接口、事件和任务兼容性。保留可用版本及配置，按迁移兼容范围回退。部署工作归 TASK-001。

## 环境与资源

开发、测试、正式环境的数据库、Redis 命名空间、文件和邮件资源分别登记。全部署核算数据库／Redis 连接、内存及队列预算；参数值和默认值待清单评审。

## 2026-11-14 与legacy共存的部署输入

袁尚峰（iy88）明确：v2与legacy同机并存、独立目录，沿用类似legacy的部署方式。PostgreSQL共用实例，v2使用独立数据库名和数据库用户；Redis共用实例，本轮采用独立键前缀，逻辑DB可在部署配置时另选。域名和OSS资源由袁尚峰分别提供独立配置。该前缀同时覆盖Session、Stream、任务队列、锁、配额及调度键。

当前先完成接口与技术设计；实际目录、端口、连接预算、域名及OSS配置在部署阶段按上述边界落实。Redis逻辑DB及键前缀用于命名空间隔离，清理与恢复按v2范围执行。
