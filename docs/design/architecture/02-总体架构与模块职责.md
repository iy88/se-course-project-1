# 2. 总体架构与模块职责

## 总体结构

采用模块化单体，后端代码和版本统一维护；API、IM、worker、scheduler 按运行需要部署多个服务实例。业务模块提供统一用例与内部能力，实例通过同一逻辑 PostgreSQL 和 Redis 协作。

“模块”表达主体数据与动作的维护边界，“服务实例”表达运行单元。数据维护责任通过模块接口落实，跨模块用例共享数据库事务。

## 主体模块

| 模块 | 主体及维护数据 | 动作 |
|---|---|---|
| 账户 | 账户、邮箱验证、凭据版本、管理资格、账户限制；Redis Session | 注册登录、退出、资料和邮箱管理、凭据失效、封禁与解除 |
| 商品 | 商品、图片引用、编辑历史、审核、评论与回复、收藏、分类关联和申请、禁发范围 | 发布编辑、审核、上下架、查询、评论收藏、取得与释放占用 |
| 分类 | 一级分类、主名称、别名、启停状态 | 创建、更名、别名维护、停用、逻辑删除及名称解析 |
| 交易 | 请求／交易、成交快照、约定版本、确认、转换历史、冻结与计时、评价 | 请求处理、约定、完成、终止、争议、异常、恢复与评价 |
| 会话 | 普通私聊、交易分支、事项会话、消息、参与关系、已读 | 建立会话、发送读取、归档及资格校验 |
| 处置事项 | 举报、事项、认领、核查、证据关联、决定及执行关联 | 举报补充、认领处理、问询申辩业务、作出决定及协调执行 |
| 通知 | 通知、接收关系、已读 | 创建、查询、未读统计及已读 |

事项沟通复用会话模块，处置事项提供关联对象和访问依据。商品评论与商品共同维护。分类模块管理公共分类，商品模块管理商品归属及随商品提出的申请。

## 数据归属与聚合

主体模块执行其数据变化；处置事项保存决定依据，账户维护账户限制，交易维护冻结及计时，商品维护展示限制。关联标识连接决定和执行结果。

本人业务、待办和统计由查询聚合能力读取各主体数据，写操作调用对应业务用例。文件、邮件、实时传输、日志审计和配置提供公共支撑。

## 账户资格

管理员保留校园用户基础功能并叠加管理能力；同一账户可使用用户端及管理端。权限按参与关系、对象归属、管理资格、认领及当前状态校验。

## 设计分工

四位成员均形成任务：TASK-001 承担账户、通知、聚合、公共技术设计及部署；其余三位承担商品与分类、交易、会话与处置事项。具体设计包见[任务索引](../tasks/索引.md)。

## 任务交界归属

[并行对接安排](../detailed-design/04-并行对接与交界归属.md)为商品占用、交易分支触发、会话模型和处置执行指定唯一设计任务。任务可以跨模块设计完整关联，主体模块依其职责执行状态维护。各 PR 指定实际交叉审查姓名。
