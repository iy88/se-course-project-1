## 模型分层与承载边界

会话是双人容器，分支是同一对用户下的具体用途线程，参与关系与已读进度挂在分支上。会话层保证“同一对用户只有一个入口”，分支层保证普通私聊、逐笔交易与事项沟通分别保存消息与已读，BR-18 的“两类可在同一双人入口组织，但消息归属与历史可区分”由该分层表达。

买卖双方消息与事项沟通消息分别建实体。买卖双方消息归属 [C-07 IM 会话](../../../appendices/class-analysis/C-07-咨询会话.md) 与 [C-08 消息](../../../appendices/class-analysis/C-08-消息.md)；事项沟通消息归属 [C-13 处置记录](../../../appendices/class-analysis/C-13-处置记录.md) 的关联沟通消息。会话模块为三类线程提供共同的存储、资格与传输能力，但不因此把事项沟通并入 C-08 消息类：C-08“消息不承载处置通知与沟通单”的边界与需求侧“管理沟通不使用 C-07／C-08”的口径保持成立，本模块的复用不改变两者的归属。

| 实体 | 职责 | 关键唯一约束 |
|---|---|---|
| 会话 | 双人容器的稳定标识与建立时间，不承载消息与已读 | 两账户 ID 升序拼接的 `pair_key` 唯一 |
| 分支 | 一次具体交流线程，持有归档状态与序号基准 | `trade_id` 唯一；`(case_id, peer_account_id)` 唯一；普通私聊每会话至多一条 |
| 参与关系 | 分支内账户的参与角色与已读进度 | `(branch_id, account_id)` 唯一 |
| 买卖双方消息 | `private`／`trade` 分支内不可变的文字或系统请求事件 | `(branch_id, seq)` 唯一 |
| 事项沟通消息 | `case` 分支内的问询、说明、申辩与管理回复，关联处置记录 | `(branch_id, seq)` 唯一；`case_id` 非空 |

## 会话与分支字段

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `conversation_id` | EntityId | 会话稳定标识，与 `pair_key` 一一对应 |
| `pair_key` | 字符串，唯一 | 两个账户 ID 升序拼接（如 `1001:1002`）；再次发起时定位既有会话，不新建（BR-18） |
| `conversation_created_at` | UTC 时间 | 首次发起时写入 |
| `branch_id` | EntityId | 分支稳定标识 |
| `branch_type` | `private`／`trade`／`case` | 建立后不变 |
| `trade_id` | EntityId，可空 | `branch_type = trade` 时必填并唯一；来自 TASK-003 的每笔有效请求（BR-01） |
| `case_id` | EntityId，可空 | `branch_type = case` 时必填 |
| `peer_account_id` | EntityId，可空 | `branch_type = case` 时必填，标识该线程对应的相关账户 |
| `branch_seq_head` | 整数，默认 0 | 分支内已分配的最大消息序号；新消息序号为其加一，仅在分支行锁内变更 |
| `branch_created_at` | UTC 时间 | 分支建立时间 |
| `archived_at` | UTC 时间，可空 | 归档单向，不重开（4.15） |
| `archive_reason` | `trade_request_closed`／`trade_completed`／`trade_terminated`／`case_closed` | 与 `archived_at` 同时写入；分支只记聚合原因，请求被拒绝、撤回、锁单关闭、下架关闭、撤销公开访问、账户封禁等实际原因由交易记录保存（BR-02），R1 就绪后核对字段对应（TR-15、TR-17） |

普通私聊分支只存在一条，建立后不因交易或请求变化归档（BR-18）；交易分支与请求／交易一一对应，不同交易不复用同一分支；事项分支按“一个事项 + 一个相关账户”划分，同一事项的不同账户各有线程。

## 参与关系字段

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `branch_id`／`account_id` | EntityId | 联合唯一；账户必须为两个不同账户，不向本人发起（BR-02、BR-18） |
| `participant_role` | `peer`／`manager` | 普通私聊与交易分支为两条 `peer`；事项会话为一条 `manager` 与一条 `peer` |
| `joined_at` | UTC 时间 | 分支建立时写入 |
| `last_read_seq` | 整数，默认 0 | 该账户已展示的最大序号，单调不回退 |
| `last_read_at` | UTC 时间，可空 | 最近一次已读推进时间 |

事项会话参与者为该事项的当前认领管理员与相关账户。管理端读取校验账户仍为该事项认领人，认领变化不转移既有线程（BR-34）。

## 买卖双方消息字段

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `message_id` | EntityId | 消息稳定标识 |
| `branch_id`／`seq` | EntityId／正整数 | 分支内自 1 递增，连续分配；并发发送按分支行锁串行化 |
| `sender_kind` | `account`／`system` | 系统事件不伪装为用户文字（BR-01） |
| `sender_account_id` | EntityId，可空 | `sender_kind = account` 时必填，须为该分支参与者 |
| `message_type` | `text`／`system_event` | 首版仅文字，不提供撤回、编辑、附件及群聊（BR-17） |
| `body` | 文本 | 长度与频率限制按配置在校验层执行，阈值随实现阶段确定（BR-17） |
| `source_ref` | `resource_type` + `resource_id`，可空 | `system_event` 记录关联的商品与请求，与通知中心定位同一业务，不重复建业务（第 4 章 4.17） |
| `message_created_at` | UTC 时间 | 发送时间；消息不可变，不设自动清理期限（4.18） |

## 事项沟通消息字段

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `case_message_id` | EntityId | 事项沟通消息稳定标识 |
| `branch_id`／`seq` | EntityId／正整数 | 与买卖双方消息相同的分支内序号规则，两类消息各自连续 |
| `case_id` | EntityId | 与分支一致；处置记录直接关联本实体，不另存一份事项依据 |
| `sender_kind` | `account`／`manager`／`system` | `manager` 为当前认领管理员；`system` 用于处置通知留痕 |
| `sender_account_id` | EntityId，可空 | `account`／`manager` 时必填；`manager` 还须为该事项当前认领人（BR-34） |
| `message_kind` | `inquiry`／`statement`／`appeal`／`manager_reply`／`system_notice` | 问询载明需要回应的范围；说明与申辩分别记录，不互相覆盖（BR-26、UC-C08-01） |
| `body` | 文本 | 长度与频率限制同买卖双方消息 |
| `created_at` | UTC 时间 | 不可变，不设自动清理期限（4.18） |

两类消息均一经写入不可修改或删除，归档、解冻与处置不删除历史；违规内容处理以事项记录为依据，不抹除消息本身。

## 消息承载边界

会话模块同时为买卖双方分支与事项线程提供存储与投递，但两类消息分别建实体、分别授权：买卖双方消息只对分支参与者开放，事项沟通消息只对该线程参与者开放。管理员读取买卖双方消息仍按事项证据引用逐条定位，不因本模块复用而获得分支整体读取权（BR-19）；举报人只获得本人举报的结论通知，不读取被举报人线程（BR-26）。

## 三类会话的业务差异

| 维度 | 普通私聊 `private` | 交易分支 `trade` | 事项会话 `case` |
|---|---|---|---|
| 建立触发 | 双方任一从个人页等入口主动发起（FR-04） | 购买请求创建成功时由交易用例建立（BR-01） | 需要与相关账户沟通的事项动作：问询，实际处置与冻结、状态调整的告知与申辩（BR-26、BR-32、BR-33、第 4 章 4.17），异常交易处理（FR-14）；商品审核结果按审核原因与重提处理，不建线程（BR-10）。具体动作与字段由第 2 批定义 |
| 复用与唯一 | 同一对用户复用唯一会话与唯一普通私聊分支 | 每笔请求／交易一条分支，不复用其他交易分支（BR-18） | 每“事项 + 相关账户”一条，同一事项各方不共享线程 |
| 参与者 | 两名用户 | 买卖双方 | 当前认领管理员与相关账户 |
| 归档 | 不随商品、请求或交易结束归档（BR-18） | 请求关闭（含锁单关闭、下架、撤销公开访问、账户封禁）及交易完成、终止时归档，只读历史（BR-02、TR-15、TR-17、4.15） | 事项结案归档，只读 |
| 发送限制 | 任一参与账户被封禁，或二人之间存在有效交易冻结时禁发（BR-32、BR-33） | 同普通私聊，并叠加归档后禁发；交易冻结不等于结束，不因此归档（BR-18） | 作为处置沟通例外，不因封禁或交易冻结禁发（BR-32、BR-33） |
| 管理访问 | 仅限认领事项证据引用定位的消息（BR-19） | 同上，不因认领某笔交易而读取全部消息（BR-19） | 由该事项当前认领管理员作为参与者读取；举报人不因举报身份读取他人线程（BR-26） |
| 消息承载 | C-08 买卖双方消息 | C-08 买卖双方消息（含系统请求事件） | C-13 关联的事项沟通消息，不复用 C-08 消息 |
| 未读口径 | 按分支独立计数 | 按分支独立计数 | 按线程独立计数 |

由此形成四点设计结论：

1. 事项会话按相关账户分别成线程，同一事项的举报人、被举报人及受处置双方各有与管理员之间的独立线程。依据是举报人不因举报身份获得对方申辩内容（BR-26）、受处置用户从本人通知或本人列表进入申辩（4.18）。
2. 事项会话不属于买卖双方 IM，冻结与封禁的禁发范围不覆盖该线程；该线程仍要求账户属于事项相关人且当前具备事项访问资格（第 4 章 4.10）。
3. 三类会话的互不替代由分支类型承担：交易文字留在交易分支，聊天位置不代替请求接受、约定确认与完成确认（BR-18）。
4. 聊天已读与通知已读分别维护，消息已读不消除通知未读，通知已读不消除消息未读（第 4 章 4.17）。

### 已确认的设计结论

| 结论 | 内容 | 确认人／日期 |
|---|---|---|
| 承载边界 | 会话模块承载三类线程；事项沟通消息独立建实体并由 C-13 关联；C-07／C-08 仍只覆盖买卖双方 IM，需求“管理沟通不使用 C-07／C-08”的口径不变 | 张新悦，2026-11-13 |
| 线程划分 | 事项线程按“事项 + 相关账户”逐一建立，同一事项各方不共享线程 | 张新悦，2026-11-13 |

## 已读进度与未读计数

- 已读推进以“已展示的最大序号”表达：客户端展示到 `seq = N` 时提交 `N`，服务端取得单调最大值，忽略回退值与乱序旧值。
- 发送方消息提交后，其 `last_read_seq` 推进到该消息序号，表达本人已展示；因此分支未读可直接取 `branch_seq_head − last_read_seq`，不重复统计本人消息，也不需要逐条未读表。
- 打开会话列表、查看其他分支、把通知标为已读、读取待办，均不推进任何分支的已读进度（第 4 章 4.17）。
- 未读计数为读取派生值，不落库为独立状态；分支归档后不再变化（消息不可新增）。
- 三类线程的已读进度都记录在参与关系上；同一事项的不同线程分别计算，管理员侧的已读不影响用户侧，反之亦然。

## 状态与数据约束

| 对象 | 状态与约束 | 依据 |
|---|---|---|
| 会话 | 无生命周期状态，建立后不删除 | BR-18 |
| 分支 | `active` → `archived` 单向；归档后只读 | BR-18、4.15 |
| 参与关系 | 无状态；已读进度单调 | 第 4 章 4.17 |
| 买卖双方消息 | 无生命周期状态，不可变 | BR-17、[C-08 消息](../../../appendices/class-analysis/C-08-消息.md) |
| 事项沟通消息 | 无生命周期状态，不可变；`message_kind` 建立后不变 | BR-26、[C-13 处置记录](../../../appendices/class-analysis/C-13-处置记录.md) |
| 数据库约束 | `conversation.pair_key` 唯一；`trade_id` 唯一；`(case_id, peer_account_id)` 唯一；`(branch_id, account_id)` 唯一；两类消息各自 `(branch_id, seq)` 唯一；事项沟通消息 `case_id` 非空；`sender_kind` 与 `sender_account_id`、`message_kind` 与发送者角色的配对校验 | 本专题 |

发送资格由“参与关系 + 分支未归档 + 账户当前资格 + 二人间冻结集合”共同判定，资格与冻结事实分别由账户与交易模块维护，本模块只读取而不再保存第二份状态。

## 发送与读取资格

| 动作 | 允许条件 | 拒绝结果 |
|---|---|---|
| 读取分支与历史 | 当前身份属于该分支参与关系；事项线程的管理端还须为事项当前认领人 | `PARTICIPANT_REQUIRED`（按公共 `RESOURCE_NOT_VISIBLE` 映射，不泄露分支存在） |
| 发送消息 | 读取资格成立，且分支未归档，且不属于封禁账户，且二人间无有效交易冻结；事项线程不受封禁／冻结限制 | `BRANCH_ARCHIVED`（按 `STATE_CONFLICT` 映射）；`MESSAGE_SEND_FORBIDDEN`（按 `ACTION_NOT_ALLOWED` 映射） |
| 建立普通私聊 | 发起人已登录，目标为其他已存在账户 | `SELF_CONVERSATION_FORBIDDEN`（按 `INPUT_INVALID` 映射） |
| 推进已读 | 读取资格成立且序号不超过当前 `branch_seq_head` | `INPUT_INVALID` |
| 事项线程发言 | 发送者角色与消息类型匹配：`manager` 只发问询、回复与处置通知，`peer` 只发说明与申辩；提交说明或申辩不自动撤销处置 | `ACTION_NOT_ALLOWED` |

具名结果与 `BusinessError` 沿用[公共事务与权限](公共事务与权限.md)的结构：成功返回 `Allowed` 或具名结果类型，业务失败抛出带稳定错误码的错误，由公共包装统一回滚并映射 HTTP 状态。

## 锁顺序与事务边界

本模块落在公共锁序第 6 级的固定子序内：会话 → 分支 → 参与关系 → 消息 → 已读进度。各动作按涉及子域推进，不越级回取更早锁域。

| 动作 | 锁与写入 | 事务边界 |
|---|---|---|
| 建立或复用普通私聊 | 会话行按 `pair_key` 唯一约束插入或读取；分支、参与关系随后插入 | 由用户入口用例持有事务并提交 |
| 建立交易分支 | 上游用例已持账户资格锁与交易行锁；本模块在同一事务内插入会话（如缺）、分支、参与关系与系统请求消息，返回 `branch_id` 与 `message_id` | 与交易接受／请求创建同一事务，由交易用例提交 |
| 归档分支 | 分支行加锁后写 `archived_at`、`archive_reason` | 请求关闭、交易结束或事项结案事务内完成；解冻不重开 |
| 发送消息 | 分支行加锁分配 `seq`（`branch_seq_head + 1`），按分支类型插入对应消息实体，推进发送方参与关系进度 | 用户入口事务 |
| 推进已读 | 参与关系行加锁后单调更新 | 用户入口事务；只写进度，不改消息 |

跨模块调用由调用方用例持有同一 `AsyncSession` 与执行上下文，内部能力通过参数接受该上下文，不在内部提交（ADR-003）。重复建分支由唯一约束兜底：冲突时返回既有分支标识，不产生第二条分支或第二条系统消息。

## 幂等、错误与并发

- 发送消息与推进已读使用公共幂等作用域 `(actor_id, operation_name, idempotency_key)`；同键同摘要返回已保存的消息或进度结果，同键不同摘要返回 `IDEMPOTENCY_PAYLOAD_CONFLICT`（[公共事务与权限](公共事务与权限.md)）。
- 分支建立由上游用例的幂等记录保证；`trade_id` 唯一约束冲突只映射为“分支已存在”，读取后返回原分支，不作为内部错误。
- 同一分支并发发送由分支行锁串行化，序号连续且不重复；并发已读取较大值。
- 锁等待、事务时间与重试次数取后端配置；死锁或锁集合变化按公共重试流程整事务重做。

## 对外能力与传输字段

内部能力按设计签名表达，参数与返回沿用公共上下文的命名：

```text
ensure_pair_conversation(tx, context, account_ids) -> conversation
create_branch(tx, context, conversation, branch_type, source, participants) -> branch
append_peer_message(tx, context, branch, actor, message_type, body, source_ref) -> message
append_case_message(tx, context, branch, actor, message_kind, body) -> case_message
archive_branch(tx, context, branch, archive_reason) -> branch
advance_read_progress(tx, context, branch, actor, displayed_seq) -> participant
require_branch_access(branch, actor, qualifications, freeze_facts) -> Allowed
```

实时投递由 TASK-001 的 C2 承接，本模块提供以下事件载荷字段：

| 字段 | 说明 |
|---|---|
| `event_id`／`event_type` | 事件标识；`message_created`、`message_read`、`branch_archived` |
| `conversation_id`／`branch_id`／`branch_type` | 定位分支与用途，客户端据此放入对应入口 |
| `source_ref` | 交易或事项关联，不含其他分支内容 |
| `actor_account_id`／`recipient_account_ids` | 发送者（或已读推进者）与投递接收账户；系统事件无发送者账户 |
| `message_id`／`case_message_id`／`message_seq` | 消息定位；承载实体由分支类型决定，两类消息标识不混用 |
| `message_type`／`message_kind`／`sender_kind` | 买卖双方消息记 `message_type`；事项线程记 `message_kind` 与发送者角色 |
| `occurred_at` | 业务发生时间，UTC |

投递与恢复约定：订阅粒度为接收账户，账户多 Session、Session 多连接各自维护本连接游标；断线恢复按分支 `seq` 增量拉取历史，不依赖 Redis 保留窗口补齐缺口（ADR-004）；重投按消息标识去重。`message_read` 只同步给该账户的其他连接，不投递给对端。事项线程事件只投递给该线程的两名参与者，不投递给举报人或买卖双方分支。R2a 不定义接口路径与参数，投递实现细节随 C2 对齐。

## 隐私与保留

- 输出字段按角色收敛：对端只读取本人参与分支的类型、对端账户标识、消息体与时间；不输出其他分支、其他事项或不相关账户信息（BR-18、BR-27）。对端显示名称按账户当前名称读取，不缓存历史名称（4.19）。
- 管理读取按事项证据引用逐条定位 `message_id`，不展开所在分支的其余消息，也不因认领某笔交易获得该分支全部消息（BR-19、BR-34）。
- 事项线程只向该线程的两名参与者输出消息与 `message_kind`；举报人仅获得本人举报的结论通知，不读取被举报人线程（BR-26）。
- 日志与审计记录 `request_id`、`operation_id`、`branch_id`、`message_id`、发送者与结果，不记录消息正文（ADR-009）。
- 会话、消息与已读进度不按时间自动清理，违规内容处理保留处理依据（4.18）。

## 验证场景与测试关联

设计阶段按下列预期核对模型与资格判定，运行条件与 TC 编号随本任务第 5 批登记：

1. 同一对用户再次发起普通私聊，复用既有会话与普通私聊分支，不新增条目（BR-18）。
2. 同一商品先后两笔交易各自建立分支，消息、已读与归档互不影响（BR-18）。
3. 分支归档后发送被拒绝、历史读取允许；解冻不重新打开分支（BR-18、4.15）。
4. 账户 p、q 之间存在有效交易冻结时，两人间普通私聊与全部交易分支禁发、历史可读；p 与第三方的会话不受影响（BR-33）。
5. 账户封禁期间两类 IM 禁发、历史可读，处置沟通线程仍可发送（BR-32、BR-33）。
6. 进入会话列表或查看其他分支不改变未读；展示到 `seq = N` 后未读为 `branch_seq_head − N`（第 4 章 4.17）。
7. 事项线程按相关账户分开，举报人无法读取被举报人的申辩内容（BR-26、4.18）。
8. 非认领管理员读取事项线程被拒绝，不泄露线程存在（BR-19、BR-34）。
9. 同一分支并发发送产生连续且不重复的序号；同键重复提交返回同一消息（ADR-003）。
10. 交易请求成功生成的分支内系统事件与通知中心定位同一请求，不重复建业务（第 4 章 4.17）。
11. 事项线程中管理员发起问询、用户提交说明、管理员回复及后续申辩分别记录并可在原事项定位；提交说明或申辩不自动撤销限制（BR-26、UC-C08-01）。
12. 商品审核不通过按审核原因与重提处理，不建立事项线程；商品审核结果不以沟通线程代替审核结论（BR-10）。

实时投递的送达与恢复（多实例分发、断线补齐、重投去重）与 2 秒可见指标由 C2 及阶段验证承接，见[质量要求](../../../requirements/06-质量要求.md)。
