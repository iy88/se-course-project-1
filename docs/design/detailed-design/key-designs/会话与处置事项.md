## 三类实体与承载边界

三类会话各自直接保存消息与阅读进度。普通私聊和交易沟通在同一双人入口展示时，按双方账户聚合查询；展示入口无需父容器实体。需求中的“交易分支”是逐笔交易沟通的业务称呼，对应 TradeConversation。

| 实体 | 标识及业务唯一性 | 固定参与者 | 生命周期 |
|---|---|---|---|
| ChatConversation | chat_conversation_id；(account_low_id, account_high_id) 唯一且 low < high | 两个不同账户 | 不随请求／交易结束归档 |
| TradeConversation | trade_conversation_id；trade_id 非空、外键、唯一 | trade_id 对应的买卖双方 | 请求拒绝／撤回／关闭或交易完成／终止时归档 |
| CaseConversation | case_conversation_id；(case_id, related_account_id) 非空、联合唯一 | 事项固定认领管理员与该相关用户 | 事项结案后归档 |

三类会话分别使用 ChatMessage、TradeMessage、CaseMessage，消息通过非空明确外键指向各自会话表，不使用多个可空会话外键或类型加 ID 的跨表外键。ChatMessage／TradeMessage 属于 [C-07](../../../appendices/class-analysis/C-07-咨询会话.md)／[C-08](../../../appendices/class-analysis/C-08-消息.md)，CaseMessage 由 [C-13](../../../appendices/class-analysis/C-13-处置记录.md) 关联，事项沟通保持独立于买卖双方 IM。

| 会话字段 | 类型及约束 |
|---|---|
| 各自会话主键 | EntityId，建立后稳定 |
| ChatConversation.account_low_id／account_high_id | 账户外键，按 ID 排序且不同 |
| TradeConversation.trade_id | 请求／交易统一记录外键；一笔记录始终对应同一会话，接受请求不另建会话 |
| CaseConversation.case_id／related_account_id | 事项、账户外键；用户须具备该事项问询／申辩等访问依据 |
| seq_head | 整数，默认 0，非负；各表分别维护消息序号 |
| created_at | UTC 时间 |
| TradeConversation／CaseConversation.archived_at | UTC 时间或 null；单向归档 |

具体拒绝、撤回、锁单关闭、下架、撤销公开、封禁等原因留在请求／交易业务记录。归档后不删除历史、不重开；已完成／已终止保持终态，不恢复交易、不重开原会话，不另建第二条交易会话，可由用户主动进入普通私聊，系统不迁移消息、不自动建立私聊。

## 参与及阅读进度

ChatReadProgress、TradeReadProgress、CaseReadProgress 各以本类型会话外键和 account_id 联合唯一，保存 last_read_seq（默认 0）、last_read_at（UTC 或 null）。账户必须是该会话有资格的参与者。私聊及交易双方角色由会话／交易关系确定，不存储恒定 peer 角色。

事项认领后固定，本版不提供转交。CaseConversation 不保存第二份管理员归属，管理访问实时校验事项认领人及其当前管理资格。资格失效不自动给其他管理员访问权，也不重建或转移线程。结案后原有合格参与者可读取历史，不能发送。相关用户按事项依据访问本人线程；举报身份本身不授予被举报人线程的访问权。管理员阅读进度按实际 account_id 保存，不共享或继承他人进度。

### 已读与未读

袁尚峰于 2026-11-14 明确选择：保留发送即推进，并接受同时清除较早未读。需求同步由 TASK-001 登记本次变更。

- 展示到序号 N 时提交 N；校验 0 ≤ N ≤ seq_head，取 last_read_seq 与 N 的最大值。
- 用户／管理员发送成功时，在同一事务将其进度推进到本次消息序号，较早尚未展示消息也被清除未读；发送失败或回滚不推进。系统消息没有发送账户，不推进任一方进度。
- 未读派生为 seq_head − last_read_seq；不另存未读总数。多 Session 共用账户进度，多连接以单调最大值同步。买卖双方发送接口可返回本次写入后、同事务内计算的对端会话未读总数；对端的具体已读游标、阅读时间及已读事件仅本人可见。
- 列表、其他会话和通知已读不推进本会话进度；聊天已读不替代任何业务确认。
- 归档后 seq_head 固定，但参与者仍可推进已读，未读可随阅读减少。

## 三类消息字段与约束

| 字段 | ChatMessage | TradeMessage | CaseMessage |
|---|---|---|---|
| 主键 | chat_message_id | trade_message_id | case_message_id |
| 非空会话外键 | chat_conversation_id | trade_conversation_id | case_conversation_id |
| seq | 各表 (会话外键, seq) 唯一、正整数 | 同左 | 同左 |
| sender_kind | account | account／system | account／manager／system |
| sender_account_id | 非空参与账户外键 | account 时非空，system 时为空 | account／manager 时非空，system 时为空 |
| message_type | text | text／system_event | text／system_event |
| body | 首版文本载荷 | 首版文本载荷／系统事件展示快照 | 首版文本载荷／告知快照 |
| message_kind | 无需存储 | 无需存储 | inquiry／statement／appeal／manager_reply／system_notice |
| business_event_id／event_type | 无 | 系统消息必填，事件标识在本表唯一 | 系统告知必填，事件标识在本表唯一 |
| source_ref | 无 | 系统消息按下节枚举关联具体业务记录，可空 | 由会话取得事项；具体处置动作引用在 R2b 绑定 |
| created_at | UTC，消息不可变 | 同左 | 同左 |

数据库约束承载外键、唯一性、序号及发送者空值配对；系统事件只能由可信用例内部能力创建，不接收客户端指定系统身份。CaseMessage 的 message_kind 与发送者匹配：用户仅 statement／appeal，管理员仅 inquiry／manager_reply，system 仅 system_notice。事项关联从会话取得，不在消息中保存第二份 case_id。

首版消息为文字；长度、频率等限制由配置校验。后续支持图片／文件时，可扩展 message_type 并为各类消息建立明确外键的附件引用明细，经 C3 验证 file_id 的用途、归属和内容稳定性；沿用会话归属、序号、权限、已读及事件机制。实际启用功能需需求确认与契约评审，本批不增加附件 API。

## 交易系统消息与业务引用

交易用例产生业务记录及稳定 business_event_id，在对应交易会话保存系统消息。body 保存当时必要展示事实，状态、约定及取消决定仍由业务记录维护；不凭文字反推业务状态。隐私字段按双方可见范围收敛，不展示举报人身份。

| event_type | 生成时机 | 展示内容 | 跳转及 source_ref |
|---|---|---|---|
| request_created | 请求成功写入 | 请求发起及时间 | 当前交易会话关联请求，source_ref 为空 |
| request_accepted／request_rejected／request_withdrawn／request_closed | 相应请求结果落库 | 结果、时间及允许展示的原因 | 所属请求，source_ref 为空 |
| agreement_proposed／agreement_change_proposed | 首约／变更提案写入 | 提案摘要与提出方 | agreement_proposal + 不可变提案 ID |
| agreement_confirmed／agreement_rejected／agreement_withdrawn | 提案确认／拒绝／撤回记录写入 | 对应提案、决定及时间 | agreement_decision + 该次决定 ID |
| completion_confirmed | 一方完成确认记录写入 | 确认方、时间及允许展示的说明 | completion_confirmation + 本次确认 ID |
| cancellation_requested | 待决取消申请写入 | 提案方、理由 | cancellation_request + 申请 ID |
| cancellation_accepted／cancellation_rejected／cancellation_withdrawn | 相应取消结果写入 | 对应申请与本次结果 | cancellation_decision + 本次决定 ID |
| dispute_opened／dispute_resolved | 争议或解决记录写入 | 争议／解决事实与允许展示的说明 | trade_transition + 本次变更 ID |
| trade_frozen／trade_unfrozen／trade_abnormal | 冻结／解除／超时异常写入 | 原因、范围及沟通入口 | trade_transition + 本次变更 ID |
| trade_completed／trade_terminated／trade_restored／trade_adjusted | 相应交易状态变更写入 | 前后状态、时间及可公开依据 | trade_transition + 本次变更 ID |

上述资源类型是 R2a 向 TASK-003 提出的引用契约；具体实体、记录 ID 与本域接口由 TASK-003 后续主体模型批次绑定并交叉核对，具体实体及标识由 TASK-003 主体模型批次定义。所有引用必须解析到本会话 trade_id 下的不可变历史记录，服务端校验归属及当前访问资格。仅定位所属交易时 source_ref 为空，由会话外键取得，不重复保存商品／交易目标。历史引用不跟随“当前提案”指针变化；历史业务记录不删除。当前操作仍重新校验状态和权限。

同一动作可产生多个子事件（例如最后一方完成确认同时触发交易完成），各自使用稳定子事件标识，按业务因果分配消息序号。需要归档时先追加最后的业务消息，再归档，同一事务完成。已完成／已终止交易保持终态；恢复仅适用于未结束交易，解除冻结不等于改变交易状态。归档会话保持只读，不追加消息。

系统消息和通知关联同一业务记录及事件，通知接收范围采用 R1／4.17，不因系统消息发给双方而给双方额外通知；管理员采用管理待办，不接收用户站内通知。读取任一项不替代接受请求、约定确认、完成确认等业务操作，消息与通知分别维护已读。

## 权限与业务差异

| 操作 | 资格与结果 |
|---|---|
| 建立私聊 | 登录用户向其他现存账户发起，账户对复用；按账户当前资格校验，禁止本人对本人 |
| 读取私聊／交易历史 | 两名固定参与者可按当前读取资格查看；封禁／冻结保留历史只读 |
| 发送私聊／交易消息 | 本人参与、交易会话未归档、双方账户无封禁、二人间无有效交易冻结；任一交易冻结覆盖二人全部私聊／交易会话，与第三方的会话不受该笔冻结影响 |
| 建立交易会话 | 仅请求成功用例内部触发，买卖双方及 trade_id 从交易记录取得 |
| 事项沟通 | 相关用户及固定认领管理员具备该事项访问依据；封禁／冻结不禁止此处说明／申辩；事项归档后只读 |
| 管理员查看私人消息 | 仅本人认领事项的必要证据逐条引用，不获得整段私聊或全部交易历史权限 |
| 商品审核 | 使用审核结论及通知，不建立事项沟通线程代替审核结果 |

具名失败：PARTICIPANT_REQUIRED → RESOURCE_NOT_VISIBLE；CONVERSATION_ARCHIVED → STATE_CONFLICT；MESSAGE_SEND_FORBIDDEN → ACTION_NOT_ALLOWED；SELF_CONVERSATION_FORBIDDEN → INPUT_INVALID。错误由 C1 BusinessError 包装回滚；已读越界为 INPUT_INVALID。消息读取保留原资格范围，不因通知链接授权。

## 锁序、事务及幂等

C1 第 6 级会话锁子序采用：ChatConversation → TradeConversation → CaseConversation → 各类消息 → 各类阅读进度 → 文件登记 → 文件引用；同一子域按稳定对象键升序。阅读进度按 chat／trade／case 及会话 ID、账户 ID 排序。所有发送与已读入口先锁本类型会话，再按该子序写消息／进度；无需的子域直接跳过。统一替换旧“会话 → 分支”锁域，由 TASK-001 同步公共源文件。

| 动作 | 原子写入与并发规则 |
|---|---|
| 建立私聊 | 账户对唯一约束仲裁重复建立，返回原会话；建立双方阅读进度 |
| 请求创建 | 已取得账户资格及交易域锁后，写请求、TradeConversation、阅读进度、request_created 系统消息、通知意图及事件；失败全部回滚 |
| 交易动作 | 锁前规划所有需创建／归档／追加消息的会话 ID 及接收账户，按商品→交易→事项→会话→消息→进度→事件顺序；关闭多个请求时按各域对象键排序，不能逐请求跨域循环回取较早锁 |
| 发送 | 会话行锁内 seq_head 加一、插入消息、推进发送者阅读进度、登记事件；回滚同时撤销序号及进度 |
| 已读 | 先锁会话校验序号，后锁对应进度行取最大值 |
| 归档 | 同一业务事务内先追加终态消息，再写 archived_at；重复返回原结果 |

调用方持同一 tx／执行上下文，本模块内部不提交。业务记录、消息、通知、审计、幂等结果和持久事件同一数据库事务；意图在第 7 级统一分配接收账户事件序号，不在消息能力内提前取得事件锁。提交后投递失败重试，不回滚业务。

发送与已读沿用 C1 (actor_id, operation_name, idempotency_key)，操作名区分会话类型，摘要包含会话 ID；同键同摘要重放，同键不同摘要拒绝。系统消息按 business_event_id 唯一，C3 通知 intent_key 按同一业务事件及通知类型构造；单次事件重试返回原消息／通知，不依赖客户端去重维护数据库唯一性。唯一键冲突时核对所属业务和载荷，冲突内容不能静默复用。补充锁域按 C1 回滚并整事务重新规划。

| C2 字段 | 语义 |
|---|---|
| event_id／event_type | 稳定投递事件 ID；message_created／message_read／conversation_archived |
| conversation_kind／conversation_id | chat／trade／case 与对应实体 ID；接收端按类型路由 |
| message_id／message_seq | message_created 时定位对应类型消息；归档事件不伪造消息 ID |
| business_event_id | 系统消息与通知共同业务来源；同一业务事件的不同投递各有 event_id |
| actor_account_id／recipient_account_ids | 由业务确定并校验的账户；系统无 actor |
| last_read_seq | 已读事件返回权威进度；含发送触发的进度推进 |
| occurred_at | UTC 时间 |

事件载荷不传整段私聊或隐私依据，消息类型、正文及业务引用按读取授权取得。订阅按接收账户，账户多 Session／多连接各有连接游标；message_read 仅同步该账户的其他连接，不告知对端。事项事件仅到相关用户及具资格的固定认领管理员；分发／重放时重新校验当前资格，不能只信历史接收清单。断线按类型会话及 seq 补拉数据库历史，不依赖 Redis 保留窗口，按 event_id／消息 ID 去重。C2 具体接口、持久游标与恢复协议随 TASK-001 对应批次完成。

## 隐私、保留与验证预期

消息不可变，不按时间自动清理；违规内容处置保留依据。当前显示名称取账户当前名称，历史业务事实不改写。日志记录请求／操作／类型会话／消息标识及结果，不记录正文。接口只返回本人有资格的会话和字段。

1. 同账户对私聊复用；每笔请求唯一交易会话，重复调用不重复系统消息。
2. 三种消息明确外键，不能写入其他类型会话；交易 source_ref 引用其他交易记录时整体拒绝。
3. 多笔交易消息、进度和归档相互独立；二人冻结影响其全部买卖双方会话，不影响第三方。
4. 固定认领人及相关用户访问本人事项线程；其他管理员／举报人读取他人线程拒绝；管理资格失效后旧连接也不能收到正文。
5. 并发发送序号唯一连续；事务回滚不遗留消息、通知、已读推进或事件。
6. 展示推进与乱序请求取最大值；发送推进至本消息并清除更早未读；发送失败不推进；系统消息不推进双方进度；多设备同步权威进度。
7. 归档后禁发而可读、可推进已读；解冻不重开已归档会话，已结束交易不得恢复，不追加系统消息。
8. 最后一方确认及交易完成产生各自系统消息后才归档；重试无重复，读取不替代业务操作。
9. 后续提案不改变历史消息引用；当前操作仍重查状态；系统消息双方可见范围与通知接收范围分别核对。
10. 事项说明／申辩分别留存，提交不自动解除限制；审核结果不建立沟通线程。

## 类规则与事实来源

按[设计约束与检查规则](../../设计约束与检查规则.md)统一规则实现。TradeConversation.participants(trade) 通过 trade_id 关联取得买卖双方；会话只保存交易外键，发送、读取及投递从同一参与方法取得账户集合。CaseConversation 通过 case_id 取得固定认领人，各自阅读进度保存实际账户标识。

ChatConversation／TradeConversation／CaseConversation 分别提供 require_read(actor, context)、require_send(actor, context)、unread_count(progress)；交易及事项会话提供 is_archived() 和 archive_reason(source)；归档原因由请求／交易终态或事项结案事实计算。require 方法校验相应类的参与资格、当前账户限制及事项例外，失败抛出具名业务错误，用例在锁后调用。未读总数由 seq_head 与阅读进度计算，seq_head 作为事务内连续序号分配基准维护，content 和历史事件按原记录保留。查询条件和对象判定采用同一规则定义。
