# 事项主体与处置执行

设计归属：TASK-004；编写：张新悦（`sourmoon-peekaboo`）。输入：design 提交 `453f4f4`；需求提交 `ff491a6`。本稿在第 4 批按 R0、R1、R2a、C1、C3 的评审版本绑定主体能力与执行记录。

## 关联需求、决策与接口

本专题定义处置事项的主体对象、动作与依据（R2b 的 M3 部分），以及事项与账户、商品、交易执行关联的登记方式。具体执行请求的动作类型、目标字段与预期结果在本任务第 2 批的另一份专题[处置与主体协同](处置与主体协同.md)定义；会话线程与消息字段见[会话与处置事项](会话与处置事项.md)。

- 需求：FR-07 举报、FR-08 事项认领与处置、FR-14 异常交易处理；BR-13、BR-19、BR-25、BR-26、BR-32—BR-34；DT-03、DT-05；TR-09、TR-10；第 4 章 4.9、4.12、4.13、4.17、4.18。
- 决策：[ADR-002 主体模块及统一业务数据库](../../decisions/adr/ADR-002-主体模块及统一业务数据库.md)、[ADR-003 统一用例事务与幂等](../../decisions/adr/ADR-003-统一用例事务与幂等.md)、[ADR-007 OSS 私有文件与授权直传](../../decisions/adr/ADR-007-OSS私有文件与授权直传.md)、[ADR-009 统一上下文与 AOP 日志审计](../../decisions/adr/ADR-009-统一上下文与AOP日志审计.md)。
- 公共输入：执行上下文、资格锁、幂等与错误映射取[公共事务与权限](公共事务与权限.md)；文件引用取 C3 的文件契约，内容稳定方案见[Q-002](../../decisions/questions/Q-002-直传授权后的对象覆盖控制.md)；通知按[账户与通知](../interfaces/账户与通知.md)的 `create_notifications` 提交意图。
- 分工：商品审核结论由 C-04 审核记录与 TASK-002 的审核流程维护，R2b 审核事项提供共享池入口与固定认领，审核进度和结论从对应 R0 审核记录投影；审核结果不建立沟通线程；发布者按审核通知与拒绝原因修改重提（BR-10）。

## 事项对象与类型

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `case_id` | EntityId | 事项稳定标识 |
| `case_type` | `product_review`／`report`／`dispute`／`exception` | `product_review` 对应一条商品审核记录；举报由举报提交产生；`dispute` 为交易争议；`exception` 为单方确认超时转来的异常交易（FR-14） |
| `target_type` | `product`／`comment`／`message`／`evaluation`／`account`／`trade`／`product_audit` | `product_review` 必为 `product_audit`；`dispute`／`exception` 必为 `trade` |
| `target_id` | EntityId | 被举报或待处理对象；审核目标通过 `ProductAudit.case_id` 的唯一外键取得，`target_id` 投影为 `audit_id`；`message` 类型附 `target_conversation_kind` 与 `target_conversation_id`；按类型查找该消息并校验所属会话和访问资格 |
| `reporter_account_id` | EntityId，可空 | 举报人为提交账户；其他事项类型为空 |
| `claimed_manager_id` | EntityId，可空 | 认领管理员；未认领为空，处理时唯一 |
| `claimed_at` | UTC 时间，可空 | 固定认领时间，随认领人同次保存；首次认领前为空 |
| `case_status` | `pending`／`claimed`／`decided` | 处置类事项按下述状态转换；审核事项按对应审核状态及认领事实投影 |
| `decision_kind` | `no_action`／`not_actionable`／`violation`，可空 | 不予处理／无法认定／认定违规并处置；处置类事项进入 `decided` 时必填；审核结论取 R0 |
| `reason_text` | 文本，可空 | 结论理由；与 `decision_kind` 同时写入，保留原文 |
| `reported_reason` | 文本，可空 | 举报人填写的举报原因，`report` 类型必填（BR-25） |
| `case_created_at`／`decided_at`／`archived_at` | UTC 时间 | 建立、决定与结案归档时间 |
| `public_result_at` | UTC 时间，可空 | 结论经管理员确认并匿名公开的时间；为空即不可见（BR-25） |

审核事项的进度投影为：审核仍待处理、事项未认领时为 `pending`；审核仍待处理且已认领时为 `claimed`；审核通过、不通过或撤回后退出共享池及个人待办。通过或不通过后投影为 `decided`，审核结论、原因、时间及内容快照取 R0。审核撤回的历史及时间取原审核记录。审核事项不走处置申辩、结案或举报公开接口。

处置类事项状态与交易、商品、账户状态分别维护：交易进入争议或异常不等于事项已决定，事项决定也不代替交易状态（第 4 章 4.13）。事项结案归档后不再接受补充、新事实或重新提交，原记录与依据保留（4.18）。

## 事项动作流水

事项的处理过程以流水记录，供处理进度展示、申诉查看与审查核对。流水与[会话与处置事项](会话与处置事项.md)的事项线程消息分别保存：流水记录动作事实与依据，消息承载可读内容。

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `case_action_id` | EntityId | 流水标识 |
| `case_id` | EntityId | 所属事项 |
| `action_kind` | `submit`／`supplement`／`claim`／`inquire`／`statement`／`appeal`／`manager_reply`／`decide`／`close`／`execute`／`lift`／`publish_result` | 动作类型；`supplement` 为同对象未结举报的补充 |
| `actor_kind`／`actor_account_id` | `account`／`manager`／`system`；EntityId 可空 | 系统动作记录触发来源 |
| `occurred_at` | UTC 时间 | 业务发生时间 |
| `message_id` | EntityId，可空 | 需要可读内容时指向事项线程消息（`inquiry`／`statement`／`appeal`） |
| `basis_ref` | 依据引用集合，可空 | 决定与执行的依据，指向证据引用记录（见下节） |

流水只追加不修改。`claim` 与 `decide` 为业务结果动作，其余为过程动作；系统动作不伪装为用户或管理员操作。

## 举报的复用与结案

| 情形 | 结果 | 依据 |
|---|---|---|
| 同一用户对同一对象存在未结举报时再次提交 | 在原事项补充：新增 `supplement` 流水与可选证据，不新建事项、不重复进入共享池 | BR-25、4.18 |
| 不同用户举报同一对象 | 各自建立独立事项；同一对象可存在多条事项，处置按各自事项进行 | BR-25 |
| 事项已结案归档后提交同对象举报 | 拒绝，返回 `CASE_CLOSED`；提示已结案且不再接受补充或重新提交 | 4.18 |
| 对象已删除或失效后提交新举报 | 拒绝；既有举报保留关联并可继续处理，举报人可查看所关联的被举报内容 | BR-25、C-12 |

未结举报由两个部分唯一约束保障，均以 `archived_at` 为空为条件。消息按 `(reporter_account_id, target_conversation_kind, target_id)` 唯一，同类消息 ID 在各自消息表内唯一；其余对象按 `(reporter_account_id, target_type, target_id)` 唯一；补充与提交并发时，后到者按唯一冲突转为在原事项补充。

## 证据引用

证据分两类，均以记录保存并在事项内逐条授权，不把证据内容复制进事项或会话。

| 类型 | 字段 | 读取授权 |
|---|---|---|
| 提交证据 | `case_evidence_id`、`case_id`、`evidence_kind = submitter_attachment`、`file_id`、`submitted_by`、`submitted_at` | 认领管理员在核查期间可读；文件须已核验归属与用途（C3）；举报人与其他参与者不读取他人提交的证据 |
| 平台记录引用 | `evidence_kind = platform_record`、`source_ref`（`message`／`trade`／`comment`／`evaluation`／`product_revision` 的 `resource_type` 与 `resource_id`）、`referenced_by`、`referenced_at`、`required_scope` | 认领管理员可读被引用记录本身；消息引用同时携带 `conversation_kind` 与 `conversation_id`；`message` 类型只读指定类型、会话及 `message_id` 对应的正文与最小上下文（发送者、时间、所属分支类型），不展开所在分支的其他消息（BR-19） |

引用记录只追加不删除；对象逻辑删除或失效后引用保留，读取按当前资格判定（4.18）。管理员读取私聊消息以“存在指向该 `message_id` 的引用记录 + 本人为该事项认领人”为唯一依据，不因认领某笔交易获得分支整体读取权（BR-19、BR-34）。

提交证据的文件引用按 C3 建立：事项用例调用 `attach_files`（`purpose=case_evidence`、`target` 为事项、`slot=evidence`），核对文件归属、用途与已核验状态，引用与证据记录同事务写入；文件内容不复制进证据记录，读取地址由 `prepare_file_read` 在获准查询时签发。事项结案后引用按证据保留规则继续持有，不随结案解除。

## 认领与处理权限

| 动作 | 允许条件 | 拒绝结果 |
|---|---|---|
| 认领事项 | 账户具备平台管理资格，事项处于 `pending` | `CASE_ALREADY_CLAIMED`（按 `STATE_CONFLICT` 映射） |
| 查看非公开记录 | 账户为该事项当前认领人，且记录属于 `required_scope` | `NOT_CASE_MANAGER`（按 `RESOURCE_NOT_VISIBLE` 映射） |
| 核查、问询、决定、解除 | 同上；决定与解除还须存在依据引用 | `ACTION_NOT_ALLOWED` |
| 提交说明或申辩 | 账户为该事项相关方，且事项处于允许阶段 | `ACTION_NOT_ALLOWED` |

认领为唯一归属，不提供转派或主管角色（BR-34）。认领与决定按当前状态校验，认领后被他人重复认领返回 `CASE_ALREADY_CLAIMED`，不覆盖原认领人与认领时间。管理资格由账户模块提供，本专题只保存认领关系。

商品审核事项按 R0 的交界能力绑定：认领调用 `REVIEW_CLAIMED`（`audit_id`、`admin_id`），结论提交调用 `REVIEW_PASSED`／`REVIEW_REJECTED`；`REVIEW_ALREADY_CLAIMED`、`REVIEW_NOT_PENDING`、`REVIEW_NOT_CLAIMED` 由商品侧取得并映射为事项的认领或状态冲突。审核记录以 `case_id` 关联事项，认领权威与固定认领人留在本专题；结论涉及的分类申请批准或拒绝在同一事务决定，本专题不另建分类申请状态。

## 问询、说明与申辩

| 动作 | 记录方式 | 业务结果 |
|---|---|---|
| 发起问询 | `inquire` 流水分记要求回应的范围，对应事项线程 `inquiry` 消息与问询通知 | 不改变账户、交易与评论状态，不表示认定违规（BR-26） |
| 提交说明 | 事项线程 `statement` 消息与流水 | 记录被询问人的说明；说明不等于申辩，不自动撤销任何处理 |
| 提交申辩 | 事项线程 `appeal` 消息与流水 | 仅实际受处置者可提交；提交不自动撤销处置，处理结果由管理员在原事项线程回复 |
| 管理员回复 | 事项线程 `manager_reply` 消息与流水 | 保留回复内容与时间；维持、撤销或调整均记录依据 |

问询与申辩分别记录、互不覆盖（UC-C08-01）。举报人只获取本人举报的结论通知，不读取对方线程（BR-26）；受处置方只读取本人线程，不看举报人身份信息。

每条问询由 `inquire` 流水标识，从关联线程取得被询问账户。说明流水以 `inquiry_action_id` 引用同事项、同线程的问询；同一问询至多一条首次答复，由引用上的唯一约束协调两次提交。事项侧按未结案、当前回应资格及尚无对应说明判断待回复问询，按事项聚合后供 C5 查询。问询被答复后只移除此子项；历史、通知和其他问询均保留。

## 处置后的申辩与结案

- 决定保存后状态为 `decided`，`archived_at` 为空表示尚未结案。对每位实际受处置的账户保存一条申辩资格记录，以 `(case_id, account_id)` 唯一，保存依据与 `appeal_deadline_at`。实际处置通知在同一事务入库，截止时间为该次通知入库时间加当前 `CASE_APPEAL_WINDOW_SECONDS`；已保存的截止时间沿用原值。截止前提交申辩，截止时起拒绝新申辩，已提交的继续处理。
- 受处置者从本人原事项线程提交 `appeal`，每次提交形成可引用的流水。同一受处置账户须等上一条申辩收到正式处理回复后，才能在原申辩期限内再次提交。认领管理员处理申辩时以 `appeal_action_id` 引用同事项同线程中未获正式处理的申辩，保存维持、撤销或调整及依据，在原线程回复，供本人查看。正式处理流水对同一申辩唯一。撤销或调整时由认领管理员选择原事项中实际影响该申辩人的、仍生效且有补偿路径的原处置项。撤销执行该项补偿，调整先补偿该项，再对同一目标执行替代动作。补偿、替代执行、处理流水、回复及相关处置通知同事务提交，任一步失败时一并回滚。
- 认领管理员结案时在事项锁后检查已决定、所有申辩期已届满且无未处理申辩；无实际处置时没有申辩期。校验成功后写 `close` 流水，将事项及各线程以同一结案时间归档。提交申辩、处理和结案按公共锁序串行；结案后原有合格参与者可读历史。举报结果由认领管理员在结案后确认并匿名公开，同次保存给举报人的结论通知。

交易争议由双方自行解决时，第一方确认只登记，第二个不同方确认后由交易用例在同一事务以 `system` 身份写该争议事项的 `close` 流水，并以同一结案时间归档该事项线程、留存全部历史；该笔交易会话继续可用，其他 `report`／`exception` 事项及其线程不受影响。该路径不替代管理结案，管理路径、终态、申辩及 7 天规则保持原样；已有冻结与资格规则不变；锁序为 TRADE→CASE→TRADE_CONVERSATION→CASE_CONVERSATION，任一步失败整体回滚，同键重放不重复结案。

## 决定与执行关联

| 记录 | 字段 | 规则 |
|---|---|---|
| 决定 | `decision_kind`、`reason_text`、`basis_ref`、`decided_by`、`decided_at` | 与 `decide` 流水同事务保存；无依据引用不可作出处置决定 |
| 执行请求 | `case_enforcement_id`、`case_id`、`target_kind`、`target_ref`、`requested_at`、`result_ref`、`result_status` | 动作类型、请求字段与预期结果见[处置与主体协同](处置与主体协同.md)；本表只保存与决定的关联和执行结果标识 |
| 解除 | `lifted_at`、`lift_reason`、`lifted_by` | 非结束状态的解除须认领管理员确认；解除按目标主体当前资格恢复，不将非在售商品变为在售（TR-10） |

执行结果由目标主体模块保存（账户限制、商品展示与内容、交易冻结与状态），事项只保存请求依据与结果标识，不复制主体状态。决定与执行在同一用例事务内完成：执行目标所需的对象集合在准备阶段收集，按公共锁序先取商品与交易，再取事项与会话，最后提交事件；决定后才确定的目标集合（例如封禁导致该账户全部待接受请求需要关闭）按公共重新规划流程整事务重做（ADR-003、[公共事务与权限](公共事务与权限.md)）。

管理员调整交易状态或有依据解除限制时不得伪造用户确认（4.15、BR-08）；决定涉及交易时同时按 BR-33 冻结并撤销涉事商品公开访问，按 TR-09 记录。

### 执行关联记录字段

| 字段 | 类型与取值 | 规则 |
|---|---|---|
| `case_enforcement_id` | EntityId | 执行记录标识；与 `case_id` 组成唯一约束，跨执行稳定 |
| `enforcement_id` | 具名字符串 | 幂等键，取请求方生成值；同一事项内唯一，重试返回原结果 |
| `case_id` | EntityId | 所属事项 |
| `action` | 具名动作 | 取[处置与主体协同](处置与主体协同.md)登记的九个动作 |
| `target_kind`／`target_ref` | 具名类型／ResourceRef | 目标对象及标识；账户、商品、评论、评价、交易 |
| `basis_ref` | 证据与决定引用集合 | 非空；指向证据引用记录与本次决定 |
| `requested_by`／`requested_at` | EntityId／UTC 时间 | 认领管理员与实际请求时间 |
| `result_ref` | ResourceRef／null | 主体返回的结果标识：限制标识、`trade_transition`、内容记录标识 |
| `result_status` | `applied`／`replayed`／`failed` | 成功、同来源幂等重放或失败；失败记录原因，主体不变 |
| `previous_state`／`current_state` | 具名状态快照 | 主体侧前后状态的可公开摘要，服务端在锁后写入 |
| `affected_scope` | ResourceRef 集合 | 实际受影响对象，例如封禁涉及的待关闭请求与商品 |
| `lifted_at`／`lift_reason`／`lifted_by` | UTC 时间／文本／EntityId | 解除记录；仅解除动作写入 |

执行记录与 `execute` 流水、主体变化、证据引用、通知意图及审计同事务提交。`result_status=failed` 只在事务回滚后以独立记录留痕，主体的任何变化都不保留。

### 执行结果回写

| 主体结果 | 事项侧写入 |
|---|---|
| `RESTRICTION_APPLIED`／`RESTRICTION_RELEASED` | `result_ref` 为限制标识，`current_state` 为可见性摘要 |
| `RESTRICTION_ALREADY_ACTIVE`／`RESTRICTION_NOT_ACTIVE` | `result_status=replayed`，`result_ref` 为既有标识 |
| `OCCUPANCY_RELEASED` | 随交易结束调整写入，`affected_scope` 含商品标识 |
| `TRADE_CONVERSATION_ARCHIVED` | 记录归档结果，不复制消息内容 |
| `TRADE_TERMINAL` | `result_status=failed`，原因为终态不可调整，交易与会话不变 |
| `REQUEST_CLOSED` | 计入 `affected_scope`，关闭原因留请求记录 |

## 匿名公开

| 字段 | 规则 |
|---|---|
| `public_result_at`／`published_by` | 由认领管理员确认后写入；确认前不产生公开记录，结果不可见 |
| `public_summary`／`public_reason` | 仅保存可公开结论与原因，不含用户身份、管理员身份、私人消息或申辩内容 |
| 公开范围 | 所有已登录用户可读；不因公开扩大任何人对原事项的访问资格（BR-25、BR-26） |

无法认定与不予处理的结论同样在确认后公开可公开部分（DT-05）。举报人另行收到关联本人举报的结果通知，通知内容不披露他人私人消息、申辩内容或管理员信息。

|---|---|---|
| 事项 | `pending` → `claimed` → `decided` 单向；`archived_at` 在结案时写入，之后拒绝补充与提交 | BR-34、4.18 |
| 认领 | `claimed_manager_id` 唯一；认领后不转派 | BR-34 |

| 数据库约束 | 未结举报按前述消息／其他对象的键分别部分唯一；消息目标必须同时有会话类型与 ID；`case_status` 与 `decision_kind`、`decided_at` 的配对校验，`archived_at` 非空须已决定；`platform_record` 引用必填 `source_ref` | 本专题 |

## 锁顺序与事务边界

本专题落在公共锁序第 5 级（处置事项行，按事项 ID 升序），子序为：事项 → 认领 → 证据引用 → 流水 → 决定 → 执行请求。执行请求涉及商品与交易时，这些锁域在事务更早阶段按公共顺序取得，事项只按既有顺序追加，不反向回取。

| 动作 | 锁与写入 | 事务边界 |
|---|---|---|
| 提交举报 | 先取账户资格锁，按对象类型取目标对象锁（商品／评论最小读取），再插入事项、提交证据与 `submit` 流水 | 用户入口事务 |
| 补充举报 | 锁事项行后追加证据与 `supplement` 流水 | 用户入口事务 |
| 认领 | 审核事项在事项锁前锁商品及审核记录，锁后重查 R0 待审事实；处置事项锁事项行。写固定认领及 `claim` 流水 | 采用登记的公共锁序（[公共事务与权限](公共事务与权限.md)） |
| 问询、说明、申辩 | 锁事项行与线程分支行，追加流水与事项线程消息 | 用户入口事务；通知意图同事务保存 |
| 决定与执行 | 按[处置与主体协同](处置与主体协同.md)第 4 批的锁集合表取得第 1、3、4、5、6 级对象，写决定、执行记录与流水，第 7 级统一分配事件 | 管理用例事务；目标集合变化时整事务重规划 |
| 结案 | 管理路径锁事项及全部线程，校验申辩期与待处理记录后写结案流水和归档时间；争议自解决由交易用例按 TRADE→CASE→TRADE_CONVERSATION→CASE_CONVERSATION 以系统身份写 `close` 并同事务归档该事项线程 | 管理用例事务／交易用例事务 |
| 公开结果 | 锁事项后校验已结案，写公开字段、流水及举报人结论通知 | 管理用例事务 |

## 幂等与错误

- 关键写操作使用公共幂等作用域 `(actor_id, operation_name, idempotency_key)`；重复提交返回原事项或原处理结果，不新建第二条事项（BR-25）。
- 举报补充与提交并发由未结唯一约束协调：先到者建事项，后到者转为补充。
- 认领并发以状态条件更新协调，失败方返回 `CASE_ALREADY_CLAIMED`，不覆盖原认领人。
- 具名错误：`CASE_CLOSED`、`CASE_ALREADY_CLAIMED`、`NOT_CASE_MANAGER`、`EVIDENCE_OUT_OF_SCOPE`、`TARGET_INVALID`；均按[公共事务与权限](公共事务与权限.md)的映射表映射 HTTP 状态。

## 验证场景与测试关联

设计阶段按下列预期核对主体关系与动作结果，TC 编号与运行条件随第 5 批登记：

1. 同一用户对同一对象提交两次未结举报，第二次进入原事项补充，共享池只有一条事项（BR-25）。
2. 两名管理员同时认领同一事项，仅一人成功，另一人返回 `CASE_ALREADY_CLAIMED`，认领人与时间不被覆盖（BR-34）。
3. 事项结案归档后提交同对象举报，被拒绝且不新建事项；原记录与依据仍可查看（4.18）。
4. 管理员读取私聊证据仅取得被引用的 `message_id`，不展开该分支其余消息；非认领人读取返回不可见（BR-19）。
5. 问询不改变账户、交易与评论状态；说明与申辩分别记录，回复后通知本人（BR-26、UC-C08-01）。
6. 决定涉及交易时，同一事务内完成交易冻结、商品公开访问撤销与双方通知；失败时整体回滚，不留部分处置（BR-26、BR-33、TR-09）。
7. 解除后按目标主体当前资格恢复，其他有效限制保留，非在售商品不变为在售（BR-32、TR-10）。
8. 公开结果不含用户与管理员身份、私人消息或申辩内容；确认前对所有登录用户不可见（BR-25、BR-26）。
