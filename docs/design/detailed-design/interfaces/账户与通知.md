| 调用者及权限 | 主体用例在完成动作资格和业务前置校验后调用；接收范围按该动作的通知规则确定；系统任务附原业务及任务依据 |

### NotificationIntent 输入

| 字段 | 类型／必填／范围与空值 |
|---|---|
| recipient_account_ids | EntityId 非空集合，去重、稳定排序；由主体规则确定 |
| event_type | 已登记具名字符串，如 trade.request_accepted；具体触发、接收范围及模板由该动作唯一维护方定义 |
| source | 必填 ResourceRef，指向来源商品／交易／事项等主体 |
| intent_key | 必填稳定字符串，按业务动作标识＋通知类型＋必要子事件构成；同次业务重试保持一致；格式与长度配置化 |
| template_key／template_version | 必填具名模板及版本；从受审查的事件类型登记表取得 |
| display_params | 必填具名结构，可为空对象；字段由模板 schema 声明，传递展示所需最少公开信息 |
| occurred_at | 必填 UTC 业务事实时间；同次意图沿用原时间 |

NotificationBatchResult 包含 items：每项为 recipient_account_id、notification_id、event_id、intent_key、created_at、read_at（新通知为 null）。event_id 在同一持久事件的重投中保持稳定；事件传输字段、游标及确认由 C2 细化。内部批量结果按接收账户 ID 排序。

### 正常、业务失败与重复请求

正常：接受请求的用例先完成交易及商品转换，再提交接收人、来源交易和具名通知意图，通知与业务统一提交。失败：后续业务校验或写入失败时整体回滚。重复：同次幂等键重放原业务结果；内部同一 intent_key 返回既有通知／事件 ID。

### 查询、已读与权限

通知已读和会话消息已读分别由各自能力维护；C4 定义通知列表、分页、已读接口。来源对象的当前可见范围决定可展示字段及跳转结果，接收通知本身保留按需求允许的事件提示。前端接收实时通知后按 event_id 去重，并按通知 ID 更新对应条目；投递恢复协议由 C2 完成。

### 事件持久化及派发

create_notifications 登记事件意图并预分配稳定 event_id；公共事务包装在完成业务锁操作后，收集全部接收账户并按 ID 升序分配各自序号、保存事件，再提交。实时派发及后台投递从持久记录推进；通知创建结果表明数据库已持久化的业务结果，投递进度按 C2 的恢复流程追踪。
