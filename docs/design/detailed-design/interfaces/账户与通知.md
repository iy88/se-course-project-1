# 账户与通知接口契约

设计归属：TASK-001；输入：design `6250473`。本批增加当前身份及退出接口；注册／登录、改密／重置、邮箱验证及通知查询／已读接口随C4其余接口组细化。

## API-COM-NOTIFY-001 创建业务通知

| 项目 | 内容 |
|---|---|
| 接口编号／名称 | API-COM-NOTIFY-001／create_notifications |
| 需求与决策依据 | FR-11 及需求第4章4.17通知触发与已读口径；ADR-003／004／009；[公共事务](../key-designs/公共事务与权限.md) |
| 方法与路径 | 后端模块内部能力：create_notifications(tx, context, intent) → NotificationBatchResult；由对应 RESTful 业务动作调用 |
| 调用者及权限 | 主体用例在完成动作资格和业务前置校验后调用；接收范围按该动作的通知规则确定；系统任务附原业务及任务依据 |
| 请求 | tx／context 为公共类型；intent 字段见下表，均为服务端构建的具名参数 |
| 成功响应 | 返回通知及事件引用，字段见下表；业务 HTTP 状态及响应由调用用例定义 |
| 失败响应 | 输入及接收范围在主体用例检查；同键不同意图为 NOTIFICATION_INTENT_CONFLICT（409）；持久化异常按公共事务回滚及错误映射 |
| 前置与后置 | 业务触发成立且接收范围明确；每位接收账户生成一条未读通知及可恢复事件，与业务同次提交 |
| 并发与幂等 | 唯一作用域 recipient_account_id＋intent_key；相同意图返回已有 ID，不同意图返回冲突；跨实例由数据库唯一约束协调 |
| 事务 | 同一 tx 保存通知、幂等依据及事件意图；用户事件序号按公共锁序统一分配；提交后派发推进 |
| 隐私 | 持久化来源引用与具名模板参数；查询依据当前来源资格生成可展示信息；签名 URL、验证码、Session 凭据使用各自专用流程 |
| 测试关联 | TC-COM-001／004／005／008 |
| 确认 | 提供方袁尚峰；调用方金婉怡、孙含佳、张新悦；实际复核结论及日期随 PR 登记 |

### NotificationIntent 输入

| 字段 | 类型／必填／范围与空值 |
|---|---|
| recipient_account_ids | EntityId 非空集合，去重、稳定排序；由主体规则确定 |
| event_type | 已登记具名字符串，如 trade.request_accepted；具体触发、接收范围及模板由该动作唯一维护方定义 |
| source | 必填 ResourceRef，指向来源商品／交易／事项等主体 |
| intent_key | 必填稳定字符串，按业务动作标识＋通知类型＋必要子事件构成；同次业务重试保持一致；格式与长度配置化 |
| template_key／template_version | 必填具名模板及版本；从受审查的事件类型登记表取得 |
| display_params | 必填具名结构，可为空对象；字段由模板 schema 声明，传递展示所需最少公开信息 |
| occurred_at | 必填 UTC 业务事实时间；同次意图沿用原时间 |

NotificationBatchResult 包含 items：每项为 recipient_account_id、notification_id、event_id、intent_key、created_at、read_at（新通知为 null）。event_id 在同一持久事件的重投中保持稳定；事件传输字段、游标及确认由 C2 细化。内部批量结果按接收账户 ID 排序。

### 正常、业务失败与重复请求

正常：接受请求的用例先完成交易及商品转换，再提交接收人、来源交易和具名通知意图，通知与业务统一提交。失败：后续业务校验或写入失败时整体回滚。重复：同次幂等键重放原业务结果；内部同一 intent_key 返回既有通知／事件 ID。

### 查询、已读与权限

通知已读和会话消息已读分别由各自能力维护；C4 定义通知列表、分页、已读接口。来源对象的当前可见范围决定可展示字段及跳转结果，接收通知本身保留按需求允许的事件提示。前端接收实时通知后按 event_id 去重，并按通知 ID 更新对应条目；投递恢复协议由 C2 完成。

### 事件持久化及派发

create_notifications 登记事件意图并预分配稳定 event_id；公共事务包装在完成业务锁操作后，收集全部接收账户并按 ID 升序分配各自序号、保存事件，再提交。实时派发及后台投递从持久记录推进；通知创建结果表明数据库已持久化的业务结果，投递进度按 C2 的恢复流程追踪。

## 系统消息、通知及 C2 的交界

依据 [R2a review 修订](https://github.com/iy88/se-course-project-1/pull/43)，交易系统消息与通知使用同一稳定 business_event_id 和原业务记录；各投递 event_id 分别稳定，不能将不同投递误作同一事件。消息按业务事件唯一，通知按 intent_key 及接收账户幂等，不凭消息接收双方扩大通知范围。业务、消息、通知、审计及持久事件同一事务，最后统一分配账户事件序号；提交后派发失败重试。具体业务记录类型由 TASK-003 主体模型绑定，不声明已完成绑定。

C2 采用 conversation_kind（chat／trade／case）与对应 conversation_id 路由传输，数据库消息仍使用各自明确外键。已读事件仅发本账户其他连接，包括发送成功触发的游标推进。本人发送成功推进至本消息序号并清除较早未读，系统消息不推进任一方已读；归档历史仍可推进已读。传输恢复以数据库序号补拉、投递去重及当前资格重查为依据，事项事件仅到相关用户及固定认领且当前有管理资格的管理员。完整 C2 协议随本任务第 4 批交付。

## API-COM-AUTH-001 读取当前账户与 Session

| 项目 | 内容 |
|---|---|
| 接口编号／名称 | API-COM-AUTH-001／get_current_identity |
| 需求与决策依据 | FR-01、BR-20—22／32、ADR-005、Q-001；[会话与身份](../key-designs/会话与身份.md) |
| 方法与路径 | GET /account/session，路径相对于统一API版本前缀 |
| 调用者及权限 | 当前Cookie对应账户；SessionGuard.require_valid统一核对Redis值、持久签发／撤销事实、当前账户版本及期限 |
| 请求 | Cookie；无请求体、分页、过滤或排序参数 |
| 成功响应 | 200；account={account_id,display_name,email,roles}、session={session_id,issued_at,absolute_expires_at}；ID字符串、时间UTC ISO 8601，所有字段必填；Cache-Control:no-store |
| 失败响应 | 401 AUTHENTICATION_REQUIRED：缺失、撤销、过期或版本不同；503 AUTHENTICATION_UNAVAILABLE：Redis／数据库查询超时或失败；采用C1错误外壳 |
| 前置与后置 | 当前身份有效；只返回本人字段，账户限制保留主体动作判定；查询不创建Session |
| 并发与幂等 | 安全只读，读取时核对当前事实；自动轮询本接口不续期 |
| 事务 | 一次身份读取构建请求上下文；Redis／数据库I/O采用有限超时，数据库查询后释放会话 |
| 隐私 | 不返回凭据、摘要、密码、CSRF秘密及其他账户数据；503时保留Cookie，401由客户端进入重新登录流程 |
| 测试关联 | TC-COM-015／017 |
| 确认 | 编写袁尚峰（iy88），Q-001覆盖方案由袁尚峰2026-11-14确认；交叉复核通过第3批PR登记 |

## API-COM-AUTH-002 退出当前 Session

| 项目 | 内容 |
|---|---|
| 接口编号／名称 | API-COM-AUTH-002／logout_current_session |
| 需求与决策依据 | FR-01、ADR-005、Q-001；会话专题的持久撤销及锁序 |
| 方法与路径 | DELETE /account/session |
| 调用者及权限 | 持有当前Session凭据；Origin及X-CSRF-Token／CSRF Cookie按本Session摘要核对，SessionGuard.require_logout检查归属；退出仅作用于当前Session |
| 请求 | Cookie、X-CSRF-Token；无请求体；利用Session自身唯一性实现自然幂等 |
| 成功响应 | 204无正文；持久撤销提交后以同路径及属性设置Session／CSRF Cookie的Max-Age=0；Cache-Control:no-store |
| 失败响应 | 403 CSRF_INVALID：Origin或CSRF不符，保留原会话；503 AUTHENTICATION_UNAVAILABLE：无法确认持久撤销提交，保留Cookie供重试；Redis删除失败采用后台重试，已提交的退出仍204 |
| 前置与后置 | PostgreSQL登记存在时核对CSRF后，在账户共享资格锁及本Session排他行锁内保存首次revoked_at、审计和唯一清理意图；提交后原Session不能再次授权 |
| 并发与幂等 | 同一凭据重复退出沿用原撤销事实；已过期、已撤销可完成本Session清理；无Cookie或持久登记不存在时，在合法Origin下返回204并清理本地Cookie，不访问其他Session；不依赖已删除Redis值验证重复退出 |
| 事务 | 退出采用专用撤销入口，绕过普通“必须有效Session”的业务鉴权；摘要定位及CSRF检查后，账户资格锁→SessionGuard FOR UPDATE→审计及清理意图→统一提交；Redis删除及IM提示在提交后 |
| 隐私 | 错误及响应不披露其他Session；不接受任意session_id、账户ID或客户端指定摘要；日志只记录内部标识及结果 |
| 测试关联 | TC-COM-015—017 |
| 确认 | 编写袁尚峰（iy88）；Q-001采用B；交叉复核通过第3批PR登记 |

正常：当前Session持久撤销后返回204，其他Session继续使用。重复：原Cookie或清理后的浏览器再次退出返回204，撤销时间及审计保持一次。失败：PostgreSQL提交结果不明返回503，客户端保留原Cookie并重试，后续读取原撤销事实收敛；Redis删除失败由持久意图恢复。
