# 运行与部署说明

## 环境与配置

开发、测试和正式环境分别登记 PostgreSQL、Redis、OSS、SMTP 和访问地址。后端统一 .env，前端各自维护开发／构建配置；配置模型检查类型、范围、必要依赖和关联关系。各实例连接池和内存统一预算。

## 启动与迁移

独立步骤执行 Alembic 迁移，再由 systemd 启动原生 API、IM、worker、scheduler 多实例。Nginx 维护静态资源与 HTTP／WS 上游。实际启动命令及监听清单待部署任务细化。

## CI/CD

GitHub Actions 验证提交，Jenkins 构建并部署明确版本，执行配置资源检查、迁移、逐实例滚动、就绪检查和业务验证。前端独立构建，发布登记接口兼容及配置版本。

## 停止与恢复

实例停止新接入／领取工作，按配置排空，IM 重连及任务认领协议衔接。保留可用版本及配置，按数据库兼容范围回退。数据库、Redis 和文件备份恢复步骤及会话恢复语义在实际部署计划中明确并验证。

## 责任

部署、服务器、Nginx、实例、配置发布、迁移执行、回退和部署验收由 TASK-001专门负责。模块成员提供交付及兼容性说明。

## TASK-001 第2批文件存储部署输入

依据：[Q-002](decisions/questions/Q-002-直传授权后的对象覆盖控制.md)、[文件协议及配置](detailed-design/key-designs/文件与邮件.md)、[上传接口](detailed-design/interfaces/文件上传.md)。袁尚峰（iy88）2026-11-14选择独立对象键与签名禁止覆盖，以从未开启版本控制的私有 Bucket 为部署前提。

1. 登记目标环境的 OSS_REGION、OSS_ENDPOINT、OSS_BUCKET 和应用凭据来源；读取 Bucket ACL 与版本状态，核对为私有且版本控制从未开启。曾开启后暂停的 Bucket 采用 Q-002 重新评估；测试状态转换使用隔离 Bucket。
2. 按环境前缀限制应用对象权限；签发端读取 Bucket 配置，上传授权仅为固定 key 的 PostObject，回收端单独具备删除能力；版本控制、ACL 与生命周期配置由部署维护方管理。启动及每次签发时检查存储条件，配置错误或依赖故障按接口返回503并记录关联标识。
3. OSS CORS 允许已登记前端 Origin 的 POST，按需开放响应头；应用后端 HEAD／GET 在服务端执行。Bucket 公共访问关闭，直传字段固定 private ACL；用户读取地址由主体当前资格签发。检查自定义域名、缓存和 CDN 的访问策略符合私有对象及签名期限。
4. 建立 file_id、对象键唯一性及原授权规则快照、引用、回收墓碑和任务查询索引；迁移和初始化的具体命令随文件能力实现提供。生命周期配置保留有效引用对象，清理任务沿数据库认领协议执行。
5. 用 TC-COM-011—014 验证真实 OSS 禁止覆盖、签名篡改、并发完成、配置状态与迟到清理，结合 TC-COM-006／007 验证引用权限和回收竞争。登记实际配置、版本、命令及原始结果。
6. 发布与回退均保留现有对象键、引用、核验事实、授权及清理墓碑；回退版本必须识别本批文件状态。切换 Bucket、启用版本控制或变更对象写权限前，通过 Q-002 评估存量对象和未到期授权的影响，纳入第6批部署计划。

本批实际交付为设计及案例；运行环境与执行证据通过对应编码任务和阶段准入记录登记。
