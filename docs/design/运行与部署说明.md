# 运行与部署说明

## 环境与配置

开发、测试和正式环境分别登记 PostgreSQL、Redis、OSS、SMTP 和访问地址。后端统一 .env，前端各自维护开发／构建配置；配置模型检查类型、范围、必要依赖和关联关系。各实例连接池和内存统一预算。

## 启动与迁移

发布脚本通过后端维护入口独立执行 Flyway 迁移，再由 systemd 按发布流程启动或滚动切换 API、IM、worker 和 scheduler。Nginx 提供静态资源并转发 HTTP／WebSocket 请求。实际入口见[部署脚本](../../scripts/deploy/activate-release.py)。

## CI/CD

GitHub Actions 验证提交，开发者在本地执行受影响业务的冒烟验证。Jenkins 对合入 main 的指定提交构建并部署，执行配置资源检查、迁移、逐实例滚动及部署就绪检查。前端独立构建，发布登记接口兼容及配置版本。

## 停止与恢复

实例停止新接入／领取工作，按配置排空，IM 重连及任务认领协议衔接。保留可用版本及配置，按数据库兼容范围回退。数据库、Redis 和文件备份恢复步骤及会话恢复语义在实际部署计划中明确并验证。

## 责任

部署、服务器、Nginx、实例、配置发布、迁移执行、回退和部署验收由 TASK-001专门负责。模块成员提供交付及兼容性说明。

## TASK-001 第2批文件存储部署输入

依据：[Q-002](decisions/questions/Q-002-直传授权后的对象覆盖控制.md)、[文件协议及配置](detailed-design/key-designs/文件与邮件.md)、[上传接口](detailed-design/interfaces/文件上传.md)。袁尚峰（iy88）2026-11-14选择独立对象键与签名禁止覆盖，以从未开启版本控制的私有 Bucket 为部署前提。

1. 登记目标环境的 OSS_REGION、OSS_ENDPOINT、OSS_BUCKET 和应用凭据来源；读取 Bucket ACL 与版本状态，核对为私有且版本控制从未开启。曾开启后暂停的 Bucket 采用 Q-002 重新评估；测试状态转换使用隔离 Bucket。
2. 按环境前缀限制应用对象权限；签发端读取 Bucket 配置，上传授权仅为固定 key 的 PostObject，回收端单独具备删除能力；版本控制、ACL 与生命周期配置由部署维护方管理。启动及每次签发时检查存储条件，配置错误或依赖故障按接口返回503并记录关联标识。
3. OSS CORS 允许已登记前端 Origin 的 POST，按需开放响应头；应用后端 HEAD／GET 在服务端执行。Bucket 公共访问关闭，直传字段固定 private ACL；用户读取地址由主体当前资格签发。检查自定义域名、缓存和 CDN 的访问策略符合私有对象及签名期限。**新增或更换前端访问来源（局域网联调地址、测试域名、生产域名）时必须同步更新该白名单**：CORS 未放行时浏览器在预检阶段即被拦下，页面只能报「上传未完成」，而服务端直传仍然正常，容易被误判为网络故障（见 #162）。
4. 建立 file_id、对象键唯一性及原授权规则快照、引用、回收墓碑和任务查询索引；迁移和初始化的具体命令随文件能力实现提供。生命周期配置保留有效引用对象，清理任务沿数据库认领协议执行。
5. 用 TC-COM-011—014 验证真实 OSS 禁止覆盖、签名篡改、并发完成、配置状态与迟到清理，结合 TC-COM-006／007 验证引用权限和回收竞争。登记实际配置、版本、命令及原始结果。
6. 发布与回退均保留现有对象键、引用、核验事实、授权及清理墓碑；回退版本必须识别本批文件状态。切换 Bucket、启用版本控制或变更对象写权限前，通过 Q-002 评估存量对象和未到期授权的影响，纳入第6批部署计划。

本批实际交付为设计及案例；运行环境与执行证据通过对应编码任务和阶段准入记录登记。


## TASK-001 第3批 Session 持久撤销部署输入

[Q-001](decisions/questions/Q-001-Session撤销与Redis故障恢复.md)采用袁尚峰2026-11-14选择的B方案；字段、锁序、Cookie、依赖失败及保留规则见[会话与身份](detailed-design/key-designs/会话与身份.md)。

- 迁移建立 SessionGuard、摘要唯一约束及撤销清理意图，发布时 API／IM 同时采用持久依据核对。协议切换期间阻断旧鉴权实例；既有Redis Session缺少登记时要求重新登录。
- 账户、凭据版本、SessionGuard和退出审计使用同一权威PostgreSQL；鉴权及锁后重查读取主库。连接预算包含逐请求及IM投递检查，按真实负载验证；应用权限禁止修改已签发凭据的归属与摘要。
- Redis读取／续期失败采用有限超时；持久撤销提交后，Redis清理或IM提示失败由持久意图重试。核对Cookie安全属性、同源Origin配置及CSRF，日志按字段白名单脱敏。
- Redis恢复可继续接受当前有效Session，逐次核对持久撤销、凭据版本及期限；缺失值不从登记自动重建。数据库历史恢复期间阻断入口并停止签发／续期，撤销所有恢复出的SessionGuard、清空Redis Session命名空间并断开现有连接后再开放入口。
- 回退版本必须识别SessionGuard及撤销依据；版本回退先核对所有API／IM的鉴权协议，采用旧鉴权逻辑的版本通过重新评估及迁移流程处理。TC-COM-015—017登记恢复与跨实例证据。

## 第3批邮箱单表与账户接口部署输入

- 本轮新增email_verification单表，验证事实、明文code及投递进度均在本表；字段、约束、索引和清理见[邮箱专题](detailed-design/key-designs/邮箱验证与投递.md)。账户邮箱唯一索引使用统一规范化函数，迁移前检查已有地址大小写冲突并形成处置记录。
- 校验SMTP TLS／端口、发件身份、连接凭据来源、验证码格式／期限／次数、重发频率、发送次数、退避、任务租约及清理周期；设置版本化账户入口签名密钥，轮换保留适用入口及幂等期限内的旧版本。具体迁移及启动命令随账户实现提供。
- 明文code只允许账户及邮件worker必要读取，关闭请求原文、SMTP调试和任务参数正文记录；任务队列只携带记录ID。核对业务日志、异常、审计与公共幂等记录均无原码；SMTP已确认发送后保留原码直到消费或失效。
- 数据库提交后触发投递并以周期扫描恢复，认领采用本表租约及token条件写回；SMTP不在数据库锁内。演练发送后退出、租约接管、队列丢失、旧邮件迟到、代码到期清理及同次错误重试。
- 换绑邮箱按Q-004同事务递增凭据版本，使全部旧Session失效；密码／邮箱变更后核对跨实例HTTP与IM行为、新邮箱重新登录及稳定用户ID。
- PostgreSQL历史恢复时先隔离账户入口及worker，失效恢复出的验证行、清空code与租约，再按会话恢复协议撤销恢复出的Session并清理Redis，之后恢复服务。备份文件按既定备份保留与访问控制管理。
- TC-COM-018—022安排真实PostgreSQL／Redis、多API／worker与SMTP验证；模拟SMTP故障和真实邮件投递分别记录。所有步骤采用实际实现版本、环境和命令登记证据。

## C7 实例拓扑与发布输入

采用 [ADR-011](decisions/adr/ADR-011-单机多实例CI-CD.md) 的同机原生进程方案。v2 使用独立发布目录、域名、服务身份、PostgreSQL 数据库及角色、OSS 桶和 Redis 键前缀。环境清单登记每个 API、IM、worker 与 scheduler 的实例编号、职责、监听、并发、就绪探针、停止预算及配置版本；发布前逐项与 legacy 清单比较。API 与 IM 仅监听本机分配的互不重复端口，worker 与 scheduler 仅登记所需内部控制端口。Nginx 由同一清单派生 API 与 WebSocket 上游及前端静态站点路径；WebSocket 上游保留 Upgrade 语义，代理超时覆盖约定心跳窗口。阶段验收按 TC-COM-035 核对端口、路由和资源边界。

实例数由目标负载、单实例容量和维护窗口决定。滚动要求 API、IM 摘除一实例后仍满足该阶段的容量下限；worker 摘除后验证剩余处理能力与积压恢复时间。PostgreSQL 最坏连接需求按各进程角色的峰值实例数（含滚动重叠）× 每实例进程数 × 每进程连接池上限（含溢出）求和，再计入迁移、健康检查及运维连接，并保留同机 legacy 和数据库管理余量。Redis 同样按长连接、阻塞消费者、短连接及滚动峰值计算，另核对 IM 长连接的文件描述符、队列和内存峰值。预算超限时调整池、实例数或发布批次并复测。scheduler 并存时沿 C2 的持久任务键与认领协议去重；不能证明兼容时，先停止旧 scheduler 接新工作再启动新实例。

发布采用已完成业务接入、统一联调和验收的应用版本，所有随版本交付的业务功能同时可用。各进程按职责装配，缺少必需的实现或依赖时停止启动。

发布清单包含 Git 提交和制品摘要、配置版本和保密来源、数据库目标与迁移头、各角色 unit、例行探针、排空命令及旧版本制品。Jenkins 记录该清单及实际执行命令。实现阶段将迁移入口、unit 模板、Nginx 配置渲染、就绪探针与排空接口落到部署代码并回填命令及路径。部署验证可先采用平台原生命令 `nginx -t`、`systemctl is-active <unit>`、`journalctl -u <unit>` 验证配置语法、服务状态及日志；业务就绪还须通过带目标环境标识的协议探针。

## C7 滚动、回退与恢复

1. 锁定单次发布，校验制品、目标资源、连接预算和备份可恢复性，登记当前应用、配置、迁移头及候选回退版本。逐项核对新旧版本可共用的数据、接口、事件 schema、任务载荷和配置。
2. 使用独立迁移角色，由流水线在应用切换前执行一次兼容性扩展迁移，检查实际迁移头与数据约束。失败即保留旧流量并停止发布。破坏性收缩迁移留到旧进程、旧载荷及回退窗口结束后的独立发布；遇到无法滚动兼容的迁移，登记停写范围及恢复演练后再安排窗口。
3. 每次摘除一个 API／IM 实例。API 停止接收新请求并排空在途事务；IM 停止新握手，告知现有连接按 C2 重连并从客户端游标恢复。worker 停止新认领，给正在执行的工作留排空预算；超时后允许租约到期接管，旧执行者靠 token 条件提交。scheduler 切换遵循上节的兼容条件。
4. 以新制品及配置启动，检查版本、迁移头、依赖和角色就绪，执行一笔可回溯的阶段业务探针，再恢复流量或认领。任一检查失败即停止下一批，保留仍就绪的实例，记录出错角色、请求标识和观察结果。
5. 兼容回退逐实例恢复已验证兼容的旧制品与配置，验证已提交数据、事件游标、任务所有权及会话撤销语义。数据库点时间恢复走独立流程：先隔离流量与 worker，恢复到确认点，按 Q-001／Q-003 撤销恢复出的会话并清理验证码和租约，轮换 C2 事件 epoch，核对文件引用及对象可读性，只清理 v2 Redis 命名空间，再开放入口。实际 RPO／RTO 由环境及阶段验收登记、演练和判定。
