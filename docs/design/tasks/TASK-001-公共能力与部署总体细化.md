## 扩展：多批次分支、提交与 PR

每份任务必须按下表拆成多个 PR，各批次使用独立分支，PR 目标统一为 `design`。每份 PR 内按独立目的组织多个小 commit，保持正文、引用及必要案例一致；较大子项继续按接口组或状态规则拆分。

| 批次 | 指定分支 | PR 交付范围 |
|---|---|---|
| 1 | `task-001/01-handover` | C1／C3 首批交接：执行上下文、事务、权限、幂等、锁序、文件引用与回收、通知内部签名及案例预期 |
| 2 | `task-001/02-files-notifications` | Q-002 与上传细化：直传授权、核验完成接口、内容稳定方案与验证、C3 配置及引用契约对齐 |
| 3 | `task-001/03-identity-mail` | C4、Q-001／003：账户、Session、邮箱及邮件验证 |
| 4 | `task-001/04-realtime-tasks` | C2：事件传输、恢复及任务执行 |
| 5 | `task-001/05-config-audit-queries` | C5：配置、审计、聚合与统计 |
| 6 | `task-001/06-deployment-validation` | C7／C8：部署与公共验证预期 |

1. Issue 登记设计输入提交；每个批次从可用的 `design` 提交建立表列分支。首批为 `task-001/01-handover`，首次推送使用 `git push -u github task-001/01-handover`。
2. 首个可审阅 commit 后提出 Draft PR，关联任务 Issue，并列出本批目标、前置输入及后续批次。
3. 每个 commit 聚焦一项完整变更，尽量缩小差异；格式整理与独立设计修改分别提交。提交前审阅差异并精确暂存。
4. 每批审查通过后合入 `design`，后续批次从已集成版本建立。可独立的批次可并行建立，跨批次依赖在 Issue 登记。
5. PR 附需求／ADR／Q、源文件范围、实际检查及审查记录。TASK-001 统一集成拼合清单及生成物。
6. 更新同一任务的进度清单，逐批关联 PR、提交和交付结果，全部完成标准满足后关闭任务 Issue。

## 完成标准

- C1—C3 的输入、返回值、前后置条件、事务参与方式和失败结果可被三个模块直接引用。
- C4 的各接口满足契约模板，C5 的参数有类型、依据和生效方式。
- Q 按实际确认及复核结果登记，C7 给出可用于实现的部署步骤。
- 案例预期可判定，并关联相应契约和风险。

接口契约包含依据、权限、请求响应、错误、前后置、幂等、事务、隐私及案例关联。案例说明需运行时验证的性质或复杂跨模块行为，设计阶段记录预期与执行安排。实际确认、复核及执行结果分别登记。

涉及需求、共享接口、架构或依赖变动时，先提交影响和候选并关联 Q／ADR 评审。部署执行归 TASK-001，各模块提交必要配置、迁移和兼容性说明。
