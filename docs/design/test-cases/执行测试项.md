# 用户故事人工执行测试项

## 口径

- 人工交互流程是主验证方式；原 TC 是规则断言，单元、接口和真实集成测试用于补充与回归，数量不设上限。
- 本文定义实际人工交互测试的 72 个执行项，四人各 18 项；一个 RUN 可从注册、准备到业务结果连续覆盖多个执行项。
- 有 10 个平台前置检查只作为执行条件，不重复计入 72 个业务项。
- 所有批次使用真实 PostgreSQL、Redis、OSS 和 SMTP；单元测试仍可继续增加，但不得用 Mock 代替人工流程所需依赖。
- 代码自动化测试中，单元测试可以使用 Mock 隔离依赖并覆盖分支；涉及跨模块事务、数据库约束、并发、Redis／OSS／SMTP 的集成测试继续使用真实依赖。
- 一个执行项可对应多个原 TC。原 TC 的详细预期仍以[公共能力](公共能力.md)、[商品与分类](商品与分类.md)、[交易与评价](交易与评价.md)和[会话与处置事项](会话与处置事项.md)为准。

## 共同环境与账户准备

每个批次从干净测试数据开始，先执行以下流程：

1. 在 `backend/.env.dev` 配置本地可连通的 PostgreSQL、Redis、私有 OSS、关闭版本控制的 Bucket 及真实 SMTP。
2. 执行依赖探针：

   ```bash
   java -jar backend/backend-app/target/backend-app-0.0.1-SNAPSHOT.jar \
     --spring.profiles.active=dependency-probe \
     --env-file=backend/.env.dev \
     --smtp-probe-to=<测试邮箱>
   ```

3. 启动系统：

   ```bash
   python3 scripts/dev.py start --env-file=backend/.env.dev
   ```

4. 在用户端注册以下普通账户，并从真实测试邮箱读取验证码完成注册：

   | 角色 | 建议标识 | 用途 |
   |---|---|---|
   | 卖方 | `qa-seller` | 商品、交易、冻结及恢复 |
   | 买方 A | `qa-buyer-a` | 请求、约定、会话、评价 |
   | 买方 B | `qa-buyer-b` | 竞争请求和用户间隔离 |
   | 无关用户 | `qa-outsider` | 权限与隐私负向验证 |

5. 使用维护工具创建 `qa-manager-a`、`qa-manager-b` 两个管理员账户。
6. 通过管理端创建基础分类；通过用户端上传真实图片并发布商品；通过管理端完成审核。交易、事项和历史数据在前置用户故事链中继续生成。
7. 只在不可稳定手工触发的 7 天、清理、故障等边界使用受控时钟或测试夹具；报告中明确列出，且最终页面结果必须实际观察。

## 自动化补充边界

人工流程负责证明用户能从实际页面完成业务并得到正确的结果、状态和反馈。以下内容优先保留或补充自动化测试作为辅助证据，不要求逐 TC 人工点击：

- 纯领域状态、错误码、时间计算、版本检查、幂等摘要、权限投影；
- 已由真实 PostgreSQL 集成测试充分覆盖的事务、回滚和行锁分支；
- 已由真实 Redis／实时集成测试覆盖的游标、去重、租约接管；
- 文件 MIME、ETag、PDF 解析和对象键组装；
- 部署、迁移、兼容回退和历史恢复。

人工执行项重点验证“用户能否在实际页面完成业务并得到正确状态和反馈”，自动化测试用于补齐不可稳定人工触发、边界密集或回归成本高的断言。
