# 测试案例模板

按用户故事建立可执行流程；原 TC 作为规则断言，可由人工流程和自动测试共同覆盖。每个测试项必须先有 design 依据。

| 字段 | 内容 |
|---|---|
| 编号／关联依据 | TC、需求、规则与外部确认记录：待填写 |
| 设计依据（必填） | design 文档路径、接口编号、关键设计章节：待填写 |
| 用户故事／执行项 | US-__、人工执行项／RUN：待填写 |
| 层级 | 按[测试策略](../implementation-plan/02-测试策略与依据.md#测试层级)填写单元／集成／系统／验收；另注明接口、端到端或性能等验证方式 |
| 主验证方式 | 前端人工业务链：待填写；一项流程可覆盖多个 TC |
| 场景和风险 | 待讨论 |
| 前置数据与角色 | 合成账户、角色、商品／交易／事项及真实依赖：待讨论 |
| 操作／输入 | 待讨论 |
| 预期结果 | 输出、数据库状态及操作前后应保持的不变量：待确认 |
| 自动化补充 | 单元／接口／集成测试位置；单元测试可使用 Mock，真实依赖边界：待填写 |
| 预期确认人 | 姓名与日期：待填写 |
| 执行结果 | 未执行 |
| 证据 | 代码版本、环境、命令、原始结果位置：待填写 |

## 扩展：选取与审查依据

- 需运行时验证的性质，或复杂关联／跨模块黑盒目标：待填写。
- 对应白盒审查位置、静态检查及差异版本：待填写。
- 预期核验依据与实际确认姓名、日期：待登记。
- 多连接、多实例、外部服务及恢复条件：按场景填写。

设计阶段填明 design 依据、场景和预期，缺少支持文档的项不得进入执行。人工交互是主验证，单元和集成测试补充。执行结果初始登记“未执行”；具备准入和执行条件后登记真实环境、页面证据及自动测试结果。
