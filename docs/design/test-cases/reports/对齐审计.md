# test-cases 与自动化测试对齐审计

## 审计口径

- 基线：`main` 提交 `23d89def` 后的工作分支 `docs/test-case-alignment`。
- 范围：四份业务测试案例文件中的 108 个 TC。它们保留为规则原子项，用于自动测试和报告映射；人工前端主验证按[执行测试项](../执行测试项.md)收敛为 72 项，四人各 18 项。
- 另保留 10 个真实依赖／部署前置检查；它们不重复计入人工业务项。
- 性能与容量使用独立 [TC-PERF-001](../性能与容量.md)，不并入本文件的 108 个业务 TC 或 72 个人工执行项；执行证据见[性能报告](performance-capacity/测试报告.md)。
- “已覆盖”：已有单元、接口或真实 PostgreSQL 集成测试对 TC 的核心业务不变量有语义等价断言；不代表报告、网页证据和 PR 已完成。
- “部分覆盖”：只覆盖部分规则、正常路径或 Mock 路径；至少一个关键分支、真实依赖、并发、事务或前端可观察结果没有自动化断言。
- “未覆盖”：找不到对 TC 核心场景的测试。
- 字符串扫描发现业务测试代码中没有 `TC-*` 标识；现有映射全部依据测试方法、断言和测试夹具人工建立。

## 结论

1. 商品互动、交易主状态、事项生命周期和实时主流程已有较强自动化基础，应复用现有测试，不为“补测试数量”重复改写。
2. 最高优先级代码缺口是 9 个未覆盖 TC，其次是并发、真实依赖、失败回滚和完整角色矩阵类部分覆盖；自动化单测可使用 Mock。
3. 人工验收以 72 个用户故事执行项为主，必须从真实前端完成注册、准备和业务链，并使用真实 PostgreSQL、Redis、OSS、SMTP。
4. 原 TC 自动测试作为补充与回归证据，不替代人工流程；只有报告、真实页面证据、必要自动测试和审查同时闭环后才标记通过。
