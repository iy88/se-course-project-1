## 1. 使用方式与边界

- 本清单只细化口径，不改变范围：18 项、三个 RUN 与「覆盖原 TC」沿用执行测试项。
- **依据以 `main` 为准。** 本地 checkout 停在 `s2/integration`：缺 `执行测试项.md`，且 `会话与处置事项.md`（接口 0.1.5 → 0.1.11）、`事项主体与处置执行.md`、`实时与任务.md`、`文件与邮件.md`、`交易与评价.md`、`聚合与管理查询.md` 版本落后；执行前先与 `main` 对齐，否则会漏掉最新视角、可用操作与统计口径。
- 真实页面上的人工业务链是主验证；核对列的 SQL、日志与网络记录用于证明状态和权限，不能替代人工流程。
- 标「受控」的步骤需要受控时钟或测试夹具（申辩期、统计时间边界、事件保留期），报告须写明注入方式、注入前后的实际时间与最终页面结果。
- 术语：**事项** = `moderation_case`；**流水** = `moderation_case_action`（`action_kind` 取 `submit`／`supplement`／`claim`／`inquire`／`statement`／`appeal`／`manager_reply`／`decide`／`close`／`execute`／`lift`／`publish_result`）；**执行** = `case_enforcement`；**证据** = `case_evidence`。
- 错误码以[会话与处置事项接口契约](../../../detailed-design/interfaces/会话与处置事项.md)、[交易与评价接口契约](../../../detailed-design/interfaces/交易与评价.md)、[聚合与管理查询](../../../detailed-design/interfaces/聚合与管理查询.md)、[账户与通知](../../../detailed-design/interfaces/账户与通知.md)为准；接口实际返回与契约不一致时按「记缺陷、不擅自改预期」处理。

## 5. 执行卡

### D01 评价唯一性与资格

**依据**：TRD-IF API-TRD-012／013／015；TRD-KD「Review」与唯一约束；QUERY-IF QUERY-003 `evaluation`；US-07-AC-01／07；原 TC-TRD-013、TC-COM-029。

**前置**：T1 已完成且双方未评价；T2 进行中；T3 已终止；`qa-outsider` 非参与方。

**步骤**：① 双方分别在 `/me/trades` → T1 详情「评价」卡选 1—5 分、填写文字并「提交评价」；② 同一方用新幂等键再次提交；③ 打开 `/me/reviews` 的「我写的评价」「我收到的评价」，并复查 `/products/P1`；④ 在 T2、T3 详情尝试评价；⑤ `qa-outsider` 打开 `/trades/T1` 并直接调用 `POST /trades/T1/reviews`；⑥ P1 下架后复查 `/me/reviews`。

**预期**：① 首次 201；② 409 `REVIEW_ALREADY_SUBMITTED`（同键重放应返回原评价）；③ 两个方向各一条、可跳转原交易，商品详情页**不**出现评价列表（`/products/*` 只有商品评论）；④ 均 409 `TRADE_NOT_COMPLETED`（含已终止，不是 `TRADE_TERMINAL`）；⑤ 页面拒绝、接口 403 `ACTION_NOT_ALLOWED`；⑥ 商品下架不删除本人评价；评分越界／空正文／超长 422。

**核对**：

```sql
select trade_id, reviewer_id, reviewee_id, rating, visible
from trade_review where trade_id = :t1 order by id;
```

T1 恰好两行、`reviewer_id`／`reviewee_id` 为买卖双方、`rating` 1—5、`content` 非空；被拒路径无新增行。

### D02 评价移除与封禁／冻结边界

**依据**：TRD-KD Review `moderation_*` 字段配对约束；R2B `remove_evaluation_content`；CASE-IF API-CASE-007；US-07-AC-02／07；原 TC-TRD-013、TC-CASE-004。

**前置**：D03 已提交 R4（E1 的举报）；R4 未认领；另备「仅交易冻结」的账户与「封禁」的账户两个独立账户，不要叠加。

**步骤**：① `qa-manager-a` 从 `#/cases?ownership=unclaimed` 认领 R4；② 在 `#/cases/R4` 打开「证据引用」确认依据；③ 「处置决定」选「认定违规」+ 理由 + 依据引用 + 处置项「移除评价」并填目标编号 → 提交；④ 作者查看 `/me/reviews`、原交易与 `/case-results`；⑤ 对 `qa-buyer-b` 依据另一事项执行「封禁账户」，其再评价已完成 T5；⑥ 对 T5 执行「冻结交易」，参与方评价另一笔已完成交易；⑦ 对同一评价再次提交移除。

**预期**：① 200 `claimed`；③ 201，`result_status=applied`，作者收到 `case.evaluation_removed` 通知；④ 「我写的评价」与「我收到的评价」均仍列出该条，但正文为空（`content=null`），评分不隐藏（契约未规定隐藏 `rating`）、交易终态与统计口径不变，「举报评价」入口因 `visible=false` 消失；⑤ 403 `ACCOUNT_WRITE_RESTRICTED`，不新增评价；⑥ 冻结不影响另一笔已完成交易的评价（201），冻结保持生效；⑦ 409 `TARGET_STATE_CONFLICT`；缺依据 → 422 `BASIS_REQUIRED`；非认领人 → 404 `NOT_CASE_MANAGER`。

**核对**：

```sql
select visible, removed_at, removed_by, removal_basis_ref from trade_review where id = :e1;
select action, result_status, result_id, lifted_at from case_enforcement where case_id = :r4;
select account_id, applied_at, released_at from account_ban where account_id = :u3;
```

`removed_at` 非空 ⇒ `visible=false` 且四列同非空；`case_enforcement.action` 为 `remove_evaluation_content`、`result_type='evaluation'`、`result_id` = 评价 ID。

### D03 举报提交、对象与证据

**依据**：CASE-IF API-CASE-001；CASE-KD「举报的复用与结案」「证据引用」；FILE-KD「状态转换与数据约束」；FILE-IF FILE-001—003；US-07-AC-03／06；原 TC-CASE-002、TC-CASE-006。

**前置**：P3 公开、C1 与 MSG1 存在、E1 存在；真实 OSS 私有桶可直传并完成核验。

**步骤**：① `qa-buyer-b` 在 `/products/P3` 点「举报商品」→ `/report` 预填 `product`，填理由、说明并上传 1—2 张真实验证过的截图 →「提交举报」；② 在 P3 评论区点评论「举报」提交（`comment`）；③ 在会话中点对方消息「举报消息」（`message` + 会话类型／标识）提交；④ 在 `/me/reviews`「我收到的评价」点「举报评价」（`evaluation`）；⑤ `/report` 手动选「账户」并填对象标识；⑥ 举报本人商品、本人评论、本人消息；⑦ 举报已下架／已删除对象；⑧ 管理端 `#/cases?ownership=unclaimed` 查看共享池。

**预期**：①—⑤ 201、`case_status=pending`、`reused=false`，证据与事项同事务；⑥⑦ 422 `TARGET_INVALID`（`target_type` 不含 `trade`；消息缺会话类型／标识也属此类）；⑧ 各条进入共享池，非认领管理员只看到概况，看不到完整证据与私聊；被举报对象状态不变、被举报人不收到通知；缺 `reason` → 422 `INPUT_INVALID`；未核验或他人 `file_id` → 422 `EVIDENCE_OUT_OF_SCOPE`。

**核对**：

```sql
select id, target_type, target_id, case_status, reporter_account_id
from moderation_case where reporter_account_id = :u3 order by id;
select evidence_kind, file_id, file_reference_id, source_ref_type, source_ref_id, required_scope
from case_evidence where case_id = :r1;
select state, purpose from file_record where file_id = :f;
```

消息目标必须同时有 `target_conversation_kind`／`target_conversation_id`；`file_reference` 为 `target_type='case'`、`slot='evidence'`；未结唯一索引（非消息对象按“举报人+类型+对象”，消息按“举报人+会话类型+消息 ID”）无重复。

### D04 补充、结案后拒绝与匿名公开

**依据**：CASE-IF API-CASE-002／009／011／012；CASE-KD「举报的复用与结案」「匿名公开」；US-07-AC-04／05；原 TC-CASE-002、TC-CASE-004。

**前置**：R1（P3）未结；R2（C1）已认领并作出「不予受理／不予处置」决定（无实际处置 → 无申辩期）。

**步骤**：① `qa-buyer-b` 对 P3 再次提交举报并追加证据；② 管理端结案 R2 →「公开匿名结果」填公开结论与原因 → 提交；③ `qa-buyer-b` 对 C1 再补充并重新提交；④ 任意登录用户打开 `/case-results`；⑤ 结案前对另一条已结案未公开的举报复查 `/case-results`；⑥ 结案后打开 `/cases/R2` 看 `available_actions`。

**预期**：① 200 `reused=true` 同 `case_id`，页面提示「该对象已有未结的举报，本次内容已作为补充记录。」，`supplement_count` +1、不新建事项（补充分支同样计入计数）；② 200 且 `public_result_at` 写入；③ 409 `CASE_CLOSED`，原事项与依据仍可读；④ 显示公开结论与原因，不含用户／管理员身份、私聊或申辩内容；⑤ 不出现；⑥ `available_actions` 为空数组（不是字段缺失）；结案前公开 → 409 `STATE_CONFLICT`；非举报人补充 → 404 `NOT_CASE_PARTICIPANT`。

**核对**：

```sql
select archived_at, public_summary, public_reason, public_result_at, published_by
from moderation_case where id = :r2;
select action_kind, count(*) from moderation_case_action where case_id = :r2 group by 1;
```

公开四列成组非空且仅 `case_type='report'` 可持有；`publish_result` 每案至多一条；公开列表投影不含 `reporter_account_id`、`reason_text`。

### D05 认领竞争与认领人隔离

**依据**：CASE-IF API-CASE-004／010；CASE-KD「认领与处理权限」「锁顺序与事务边界」；公共事务与权限 C1 锁序；US-08-AC-01；原 TC-CASE-001、TC-CASE-003。

**前置**：R1 仍 `pending`；`qa-manager-a`、`qa-manager-b` 各自浏览器。

**步骤**：① 打开 `/me/notifications` 列表；② 打开其中一条详情（前端打开即写已读）；③ 同账户两标签并发打开同一条；④ 复查 `/conversations` 未读与 `/me/todos`；⑤ 封禁账户读取获准事项通知并标记已读；⑥ 标记他人通知。

**预期**：① 列表不标读，未读 chip 不变（`total` 按过滤、`unread_count` 为本人全部未读）；② 仅该条 `read_at` 写入、显示「首次已读 <时间>」，`unread_count` 减一；③ 首次时间不变、不重复事件；④ 聊天未读与待办均不变（已读不办结待办）；⑤ 200 且可写已读（契约允许），其他写操作仍受限；⑥ 404 `RESOURCE_NOT_VISIBLE`；缺 CSRF → 403 `CSRF_INVALID`；未知 `event_type`／分页非法 → 422。

**核对**：

```sql
select notification_id, read_at from notification
where recipient_account_id = :u2 order by notification_id desc limit 5;
select count(*) filter (where last_read_seq > 0) from case_read_progress where account_id = :u2;
```

### D16 实时双端、断线补取与撤权

**依据**：RT-KD「事件提示 schema」「Redis 发布、IM 广播与缺口修复」「初次加载、超期游标与事件保留」；ACC-IF AUTH-001；C1 当前资格；US-11-AC-05／06；原 TC-COM-023—025。

**前置**：同一账户两个浏览器（WebSocket `/api/v1/realtime`）；乙端记录 `hello_ok` 的 `epoch`／`head_seq` 与 `cursor{epoch, after_seq}`。

**步骤**：① 双端建立连接；② 甲端触发事件（对方发消息、接受请求），观察乙端；③ 乙端断网后恢复，期间继续产生事件；④ **受控**把 cursor 置为超期或改 `epoch`；⑤ 退出或改密撤销 Session；⑥ 请求无权对象的提示；⑦ 提交传输 ACK 但不打开正文。

**预期**：① `hello_ok` 返回 `connection_id`／`epoch`／`replay_floor`／`head_seq`／`heartbeat_seconds`；② 双端同步、`account_seq` 连续、`event_id` 去重、会话内按 `message_seq` 展示；③ 重连后按数据库补齐缺口（`GET /account/events?epoch&after_seq`），`items=[]` 时游标仍推进，不重复不跳号；④ 返回 `sync_reset` 并暂停业务事件，重新加载通知与会话后从 `head` 恢复；`epoch` 不符／`after_seq < replay_floor`／`> head` → 409 `EVENT_RESYNC_REQUIRED`；未知 `schema_version` → 提示协议升级并停止该段投递，不静默丢弃（事件保留期默认 604800 秒，需受控时钟造超期游标）；⑤ 停止受保护推送并断开（4401／4403）；⑥ 只返回 `cursor_advance`，不含类型、对象与正文；⑦ ACK 不改变聊天或通知已读、待办与业务确认。

**核对**：UserEvent（`account_seq`、`intent_key`、`published_at`）、Redis Stream 读取位置、客户端 `cursor` 日志、`notification` 与 `case_message` 最终可见数据。

### D17 本人业务聚合

**依据**：QUERY-IF API-COM-QUERY-001／003；PRD-KD 生命周期与收藏；TRD-KD 本人交易；CASE-KD 举报可见性；US-12-AC-01—05；原 TC-COM-029。

**步骤**：① `qa-buyer-a` 打开 `/me` 概览并逐个进入「我的商品／交易／收藏／评价／事项」子页；② 按 `kind`（product／trade／favorite／evaluation／report）、方向（written／received）、角色（buying／selling）、状态与分页遍历接口；③ 造空分组；④ 失效收藏；⑤ 已结束交易与下架商品历史；⑥ `received` 举报复查；⑦ 用他人对象 ID 直接取数。

**预期**：① 概览卡片与各列表 `total` 一致；② 每对象只出现一次、total 与同过滤列表等价、分页稳定（`page_size` 上限 100，越界 422）；③ 计数为 0 且列表为空；④ `state=invalid`、`product_summary=null`，不显示失效原因，`favorites.total` 含失效；⑤ 历史可读、只读；⑥ 只含曾实际处置的事项，仅问询的不出现；⑦ 404 或空；`evaluation`／`report` 的 `direction` 必填，`role` 仅 trade 接受，参数组合非法 → 422；依赖故障 503（仅概览有具名 `QUERY_DEPENDENCY_UNAVAILABLE`）；查询不改业务与已读。

**核对**：

```sql
select count(*) from product where seller_account_id = :u2 and deleted_at is null;
select count(*) from trade where buyer_id = :u2 or seller_id = :u2;
select count(*) from trade_review where reviewer_id = :u2;
select count(*) from trade_review where reviewee_id = :u2;
select count(*) from moderation_case where case_type = 'report' and reporter_account_id = :u2;
```

聚合页无「举报」独立分组：`report` 视角以 `/me/cases` 页面 + `GET /account/resources?kind=report` 接口分别核对。

### D18 旧链接与资格重校验

**依据**：QUERY-IF「统一规则及适配接口」；C1 当前权限；PRD-IF API-PRD-011；PRD-KD P3-5；US-12-AC-06／07；原 TC-COM-029、030、TC-PRD-014、041。

**前置**：已结束交易 T1、下架商品 P1、`qa-buyer-b` 封禁状态、他人事项 ID。

**步骤**：① 从旧通知打开已结束交易；② 直接访问他人事项与交易链接；③ 封禁后从 `/me` 继续写操作；④ 买方从历史入口查看商品后续编辑历史（`GET /products/{id}/history` 之类按 PRD-011）；⑤ 复查该买方是否收到商品变更通知；⑥ 管理员带 `case_id` 访问商品编辑历史。

**预期**：① 只读、可执行操作按 `available_actions` 隐藏，提交被按当前状态拒绝；② 他人链接 404 `RESOURCE_NOT_VISIBLE`（PRD-011 的越权表现是 404 而非 403）；③ 403 `ACCOUNT_WRITE_RESTRICTED`，只读仍可用；④ 按本人资格可见「请求／交易时点及之后变更」，不是至今全量；⑤ 不向已结束请求／交易发送商品变更通知；⑥ 仅本人认领事项的必要范围可见。

**核对**：`trade.status`／`ended_at`；`product.content_version` 与编辑历史（按 `edited_at` 排序）；`notification` 无对应新增行；聚合列表按 `updated_at` 排序，与编辑历史的 `edited_at` 是两套顺序。

## 6. 判定口径与已知差异

| 口径 | 说明 | 断言时注意 |
|---|---|---|
| 「未结」 | 事项列表／详情用 `archived_at is null`；统计 `pending.reports` 用「无 `close` 流水」 | 两处数字可能不同，报告写明用哪一套 |
| 统计默认范围 | 页面进入默认近 7 天并显式传 `range`；接口无默认值（需求变更 2026-11-26，US-10-AC-03 由「无默认范围」改为「默认近 7 天」） | 接口直调仍必须带 `time_scope`；页面默认值由前端计算 |
| 统计时间字段 | `completed_in_selection` 用 `trade.ended_at`；封禁用 `account_ban.applied_at`／`released_at` 的 as-of 语义 | 不用 `created_at`／`updated_at` |
| 执行影响范围 | `case_enforcement.affected_scope` 的 `resource_id` 是 JSON 字符串 | 用 `->> 'resource_id'` 文本比较 |
| 评价列表 | 存在带／不带 `join trade` 对手校验的两条读取路径 | 先确认接口实际路径，再对账方向与 total |
| 申辩期 | 设计未固定数值，代码默认 604800 秒 | 用测试配置并记录；改配置不改既有截止时间 |
| 幂等重放 | 同 `enforcement_id` 重放使 `result_status` 变为 `replayed` | 不按「新增一行」判断 |
| 可解除执行 | 仅 `freeze_trade`／`restrict_account`／`withdraw_public_access` 可解除，且需 `applied` 且未解除 | 其他动作解除应失败 |
| 评价终态 | 已终止交易评价返回 `TRADE_NOT_COMPLETED` | 不写成 `TRADE_TERMINAL` |
| 非参与方 | 评价接口对非参与方返回 403 `ACTION_NOT_ALLOWED` | 与「非参与方 404」的通用约定冲突，记录冲突 |
| 公开结果 | 页面 `/case-results` 需登录 | 「匿名」指结果不含身份，不是匿名可访问 |

## 8. 自动化补充边界

- 人工主验证只承担「页面能否完成、结果与反馈是否正确」；以下由自动化补齐：纯领域状态与错误码、时间计算、幂等摘要、权限投影、SQL 谓词等价性。
