## 拓扑与操作配比

API 和 WS 使用相同 infrastructure JVM 镜像，分别置于两个 nginx upstream；scheduler 和 worker 使用独立 profile 且无 HTTP 监听。所有实例共享同一 PostgreSQL 和 Redis 命名空间。

| 闭环槽 | 数量／20 | 操作 |
|---|---:|---|
| home | 6 | `GET /products?page_size=20` |
| search | 5 | 关键词 + 分类 + 翻页搜索 |
| detail | 5 | 打开浏览池商品详情 |
| publish | 1 | OSS 上传、完成核验、发布商品 |
| trade | 1 | 请求、接受、约定、双方完成确认、校验、重上架 |
| IM | 2 | 发送、接收 WS hint、HTTP 回读正文、推进已读 |

默认 capacity 为 Single Search：起点 200、上限 400 HTTP RPS、5 秒预热、30 秒阶段、300 秒验证、12 次 refinement、1 RPS 精度、2,048 in-flight、100 ms 最大调度滞后、零错误预算。性能上限档按报告另列短窗参数。

### P-RUN-01：100 用户／10,000 商品代表性稳态

| 字段 | 内容 |

| 设计依据 | QUALITY、ACCEPTANCE、RT |

| 输入 | 30 秒预热、120 秒采样、think 1 秒；20 槽混合操作 |
| 实际结果 | 干净提交 `93f612b7` 复跑：21,334 个测量 HTTP 请求，177.78 HTTP/s；HTTP 错误 0、WS 断连 0、重连失败 0；必需 HTTP 操作 P95 最大 341.72 ms；`im_delivery` P95 314.74 ms、`im_retrieval` P95 2.44 ms |
| 结论 | 通过 |
| 证据 | [baseline-100u-10k JSON](evidence/P-RUN-01/baseline-100u-10k-20261127.json)、[干净源码汇总](evidence/P-RUN-01/clean-source-summary.json) |

`im_delivery` 从发送 POST 前开始，在接收方正文通过真实 HTTP 回读并按 `message_id + seq + body` 核对后结束；`im_retrieval` 单独从接收 hint 起算。若 hint 先于发送响应到达，驱动保存正文回读完成时刻，并在发送响应返回后补做 ID／seq 核对，不把等待发送响应的时间追加到已经完成的回读样本。该结果是 API／WS 层可读取性，不是浏览器实际渲染或目标部署 WAN 验收。

首次 P-RUN-01 使用含其他未提交案件改动的开发 JAR；初审后改为干净源码复跑。复审又发现 IM 送达起点错误，随后在同一正式负载下验证。最终干净提交 `93f612b7` 还修复了两项实测问题：Bucket ACL／versioning 只在部署依赖探针中校验；上传控制器复用进程级 OSS 客户端，避免每请求创建 SDK 客户端。两份 JAR 摘要、额外改动范围和旧容量实验实际版本见[环境准备](evidence/env-setup.md#版本对应与未混入改动)。

#### Search / API

| API | 400 RPS 正式 | 600 RPS 短窗 | 800 RPS 短窗 |
|---:|---|---|---|

| 2 | P95 19.55 ms，通过 | P95 23.8—2,191 ms；第二窗通过，冷窗已排队 | P95 5.36 s，pending 4,089，40 个错误 |
| 4 | P95 19.26 ms，通过 | P95 4.71 s，pending 2,546，过载 | P95 9.21 s，pending 4,087，2,911 个错误 |

#### IM / WebSocket

| WS | 400 场景/s 旧版送达 P95 | 600 场景/s 旧版送达 P95 | 800 场景/s 旧版送达 P95 |
|---:|---|---|---|
| 1 | 通过；559 ms | 10.07 s；492 个错误 | 7.34 s；58 个错误；pending 2,032 |
| 2 | 通过；110 ms | 10.12 s；527 个错误 | 6.82 s；pending 2,047 |
| 4 | 通过；240 ms | 8.71 s；85 个错误 | 5.14 s；pending 2,027 |

这些历史档位来自初审前驱动，实际测量从发送开始到接收方正文 HTTP 回读完成，但存在发送响应与接收事件关联竞态；不是单独的 hint 到达时延，仅作相对容量分析，不复用为修复后的端到端 `im_delivery` 证据。400 场景/s 实际约 1.2k HTTP/s；600 场景/s 实际约 1.8k HTTP/s。WS 2 在 400 场景/s 改善明显，WS 4 无进一步容量收益。

#### mixed

- worker 1：100 场景/s 通过；150 场景/s 发布／上传样本不足；200 场景/s 失败。
- 200 场景/s 时 nginx 记录约 52—55 个 503；publish／upload 样本短于计划，而普通搜索、交易步骤仍为低毫秒级。
- mixed 的可用稳定档按本次证据记录为 100 场景/s，100—200 之间的准确上限尚未做长期验证。

| WS hint 先于发送 HTTP 响应 | 缓存实际到达时刻，响应后核对 message_id／seq／body，再完成样本 |
| `im_delivery` 错把 HTTP 回读开始当送达起点 | 恢复发送前 `Instant`，以正文回读完成作为终点；另报 `im_retrieval` |
| 上传授权／完成／清理重复查询 Bucket ACL／versioning | 检查收敛到部署依赖探针；请求路径不重复查询，新增无 OSSClient 交互单测 |
| 高并发上传反复创建 OSS SDK 客户端 | 上传控制器复用进程级客户端并在关闭时释放；同一正式负载复跑零错误 |

## 未覆盖与阻塞

- 400 RPS 以上只有 20 秒短窗，不能写成长期 SLA。
- 驱动与后端同机，CPU、内存和 loopback 会共同限制实验上限；结果不外推到独立部署主机或 WAN。
- 未覆盖浏览器渲染、首屏水合、图片解码、WAN 丢包／RTT 和 CDN。
- 未完成目标部署下“两端浏览器实际显示”和跨目标 IM 实例的完整客户端验收；本报告只证明 API／WS 驱动与 HTTP 回读口径通过。
- OSS 仅覆盖 seed 固定图片大小；不同文件大小的上传时延需另案记录。
- SMTP 不在性能操作配比中，未在本案例执行；不据此声明邮件性能。
- 当前 HTTP 与 WS 仍是同一 infrastructure 应用镜像，通过 nginx 分池；没有独立 API／IM profile 的部署级证据。
- mixed 200 场景/s 的 503 需后续定位到具体上传／发布阶段；本报告只证明它不是 `TaskWorker` 容量问题。
