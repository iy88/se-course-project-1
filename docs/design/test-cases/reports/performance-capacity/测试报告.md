## 拓扑与操作配比

API 和 WS 使用相同 infrastructure JVM 镜像，分别置于两个 nginx upstream；scheduler 和 worker 使用独立 profile 且无 HTTP 监听。所有实例共享同一 PostgreSQL 和 Redis 命名空间。

| 闭环槽 | 数量／20 | 操作 |
|---|---:|---|
| home | 6 | `GET /products?page_size=20` |
| search | 5 | 关键词 + 分类 + 翻页搜索 |
| detail | 5 | 打开浏览池商品详情 |
| publish | 1 | OSS 上传、完成核验、发布商品 |
| trade | 1 | 请求、接受、约定、双方完成确认、校验、重上架 |
| IM | 2 | 发送、接收 WS hint、HTTP 回读正文、推进已读 |

默认 capacity 为 Single Search：起点 200、上限 400 HTTP RPS、5 秒预热、30 秒阶段、300 秒验证、12 次 refinement、1 RPS 精度、2,048 in-flight、100 ms 最大调度滞后、零错误预算。性能上限档按报告另列短窗参数。

### P-RUN-01：100 用户／10,000 商品代表性稳态

| 字段 | 内容 |

| 覆盖执行项 | P01 |
| 设计依据 | QUALITY、ACCEPTANCE、RT |
| 前置条件 | 100 用户全部登录，100 个接收方 WebSocket 在线；同一 seed 快照 |
| 输入 | 30 秒预热、120 秒采样、think 1 秒；20 槽混合操作 |
| 实际结果 | 干净提交 `d98552f2` 复跑：21,279 个测量 HTTP 请求，177.33 HTTP/s；HTTP 错误 0、WS 断连 0、重连失败 0；必需操作 P95 最大 401.70 ms；接收方 hint 到达 P95 2.24 ms，后续 HTTP 回读 P95 2.25 ms |
| 结论 | 通过 |
| 证据 | [baseline-100u-10k JSON](evidence/P-RUN-01/baseline-100u-10k-20261127.json)、[干净源码汇总](evidence/P-RUN-01/clean-source-summary.json) |

WebSocket 连接记录接收方 hint 的实际到达时刻；随后用接收方 Cookie 通过真实 HTTP 读取消息，并按 `message_id + seq + body` 核对。若 hint 先于发送响应到达，驱动缓存该观测并在发送响应返回后补做 ID／seq 核对。该结果是 API／WS 层可读取性，不是浏览器实际渲染或目标部署 WAN 验收。

首次 P-RUN-01 使用含其他未提交案件改动的开发 JAR；初审后已从干净提交 `d98552f2` 重建后端、维护工具和驱动并完整复跑。两份 JAR 摘要、额外改动范围和旧容量实验实际版本见[环境准备](evidence/env-setup.md#版本对应与未混入改动)。

### P-RUN-03：Search、IM 与 mixed 性能上限

| 字段 | 内容 |
|---|---|
| 覆盖执行项 | P03 |
| 设计依据 | QUALITY、ACCEPTANCE、RT、DRIVER |
| 前置条件 | 每档从 seed 快照恢复；API／WS 分池；nginx access log 保留 upstream 结果 |
| 输入 | Search 600／800 RPS；IM 200／400／600／800 场景每秒；mixed 100／200 场景每秒；上限档 20 秒短窗 |

| 结论 | 完成边界定位；400 HTTP RPS 有正式 300 秒证据，600／800 仅作短窗性能分析 |
| 证据 | [分档汇总](evidence/P-RUN-03/capacity-limits-20261127.json)、[600 定向汇总](evidence/P-RUN-03/capacity-perf-narrow-20261127.json)、[单档报告索引](evidence/README.md) |

P-RUN-03 同样使用首次开发 JAR `125d57f4…` 和竞态修复前驱动 `8f32db78…`，仅用于 Search／IM／mixed 的相对边界和横向扩容观察；IM 档不作为最终送达结论。干净提交与修复后驱动重新证明的是 P-RUN-01 代表性路径。

#### Search / API

| API | 400 RPS 正式 | 600 RPS 短窗 | 800 RPS 短窗 |
|---:|---|---|---|
| 1 | P95 17.68 ms，通过 | P95 18.7—221.3 ms，基本排空；确认窗仅 1 个本机 late arrival | P95 5.86 s，pending 3,454 |
| 2 | P95 19.55 ms，通过 | P95 23.8—2,191 ms；第二窗通过，冷窗已排队 | P95 5.36 s，pending 4,089，40 个错误 |
| 4 | P95 19.26 ms，通过 | P95 4.71 s，pending 2,546，过载 | P95 9.21 s，pending 4,087，2,911 个错误 |

#### IM / WebSocket

| WS | 400 场景/s | 600 场景/s | 800 场景/s |
|---:|---|---|---|
| 1 | 通过；送达 P95 559 ms | 送达 P95 10.07 s；492 个错误 | 送达 P95 7.34 s；58 个错误；pending 2,032 |
| 2 | 通过；送达 P95 110 ms | 送达 P95 10.12 s；527 个错误 | 送达 P95 6.82 s；pending 2,047 |
| 4 | 通过；送达 P95 240 ms | 送达 P95 8.71 s；85 个错误 | 送达 P95 5.14 s；pending 2,027 |

400 场景/s 实际约 1.2k HTTP/s；600 场景/s 实际约 1.8k HTTP/s。WS 2 在 400 场景/s 改善明显，WS 4 无进一步容量收益。

#### mixed

- worker 1：100 场景/s 通过；150 场景/s 发布／上传样本不足；200 场景/s 失败。
- 200 场景/s 时 nginx 记录约 52—55 个 503；publish／upload 样本短于计划，而普通搜索、交易步骤仍为低毫秒级。
- mixed 的可用稳定档按本次证据记录为 100 场景/s，100—200 之间的准确上限尚未做长期验证。

### P-RUN-04：worker 扩缩容归因

| 字段 | 内容 |
|---|---|
| 覆盖执行项 | P04 |
| 设计依据 | RT；`TaskWorker` / `TaskStream` 实现 |
| 前置条件 | API 2、WS 2 固定；mixed 100／200 场景/s；worker 分别 1／2 |
| 输入 | 同负载顺序 A/B；同时采样 event stream、work stream、pending、未发布事件、DB 活动会话／锁和进程 CPU |
| 实际结果 | worker 1 与 2 结果无提升；`work_stream=0`、worker pending=0、worker CPU 峰值约 1%；200 场景/s 的失败与 worker 无关 |
| 结论 | 当前不增加 worker |
| 证据 | [worker A/B 汇总](evidence/P-RUN-04/worker-ab-summary.json)、[原始分档](evidence/P-RUN-03/capacity-limits-20261127.json)、[运行日志](evidence/run-log.md) |

`TaskWorker` 只消费 scheduler 排入 Redis 的定时任务；IM 实时投递走 API outbox、Redis Stream 和 WS，发布失败发生在真实上传／发布链路，均不能通过增加 worker 改善。

## 未覆盖与阻塞

- 400 RPS 以上只有 20 秒短窗，不能写成长期 SLA。
- 驱动与后端同机，CPU、内存和 loopback 会共同限制实验上限；结果不外推到独立部署主机或 WAN。
- 未覆盖浏览器渲染、首屏水合、图片解码、WAN 丢包／RTT 和 CDN。
- 未完成目标部署下“两端浏览器实际显示”和跨目标 IM 实例的完整客户端验收；本报告只证明 API／WS 驱动与 HTTP 回读口径通过。
- OSS 仅覆盖 seed 固定图片大小；不同文件大小的上传时延需另案记录。
- SMTP 不在性能操作配比中，未在本案例执行；不据此声明邮件性能。
- 当前 HTTP 与 WS 仍是同一 infrastructure 应用镜像，通过 nginx 分池；没有独立 API／IM profile 的部署级证据。
- mixed 200 场景/s 的 503 需后续定位到具体上传／发布阶段；本报告只证明它不是 `TaskWorker` 容量问题。
