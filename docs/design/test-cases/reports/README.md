# 测试执行报告规范

本目录保存按用户故事组织的实际测试报告、证据和汇总。人工交互是主验证，原 `test-cases` 中的 TC 是规则断言；实际执行以[执行测试项](../执行测试项.md)定义的 72 个功能项为主，一项完整前端流程可同时覆盖多个 TC，单元和集成测试作为补充与回归。性能与容量使用独立 [TC-PERF-001](../性能与容量.md)，不占 72 项，但沿用相同的报告、RUN、前置和证据要求。

## 工作颗粒度

- 全部人工功能测试共 72 个执行项，四人各 18 项。
- 每批按用户故事和完整业务链执行，不为每个 TC 单独建报告、commit 或 PR。
- 每批只维护一份执行报告，报告内按 RUN 流程记录多个执行项及其覆盖的原 TC；每项必须先列出 design 文档、接口或关键设计依据。
- 另有 10 个平台前置检查，验证本地真实 PostgreSQL、Redis、OSS、SMTP 及部署边界；由公共能力负责人维护。
- 性能批次按 `TC-PERF-001` 维护，执行项以 `P` 编号、证据按 `P-RUN-*` 归档；容量边界和 worker 归因也必须有真实报告，不以口头结论替代。
- 代码自动化测试中，单元测试可以使用 Mock；跨模块事务、数据库约束、并发及外部依赖行为使用真实集成测试。
- 发现实现问题时单独创建缺陷 Issue；修复使用独立 PR。原测试批 PR 继续保留证据，修复合入后在同一批报告中追加复测结果。

## 每批必须从真实栈开始

1. 使用 `backend/.env.dev` 配置的本地或联调环境，启动真实 PostgreSQL、Redis、OSS 和 SMTP，不把核心依赖替换为内存实现。
2. 先运行依赖探针，确认数据库、Redis、私有 OSS 写入／读回／删除和真实邮件投递均可用。
3. 通过前端注册页面创建普通账户，并在测试邮箱中读取真实验证码完成注册；管理员账户使用维护工具创建。
4. 通过用户端和管理端创建分类、商品、请求、交易、事项等前置数据。只在不可稳定到达的边界状态下使用受控时钟或测试辅助写入，并在报告中列明。
5. 按[执行测试项](../执行测试项.md)的 RUN 链条一次走完一组业务，再完成断言和证据归档。

性能与容量批次的前置为真实 PostgreSQL、Redis 和 OSS、100 用户／10,000 商品种子、固定驱动二进制、实例池和网络条件；SMTP 只有进入操作配比时才要求执行，否则必须在报告中明确记为不适用。容量上限短窗与正式 SLA 验证必须分栏记录。

## 一个测试批次的交付

每批形成：

1. 一份 Markdown 测试报告；
2. 按 RUN 归档的页面截图、浏览器网络记录、真实依赖日志及必要的测试命令；
3. 本批执行项所需而缺失的自动化测试代码；
4. 对测试项前置数据或流程粒度的必要细化；
5. 一个关联 Issue 和一个 Draft PR。

报告、证据和相关测试代码作为该批的主要测试 commit 提交。若发现产品缺陷，先提缺陷 Issue，再由独立 PR 修复；不要用修复提交覆盖原始失败证据。修复后追加复测 commit 和结果。

## 前端优先

- 主流程必须从用户端或管理端页面执行，包括注册验证、角色切换、状态变化、权限反馈和最终结果。
- 接口响应、数据库和 Redis／OSS 记录用于确认页面背后的实际业务事实，不替代前端观察。
- 并发、故障注入、真实 SMTP 退信或时钟边界无法稳定手工触发时，可用测试夹具制造条件；报告中必须标明构造方式及页面最终观察结果。

## 报告与汇总

- 每批负责人只修改本批 `测试报告.md` 和证据目录。
- `汇总.md` 由袁尚峰（`iy88`）维护，按 72 个人工功能项和 10 个平台前置检查更新状态。
- 报告必须列出实际执行的 RUN、覆盖项、原 TC 映射、通过／失败／阻塞、缺陷链接和复测结果。
- 截图与日志必须脱敏；不得提交密码、验证码、Cookie、签名 URL、云凭据或真实个人信息。
