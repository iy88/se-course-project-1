# 1. 阶段划分与依赖

## 设计准备 D0

四人任务并行开展需求核对、主体关系与 Q 整理；TASK-001 先形成公共契约和必要技术验证输入，模块成员依次细化当前阶段接口。四任务设计交付与交界复核完成后，将评审结果集成到design并形成已确认基线，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。

## 设计固化与编码边界

D0期间完成四任务的模型、接口契约、关键规则、验证预期及交界复核。四任务设计评审并集成到design、形成已确认基线后，再准备拟进入阶段的编码任务卡与准入材料；通过阶段准入批准后开始业务编码。各设计批次的并行安排用于设计交付。

依据：袁尚峰2026-11-15明确的推进顺序。设计固化采用四任务完整交付与实际审查结果，编码准备采用固化后的版本、经核验的预期及阶段运行条件。

## 候选实现阶段

| 阶段 | 可运行业务链 | 需求范围 | 前置Q/ADR | 接口 | 必测风险 | 退出条件 |
|---|---|---|---|---|
| S1 | 邮箱验证注册→登录→上传发布→分类申请／审核→检索详情→评论收藏及本人查询 | FR-01、02、03、04 商品部分、08 审核部分、09、13；FR-11／12 对应部分 | ADR-001—011 中适用于账户、通知、商品和部署的决定；Q-001—004 对应身份、文件、邮件及换绑 | 账户／邮箱验证、文件、商品审核／分类、检索评论收藏、本人查询及基本通知／待办；具体编号见动作映射 | 身份、配置、文件协议；审核与分类原子性，资格与上传引用 | 覆盖本阶段接口和预期，完成实现审查、人工联调及适用的开发测试 |
| S2 | 普通私聊→购买请求→交易分支→接受锁单／拒绝撤回→通知与本人交易 | FR-04 会话部分、FR-05 请求部分、09；FR-11／12 对应部分 | S1；ADR-003—005、010；C1—C4 与商品占用契约 | 会话、购买请求、接受拒绝撤回、通知；具体编号见动作映射 | S1 商品及账户能力；跨实例分发、竞争锁单、幂等 | S1 受影响回归及本阶段人工联调、适用开发测试 |
| S3 | 有效约定→变更→双方完成确认／协商终止→评价及历史 | FR-05 约定与结束部分、06、07 评价部分、09；FR-11／12 对应部分 | S2；ADR-002、003、006、010；确认及结束契约 | 约定、确认、终止、评价与历史；具体编号见动作映射 | S2 占用与会话；确认重置、关联结束、规则版本 | 前阶段受影响回归及本阶段规则、接口审查与人工联调 |
| S4 | 举报／争议／超时异常→认领沟通→处置冻结／恢复／封禁→管理统计与本人事项 | FR-07 举报、08 处置、10、14；FR-05 争议、FR-02 纠类部分、FR-09／11／12 完整覆盖 | S1—S3；ADR-002—005、009、010；事项及主体执行契约 | 举报、认领、事项沟通、申辩与结案、限制／调整、统计；具体编号见动作映射 | 各主体状态执行、事项会话、调度；限制叠加与恢复、匿名范围 | 全需求实现覆盖核对、前阶段受影响回归、人工联调及必要集成检查 |

阶段范围按 FR 拆分记录，已批准功能逐项映射至对应阶段。S1 即包含审核认领与基本通知、待办及本人入口；后续阶段随主体能力补齐聚合内容。S1 处理发布审核及分类目录维护，已发布商品的管理员纠类随 S4 事项处置上线。逐项阶段归属、接口及案例采用[需求与接口映射](../detailed-design/01-需求与接口映射.md)。

- S1 的管理待办只启用商品审核；通知须能持久保存、查询及标读，并验证已启用的通知投递与恢复契约。普通私聊与购买请求属于 S2，举报和申辩属于 S4。
- S2 验证普通私聊及交易分支，并核对请求竞争、下架关闭与归档；约定、完成确认及普通终止由 S3 实现并验证适用契约。
- S3 的约定和取消用例直接核对正常进行中状态；S4 启用争议和异常后，补验争议期间约定暂停、争议中协商取消、超时冻结及恢复。适用阶段由动作及案例前置状态共同确定。

## S1 工作顺序

1. 袁尚峰先建立 Maven 多模块、双 Vue 应用、共享 API 类型生成和 CI 入口，发布模块依赖、服务接口及本地启动方式。
2. 金婉怡可先实现商品／分类独立规则，张新悦可先实现审核认领规则，孙含佳可使用 OpenAPI 与受控响应开发移动优先并适配桌面的用户界面。需联调的工作在相应服务、接口和迁移可用后接入。
3. 审核认领后处理采用同一事务，商品与分类由金婉怡提供服务，张新悦提供固定认领及管理端，袁尚峰装配用例、通知、待办和审计，孙含佳接通用户侧流程。各接口与验证归属见[编码任务索引](../tasks/索引.md#s1-编码任务)。

## S2—S4 的确定时点与并行范围

阶段的业务边界、接口编号和用例预期已按[需求与接口映射](../detailed-design/01-需求与接口映射.md)划定。交付批次、负责人、联调版本和准入证据随阶段任务卡确定。先在 S1 期间根据公共骨架整理 S2—S4 的候选任务和交界；当前一阶段提供相关服务签名、错误语义和测试数据时，复核下一阶段任务卡。涉及真实调用的能力按可用接口及阶段准入批准放行。

| 阶段 | 可独立准备或在获准后先行实现 | 真实联调所需输入 |
|---|---|---|
| S2 | 交易请求状态机与普通私聊可分开开发，前端按 OpenAPI 和受控响应并行 | S1 账户、商品和通知服务。交易分支创建／归档及竞争锁单需会话服务、商品占用端口和公共事务可运行 |
| S3 | 约定变更、确认重置、评价资格及历史投影可按既有契约开发和做单元测试 | S2 已接受交易、商品占用与交易会话。最后确认、终止和评价使用实际状态、事件和释放占用实现 |
| S4 | 事项认领、问询、申辩、申辩期及匿名投影可复用 S1 骨架开发。处置执行方先给具名命令与受控结果 | 争议和冻结／恢复、超时与封禁连动、管理统计依赖 S2／S3 活动交易的状态、计时与会话，并需账户、商品、交易和调度适配可运行 |

S1-001 完成首个共享交付后，S1-002／003／004 根据任务卡并行推进，公共模块的后续实现与各自主体规则可以交错进行。并行开发先交付模块公开接口、DTO、可生成的 OpenAPI 和代表性数据；用例由应用装配，迁移修改由数据归属模块维护。跨领域真实联调按 S1 → S2 → S3 → S4 的能力依赖推进。阶段重叠时，派发前核对同一成员承担的任务以及共享应用装配、迁移和接口的修改边界。

## 准入关联

各阶段在接口细化时登记具体 API、TC、前置 Q／ADR 和任务，按[准入模板](../acceptance/阶段准入记录模板.md)批准。S1—S4 的开发完成条件采用静态检查、审查、人工前后端联合测试及适用的单元与集成证据。系统测试和人工验收在开发完成后开展，按[测试策略](02-测试策略与依据.md#分阶段回归)执行。任务参见[四人索引](../tasks/索引.md)。
