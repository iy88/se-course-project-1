# 2. 测试策略与依据

## 预期来源

需求正文、BR／TR／权限矩阵、详细 US／UC／SC 与人工确认构成预期依据。AI 辅助扩展案例，对应任务登记的审查姓名核验预期及适用范围。

## 静态与白盒验证

后端执行 Maven 编译与静态检查。前端使用 Oxlint、Oxfmt、`vue-tsc` 严格类型检查及 Rsbuild 构建检查。全部业务逻辑白盒核对输入、主体资格、状态、不变量、事务、锁序、失败分支与审计。审查记录对应版本和差异。

## 运行时验证选取

人工前端交互是主要业务验证方式。按[用户故事执行测试项](../test-cases/执行测试项.md)的 72 项流程从注册、数据准备到页面结果连续执行，一条流程可以覆盖多个 TC。使用真实 PostgreSQL 多连接验证并发；使用多 API／IM／worker 实例验证共享机制。合成数据和环境版本随案例登记。

## 测试层级

| 层级 | 验证对象 | 本项目示例 |
|---|---|---|
| 单元测试 | 独立的领域方法或纯逻辑，使用显式输入和可控时钟 | 状态转换资格、配置校验、有效等待时间计算 |
| 集成测试 | 模块、接口或外部依赖之间的契约及协作 | 真实 PostgreSQL 多连接竞争锁单，PostgreSQL／Redis 会话撤销，OSS 与邮件投递 |
| 系统测试 | 已部署系统的完整业务链路与质量要求 | 跨实例发消息并在接收端显示，浏览器端到端交易链路，滚动更新与故障恢复 |
| 验收测试 | 以需求和阶段退出条件为依据，由实际验收人确认结果 | 阶段主流程与异常演示，最终部署的全链路、权限、性能与恢复验收 |

接口测试按被测范围归入相应层级。只验证 API 与数据库协作时属于集成测试，经已部署系统完成跨模块用户流程时属于系统测试。性能是测试目标，可在集成、系统或验收阶段测量。验收可引用已有运行证据，并按验收记录登记确认人和日期。单元案例在实现任务中按独立规则和回归风险登记，白盒审查及静态检查另记证据。

## 开发阶段验证方式

业务逻辑验证以人工前后端联合测试为主，使用当前阶段可启动的前端、API 和明确的测试数据。按角色覆盖正常操作与关键异常，核对界面反馈、API 响应及相关状态。记录版本、环境、数据、操作步骤和实际结果。

- 单元测试作为补充，覆盖有分支的资格、状态、时间边界和界面状态转换；可以使用 Mock 隔离无关依赖。每例登记输入、固定时间或模拟依赖及可观察预期。
- 按需补集成测试，覆盖需稳定复现的真实依赖或跨模块契约行为，例如数据库约束、事务回滚、并发竞争、会话失效、持久化事件恢复，以及生成 API 客户端与接口契约协作。并发用真实 PostgreSQL 的独立连接，Session 或队列行为用真实 Redis。可控替身用于触发 OSS 或 SMTP 的指定响应。登记所接入的依赖和所用替身。
- 测试预期沿用已有 TC 的业务规则，注明具体子场景及验证层级。前端对受控接口响应可验证页面状态及错误处理，真实浏览器跨模块端到端链路列入各阶段的主链验证及最终系统回归。

人工主验证必须使用真实 PostgreSQL、Redis、OSS 和 SMTP。自动单测中的 Mock 结果不得替代人工页面结果；跨模块事务、数据库约束、并发和真实依赖行为仍须有集成测试作为补充证据。

## 必要技术验证计划

| 专题 | 场景 | 预期及证据 |
|---|---|---|
| 事务及锁单 | 两实例竞争接受；提交失败；同次重试 | 唯一占用、整体回滚、稳定结果；数据库状态与命令 |
| IM | 用户连接分布两实例；重连；流裁剪或分发中断 | 目标覆盖、去重、补取与已读独立；系统测试以接收端真实显示记录验证正常网络双方在线的 2 秒可见目标，测量口径见[部署验收安排](04-最终部署验收安排.md#性能测量) |
| 任务调度 | worker 退出、租约接管、重复投递 | 幂等业务结果、可恢复执行权；领取与执行证据 |
| Session | 跨实例续期、退出、改密、换绑邮箱及 Redis 恢复 | Q-001／Q-004；逐会话撤销与凭据版本变更分别核验，客户端身份错误按共享接口约定 |
| 文件 | 上传中断、重复完成、核验后覆盖、回收竞争 | 文件内容稳定、引用与权限正确；Q-002 作为预期 |
| 邮件 | 异步重试、重发替代、并发错误提交 | 单表原码生命周期、幂等计数、worker恢复及脱敏；Q-003实际决定、TC-COM-018—021作为预期 |

测试代码、批准执行范围、环境与真实结果在各任务及证据记录中登记。

## 分阶段回归

S1 验证工具链、基础设施和维护操作，并提供隔离资源与装配入口。各工作包同步编写业务测试，先在受控环境验证，再在阶段合成版本中接入真实依赖。每次增量合入前，在本地用对应提交启动服务，冒烟验证受影响的关键路径并记录结果。Jenkins 负责 `main` 合入后的构建和部署。

每个阶段以[主链](01-阶段划分与依赖.md#实现目标与用户故事)为范围，开展真实前后端联合验证，覆盖正常流程、关键异常及上一阶段回归。阶段验收复用适用的开发验证证据。最终系统测试与部署验收继续覆盖全链路、跨实例行为、性能及恢复，见[部署验收安排](04-最终部署验收安排.md)。
