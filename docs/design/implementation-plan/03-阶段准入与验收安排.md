# 3. 阶段准入与验收安排

## 准入

阶段任务以 `main` 中的设计基线准备编码任务卡及准入材料；通过阶段准入批准后开始业务编码。按阶段核对前置 Q 关闭、ADR 接受、接口双方及复核确认、状态／错误／事务／权限明确、人工前后端联合测试及适用的单元／集成预期已核验、环境与配置齐备、责任及完成条件。批准记录采用[准入模板](../acceptance/阶段准入记录模板.md)。

## Issue 与任务分支

派发 Issue 记录阶段、责任、文件边界、依赖及验收条件，引用最新 main 的需求与 ADR／Q。实际采用的代码基线提交在 PR 和准入记录登记。TASK-001 统筹正式决定、共享文档与生成物，各成员维护本模块源文件并交叉审查。每个工作包维护一条阶段工作分支，按[任务索引](../tasks/索引.md#提交与集成)组织小步提交及 Draft PR。独立可交付增量从最新 `main` 开发并提交到 `main`，有依赖的改动先在明确的联调基线上评审和验证。

## 阶段开发基线

1. 当前一阶段正式基线尚未形成，阶段集成人从其共同基线合入四条工作分支的明确提交，建立临时开发基线，并登记各分支 SHA、合成 SHA 和组合检查结果。下一阶段可据此开工。S2 先供给 S3，S3 的合成结果可继续供给 S4。
2. 任一输入分支更新时，提供方登记新提交和受影响的契约。阶段集成人刷新临时基线，验证组合构建及受影响检查。下游负责人逐次同步合成版本，修正本工作包内的适配、迁移、生成物及测试，并记录已同步 SHA。有多级依赖时按 S2 → S3 → S4 传递。
3. 上一阶段完成主链验收和修正并正式合入 `main` 后，登记包含该阶段完整交付的 `main` SHA。下游把自身改动迁移到包含该 SHA 的最新 `main`，核对差异、数据库升级、构建及跨阶段主链，再更新下游联调基线和 PR 目标。

## 审查与阶段验收

开发阶段按[审查模板](../reviews/模板.md)记录版本、业务与约束检查、单元和适用集成测试，以及本地冒烟结果。通过当前范围检查、具备所需真实依赖且可运行的增量可合入 `main`，由 Jenkins 构建与部署。同一阶段可多次合并与部署。

阶段验收使用真实用户端、管理端及后端依赖，验证本阶段主链、关键异常和上一阶段回归。按[验收模板](../acceptance/阶段验收单模板.md)记录结果、证据及验收人。最终部署完成全量需求覆盖、质量要求及恢复验收。

## 变更

原因→影响需求／ADR／接口／数据／测试→人工决定→修改→回归。重大取舍新建替代 ADR，原版本通过 Git 及记录追踪。
