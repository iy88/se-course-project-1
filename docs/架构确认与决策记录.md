### 可行方案比较

| 方案 | 收益与代价 |
|---|---|
| 方案 A | Redis Streams 复用既有 Redis，需明确独立读取／消费组与恢复 |

## ADR-005 持久 Cookie 与 Redis Session

| 字段 | 内容 |
|---|---|
| 编号/标题 | ADR-005 持久 Cookie 与 Redis Session |
| 协作入口 | [任务 Issue](https://github.com/iy88/se-course-project-1/issues/38) |
| 背景 | FR-01；账户凭据失效及多连接。 关联 Q：Q-001。 |
| 比较 | 见下表可行方案及影响 |
| 决定 | 持久 HttpOnly Cookie＋Redis Session；绝对与空闲期限、有效活动节流续期；PostgreSQL 保存账户凭据版本及资格，每次鉴权核验；支持账户多 Session 和 Session 多连接。按 Q-001 的 B 方案持久保存 SessionGuard 及逐会话撤销事实，鉴权同时核对。 |
| 理由 | 统一退出及身份依据，以 Redis 承担 Session 查询、续期和过期回收。 |
| 代价 | 账户校验仍有数据库读取；逐会话鉴权增加 SessionGuard 查询；退出先提交持久撤销，再清理 Redis 及连接。 |
| 验证 | 跨实例退出、改密失效、续期竞争及 Redis 故障恢复。 预期由对应任务的实际审查人核验，执行版本、环境、命令和结果在任务证据中登记。 结果位置随任务证据登记。 |
| 确认 | 本会话已明确采纳；确认姓名：袁尚峰；实际确认日期按会话记录登记，整理日期2026-11-13；交叉复核姓名及日期待登记。 |
| 重新评估条件 | 身份客户端、性能或撤销要求变化。 |
| 替代关系 | 首次登记；后续替代关联新旧 ADR |

### 可行方案比较

| 方案 | 收益与代价 |
|---|---|
| 方案 A | JWT 本地验签可减少会话查询，及时撤销需补充机制 |
| 方案 B | 服务端 Session 集中维护失效；Redis 支持共享查询及 TTL |

数据库 Session 便于持久查询，额外承担会话更新及清理；选 Redis Session 并以账户版本保障账户级失效。

### 2026-11-14 逐会话撤销决定

袁尚峰（iy88）在 Q-001 逐轮决策中选择 B。Redis 保存运行时 Session 与空闲期限，PostgreSQL 保存会话签发及撤销依据；不存在有效持久依据时拒绝认证，Redis 旧数据不能重新授权。设计与运行预期见[会话与身份](design/detailed-design/key-designs/会话与身份.md)及 TC-COM-015—017。

### 2026-11-14 换绑邮箱的会话处理

袁尚峰（iy88）通过Q-004逐轮问题选择换绑成功后全部旧Session失效。新邮箱保存、凭据版本递增与两份邮箱验证消费原子提交，采用新邮箱重新登录；用户ID及历史归属保持。

### 技术依据与实现验证

[OSS PostObject](https://www.alibabacloud.com/help/en/oss/developer-reference/postobject) 定义禁止覆盖表单字段及版本控制限制；[POST V4 签名](https://www.alibabacloud.com/help/en/oss/developer-reference/signature-version-4-recommend) 定义 policy 条件。2026-11-14 查阅官方文档后采用以下实现约束：

- key、禁止覆盖值、私有 ACL、内容类型及大小边界纳入签名条件；客户端修改字段无法取得另一有效授权。
- 完成接口从服务端登记定位对象，核验实际内容，事务外 OSS I/O 完成后锁行重查，推进 verified。PostObject ETag 用作对象标识，内容摘要由后端读取字节计算。
- Bucket 版本状态在部署、启动及每次签发前检查；无法取得状态返回暂时服务错误。运维账户控制版本配置，应用角色仅获所需对象权限。
- 回收在授权到期后执行，保留登记和删除墓碑，周期复查迟到上传；deleted 始终拒绝引用，对象键永久不复用。

真实 OSS 验证覆盖签名篡改、重复上传、核验并发、Bucket 状态变化及迟到上传；运行环境、命令及结果随文件能力编码任务登记。

| 业务依据 | FR-01、BR-20—22、需求4.19、ADR-008；本轮先确认 PostgreSQL，再通过两处标注确定单表及明文方案。 |
| 依赖范围与就绪条件 | TASK-001 邮件实现契约及恢复验证；其他模块设计可继续。 |
| 需同步资产 | ADR、共享设计、接口、配置、测试及部署记录 |
| 验证场景 | 正常：有效请求可投递并验证；边界：重试遇到到期或被新轮替代时结束；异常：SMTP结果不明、租约接管、错误尝试并发及清理中断按单表协议恢复；验证码不进入日志、审计正文及任务参数。 |
| 交付与复核依据 | [邮箱验证与投递](design/detailed-design/key-designs/邮箱验证与投递.md)、账户接口及TC-COM-018—021；检查与实际交叉复核通过第3批PR登记。 |

### 决定适用范围

明文值供本轮验证与同轮SMTP重试共用，邮件发送成功后仍保留到验证码被消费或失效；成功消费、重发替代、到期或尝试耗尽时清空code，周期清理兜底。单表由账户模块维护，邮件worker读取必要字段；日志、审计、任务队列和公共幂等响应均不保存原码。数据库有权读取者可在其有效期内取得原码；历史备份随备份策略保留，恢复流程使恢复出的验证请求失效。

本轮选择替代原候选中“校验端固定保存摘要、投递端另存加密载荷”的组织方式。普通业务密码继续采用密码专用散列，Session凭据继续按Q-001协议保护。
