# 人工验收工作流程（2026-11 批次）

> 适用对象：金婉怡、孙含佳、张新悦三个任务 Issue；复核人袁尚峰。
> 使用 GitHub Issues + Project + Sub-issue；缺陷和需求缺口一律作为任务 Issue 的子 Issue 跟踪。
> 本文件是 `bits/` 工作笔记，不是需求交付材料。

## 一、总流程

```text
任务 Issue（Project: Todo）
  → 回填环境/前置，开始测试（In Progress）
  → 执行 P0/P1/P2 与逐 AC 核对，记录证据
  → 发现问题
      ├─ 需求已实现但行为错误 → 缺陷 sub-issue（bug）
      ├─ 未实现/部分实现/缺入口/结果不可见 → 需求缺口 sub-issue（feature）
      └─ 环境/账号/设备不可用 → 任务 Issue 记 BLOCKED
  → 修复/补齐（fix/ 或 feat/ 分支）
  → PR（Closes #子Issue，Reviewer 袁尚峰，评论“申请 review”）
  → 负责人 review、合并；子 Issue 自动关闭（Project: Done）
  → 成员在合并后代码上回归，证据补到子 Issue
  → 任务结果表 + AC 状态表 → 任务 Issue: In Review
  → 负责人复核 → 任务 Issue: Done
```

要点：

- 任务 Issue 是父 Issue，不因 PR 合并自动关闭；由负责人复核后关闭。
- 缺陷/缺口子 Issue 由 PR 的 `Closes #<子Issue>` 关闭；PR 不写 `Closes #<任务Issue>`。
- 自动化 API 验收 51/51 PASS 只证明接口规则；人工仍要核对页面入口、展示、错误提示和 AC 是否完整落地。

## 二、角色与职责

| 角色 | 职责 |
|---|---|
| 执行成员 | 回填环境、执行检查、记录证据、建 sub-issue、修复/补齐、提 PR、回归、提交结果表与 AC 表 |
| 负责人（袁尚峰） | 确认范围与环境；决定 feature 缺口“补/延后/不补”；review 并合并 PR；复核任务；关闭任务 Issue；更新整体验收记录 |
| 成员之间 | 需要另一角色配合时（如管理员问询、封禁自建账号）在任务 Issue 约定顺序，不互相覆盖状态 |

禁止：

- 成员不自行合并 PR、不自行关闭父任务 Issue、不自行 reset/seed 生产；
- 不在 `dev` 或 `main` 上直接修改、提交，必须从 `dev` 拉 `fix/`/`feat/` 分支并走 PR；
- 不把“自动化 PASS”写成“人工 PASS”，不把“没发现问题”当成有证据的结论；
- 不把密码、token、连接串、签名 URL、manifest 内容写进 Issue、截图或终端记录。

## 三、开始任务

1. 任务 Issue 已指派给自己；Project 状态从 `Todo` 改为 `In Progress`。
2. 在任务 Issue 评论回填：
   - HEAD：`git rev-parse HEAD`；
   - 环境：生产 / 本地，manifest tag 或 run_id；
   - `demo-verify` 结果（本地必填；生产由负责人确认）；
   - 服务地址与 `/api/health` 结果；
   - 浏览器/OS/视口；
   - 账号来源（manifest demo 账号或自建账号，不记录密码）；
   - 证据目录：`var/manual-acceptance/<run_id>/<member>/`。
3. 阅读自己的任务 Issue、`docs/development/demo-seed.md`、`docs/development/整体验收.md`，以及 Issue 列出的 US/UC/SC 材料。
4. 生产是主验收环境，可以执行完整写流程，也可以自建账号和测试数据；代码修改后的回归用本地 SQLite + local。

### 环境与数据规则

- demo 场景对象一次只由一人操作；自建对象归创建者使用。
- 自建账号显示名用 `测试-<姓名>-<序号>`；自建商品/举报说明加 `【测试】<姓名>-<序号>`；结果表登记账号邮箱与对象 ID。
- 若 demo 场景状态已被改过，用自建账号/商品/请求复现前置，不直接记 `BLOCKED`；确实无法复现（如真实 7 天等待）才记 `BLOCKED` 并说明。
- 不 reset/seed/删除、不批量灌数据/压测、不修改他人账号。

## 四、测试执行

1. 按任务 Issue 的 **P0** 全部执行；**P1** 有时间就做；**P2** 记录执行或未执行原因。
2. 每项记录：检查号、环境、步骤、预期、实际、结论、证据文件、时间。
3. 结论只用：`PASS`、`FAIL`、`BLOCKED`、`NOT-RUN`。
4. 证据：
   - 目录 `var/manual-acceptance/<run_id>/<member>/`；
   - 文件命名如 `A-P0-03-01.png`；
   - 截图脱敏；不提交 `var/`、截图、manifest。
5. 跑完需求核对后，在任务 Issue 评论贴 **AC 状态表**：
   - 结论：`已实现`、`部分实现`、`缺界面入口`、`未实现`、`与需求不一致`、`BLOCKED`、`N/A`；
   - 只有 `已实现` 才算通过；接口 PASS 不能填 `已实现`；
   - 统计六类数量。

## 五、发现问题：先判类型

| 情形 | 处理 |
|---|---|
| 需求已实现，但页面行为/提示/状态错误 | 建 **缺陷** sub-issue，走 `fix/` |
| 需求未实现、部分实现、缺页面入口、结果不可见 | 建 **需求缺口** sub-issue，走 `feat/`；负责人先决定“本轮补/延后/不补” |
| 页面与需求规则不一致，可能是需求歧义 | 建 **需求缺口**，类型选“与需求规则不一致/待决定”，交负责人决定，不自行改需求 |
| 缺账号/设备/环境，且无法自建数据复现 | 任务 Issue 记 `BLOCKED`，写清所需支持；不建 bug/feature |
| 需求已实现且有入口、结果正确 | 不建 Issue，记录 PASS 与证据 |

判定原则：

- 先查自动化结果和需求原文，再判断是 bug、缺口还是环境问题；
- 同一问题只建一个 Issue，先搜索是否已有未关闭记录；
- 不把“缺少界面入口”写成缺陷；它属于需求缺口。

### 先在 dev 分支复现与判断（必须）

所有“是不是 bug / 是不是需求缺口 / 是不是环境问题”的判断，以**最新 `dev` 分支 + 本地 SQLite+local** 为准；生产只作为真实部署的验收环境。

1. 切到最新 `dev`，记录 HEAD：

```bash
git fetch origin
git switch dev
git pull
git rev-parse HEAD
```

2. 用 SQLite + local 启动最新 `dev`，按原步骤复现。
3. 判定：
   - **dev 可复现**：按上面的表判断类型，建缺陷/缺口 sub-issue；
   - **dev 不可复现、生产可复现**：可能是生产部署版本、演示数据状态或缓存差异；记录生产版本/manifest tag，交负责人确认，不直接建 bug；
   - **两边都可复现但表现不同**：以 `dev` 判断代码问题，生产差异单独写在证据里。
4. 分支纪律：
   - **不在 `dev` 或 `main` 上直接修改、提交**；所有修复/补齐都在新分支进行；
   - 修复/补齐从最新 `dev` 拉分支，PR base 选 `dev`；
   - `dev` 只用于同步最新代码、合并和合并后回归；`main` 只放交付文档，不改代码；
   - 合并后回归也在 `dev` 上做，不使用旧分支或生产旧构建代替。

## 六、创建 Sub-issue

1. 打开父任务 Issue → 右侧 **Sub-issues** → **Add sub-issue**：
   - **Create new sub-issue**：新建；
   - **Add existing issue**：把已建 Issue 挂进来。
2. 使用「缺陷报告」或「需求缺口」模板。
3. 填写：
   - 标题：`[缺陷] <页面/模块>：<现象>` 或 `[需求缺口] <功能/入口>：<现状>`；
   - 环境：HEAD、manifest tag/run_id、页面、浏览器/视口、角色；
   - 复现步骤、预期、实际；缺口写现状、期望（引用 AC 原文）、影响与边界；
   - 证据：脱敏截图或文本；
   - 需求依据：US/UC/SC/AC/BR；
   - 严重级别（缺陷）或影响级别（缺口）。
4. 设置：
   - Assignee：自己；
   - Labels：`bug` 或 `feature`，再加对应 `area:*`；
   - Project：同一 Project，状态 `Todo`。
5. 子 Issue 会自动显示 `Parent: #<任务Issue>`；不要在 PR 里关闭父任务。
6. 如果仓库没有 Sub-issues 功能：在任务 Issue 正文加任务列表 `- [ ] #子Issue`，并在子 Issue 正文写 `Parent: #<任务Issue>` 作为退路。

建完后在任务 Issue 评论一句：`发现缺陷/缺口：#<子Issue>，已作为 sub-issue 挂到本任务。`

## 七、修复 / 补齐

1. 先在最新 `dev` 上复现并确认问题仍存在（把 dev HEAD 写进子 Issue），再从 `dev` 拉分支（PR 目标分支是 `dev`，不是 `main`）。**不要直接在 `dev` 或 `main` 上改代码/提交**：

```bash
git switch dev
git pull
git switch -c fix/<子issue号>-<短描述>   # 缺陷
git switch -c feat/<子issue号>-<短描述>  # 缺口
```

2. 只改必要代码，保留无关修改。
3. 提交：

```bash
git add <相关文件>
git commit -m "fix: <现象> (#<子issue号>)"
# 或
git commit -m "feat: <缺口> (#<子issue号>)"
```

4. 本地验证：
   - SQLite + local 启动并回归原步骤；
   - 后端改动跑相关测试；必要时按负责人同意的范围跑自动验收；
   - 前端改动跑 `npm run build` 并手动回归；
   - 不提交 `var/`、截图、manifest、密码或生产配置。
5. 子 Issue 的 Project 状态改为 `In Progress`。

## 八、提 PR 与 assign reviewer

1. 推送分支并开 PR（base 选 `dev`）：

```bash
git push -u origin fix/<子issue号>-<短描述>
```

2. PR 标题：

```text
fix: <现象> (#<子issue号>)
feat: <缺口> (#<子issue号>)
```

3. PR 正文：

```markdown
## 关联
Closes #<子issue号>

## 问题/缺口
<复现步骤与预期/实际，或需求 AC 与现状>

## 修改
<改动点>

## 验证
- [ ] 本地 SQLite+local 回归原步骤
- [ ] 相关测试/构建（写命令与结果）
- [ ] 影响范围页面回归

## 影响与风险
<可能影响的角色/场景/AC；是否需要部署或重置演示数据>
```

4. 右侧 **Reviewers** 选袁尚峰；评论一句“申请 review”。
5. 子 Issue 的 Project 状态改为 `In Review`。
6. PR 不写 `Closes #<任务Issue>`；只关闭子 Issue。

## 九、Review 与合并

负责人：

1. 看 PR 的 diff、范围、验证命令与结果、是否夹带无关修改、是否含秘密；
2. 必要时本地复跑或要求补证据；
3. 通过：**Review changes → Approve**，评论一句“Review 通过”；
4. 合并 PR（按仓库习惯），删除分支；
5. 检查子 Issue 是否自动关闭；没有则手动 `Close as completed`，Project 改 `Done`。

成员：

1. 处理 review 意见，推新提交；不要静默 force push 已 review 的分支；
2. 合并后同步 `dev`，准备回归。

## 十、回归

1. 切到合并后的 `dev`，重启服务；
2. 按子 Issue 的原步骤回归，证据补到子 Issue 评论；
3. 通过：子 Issue 评论“回归通过”，任务 Issue 勾掉对应项；
4. 失败：重新打开子 Issue，回到第七步；不要关闭任务 Issue。

## 十一、完成任务

1. 在任务 Issue 评论贴：
   - 结果表（检查号、环境、结论、缺陷/缺口号、证据、备注）；
   - AC 状态表与统计；
   - 未执行项及原因；
   - 剩余风险/待负责人决定事项。
2. 确认：
   - P0 全部 PASS，或未通过项均有已关闭子 Issue 且回归通过；
   - 所有缺陷/缺口子 Issue 已关闭，或 feature 有负责人书面“延后/不补”决定；
   - `BLOCKED` 项已书面说明并被负责人接受；
   - 证据目录可复查、截图脱敏。
3. 任务 Issue 的 Project 状态改为 `In Review`，评论 @袁尚峰 复核。
4. 负责人复核通过后：
   - 评论“复核结论：通过”；
   - `Close as completed`（不要 not planned）；
   - Project 改 `Done`；
   - 检查所有 sub-issue 均为 Done。

任务复核评论模板：

```markdown
## 复核结论：通过

- 环境：生产 / 本地；manifest tag：______
- P0：__/__ PASS
- AC：已实现 __ 条；无未决缺口（或：缺口 #__ 已关闭 / 已书面决定延后）
- 缺陷/缺口：__ 个，全部关闭
- 证据：已抽查 ______，结果表与 AC 状态表完整

结论：本任务通过，关闭 Issue，Project 状态改为 Done。
```

## 十二、状态速查

| 阶段 | 任务 Issue（父） | 子 Issue | PR |
|---|---|---|---|
| 未开始 | Todo | — | — |
| 测试中 | In Progress | — | — |
| 发现缺陷/缺口 | In Progress | Todo | — |
| 修复中 | In Progress | In Progress | Draft/Open |
| 已提 PR | In Progress | In Review | Open |
| 合并后 | In Progress | Done（自动关闭） | Merged |
| 回归通过 | In Review | Done | Merged |
| 复核通过 | Done | Done | Merged |

## 十三、常用操作清单

- 开始测试：任务 `In Progress` + 回填环境评论；
- 发现问题：建 sub-issue，assign 自己，`bug`/`feature` + `area:*`，Project Todo；
- 修复：`fix/` 或 `feat/` 分支，PR 写 `Closes #子Issue`，Reviewer 袁尚峰，评论“申请 review”；
- PR 合并：负责人操作；子 Issue 自动关闭，Project Done；
- 回归：合并后 `dev` 上重跑原步骤，证据补子 Issue；
- 任务完成：结果表 + AC 表 → `In Review` → 负责人复核 → `Done`；
- 收尾：负责人更新 `docs/development/整体验收.md`；必要时 reset + demo-seed 恢复生产演示数据；证据归档到本地 `var/manual-acceptance/`。
