# Project1 v2 首发与发布配置

v2 与 legacy 共用生产主机、PostgreSQL 和 Redis 实例。v2 使用独立的站点、发布目录、服务用户、数据库与应用角色、Redis ACL 与命名空间，以及生产 OSS 桶。管理员一次性准备生产环境。之后向 Gitea `main` 推送提交会触发 Jenkins 自动部署，首发与后续更新使用同一个任务。

## Jenkins

| 字段 | v2 配置 |
| --- | --- |
| Job | `project1-v2-cicd`，使用 Pipeline script from SCM |
| 源码 | 同步到 Gitea 的 Project1 仓库，远端名 `origin`，分支 `*/main`，脚本 `Jenkinsfile` |
| Git 凭据 | 给 Gitea 仓库配置只读凭据，在 Jenkins SCM 配置中选用 |
| 构建节点 | Linux、Bash、Git、Python 3。Jenkins Tools 使用 `jdk-27`、`maven-3.10.1` 和 `node-latest`，Node.js 与 pnpm 版本须匹配仓库锁定值 |
| 生产发布凭据 | Jenkins 创建凭据 ID `project1-v2-deploy`，使用生产 `deploy` 账号的 SSH 密钥及 SSH Agent 插件。构建节点录入并校验源站公钥，源站地址和 SSH 用户由 Jenkinsfile 的 `environment` 提供 |
| 发布触发 | 在 Jenkins Job 配置 Generic Webhook Trigger 和 v2 专用 token。Gitea Webhook 只订阅 `main` 的 Push Events |

在 Jenkins Job 的 Generic Webhook Trigger 中，从 `$.ref` 提取 `webhook_ref`。Optional filter Text 为 `$webhook_ref`，Expression 为 `^refs/heads/main$`。使用 v2 专用 token，关闭请求内容和变量输出。

在 Gitea 仓库新建 Gitea 类型 webhook，目标为 Gitea 可达的 Jenkins 基地址加 `/generic-webhook-trigger/invoke`，选择 JSON、Push Events，Branch Filter 填 `main`。使用 `Authorization: Bearer <v2 token>`。保留 legacy webhook 原有的 `legacy` 分支过滤和 token。

[Jenkinsfile](../Jenkinsfile) 检出 Gitea 当前的 `main` 并记录实际 SHA，随后构建、归档、上传并在源站部署。Jenkins 打包使用预装的 `mvn`，Maven Central 镜像由 Jenkins 执行账号的 `~/.m2/settings.xml` 提供。本地直接运行打包脚本时默认使用 Maven Wrapper。GitHub Actions 执行测试、lint 和格式检查。只将经过审查和 CI 的 GitHub `main` 同步到 Gitea；连续推送时任务按开始时检出的分支头部署。

## 生产布局与资源

```text
/srv/se-course-project1-v2/
├── state/
│   ├── current -> ../releases/<sha>-<build>
│   └── backups/<sha>-<build>.pgdump
├── incoming/<sha>-<build>/
├── instances/
│   ├── 18081 -> ../releases/<sha>-<build>
│   ├── 18082 -> ../releases/<sha>-<build>
│   ├── scheduler -> ../releases/<sha>-<build>
│   ├── worker-1 -> ../releases/<sha>-<build>
│   └── worker-2 -> ../releases/<sha>-<build>
├── releases/<sha>-<build>/
│   ├── backend/
│   │   ├── backend-app.jar
│   │   ├── maintenance.jar
│   │   └── .env.prod
│   ├── user-web/
│   ├── admin-web/
│   ├── deploy/
│   ├── release.txt
│   └── .prepared
└── shared/
    ├── .env.deploy
    ├── .env.prod
    └── .env.maintenance.prod
```

- 复用生产 `deploy` 账号上传和准备候选制品。systemd 三种 unit 均以专用的不可登录账号和组 `se-project1-v2` 运行，将 `deploy` 加入该组，以便发布脚本给应用配置快照设定服务组读权限。
- 管理员控制 v2 根目录及 `shared/` 的写权限，将 `incoming/`、`releases/`、`instances/` 和 `state/` 的写权限授予 `deploy`。`state/` 可供 Nginx 遍历，`state/backups/` 和 `incoming/` 限发布账号访问。按[部署配置样例](../scripts/deploy/config/.env.deploy.example)在 `shared/.env.deploy` 设置 API 回环端口和 worker 数量。
- 按[应用配置样例](../scripts/deploy/config/.env.prod.example)填写 `shared/.env.prod`。发布时复制一份配置到候选版本的 `backend/.env.prod`，由发布脚本设为 `deploy:se-project1-v2` 和 `0640`。共享源文件需让 `deploy` 可读。发布目录及双端静态资源对 Nginx 用户开放所需的目录遍历和文件读取权限。
- 按[维护配置样例](../scripts/deploy/config/.env.maintenance.prod.example)填写 `shared/.env.maintenance.prod`，供 `deploy` 配合包内维护 JAR 做备份和迁移，权限设为 `0600`。部署节点安装与数据库兼容的 `pg_dump` 和 `pg_restore`，维护 JDBC URL 使用示例中的单主机和数据库格式。配置中的 PostgreSQL 目标、应用角色与密码、Redis 命名空间和 OSS 桶须与应用配置对应。数据库 owner 凭据只写入维护配置。执行维护命令时通过必需的 `--env-file` 参数指向该文件；`db init` 由管理员从终端提供 PostgreSQL 管理员用户名及密码，并确保 owner 具有 `CREATEDB`。后续 `db reset` 使用 owner 凭据，只有遗留数据库不属于 owner 时才需要管理员回退路径。
- PostgreSQL、Redis 实例已就绪。首发前建立 v2 目标数据库及 owner／app 角色，配置应用 Redis ACL 和维护 Redis ACL。维护账号在 v2 命名空间中需要 `SCAN` 和 `DEL`。列出参与发布的实例及连接池预算，核对同机 legacy 和运维连接余量。
- 生产 OSS 尚待配置。v2 使用从未开启版本控制的私有桶。按 `https://mobile.v2.cm.iy88.site` 和 `https://admin.v2.cm.iy88.site` 配置浏览器直传 CORS。生产应用与维护 RAM 权限按实际操作区分。启用邮件或依赖探针时，SMTP 字段按[开发配置样例](../backend/.env.example)填写生产值。

## systemd、Nginx 与入口

| 资产 | 安装路径与职责 |
| --- | --- |
| [API unit](../scripts/deploy/systemd/project1-v2-api@.service) | `/etc/systemd/system/project1-v2-api@.service`。JAR 通过实例软链启动，OpenJDK 27 路径为 `/opt/project1-v2/java/bin/java`。 |
| [调度器 unit](../scripts/deploy/systemd/project1-v2-scheduler.service) | `/etc/systemd/system/project1-v2-scheduler.service`。以 `delivery-scheduler` profile 运行一个实例。 |
| [worker unit](../scripts/deploy/systemd/project1-v2-worker@.service) | `/etc/systemd/system/project1-v2-worker@.service`。以 `delivery-worker` profile 运行多个实例。 |
| [Nginx 站点与上游](../scripts/deploy/nginx/project1-v2.conf) | `/etc/nginx/conf.d/project1-v2.conf`。按 Host 提供两个静态站点，API 和 WebSocket 共用从 `.env.deploy` 生成的回环上游。 |
| [Nginx 路由](../scripts/deploy/nginx/project1-v2-routes.conf) | `/etc/nginx/snippets/project1-v2-routes.conf`。支持同源 API、SPA 回退、静态资源缓存以及 WebSocket Upgrade。 |
| [实例清单生成器](../scripts/deploy/render-runtime.py) | 从同一份 `.env.deploy` 生成 Nginx 上游、systemd unit 清单及发布 sudoers。权限精确到当前批准的 unit 和 start／stop／restart。 |

管理员确认清单里的端口可用，并按清单核对数据库和 Redis 的连接预算。在受管理员控制的目录中，用审阅过的生成器渲染实例清单、上游和授权。

```bash
python3 ./render-runtime.py /srv/se-course-project1-v2/shared/.env.deploy units
python3 ./render-runtime.py /srv/se-course-project1-v2/shared/.env.deploy upstream > project1-v2-upstream.conf
python3 ./render-runtime.py /srv/se-course-project1-v2/shared/.env.deploy sudoers --deploy-user deploy > project1-v2-publish
```

安装 systemd 模板后执行 `systemd-analyze verify` 和 `systemctl daemon-reload`。将 upstream 片段安装到 `/etc/nginx/snippets/project1-v2-upstream.conf`，与站点、路由一起通过 `nginx -t` 后加载。用 `visudo -cf` 校验后安装 v2 的 sudoers，权限 `0440`。用 `sudo -l -U deploy` 对照生成清单。变更实例拓扑安排单独维护窗口，同步 Nginx 上游、sudoers、实例状态和当前 release 的 `.units`，再恢复发布。

公网链路沿用 ESA → 公网 Nginx → frp → 生产源站 HTTP。预计用户端域名为 `mobile.v2.cm.iy88.site`，管理端为 `admin.v2.cm.iy88.site`。公网层保留 Host 并支持 WebSocket Upgrade，源站按 Host 选择站点并向后端传递 HTTPS 协议信息。首发验证双前端和 API。正式 Session 适配接入后启用实时入口并验证 WebSocket，API、调度器和 worker 使用独立进程。开发使用相同的 Spring profile 和 Rsbuild 同源代理，生产由 systemd 和 Nginx 管理。服务模板与配置随包交付。

## 首发与日常发布

1. **一次性准备。** 配置账号、目录、三份环境文件、systemd、Nginx、sudoers 和 Jenkins。管理员在开启 webhook 前使用审阅过的维护 JAR 和 `db init --env-file PATH --admin-user USER` 建立 v2 数据库，配置 Redis ACL 和命名空间。若先通过 SQL 建库，则须建立对应 owner 和应用角色，并验证维护配置可以连接。Nginx 本机 `:80` 要能按两个 Host 提供 v2 路由。
2. **触发。** 启用 v2 webhook，推送通过 CI 的 GitHub `main` 到 Gitea。若该提交已同步，使用 Job 的 Build Now 执行同一条流水线，或重投对应的 Gitea Push 记录。
3. **自动部署。** Jenkins 归档制品后以 `deploy` 上传。源站核对摘要和发布清单，解包并写入 `.prepared`。激活脚本持有源站发布锁，核对安装的 upstream，保存应用配置快照，成套停止 v2 服务，备份目标库并检查备份目录表，再运行 Flyway 迁移。API、worker、调度器启动后，逐个验证 API 的健康和业务探针，检查后台 unit 状态，切换 `state/current`，对两个 Host 验证首页和同源 API。更新期间 v2 有停机窗口。
4. **确认。** Jenkins 输出 `ACTIVATED_RELEASE` 后，从公网打开用户端和管理端验证。记录提交、摘要、备份和 Flyway 版本。OSS 就绪后验证上传、核验、读取与回收。
5. **失败处理。** 激活失败时停止候选。有上一版本且数据库仍通过上一版本的严格 Flyway 校验时，恢复上一版本及其配置快照。数据库已经不兼容时保留备份并报告错误，由管理员决定恢复方案。首发失败时停止候选，保留日志并检查 Jenkins 的失败阶段。
