# Project1 v2 首发与发布配置

v2 与 legacy 共用生产主机、PostgreSQL 和 Redis 实例。v2 使用独立的站点、发布目录、服务用户、数据库与应用角色、Redis ACL 与命名空间，以及生产 OSS 桶。实际部署测试安排在变更合入 `main` 后，首次由管理员手动触发 Jenkins。Jenkins 发布和生产验收安排在后续部署工作，S1 交付开发和生产共用的进程角色。

## Jenkins

| 字段 | v2 配置 |
| --- | --- |
| Job | `project1-v2-cicd`，使用 Pipeline script from SCM |
| 源码 | 同步到 Gitea 的 Project1 仓库，远端名 `origin`，分支 `*/main`，脚本 `Jenkinsfile` |
| Git 凭据 | 给 Gitea 仓库配置只读凭据，在 Jenkins SCM 配置中选用 |
| 构建节点 | Linux、Bash、Git、OpenJDK 27、Python 3、Maven Wrapper、仓库指定版本的 Node.js 与 pnpm |
| 生产发布凭据 | Jenkins 创建凭据 ID `project1-v2-deploy`，使用生产 `deploy` 账号的 SSH 密钥及 SSH Agent 插件。构建节点录入并校验源站公钥，配置 `PROJECT1_V2_DEPLOY_USER=deploy` 和 `PROJECT1_V2_DEPLOY_HOST`（主机名或 IPv4 地址） |
| 发布触发 | 手工输入通过 GitHub Actions 的 `main` 完整 SHA（`EXPECTED_REVISION`）。勾选 `STAGE_ON_SOURCE` 后才上传到源站候选目录 |

[Jenkinsfile](../Jenkinsfile) 执行检出、部署配置样例校验、构建和归档。启用源站候选阶段后，流水线上传制品，校验摘要和发布清单并解包，成功时写入候选目录的 `.prepared`。Maven 跳过测试，双前端构建保留 TypeScript 类型检查。单元测试、集成测试、lint 和格式检查由 GitHub Actions 执行。备份、迁移、启停和流量切换按下文手动执行，后续接入 Jenkins。

## 生产布局与资源

```text
/srv/se-course-project1-v2/
├── current -> releases/<sha>-<build>
├── incoming/<sha>-<build>/
├── instances/
│   ├── 18081 -> ../releases/<sha>-<build>
│   ├── 18082 -> ../releases/<sha>-<build>
│   ├── scheduler -> ../releases/<sha>-<build>
│   ├── worker-1 -> ../releases/<sha>-<build>
│   └── worker-2 -> ../releases/<sha>-<build>
├── releases/<sha>-<build>/
│   ├── backend/
│   │   ├── backend-app.jar
│   │   ├── maintenance.jar
│   │   └── .env.prod
│   ├── user-web/
│   ├── admin-web/
│   ├── deploy/
│   ├── release.txt
│   └── .prepared
└── shared/
    ├── .env.deploy
    ├── .env.prod
    └── .env.maintenance.prod
```

- 复用生产 `deploy` 账号上传和准备候选制品。systemd 三种 unit 均以专用的不可登录账号和组 `se-project1-v2` 运行，发布账号无需加入该组。首次由管理员管理实例软链和 `current`。
- 管理员控制 v2 根目录、`instances/` 及 `shared/` 的写权限，将 `incoming/` 和 `releases/` 的写权限授予 `deploy`。按[部署配置样例](../scripts/deploy/config/.env.deploy.example)在 `shared/.env.deploy` 设置 API 回环端口和 worker 数量。
- 按[应用配置样例](../scripts/deploy/config/.env.prod.example)填写 `shared/.env.prod`。发布时复制一份配置到候选版本的 `backend/.env.prod`，首发时由管理员设置为 `root:se-project1-v2` 和 `0640`。发布目录及双端静态资源对 Nginx 用户开放所需的目录遍历和文件读取权限。
- 按[维护配置样例](../scripts/deploy/config/.env.maintenance.prod.example)填写 `shared/.env.maintenance.prod`，首发由执行迁移的管理员登录账号持有，权限为 `0600`。用该管理员的普通登录身份运行维护 JAR，系统级操作单独使用 sudo。接入 Jenkins 自动迁移时再单独配置维护凭据。配置中的 PostgreSQL 目标、应用角色与密码、Redis 命名空间和 OSS 桶须与应用配置对应。数据库 owner 凭据只写入维护配置。执行维护命令时通过必需的 `--env-file` 参数指向该文件；`db init` 由管理员从终端提供 PostgreSQL 管理员用户名及密码，并确保 owner 具有 `CREATEDB`。后续 `db reset` 使用 owner 凭据，只有遗留数据库不属于 owner 时才需要管理员回退路径。
- PostgreSQL、Redis 实例已就绪。首发前建立 v2 目标数据库及 owner／app 角色，配置应用 Redis ACL 和维护 Redis ACL。维护账号在 v2 命名空间中需要 `SCAN` 和 `DEL`。列出参与发布的实例及连接池预算，核对同机 legacy 和运维连接余量。
- 生产 OSS 尚待配置。v2 使用从未开启版本控制的私有桶。按 `https://mobile.v2.cm.iy88.site` 和 `https://admin.v2.cm.iy88.site` 配置浏览器直传 CORS。生产应用与维护 RAM 权限按实际操作区分。启用邮件或依赖探针时，SMTP 字段按[开发配置样例](../backend/.env.example)填写生产值。

## systemd、Nginx 与入口

| 资产 | 安装路径与职责 |
| --- | --- |
| [API unit](../scripts/deploy/systemd/project1-v2-api@.service) | `/etc/systemd/system/project1-v2-api@.service`。JAR 通过实例软链启动，OpenJDK 27 路径为 `/opt/project1-v2/java/bin/java`。 |
| [调度器 unit](../scripts/deploy/systemd/project1-v2-scheduler.service) | `/etc/systemd/system/project1-v2-scheduler.service`。以 `delivery-scheduler` profile 运行一个实例。 |
| [worker unit](../scripts/deploy/systemd/project1-v2-worker@.service) | `/etc/systemd/system/project1-v2-worker@.service`。以 `delivery-worker` profile 运行多个实例。 |
| [Nginx 站点与上游](../scripts/deploy/nginx/project1-v2.conf) | `/etc/nginx/conf.d/project1-v2.conf`。按 Host 提供两个静态站点，API 和 WebSocket 共用从 `.env.deploy` 生成的回环上游。 |
| [Nginx 路由](../scripts/deploy/nginx/project1-v2-routes.conf) | `/etc/nginx/snippets/project1-v2-routes.conf`。支持同源 API、SPA 回退、静态资源缓存以及 WebSocket Upgrade。 |
| [实例清单生成器](../scripts/deploy/render-runtime.py) | 从同一份 `.env.deploy` 生成 Nginx 上游、systemd unit 清单及发布 sudoers。权限精确到当前批准的 unit 和 start／stop／restart。 |

管理员确认清单里的端口可用，并按清单核对数据库和 Redis 的连接预算。在受管理员控制的目录中，用审阅过的生成器渲染三份输出。

```bash
python3 ./render-runtime.py /srv/se-course-project1-v2/shared/.env.deploy units
python3 ./render-runtime.py /srv/se-course-project1-v2/shared/.env.deploy upstream > project1-v2-upstream.conf
```

安装 systemd 模板后执行 `systemd-analyze verify` 和 `systemctl daemon-reload`。将 upstream 片段安装到 `/etc/nginx/snippets/project1-v2-upstream.conf`，与站点、路由一起通过 `nginx -t` 后在源站 reload。首发由管理员启停服务和加载 Nginx。后续如需授权 `deploy` 启停 v2 服务，用生成器的 `sudoers --deploy-user deploy` 生成配置，使用 `visudo -cf` 校验后由管理员安装，权限 `0440`。扩容先启动并检查新 unit，再加入上游。缩容先摘除端口并排空，再停止实例。

公网链路沿用 ESA → 公网 Nginx → frp → 生产源站 HTTP。预计用户端域名为 `mobile.v2.cm.iy88.site`，管理端为 `admin.v2.cm.iy88.site`。公网层保留 Host 并支持 WebSocket Upgrade，源站按 Host 选择站点并向后端传递 HTTPS 协议信息。首发验证双前端和 API。正式 Session 适配接入后启用实时入口并验证 WebSocket，API、调度器和 worker 使用独立进程。开发使用相同的 Spring profile 和 Rsbuild 同源代理，生产由 systemd 和 Nginx 管理。初次启停调度器和 worker 由服务器管理员执行，服务模板与配置随包交付。

## 合入 main 后的首发

### 先由管理员准备源站

1. 确认已有 `deploy` 可通过 SSH 登录，建立系统账号及同名组 `se-project1-v2`，设置禁止登录的 shell。保留 legacy 的目录和服务。
2. 建立 v2 发布目录。确认生产的 `deploy` 主组后，将 `incoming/` 和 `releases/` 交给 `deploy`，根目录、`shared/` 和 `instances/` 保持管理员管理。Nginx 和应用服务需要能遍历到各自的资源，`incoming/` 可限制为发布用户访问。
3. 填写三份 v2 环境文件，确认端口、JDK 路径、PostgreSQL 与 Redis 资源。安装并校验 systemd 模板。待候选服务就绪后再安装并加载 Nginx 站点。

### Jenkins 准备候选，管理员激活

1. 确认 GitHub 检查通过。把合并后的同一 `main` 提交同步到 Gitea。首次可先以完整 SHA 运行一次只打包的任务，再用同一 SHA 勾选 `STAGE_ON_SOURCE` 运行正式候选任务。后续步骤使用该次构建生成的 `<sha>-<build>`。
2. Jenkins 归档并上传压缩包与 `SHA256SUMS`，源站使用 [prepare-release.sh](../scripts/deploy/prepare-release.sh) 核对摘要、解包、检查两个 JAR、双前端及 `release.txt`，保留 `.prepared` 作为候选就绪记录。
3. 确认维护配置只指向 v2。首次建库使用包内维护 JAR 并通过 `--env-file` 指向维护配置执行 `db init`。已有库升级前备份 v2 数据库并校验备份可读，再通过同一参数运行 `db migrate`。登记成功迁移的 Flyway 版本。
4. 管理员将应用配置快照安装到候选版本，按清单建立 `instances/<端口>`、`instances/scheduler` 和 `instances/worker-<编号>` 软链，全部指向这一候选。启动对应 unit，分别检查 systemd 服务状态、每个 API 实例的 `http://127.0.0.1:<port>/actuator/health` 和 `/api/v1/hello`。全部就绪后将 `current` 指向候选，执行 `nginx -t` 后加载入口。用两个公网域名验证静态页面与同源 API。
5. 保存提交号、制品摘要、配置版本、Flyway 版本、实例就绪结果及上一可用版本。OSS 配置就绪后验证上传、核验及签名读取。手动首发通过后再启用发布 Webhook。

后续升级先备份并确认数据库兼容性，再逐个从 Nginx 上游摘除实例，等待停机排空，切换该实例的版本并通过就绪检查后恢复流量。全部 API 实例就绪后切换前端。迁移失败时保持旧版本流量。激活失败且数据库兼容时恢复上一版本和它的配置快照，再验健康。首发没有上一版本时停止候选实例并保留发布与服务日志。数据库历史恢复单独安排。
