# Project1 v2 首发与发布配置

v2 与 legacy 共用生产主机、PostgreSQL 和 Redis 实例。v2 使用独立的站点、发布目录、服务用户、数据库与应用角色、Redis ACL 与命名空间，以及生产 OSS 桶。实际部署测试安排在变更合入 `main` 后，首次由管理员手动触发 Jenkins。

## Jenkins

| 字段 | v2 配置 |
| --- | --- |
| Job | `project1-v2-cicd`，使用 Pipeline script from SCM |
| 源码 | 同步到 Gitea 的 Project1 仓库，分支 `*/main`，脚本 `Jenkinsfile` |
| Git 凭据 | 给 Gitea 仓库配置只读凭据，在 Jenkins SCM 配置中选用 |
| 构建节点 | Linux、Bash、Git、OpenJDK 27、Python 3、Maven Wrapper、仓库指定版本的 Node.js 与 pnpm |
| 生产发布凭据 | Jenkins 中为 `project1-v2-deploy` 建立独立凭据，校验生产 SSH 主机公钥 |
| 发布触发 | 首次手动选择通过 GitHub Actions 的 `main` 提交，在 Jenkins 核对检出 SHA 后构建 |

[Jenkinsfile](../Jenkinsfile) 的当前配置执行检出、构建和归档。Maven 跳过测试，双前端构建保留 TypeScript 类型检查。单元测试、集成测试、lint 和格式检查由 GitHub Actions 执行。上传、备份、迁移及激活是后续发布阶段接入的步骤。

## 生产布局与资源

```text
/srv/se-course-project1-v2/
├── current -> releases/<sha>-<build>
├── instances/
│   ├── 18081 -> ../releases/<sha>-<build>
│   └── 18082 -> ../releases/<sha>-<build>
├── releases/<sha>-<build>/
│   ├── backend/
│   │   ├── backend-app.jar
│   │   ├── maintenance.jar
│   │   └── .env.prod
│   ├── user-web/
│   ├── admin-web/
│   ├── deploy/
│   └── release.txt
└── shared/
    ├── .env.prod
    └── .env.maintenance.prod
```

- `project1-v2-deploy` 管理发布目录和版本软链。systemd 以 `project1-v2` 用户运行后端。发布账号加入 `project1-v2` 组。两个 JAR 随同一版本交付。
- 按[应用配置样例](../scripts/deploy/config/.env.prod.example)填写 `shared/.env.prod`。发布时复制一份配置到候选版本的 `backend/.env.prod`，属主为发布用户，组为 `project1-v2`，文件权限为 `0640`。发布目录及双端静态资源对 Nginx 用户开放所需的目录遍历和文件读取权限。
- 按[维护配置样例](../scripts/deploy/config/.env.maintenance.prod.example)填写 `shared/.env.maintenance.prod`，文件权限为 `0600`，由发布账号读取。配置中的 PostgreSQL 目标、应用角色与密码、Redis 命名空间和 OSS 桶须与应用配置对应。数据库 owner 凭据只写入维护配置。执行 `db init` 时由管理员从终端提供 PostgreSQL 管理员用户名及密码。
- PostgreSQL、Redis 实例已就绪。首发前建立 v2 目标数据库及 owner／app 角色，配置应用 Redis ACL 和维护 Redis ACL。维护账号在 v2 命名空间中需要 `SCAN` 和 `DEL`。列出参与发布的实例及连接池预算，核对同机 legacy 和运维连接余量。
- 生产 OSS 尚待配置。v2 使用从未开启版本控制的私有桶。按 `https://mobile.v2.cm.iy88.site` 和 `https://admin.v2.cm.iy88.site` 配置浏览器直传 CORS。生产应用与维护 RAM 权限按实际操作区分。启用邮件或依赖探针时，SMTP 字段按[开发配置样例](../backend/.env.example)填写生产值。

## systemd、Nginx 与入口

| 资产 | 安装路径与职责 |
| --- | --- |
| [API unit](../scripts/deploy/systemd/project1-v2-api@.service) | `/etc/systemd/system/project1-v2-api@.service`。JAR 通过实例软链启动，OpenJDK 27 路径为 `/opt/project1-v2/java/bin/java`。 |
| [Nginx 站点与上游](../scripts/deploy/nginx/project1-v2.conf) | `/etc/nginx/conf.d/project1-v2.conf`。按 Host 提供两个静态站点，API 上游草案使用回环端口 `18081`、`18082`。 |
| [Nginx 路由](../scripts/deploy/nginx/project1-v2-routes.conf) | `/etc/nginx/snippets/project1-v2-routes.conf`。支持同源 API、SPA 回退、静态资源缓存以及 WebSocket Upgrade。 |
| [发布 sudoers](../scripts/deploy/sudoers/project1-v2-publish) | `/etc/sudoers.d/project1-v2-publish`，权限 `0440`。仅授予发布账号对两个 v2 API unit 的 start／stop／restart。 |

首发前确认两个端口可用，如需换端口，同时修改 Nginx 上游、sudoers、实例名和应用配置样例。管理员使用 `systemd-analyze verify`、`visudo -cf` 和 `nginx -t` 校验系统资产。

公网链路沿用 ESA → 公网 Nginx → frp → 生产源站 HTTP。预计用户端域名为 `mobile.v2.cm.iy88.site`，管理端为 `admin.v2.cm.iy88.site`。公网层保留 Host 并支持 WebSocket Upgrade，源站按 Host 选择站点并向后端传递 HTTPS 协议信息。首发验证双前端和 API。正式 Session 适配接入后启用实时入口并验证 WebSocket，worker 与 scheduler 按已接入职责配置独立运行单元。

## 合入 main 后的首发

1. 确认 GitHub 检查通过。同步同一 `main` 提交到发布源并核对 SHA，手动执行 v2 Jenkins job。
2. 归档并上传这一版本的压缩包与 `SHA256SUMS`，在目标机执行 `sha256sum -c SHA256SUMS`，解包到新版本目录。核对两个 JAR、双前端、部署资产和 `release.txt`。
3. 确认维护配置只指向 v2。首次建库使用包内维护 JAR 的 `db init`。已有库升级前备份 v2 数据库并校验备份可读，再以 `APP_ENV_FILE` 指向维护配置运行 `db migrate`。登记成功迁移的 Flyway 版本。
4. 为两个实例设置候选版本软链并启动。分别检查 systemd 服务状态、`http://127.0.0.1:<port>/actuator/health` 和 `/api/v1/hello`。两端就绪后切换 `current`。入口配置经检查后由管理员加载。用两个公网域名验证静态页面与同源 API。
5. 保存提交号、制品摘要、配置版本、Flyway 版本、实例就绪结果及上一可用版本。OSS 配置就绪后验证上传、核验及签名读取。手动首发通过后再启用发布 Webhook。

后续升级先备份并确认数据库兼容性，再逐个从 Nginx 上游摘除实例，等待停机排空，切换该实例的版本并通过就绪检查后恢复流量。两个实例就绪后切换前端。迁移失败时保持旧版本流量。激活失败且数据库兼容时恢复上一版本和它的配置快照，再验健康。首发没有上一版本时停止候选实例并保留发布与服务日志。数据库历史恢复单独安排。
