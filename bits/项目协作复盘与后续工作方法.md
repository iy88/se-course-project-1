## 3. 把问题归到四个协作接口

与其给每个错误增加独立审批，更适合明确任务在不同人和材料之间传递时必须携带什么。

| 接口 | 必须传递的信息 | 接收后首先判断什么 | 未满足时怎样继续 |
|---|---|---|---|
| 人到Agent | 本次目标、实际负责人、已知工具模型、材料基线、允许范围、产物及完成标准 | 是否理解为同一个任务；哪些事实已经确认、哪些只是候选 | 先完成可独立部分；只问影响判断的缺失信息，不重复询问已明确授权 |
| 上游分析到下游材料 | 决定内容与来源、涉及对象／角色／状态、改变前后的含义、受影响文件 | 是新业务选择、既有规则纠错，还是纯格式／引用调整 | 新选择待实际决定者处理；明确的旧表述在授权范围内对齐，保留原稿归属 |
| 成员到汇总负责人 | 输入基线、本人实际修改、决定及证据、已做检查、未覆盖项、待同步生成材料 | 共享条目是否覆盖他人成果；本地材料与当前主线的业务含义是否仍兼容 | 不整份替换共享报告；冲突按AGENTS保存现场，未受影响工作继续 |
| 源材料到交付副本 | 唯一源、引用关系、生成规则、依赖条件及实际检查范围 | 是否从最新源生成，产物本身是否可打开、阅读和跳转 | 修复受影响链路；缺少环境或授权时注明具体未执行项，不扩大为全部完成 |

这些接口的信息可以直接写在任务交互、已有ai-usage和收尾说明中，不要求每次增加独立任务文档、重复登记表或新的自动化工具。

## 4. 以一个可核查的任务贯穿工作

任务按“明确输入 → 形成代表内容 → 展开并记录 → 同步影响 → 核对并交接”推进。提交、改名定稿和导出仍按现有授权与检查规则执行。

### 4.1 开始前：先明确最小任务说明

| 项目 | 需要表达的内容 |
|---|---|
| 目标与范围 | 要解决的具体问题；本次允许修改什么、暂缓什么 |
| 人与责任 | 本人实际负责的内容、决定者及需谁核验；已确认信息沿用，不根据账号推定模型 |
| 输入基线 | 当前HEAD、会影响任务的工作区差异及实际阅读的文档版本；仅记录HEAD不足以代表未提交材料 |
| 产物与使用者 | 是详细用例、图、报告还是原型；由谁阅读、通过什么方式使用 |
| 完成标准 | 本次检查哪些含义、路径或实际产物；哪些结果须由人参与才可记录 |
| 依赖和未决 | 依赖谁的哪项材料，缺口影响哪一部分，哪些工作仍可独立继续 |

该说明不是新的审批步骤。范围已经明确的任务可直接开展，错字和确定的断链等小修改只需必要信息，不套用整套表格。工作区有修改时先检查和保留，不为取得“干净基线”擅自reset、覆盖、stash或拉取合并。

### 4.2 展开前：先核对一个代表实例

批量用例、类协作表、图稿、原型页面或导出格式，先形成一个能审阅的代表实例，核对关键术语、信息粒度和产物形式后再展开。已有明确、仍适用的样式和范围可直接复用，不为每个同类文件新增确认。

例如，原型先以一个实际US展示任务入口、正常结果、权限或异常提示及跳转；领域关系先用“争议后重新确认”的实例核对历史记录和当前确认；导出先用含中文／空格文件名、页内／跨文件锚点及宽表的样本核对实际PDF。这里只说明检查思路，不把样本通过写成全量通过。

### 4.3 工作中：决定、材料和证据一起前进

已有规则发生实质变化时，先判断下面哪些关系受影响，再改对应源文件。不要把此表变成每次都全文重写所有文档的要求。

| 变化类型 | 需要检查的下游关系 | 典型反例 |
|---|---|---|
| 增加或改变一项能力 | FR、相关US／UC具体路径、支撑对象及职责、SC预期和验收条件 | BR写了禁发范围维护，用例却没有入口或对象无法保存细目 |
| 改变资格或对象范围 | 执行角色、对象归属、状态／限制、规则视图、用例拒绝路径及模型 | 把所有管理员操作都套用认领前提，遗漏禁发范围独立维护与具体事项审核的区别 |
| 改变状态或恢复条件 | 当前／目标状态、触发与计时、历史／当前进度、BR／TR、类关系及活动／状态图 | 恢复交易就立即启动计时；把当前最多两条确认写成历史只能两条 |
| 改变术语、编号或目录 | 独立源、索引、章节节选、总报告、A／B引用、证据及必要映射 | 链接能打开但仍指旧含义；完成材料仍被别处称为占位 |
| 改变图或原型形式 | 内容语义、可编辑源、预览、正文入口、模拟范围和实际观察记录 | 生成图片就说人工看过；页面可点击就说后台实现 |
| 改变生成或导出方式 | 实际输入、依赖、缓存、真实产物及关联链接 | 只改源而复用旧PDF；只检查改写路径而没检查PDF注解 |

实质AI建议及人工反馈当场写入对应ai-usage；业务决定需要独立留据时写入evidence并互引。一般排版、Git及同步操作不另建项目AI贡献。同一决定引用一个来源，不再为正文、报告、个人摘录各维护一份原文。

### 4.4 汇总时：先检查含义，再检查格式

先按变化对象读成员实际修改和必要来源，判断业务决定是否兼容，再处理编号、引用、版本和生成物。一个分支只负责自己小节，不意味着可以忽略上游规则；一次合并未产生冲突，也不能说明共享索引和状态说明已经正确。

Git出现冲突时沿用AGENTS的现场备份和逐文件人工审核流程；不另建立简化的覆盖方案。没有业务冲突时按授权落实明确对齐，不把一般同步都升级成新业务审批。跨成员的新选择或归属不清只阻塞受影响部分。

## 5. 分开说明“完成”的含义

| 已有事实 | 可以据此说明 | 还不能据此说明 |
|---|---|---|
| 文件、编号及链接检查成功 | 已有对应材料，结构和引用可定位 | 能力覆盖完整、业务正确、人工核验完成 |
| 对照规则与模型，没有发现所查范围内的冲突 | 指定版本及范围的材料对照结果 | 已获得真实业务方或教师认可 |
| 图源语法正确且渲染成功 | 可生成指定图稿 | 关系方向正确，原尺寸及报告中所有文字可读 |
| 人实际按任务观察原型并提供反馈 | 所记录页面或模拟交互的观察结果 | 未观察分支通过，或业务后台已经实现 |
| PDF生成并检查实际目标、字体和代表页面 | 指定输出及范围的交付检查结果 | 最新全部文件已导出，或每页均经人工验收 |
| 成员提交或负责人接受分析材料 | 可定位该次修改及明确的接受范围 | 该成员原创全部合并材料、已执行所有计划任务 |

因此收尾应明确：改了什么、实际查了什么、结果支持什么、什么仍缺证据、下一步由谁处理。已有R／V问题继续沿用；未执行写未执行，不以模糊的“全部通过”掩盖检查层次。

## 6. 成员交付与统筹汇总的分工

成员在各自设备和Git账号下，交付本人实际修改及关键来源；保留原稿、后续修订和人工判断的区别。成员后续修改仍不运行scripts；只检查本人材料、链接和差异，列明需要统筹同步的章节、图片或导出副本。未运行的检查不得写通过。

袁尚峰统筹上游规则、新编号、共享报告及索引合并，检查成员材料的语义影响，统一构建、渲染和按授权导出。这里只明确职责接口，不推定所有业务决定、实际观察或逐文件复核已经由某人完成，也不把分工变为自动提交授权。

最小交接内容为：

1. 依据的提交与相关工作区变化、实际输入版本。
2. 本人修改的源文件与具体内容、相关决定及ai-usage／E／V位置。
3. 实际执行的检查、结果及范围；未覆盖、未核实或受阻内容。
4. 影响其他成员或共享材料的事项，以及尚需统筹同步的生成产物。

交接可以放在本次收尾说明中；现有文档已经承载的信息直接引用，不再建立重复历史流水。每次commit／amend仍执行AGENTS完整workflow，授权提交不等于授权推送或报告定稿。

## 7. 如何判断这些改进有效

后续以实际任务回看以下现象，不设置无依据的工时或返工比例目标：

- 提出业务修改时，能直接找到当时输入、实际决定者及关键理由，无需事后猜测或恢复整段聊天。
- 分块材料交付后，接收者能识别其基线和影响；上游变更不会直到报告整合才暴露。
- 具体能力能从用户目标追到路径、对象及验收预期，避免只按文件数量和编号验收。
- 报告不再重复保留过时占位、已撤销的现行口径或失效附件安排；历史仍可追溯。
- 格式或工具调整先在代表实例上发现问题，验证结论明确限定范围。
