# S2—S4 用户端交接与验证

本记录覆盖孙含佳（`shjj11`）的三个用户端工作包：[#75 S2-03](../docs/design/tasks/S2-商品与交易.md) 账户与商品用户端、[#79 S3-03](../docs/design/tasks/S3-账户与沟通.md) 交易与沟通用户端、[#83 S4-03](../docs/design/tasks/S4-治理与管理.md) 事项用户端，以及 #75 要求由本工作包提供的站内通知持久化与查询。

## 输入与分支

| 项目 | 内容 |
|---|---|
| 输入基线 | 最新 `main`（S1 正式基线），取 `main` 的 `f20693d` |
| 依赖状态 | #73 交易、#77 商品审核、#81 处置、实时同步已有 Draft PR（#97／#106／#103）；#74 账户与商品后端、#76 商品互动、#80 会话与评价、#84 事项生命周期尚无分支 |

三条分支都从 `main` 建立，按提交堆叠，每个提交只属于一个工作包：

| 分支 | 内容 | 在 `main` 之上新增 | PR 目标 |
|---|---|---|---|
| `s2/75-account-product-web` | 共享骨架 + #75 + 后续工作包的占位视图 + 本记录 | 4 个提交 | `main` |
| `s3/79-trade-chat-web` | 上列全部 + #79 | 1 个提交 | `s2/75-account-product-web` |
| `s4/83-case-web` | 上列全部 + #83 | 1 个提交 | `s3/79-trade-chat-web` |

用户端是同一个应用，路由表引用三个工作包的视图。若三条分支各自只放本工作包的视图，后两条引用不到前一条的页面而无法编译；因此改为堆叠，并在第 1、2 条分支对尚未提交的页面放置占位视图，占位文件只说明该页面由哪个工作包提供，由对应工作包的提交整体替换。这样每条分支都能独立通过 lint、格式、类型、构建与单元测试，每个 PR 的 diff 也只包含自己工作包的内容。

若阶段集成人希望三条 PR 都直接指向 `main`，可在合入前把三条分支按 `s2 → s3 → s4` 顺序合入，或改用一个工作包 PR 承接三个问题；两种方式都不需要改代码，只调整 PR 目标。

## 改动

### 前端 `frontend/user-web`

| 目录 | 内容 |
|---|---|
| `src/api` | 统一 HTTP 接缝（Cookie/CSRF、`Idempotency-Key`、`X-Origin-Connection-Id`、C1 错误外壳归一化）、临时契约类型、按域划分的调用封装 |
| `src/mock` | 可切换的内存数据源：账户、商品、分类、禁发范围、文件、交易、会话与消息、已读进度、通知、事项、聚合查询；含版本冲突、占用、归档、幂等重放与按接收人的可见性过滤 |
| `src/app` | 路由与登录守卫、会话状态、账户入口上下文、错误文案、枚举文案、格式化、幂等键、异步状态、提示条、未读角标、实时客户端 |
| `src/components` | 设计系统与通用组件；`components/interaction/` 为 S2-04／S3-04 的评论、收藏、成交评价占位插槽，文件头写明真实组件应满足的 props 与接口 |
| `src/views` | 账户（注册／登录／找回密码／资料／安全）、商品（检索／详情／发布编辑／我的商品／禁发范围）、我的聚合、通知、交易、会话、事项 |
| `tools` | 零依赖测试运行所需的 TypeScript 解析钩子 |

### 后端 `backend/notification`

- `V5_75__create_notifications.sql`：`notification` 表以 `(recipient_account_id, intent_key)` 为唯一作用域，`read_at` 只记首次，不存展示摘要（摘要按读取人当前可见性投影）。编号沿用 #77 的 `V5_77` 工作区后缀约定，避免与其他批次并行时冲突。
- `NotificationApplication.createNotifications`：同一事务写入通知与投递意图；重放返回已有记录，同键异内容返回 `NOTIFICATION_INTENT_CONFLICT`（409）。
- `NotificationApplication.markRead`：只写首次已读并登记一次 `notification_read` 事件；非接收人返回 `RESOURCE_NOT_VISIBLE`（404）。
- `NotificationQueries.list／get`：只读本人；`read`／`event_type` 过滤先于分页，`unread_count` 为本人全部未读、不受过滤影响；来源不可见时只返回获准提示且不提供跳转。
- `NotificationSourcePort`：来源投影端口，由商品／交易／事项模块实现。
- `ReviewNotificationAdapter` / `EnforcementNotificationAdapter`：与 #77 `ReviewNotifications.reviewDecided`、#81 `EnforcementNotifications.create` 签名一致，装配时用方法引用绑定即可；事件类型点分名按 S1 `EventIntent` 的 `[a-z][a-z0-9_]*` 规则折叠为下划线。

### 未覆盖与待联调

- 前端未在真实浏览器中做人工走查（本轮无浏览器环境）；`live` 数据源下的页面行为需在各提供方接口合入后联调。
- `frontend/shared/openapi.json` 本轮未改动，因此 `generate:api` 与生成类型检查保持原状；用户端消费的接口以 `src/api/contracts.ts` 的临时契约描述，提供方发布 OpenAPI 后应替换为生成类型。
- notification 模块尚未加入 `backend-app` 依赖，也还没有 HTTP 控制器：读取接口需要账户 Session 解析（#74 提供），写入需要经 `WriteExecutor` 的用例装配。把它们加进 `backend-app` 时要同时让该模块的 JPA Repository 依赖数据源，否则 `BackendAppApplicationTests` 那个排除了 DataSource 自动配置的上下文会失败。
- `mvn -f backend/pom.xml verify` 的 `backend-app` 重打包步骤因本地开发进程占用了 `backend-app-0.0.1-SNAPSHOT.jar` 而失败；本轮以 `mvn test` 完成全模块单元测试。停止本地开发进程后可重跑 `verify`。
- 交接记录中未使用真实 OSS、SMTP 与 Redis：文件上传在模拟数据源下不访问 OSS；真实直传与核验待 #74／#84 的文件 API 合入后联调。

## 跨模块影响与后续条件

1. **`frontend/shared/openapi.json` 的归属**：用户端消费的账户、商品、会话、事项接口目前只在设计文档与临时契约里。建议由各提供方在其批次内发布 OpenAPI；在此之前用户端的 `contracts.ts` 是唯一来源，变更须同步。
2. **通知接入口**：#77 在审核决定事务内调用 `ReviewNotifications.reviewDecided`，装配处绑定 `ReviewNotificationAdapter::reviewDecided` 即可；#81 同理绑定 `EnforcementNotificationAdapter::create`。意图键用 `product_audit.decision:<audit_id>`，收件人只取卖方。
3. **通知读取接口**：`GET /account/notifications`、`GET /account/notifications/{id}`、`PUT /account/notifications/{id}/read` 的响应形状由 `NotificationQueries` 决定，控制器只需把 `ExecutionContext` 传入并按 C1 外壳输出。
4. **实时协议**：`app/realtime.ts` 的 `hello`／`ack`／`resume` 帧形状来自 README 的投递描述，未在 OpenAPI 中登记，需与 S3-01 核对后再启用对真实服务端的连接。
5. **占位插槽**：`ProductCommentSection`、`ProductFavoriteControl`、`TradeReviewSection` 需由 S2-04／S3-04 的同名真实组件替换，替换前收藏与成交评价在界面上显示为「待接入」。
6. **前端单元测试与 CI**：`frontend/package.json` 已提供 `test` 脚本（`pnpm --dir frontend test`），但 GitHub Actions 目前只跑 lint、格式、类型与构建。前端测试的 CI 步骤由 TASK-001 维护，需要时再补。
