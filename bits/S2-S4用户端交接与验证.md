### 本地实测发现与修正（0.9.0）

| 现象 | 原因 | 处理 |
|---|---|---|
| 选图确认后界面显示 `Failed to fetch` | 浏览器直连对象存储，传输失败只被当作原始 `TypeError` 抛出；真实环境在 Bucket 不可达或 CORS 拒绝时同样如此 | `uploadToOss` 把传输失败与状态码失败统一为可重试的 `UPLOAD_TRANSFER_FAILED`，并在 `problems.ts` 登记文案；新增 4 项传输测试 |
| 本地模拟环境永远传不上去 | 模拟服务返回占位域 `https://oss.example.invalid/` 作为签名地址，浏览器真的去 POST 它 | 改为同源：签名地址 `/api/v1/files/mock-upload`、预览 `/api/v1/files/{id}/content`，均由 dev server 反代到模拟服务；模拟服务只解析 JSON 请求体并为内容端点返回占位图 |
| 独立实例启动即报 `Provide exactly one --env-file=<path>` | 应用启动强制要求该参数（`bootstrap.ApplicationEnvFile.load`） | 冒烟命令必须带 `--env-file`，见下 |

单实例冒烟的正确命令（端口避开本地 8080）：

```powershell
mvn -f backend/pom.xml -pl backend-app spring-boot:run `
  "-Dspring-boot.run.arguments=--env-file=E:/se-course-project-1/backend/.env.dev --spring.profiles.active=infrastructure --server.port=18080 --server.address=127.0.0.1"
```

`--env-file` 用正斜杠或转义后的反斜杠；PowerShell 会把裸 `--` 参数当成自己的开关，所以要整段加引号。

按 #74 的 S2-02 交接文档做了一次真实链路联调，用来验证此前只能靠模拟服务覆盖的部分。

**环境**：合并基线 `test/s2-plus-74`＝`s2/75` `5eaf510` + `origin/s2/74-account-product` `ea90ba3`（本地分支，未推送）；独立库 `project1_s2_02`（PostgreSQL 18.7，容器 `project1-postgres`）；Redis `127.0.0.1:6379/0`，命名空间 `project1:dev:s2-02`；应用 `18081`，`Origin: http://127.0.0.1:3999`。配置文件 `backend/.env.s2-02` 本地生成并由 `.gitignore` 的 `.env.*` 覆盖，不入库。

### 真实 OSS 头像链路（0.12.0）

补齐上一节未完成的两项后，用**真实 Bucket** 把头像链路走完了。

**做法说明**：#74 分支只提供 dev 专用的 `/__dev/file-probe`（`FileProbeController`，profile `file-probe & infrastructure & !dependency-probe`，要求 `APP_ENV=dev` 与 `127.0.0.1` 绑定），**没有面向用户的 `/api/v1/files/*` 上传接口**。因此本轮用该探针产生真实的 OSS 对象与已核验记录，再把记录归属改到测试账号（`UPDATE file_record SET owner_account_id, target_type, target_id`），随后用正式的 `PATCH /api/v1/account/profile` 完成绑定与移除。除"上传授权入口"外，其余环节都是产品接口。

| 步骤 | 结果 |
|---|---|
| 探针授权 `account_avatar` 上传 | 201，返回表单签名（`OSS4-HMAC-SHA256`、key、policy） |
| 表单 POST 到 Bucket | **204**（真实写入 `project1/dev/account_avatar/…`） |
| 探针核验 | 200，`verified_at` 落库，可被引用 |
| `PATCH /account/profile` 绑定 `avatar_file_id` | **200**，返回**真实签名 URL** |
| 签名 URL 读取 | **200，693 字节**（与上传文件一致） |
| `PATCH /account/profile` 传 `"0"` | **200，`avatar_url` 为空（移除成功）** |
| `GET /account/session` 复核 | `avatar_url` 仍为空 |

**结论**

1. `"0"` 移除头像的口径在真实链路成立，与 S2-02 交接一致；我此前按交接做的客户端改动得到端到端验证。
2. 头像绑定会返回短期签名 URL，且该 URL 可直接取到对象内容。
3. **仍未验证的部分**：浏览器端的界面走查。原因不是配置，而是 **#74 没有用户端上传 API**——用户端调用 `/api/v1/files/uploads`、`/api/v1/files/{id}/completion`、`/api/v1/files/{id}/content` 全部 404，界面上的头像上传无法完成。这不是本工作包能补的，需要在 #74 侧提供接口。
### 实时 HTTP 端点的 profile 依赖（0.13.0）

联调时顺带确认一处与实时层相关的配置事实，不属于 #74 范围，但会让实时链路在默认启动下不可用。

- `EventRecoveryController`（提供用户端记录头部游标用的 `GET /api/v1/account/events/head`）标注 `@Profile("realtime-api & infrastructure & !dependency-probe")`，`RealtimeConfiguration` 同样如此。
- `BackendStartup` 只追加 `infrastructure`；`application.properties` 也没有把 `realtime-api` 编进任何 profile 组。
- 结果是：按交接文档的方式启动（`--spring.profiles.active=infrastructure`）时，`/api/v1/account/events/head` 与 `/api/v1/realtime` 都不会注册。用户端的行为是保持在"正在重新连接…"并退回轮询，不阻塞页面，但这不能算实时链路已验证。
- 需要实时模块的负责人确认：`realtime-api` 应由启动参数显式开启，还是并入 `infrastructure`。在确认前，"实时链路已验证"的结论不成立。

`#113` 补上了身份适配器（`api.account.AccountNotificationActorResolver`）与三个文件端点（`api.file.FileController`）后，在合并基线上复验：**之前 503 与 404 的两个阻塞项都已消失**。

复验中还确认了两件事：`PATCH /products/{id}` 必须带 `expected_version`，其值取详情里的 `content_version`（不带或取值错误分别是 409／422）；`POST /files/uploads` 的幂等重放会返回**旧的**上传授权，其 policy 已过期，直传会 403，因此每次上传要用新的 `Idempotency-Key`。

**仍待与 #74 对齐的两处契约差异**

1. **`target` 字段名**：设计里 `target` 是 `ResourceRef`，字段为 `resource_type`／`resource_id`（`key-designs/公共事务与权限.md`）；`FileController.TargetInput` 实现为 `{type,id}`。用户端按设计发送，联调时用 `{type,id}` 临时验证尾部链路通过，但口径必须统一。
2. **新建商品时的 `product_image` target**：设计允许 `null` 作为"创建主体前的暂存"并校验创建资格；实现要求必须传已存在的商品并校验卖家。用户端在"新建商品"页还没有商品 ID，只能传 `null`。

两处都不影响 `account_avatar` 与 `case_evidence`（`target:null`）的现有链路，但会让"新建商品带图"和"编辑商品带图"卡住，已连同设计条文一起在 #74 留言。

**口径归属的结论**：这两处按设计文档与协作约定收敛到用户端现状，不改用户端。依据是（1）`公共事务与权限.md` 已定义 `ResourceRef` 的字段名；（2）`文件上传.md` 已写明 `null` 仅用于创建主体前的暂存；（3）用户端 `2987fc0`（2026-11-22 20:22）先于 `FileController`（2026-11-23 19:21）落地。按 `AGENTS.md` 跨功能关联约定，后到者沿用已确立的口径；若设计本身要改，应先改 `公共事务与权限.md` 与 `文件上传.md` 并同步 OpenAPI，再改实现。已请 #74 在争议时拉袁尚峰裁决。
### 后端 `backend/notification` 与通知入口

- `V5_75__create_notifications.sql`：`notification` 表以 `(recipient_account_id, intent_key)` 为唯一作用域，`read_at` 只记首次，不存展示摘要（摘要按读取人当前可见性投影）。编号沿用 #77 的 `V5_77` 工作区后缀约定，Flyway 视为 `5.75`，排在 `V5` 之后、`V6` 之前。
- `NotificationApplication.createNotifications`：同一事务写入通知与投递意图；重放返回已有记录，同键异内容返回 `NOTIFICATION_INTENT_CONFLICT`（409）。
- `NotificationApplication.markRead`：只写首次已读并登记一次 `notification_read` 事件；通知行经 `WriteTransaction.lock` 按公共锁序加锁；非接收人返回 `RESOURCE_NOT_VISIBLE`（404）。
- `NotificationQueries.list／get`：只读本人；`read`／`event_type` 过滤先于分页，`unread_count` 为本人全部未读、不受过滤影响；来源不可见时只返回获准提示且不提供跳转。
- `NotificationSourcePort`：来源投影端口，由商品／交易／事项模块实现。
- `ReviewNotificationAdapter` / `EnforcementNotificationAdapter`：与 #77 `ReviewNotifications.reviewDecided`、#81 `EnforcementNotifications.create` 签名一致，装配时用方法引用绑定即可；事件类型点分名按 S1 `EventIntent` 的 `[a-z][a-z0-9_]*` 规则折叠为下划线。
- HTTP 入口：`GET /api/v1/account/notifications`、`GET /api/v1/account/notifications/{id}`、`PUT /api/v1/account/notifications/{id}/read`。已读走 `WriteExecutor` 用例（声明 `NOTIFICATION` 锁键、事务内锁行、按 `Idempotency-Key` 重放）。身份经 `NotificationActorResolver` 端口解析，未装配时返回 503 `AUTHENTICATION_UNAVAILABLE` 而非放行。
- 装配：`notification` 已加入 `backend-app` 依赖；模块内 JPA 存储与配置均为 lazy，排除了数据源的探测上下文仍能启动。已读绑定只在 `infrastructure` profile 下注册。

## 跨模块影响与后续条件

1. **通知身份端口**：`api.notification.NotificationActorResolver` 与交易侧 `TradeActorResolver` 形状一致（`accountId`、`sessionId`、`credentialVersion`）。建议 #74 提供一个基于 Session Cookie 的适配器同时绑定两者，或改为 `api` 包下的公共 `SessionActorResolver` 供各控制器复用；届时通知接口自动由 503 转为正常，无需改本模块。
2. **通知接入口**：#77 在审核决定事务内绑定 `ReviewNotificationAdapter::reviewDecided`，#81 绑定 `EnforcementNotificationAdapter::create`。意图键为 `product_audit.decision:<audit_id>`，收件人只取卖方。
3. **CSRF**：通知已读是浏览器写请求，需要 #74 绑定的 `CsrfGuard.Verifier`；未绑定时按设计返回 403。
4. **`frontend/shared/openapi.json` 的归属**：账户、商品、会话、事项接口目前只在设计文档与临时契约里。建议由各提供方在其批次内发布 OpenAPI；在此之前 `contracts.ts` 是唯一来源，变更须同步。
5. **实时协议**：`app/realtime.ts` 已按 `实时与任务.md` 与服务端实现对齐（`hello`／`hello_ok`／`ping-pong`／`ack`／`cursor_advance`／`resume`／`sync_reset`／关闭码），并有 7 项协议级测试；仍未在真实 Socket 上跑端到端链路，且帧形状未登记到 OpenAPI。
6. **占位插槽**：`ProductCommentSection`、`ProductFavoriteControl`、`TradeReviewSection` 需由 S2-04／S3-04 的同名真实组件替换，替换前收藏与成交评价在界面上显示为「待接入」。
