# S1 工程交接与验证

S2、S3、S4 从 S1 实现合入后的 `main` 开工。各子任务用同一工程底座独立开发和验证，通过所属业务模块提供规则、资格和测试样例。阶段要求见 [S1 准入](../docs/design/acceptance/S1-阶段准入.md)，实现汇总见 [PR #85](https://github.com/iy88/se-course-project-1/pull/85)。

## 开工入口

1. 从 [配置样例](../backend/.env.example) 准备本地 `backend/.env.dev`，取得所在任务的开发数据库、Redis 命名空间、OSS 测试范围和 SMTP 配置。按 [初始化与全量重置](../README.md#初始化与全量重置) 建库或迁移。整桶 OSS 清理用于已核对的独立测试桶。
2. 在仓库根目录运行以下命令。默认启动一个 API、一个调度器、两个 worker JVM 和双前端。API 服从配置中的监听地址，双前端通过 Rsbuild 同源代理访问 API。

   ```bash
   mvn -f backend/pom.xml install
   pnpm --dir frontend install --frozen-lockfile
   python3 scripts/dev.py start --env-file=backend/.env.dev
   python3 scripts/dev.py status
   ```

   Windows PowerShell 5.1 或更高版本使用：

   ```powershell
   mvn -f backend/pom.xml install
   pnpm --dir frontend install --frozen-lockfile
   .\scripts\dev.ps1 start -EnvFile backend/.env.dev
   .\scripts\dev.ps1 status
   ```

3. 分别从 `http://127.0.0.1:3000/api/v1/hello` 和 `http://127.0.0.1:3001/api/v1/hello` 核对 JSON 响应。默认启动命令显式使用 `backend/.env.dev`；使用其他配置时，将 `dev.py` 的 `--env-file` 或 `dev.ps1` 的 `-EnvFile` 后的路径替换为目标文件，按需要设置 `API_PROXY_TARGET` 和工作进程数。分别用 `python3 scripts/dev.py stop` 或 `.\scripts\dev.ps1 stop` 停止本次启动的进程。

## 公共能力装配

| 能力 | 业务接入入口 | 开发验证 |
| --- | --- | --- |
| 统一写入 | `backend-core` 的 `WriteExecutor`、`WriteTransaction` 和锁计划。业务用例提供资格、查询与写入回调。 | [写入说明](../README.md#共享写入用例)。集成用例覆盖并发幂等、事务回滚和事件落库失败。 |
| 文件 | `file-storage` 的上传授权、核验、读取和引用服务。商品与事项各自提供用途、主体权限和绑定规则。 | [文件测试页](../README.md#文件服务测试页) 可执行开发桶上传、完成核验、签名读取和释放引用。 |
| 实时与任务 | `RealtimeAccess` 接入正式 Session 及读取资格，`TaskSchedules` 和 `TaskHandler` 接入延时任务。调度器和所有 worker 装配相同的任务类型。 | [事件、调度与 WebSocket](../README.md#事件投递与定时任务)。集成用例验证 WebSocket 游标恢复、Redis 待确认消息和 PostgreSQL 过期租约接管。 |
| SMTP | 邮件发送适配器由账户邮件用例接入，账户模块维护邮件记录和租约。 | [单次依赖探针](../README.md#依赖探针) 验证实际投递，收件方按邮件 ID 核对。 |

## 验证和发布

- 默认 `mvn verify` 运行后端测试并生成覆盖率。本机运行 `mvn verify -Pintegration` 时使用开发 PostgreSQL 和 Redis。GitHub Actions 的集成 job 使用自己的服务容器。
- 维护工具用 `mvn -pl maintenance -am verify` 验证故障恢复。故障注入覆盖 Redis 预检失败、PostgreSQL 失败后停止 Redis 删除、PostgreSQL 已完成而 Redis 清理失败后重跑，以及 OSS 第一批已删除而后续批次失败后重跑。
- 2026-11-19 用 `backend/.env.dev` 在 `campus_market_v2_dev` 和 `campus_market_v2:s1:dev:*` 实测中途失败恢复。临时 Redis ACL 用户允许 `SCAN` 但拒绝 `DEL`，受控键存在时 PostgreSQL 先重建并完成 Flyway V1–V5，随后 Redis 删除失败，受控键保留。原权限重跑后受控键被删除。数据库 OID 从 `181709` 变为失败后的 `181933`，恢复后为 `182157`。最终 Redis 命名空间键数为 0，三个自增序列均为 `last_value=1`、`is_called=false`。开发 OSS Bucket 首次清理和重复清理都返回 0 个对象。临时 ACL 用户和临时配置已删除。
- 用真实开发 OSS 和 SMTP 复核涉及对象权限、回收或邮件投递的改动。前端业务流程按对应任务的独立启动说明做前后端联合验证。
- Jenkins 发布、生产主机配置与验收按 [v2 首发与发布配置](v2首发与发布配置.md)推进。
